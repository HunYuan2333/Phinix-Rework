# 主题 ZIP 导出与快捷提交商店评估

日期：2026-10-11。性质：方案评估，本次不修改代码、不上传、不创建 Issue/PR、不发布 Index。在线交付仍按原约束延期。

## 1. 最新需求与结论

- 主题编辑器保留导出，目标改成商店能安装的本地 ZIP；本地导入入口统一交给商店。
- 导出成功先交付本地文件、显示绝对路径、提供复制路径/打开目录；目录打不开不影响导出成功。
- 可在导出结果里提供“提交商店”，用户主动选择后才开始认证和网络流程；关闭提示、拒绝上传或上传失败都保留本地 ZIP。
- 主题作者不需要编译插件、安装 SDK、运行 gh 或手填摘要。打包、长度/摘要计算和候选字段生成应由工具完成。
- 推荐先完成本地闭环，再做 GitHub 作者的快捷提交。无 GitHub 账号的作者先允许 ZIP 分享/委托发布；若要求真正一键公开提交，需要单独建设有身份和责任边界的接收服务。

“没有账号、不依赖发布服务、直接写入公开商店”缺少可授权写入的位置。gh 不能消除 GitHub 身份要求。可以把步骤隐藏在工具里，但不能把维护者的写入凭据放进客户端。

## 3. 本地导出先做什么

建议流程：编辑主题 → 导出 → 填写最少包信息 → 校验并写 ZIP → 展示文件路径及“提交商店”可选入口。

1. 默认单变体包；复用已实现 ThemePackage 数据契约，生成 manifest.json 和声明的 Themes XML。游戏内调用共享打包核心，不启动 gh/dotnet 子进程，也不要求玩家安装命令行工具。
2. 本地初次导出需要名称、显示作者、稳定包 ID 和版本；ID 可生成并保存在作者草稿元数据中，后续导出复用。版本/文件名不能充当主题身份。
3. 导出当前草稿的显式颜色、参数、inherit、未知键及对应用户覆盖；不默认展开所有继承值。缺键继续按运行时规则回退，插件缺失不阻止打包。
4. 编辑已安装他人主题后另存为自己的新包身份，不能默认沿用官方来源及所有权。选择“同一作者包的新版本”必须有独立身份验证，不能靠显示作者名称。
5. 提交前冻结实际 ZIP、计算摘要并验证；上传对象就是该文件。编辑器后续修改不改变已提交候选；已发布同版本不同摘要拒绝，更新增加版本。
6. 临时文件写完、静态验证成功后提交为目标 ZIP，避免失败留下看似成功的文件；目标冲突提供明确另存/覆盖决策。三端路径规范与现有限额继续复用。

本地导出不要强迫登录或填仓库信息。许可证/再分发授权、说明、预览图属于发布资料：当前严格清单尚无这些字段，增加字段需要明确契约版本和 Validator 支持；不能直接塞额外文件绕过已有校验。首版可用受校验的提交资料承载许可证选择，后续再决定是否纳入包清单。

导出可在主菜单、断线、商店禁用时使用。主题编辑器依赖中立打包能力；商店接管安装/来源/收据，发布 adapter 接管授权和传输。主题运行时与普通插件业务不需要知道 GitHub、Index schema 或旧格式。

## 4. 快捷上传可选路线

| 路线 | 作者操作 | 基础设施/身份 | 评价 |
| --- | --- | --- | --- |
| 本地 ZIP 分享 | 导出，发送给别人或交给发布者 | 不需要 GitHub；接收者经商店本地安装 | 最先可落地，支持无账号；不是公开上架 |
| 作者仓库快捷提交 | 浏览器登录/授权，确认目标仓库与版本，然后提交 | 作者 GitHub 身份；受限授权或网页工具 | 推荐的正式作者路线，保留资产来源和更新控制 |
| 共享主题仓库 | 提交 ZIP/元数据，经维护者批准发布主题资产和索引 | GitHub 作者或代提交者；可信工作流管理共享仓库 | 省掉每个主题单独建仓库；仍需要提交身份或人工代办 |
| 无 GitHub 接收服务 | 上传 ZIP，获得提交编号，经审核上架 | 独立登录/所有权恢复、限额、存储、队列、维护成本 | 体验最简单，但必须承认有中心化接收/代发布环节 |
| 任意来源目录 | 作者自行托管，用户添加源 | 来源信任、签名/身份、目录冲突和维护策略 | 与当前固定官方源差距大，不适合为快捷上传顺带实现 |

### 推荐分两步降低复杂度

第一步提供“准备商店提交”：自动生成 ZIP、摘要与预填候选资料，打开网页提交入口。没有账户时明确提供复制资料/委托发布路径。预填入口只简化表单，不能假设能通过 URL 自动上传 ZIP，也不能让客户端替用户伪造来源证据。

第二步再考虑完整授权发布：浏览器认证或网页接收 ZIP，发布 adapter 根据明确授权创建作者资产和候选。OAuth/device flow、GitHub App、仓库权限和上传方式需另行验证后选型；本次未实现或验证授权流程。不能将开发机 gh 登录状态当作最终产品方案，也不能要求玩家给维护者账号凭据。

如果多数主题作者没有 GitHub，可优先采用“共享主题库 + 人工/网页接收”，而不是要求所有人建仓库。若没有网页服务，人工委托就是现实的过渡方式；快捷按钮只能辅助交接，不能声称自动完成上架。

接收服务只负责投稿/代发布，不成为主题运行时依赖；可下载 ZIP、本地安装和已安装主题仍独立可用。公开包资产继续可独立校验和镜像，但服务本身不是去中心化的，必须明确这个范围。

## 5. 身份、审核与更新边界

- creator 显示名称与 publisher 仓库/账号身份分开；委托发布清楚标识实际发布者，不能要求作者声明拥有代发布仓库。
- 自动生成候选不等于自动批准。沿用可信校验、审批和不可变目录发布；纯数据可以精简代码审查，仍要校验数据、来源、摘要、再分发授权和身份冲突。
- 无账户匿名首次投稿不能仅凭昵称获得后续覆盖权限。服务方案需要可恢复的作者身份或明确的委托维护关系；本地包 ID、摘要、草稿文件都不能替代更新授权。
- 状态至少区分本地已导出、待提交、已提交、校验失败、待审核、已上架/被拒绝。超时为状态未知，先查已有提交再重试；以包身份/版本/摘要关联候选，避免重复 Issue 或发布资产。
- 用户在提交前能看到目的来源、包名/版本、发布资料及上传内容。导出不自动触发网络，取消提交不删除本地文件。
- 正式来源与本地包来源仍不同；本地包不能静默覆盖正式包。后续正式收录也不能把本地已安装收据自动改成官方可信来源。

## 6. 兼容与职责边界

1. 新包使用 phinix-theme/theme-zip，不假造 DLL 模块，也不附带代码插件 SDK/CLR 范围。缺键/可选插件键是当前主题解析语义，不是旧客户端兼容开关。
2. 新客户端读取既有 DLL 收据/journal 和用户主题配置的能力保留，旧 schema/旧别名转换只在输入 adapter。主题编辑器和普通业务不接触这些兼容信息。
3. 不为未支持主题包的旧客户端伪装旧目录条目；维持新客户端上线和主题目录发布协调。红包/人才贸易已承诺的 1.9 内部 adapter 不因这次主题方案而删除。
4. 本地导入迁到商店后删除选择器入口与相应窗口状态；先完成商店可安装/卸载纯主题包。已有用户 XML/配置继续可读，不能因入口删除而删除文件、覆盖或自动取得受管所有权。
5. 对旧 XML 的转换作为输入边界/作者工具能力保留；是否提供商店“转换为本地包”另行决定，不把任意 XML 当成已校验 ZIP，更不绕过安装事务。
6. 共享打包/校验核心负责数据，Store 负责来源与持久事务，发布 adapter 负责远端身份与提交。不要让主题 runtime、UI 配色 provider 或插件业务判断历史包/来源格式。

## 7. 建议实施顺序与本轮结束点

1. 完成 T5 共用事务、主题收据/恢复、目录发现、本地安装/更新/卸载与选中主题回退。
2. 编辑器接入同一 ZIP 打包核心，补齐草稿包元数据、版本/身份选择、导出路径反馈；商店入口可用后移除选择器本地导入。导出继续保留。
3. 提供同批客户端、主题样例和游戏操作步骤，达到原本本地 UI 评估交接标准；不要求先建设投稿服务。
4. 后续单独实现 Index 主题类型、可信 Validator/目录升级及预填提交；发布仍需明确恢复线上交付授权。
5. 根据无 GitHub 作者的真实比例，再决定共享主题库或接收服务。完整一键发布不作为当前 T5 的隐藏前置。

目前 T5 只有包契约/校验/命令行作者工具；商店主题安装和编辑器 ZIP 导出尚未实现，现有窗口仍导出 XML。本次仅完成评估和计划修订，没有进行构建、测试或远端写操作。
