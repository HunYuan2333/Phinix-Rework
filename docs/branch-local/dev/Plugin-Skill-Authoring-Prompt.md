# Phinix Rework 插件开发 skill：编写提示词

请编写可分发的 **Phinix Rework 插件开发 skill**。先读取并使用 `skill-creator`，依据当前工作区源码、整理后的开发文档和真实插件实践完成。

本轮只编写和验证 skill。不要修改业务代码、实施或修改 Actions、安装外部 skill、安装本 skill、提交/推送 Git、创建远端仓库、发布插件或提交 Index 更新。保留所有并行修改，包括未跟踪文件和 Common 子模块里的未提交实现；不能只看 HEAD。

## 1. 先确认版本和交付状态

在维护者提供的工作区定位相关仓库，先读各仓 AGENTS.md，检查分支、工作区差异、固定宿主及 Common/protobuf gitlink。不要重置、切换覆盖修改或使用 `submodule update --remote`。

先读取客户端的 `docs/branch-local/dev/Developer-Foundation-Delivery-Plan.md` 和 `docs/Local-Plugin-Quickstart.md`，核对开发者基础功能的实施及验收记录。本地侧载、开发修订、现代 DI Example、打包配置、离线预检和诊断摘要已存在于工作区，但文档仍有待完成的游戏验收。已有明确验收记录或用户确认时不要重复询问；没有时在交付中列明，不能自行宣布已正式验收。可以完成本轮 skill 草案及静态/场景验证，不把草案描述为已对正式发行版本完成游戏验证。

区分工作区实现、已提交版本、Actions 固定引用和正式发行包。源码与文档矛盾时核对实际接口，记录问题，不编造 API，也不顺手修业务代码。不要用过期本地 origin 引用推断远端现状；必要时只读核对远端，网络不可用则明确未知。

Skill 面向希望得到引导的小白和能够独立开发的技术人员，帮助他们完成需求分析、路线选择、环境准备、实现、本地迭代、验证、打包及正式发布。

主要资料位于维护者工作区 `/home/hunyuan2333/Phinix/`，该路径仅用于本轮查阅，不写进可分发 skill：

- **Phinix-Rework**：双语插件开发指南、Local Plugin Quickstart、设计哲学、兼容性与恢复约束、Inventory 文档、F7/开发者基础交付记录及实际客户端公开接口。
- **Phinix-Rework-Common**：框架契约和托管包协议。本轮优先核对客户端实际引用的 `Dependencies/Phinix.Common` 工作区及其修改；不要假设同级 Common 仓库已同步。
- **Phinix-Example-Plugin**：当前现代 Compose/中立 DI 示例、独立插件构建、`example/package-config.json`、`pack.py`、生命周期验证，以及 main 上的 CI 实践。
- **Phinix-Legacy-RedPacket、Phinix-Legacy-TalentTrade**：真实业务、构建和发布实践。核对具体版本，它们的传统入口及历史限制不作为新插件推荐写法。
- **Phinix-Plugin-Index**：托管 DLL 与工坊条目准入、受控发布、更新策略和来源更新流程。其工作区可能不是最新 main，读取时说明依据。

项目叫 **Phinix Rework**，与原 Phinix 区分。规范仓库名为 Phinix-Rework、Phinix-Rework-Common、Phinix-Rework-Server；不要因命名整理改协议、程序集、命名空间、模块 ID、packageId、持久化键或子模块目录。

优先准备可分发目录，遵循用户指定或仓库约定；没有既定位置时放在客户端 `skills/phinix-rework-plugin-development/`。不自动安装，不创建远端仓库。

## 3. 渐进式披露

SKILL.md 保持简短，只放适用范围、必要约束、判断流程和参考入口。frontmatter 符合 skill-creator，description 应能识别实际触发场景。

详细内容按需放入 references，划分以实际内容为准，不强制创建空文件。建议覆盖：

- 需求评估与托管插件/RimWorld Mod 路线：需求尚未确定时读。
- 环境与版本定位：进入构建或发布前读。
- API、DI、生命周期和资源所有权：实现模块或服务时读。
- UI、消息、库存等能力：仅实现对应功能时读。
- 本地编译、配置、预检、侧载、修订和诊断：开发迭代时读。
- 游戏验证、恢复与兼容性：验收、排障或升级时读。
- DLL Release/Index 与工坊索引：准备正式交付时读。
- main 自动发行与失败排查：配置或使用 CI 时读。

每个入口写清“什么时候读”。不要一开始加载所有仓库、复制完整 API 手册或堆积通用工程常识。尽量在 skill 内提供简短可用操作，再按目标版本定位官方文档与源码；不能只给维护者机器上的失效链接。

记录依据的版本和能力前提，避免把未发行工作区功能当成任何已安装宿主都支持。相对引用必须有效，文件和脚本应随 skill 分发或有可靠的版本化获取办法。不要生成与开发无关的 README、变更记录或占位脚本。

## 4. 先理解用户

信息不足时用少量简短问题了解：

- 用户希望逐步引导，还是直接讨论接口和实现；
- 要实现什么、使用场景及交付对象；
- 目标 RimWorld/宿主版本，以及本地试用还是正式发布。

已有答案时不重复问。小白用自然语言，解释必要术语，一次提供可执行步骤；技术人员直接给接口、约束和取舍。技术正确性与验证标准一致。

按复杂度分析范围、依赖、状态和数据所有权、失败恢复、测试及验收。简单页签不要求冗长设计报告；复杂功能先拆分再实施。用具体事实表达，避免空泛宣传和 AI 套话。

## 5. 托管插件与 RimWorld Mod

解释两条路线的职责和文件管理者。Phinix 托管 DLL ZIP 由 Phinix 安装和管理；RimWorld Mod 的 About、Defs、资源和程序集由 RimWorld/Steam 管理。

涉及游戏原生生命周期、Defs、资源或较多 Harmony 修改时建议评估 Mod 路线，说明理由、限制和发布方式，让用户决定。不要只按“复杂”强制选 Mod，也不要为了本地试用托管插件临时伪装成传统 Mod。一般托管插件优先用现有开发者侧载闭环。

选择 Mod 路线时可以建议联合使用：

https://github.com/HunYuan2333/rimworld-mod-engineering-skills

先询问是否同意下载并启用外部 skill。授权后再核对实际内容、适用范围和安装方法；外部 skill 负责 RimWorld 工程，本 skill 负责 Phinix 接口、契约和发布边界。保留已有授权，避免重复询问。本轮编写 skill 不实际安装它。

## 6. 按阶段检查环境

检查阶段需要的 Python、Git、.NET SDK、游戏/Unity/mscorlib/Harmony 编译引用、固定宿主公开程序集与 Common/protobuf gitlink；发布时才检查 gh 登录和相关网络端点。

本地开发不要求 GitHub、token、Release 或 Index。缺 gh 不阻塞本地实现。尽量复用已安装/已构建宿主的公开 DLL，独立编译插件，不要求每次重编整个宿主。

缺失工具时给获取指导、验证方法和实际可用替代路线，区分“现在必须”与“发布才需”。不要擅自安装软件、修改系统或登录账号；不读取、打印或收集 token。无 Git、无网络时只能使用已有且已验证的固定引用/源码获取方案，说明首次依赖恢复可能联网，不虚构离线下载器。没有额外的 Phinix NuGet SDK 渠道。

云端引用凭据与本地编译引用不同。维护者三个插件仓库使用私有编译引用和 `BUILD_REFERENCES_TOKEN`；不能要求第三方使用维护者私有仓库或索取该 token。第三方需自行提供合法编译引用和合适的安全获取方式。游戏、宿主和 Harmony DLL 不进入插件 ZIP 或公开引用资产。

## 7. 实现约束与实际示例

新插件优先用当前 `ClientExtensionModule.Compose` 和中立 DI 入口。当前 Example 工作区已迁移，检查被动构造、共享状态、借用 settings/dispatcher、localizer 清理及 generation 防止过期回调的具体写法；不要再宣称三个示例都尚未迁移 DI。

保持：

- 构造被动，注册/激活失败可清理；模块、连接、存档、操作生命周期分别处理。
- 借用宿主服务和跨插件 API 不由消费者释放；订阅和自有资源成对清理。
- 游戏对象与 GUI 在主线程操作；延迟回调重新确认当前模块/世界/连接上下文。
- 权威确认、整批物品交付、幂等，以及结果未知时的保留和核对。
- 只依赖公开契约，不引用内部类或具体容器，不改宿主迁就单个插件，不越权扫描/管理第三方 RimWorld Mod。
- API 可发现不等于该插件已启用/已激活；缺依赖时根据公开约束拒绝或明确降级。

红包和人才贸易作为版本明确的业务参考，不能把传统入口、已知缺陷或尚未发布的修复描述为推荐方案。明确自动化验证、编译和游戏验收各自能证明什么；源码修复不等于商店已发布修复包。

## 8. 本地开发闭环必须成为主要路线

依据当前 Quickstart 与代码，给出以下可重复步骤，实际命令按目标版本和插件仓库核对：

1. 从 Example 做独立身份的插件：程序集、包、模块、设置前缀/SectionId 等一起核对。不要只改 ZIP 名，也不要手工改生成后的 manifest。
2. 通过配置声明兼容范围、插件依赖和外部 Mod。当前工具支持 `--config`；不要套用对所有插件都一样的 pack.py 参数。
3. 独立编译、生成规范 ZIP；使用 `ManagedPackageTool --validate ZIP` 做无安装、无 DLL 执行的离线预检。可重复提供 `--host-assembly` 检查实际 CLR 引用。静态通过不能证明实际宿主兼容、依赖已启用或游戏可加载。
4. 在 RimWorld 开发者模式下从商店“dev: 安装本地插件 ZIP”进入，窄窗口走溢出菜单。选择绝对 ZIP 路径或明确目录，不扫描全盘。核对包 ID、版本与摘要后确认，再重启游戏。
5. 从扩展管理核对来源、模块发现/激活、当前会话与已安装构建摘要；使用“复制摘要”排查，不要求用户分享整份包含私人内容的日志。
6. 同本地 ID、同版本且不同 ZIP 摘要可作为开发修订；重复摘要、降级和覆盖正式来源同 ID 包被拒绝。优先使用独立开发 ID，正式包需要正常卸载并重启后才能换来源。修订后的代码要重启才加载，没有 DLL 热替换。
7. 关闭开发者模式后已安装本地包仍可管理；安装确认会重新核对模式。解释取消、重启与恢复，不建议手工删除事务或收据。
8. 验证启停/卸载及商店与扩展管理同步，区分下一启动状态和当前运行状态。取消卸载不能误称自动恢复之前的启用状态。

本地来源为 `local-development`，本地收据 schema 2 不伪装正式目录审批，旧正式 schema 1 收据仍可读。不要与 Index 公共目录版本或历史协议退役混为一谈。降级到只支持旧收据的宿主前，应在新宿主正常卸载本地包并重启完成移除；未完成事务不跨不兼容版本降级。

不要新增开发专用宿主业务 API、项目生成器、热加载、签名体系或额外 SDK。发现确需增强的能力，单独记录待办。

## 9. Git 与正式发布

新插件使用 main/dev：dev 开发；main 是维护者确认交付后的正式发行入口。已有项目先核对分支和并行修改，不强改历史。固定宿主提交及其 Common/protobuf gitlink，不使用浮动分支获取契约。

讲清两条发布路线：

- 托管 DLL：规范 ZIP/验证 → 正式 GitHub Release → Index candidate/准入审核 → 更新策略和来源更新 → 索引正式发布 → 商店可见。
- RimWorld Mod：Steam 工坊发布及工坊索引申请；RimWorld/Steam 管文件。不要沿用已取消的商店整 Mod ZIP 安装路线。

创建 Release 不等于准入通过或立即上架。新插件不会仅因 Release 存在自动加入 Index；已有获批准更新策略的插件才走受控来源更新。说明单次检测的失败/等待、版本策略限制及手动入口，不能承诺所有中间 Release 都自动逐一入库。

旧发行资产不可覆盖，同提交重试与新版本要遵循实际不可变发布规则。推送、创建 Issue/PR、发布和安装外部内容遵守用户授权；本地准备先完成。本轮不执行这些外部操作。

## 10. Actions 已有实践，准确说明版本差异

不要沿用“完整 Actions 尚未实施”的旧说法。三个插件的 main 已有自动编译、打包并发布正式 GitHub Release 的流程：

- 仅 main 的 push 触发；dev 与 PR 不触发发布构建，当前插件流程无手动编译入口。
- 每个 main 提交是一次正式发行意图，不只是发布编译产物；失败可能保留未公开草稿，应按实际重试流程处理。
- 版本按提交分配；重复执行同提交不会覆盖已发行资产。成功产物包含插件 ZIP、摘要与构建说明，排除游戏/宿主/Harmony DLL。
- 核对 workflow、ci/config.json、构建和发布脚本，而非直接复制其他仓库的权限、身份、版本及路径。

目前 Example main 的流程仍固定旧宿主提交 `403cea6c207a630fae391c6dc29bbce5a5a17b3b`；工作区新的 DI Example、配置/预检能力不能据此宣称已在 main 云端验证。正式发布这批能力前，需要先交付 Common、更新客户端准确 gitlink，再在另批工作更新相应 CI 固定引用。这个事实作为当前状态记录，不能把旧提交写成所有未来用户永久必须使用的版本。

## 11. 验证与交付

使用 skill-creator 的结构验证器检查 frontmatter 和目录，检查全部引用、跨平台路径、占位值和可执行脚本。添加脚本时实际执行，不能只通过语法检查；没有必要就不添加脚本。

结构验证不证明引导正确，还需演练并记录这些场景的走向、按需读取的参考和停止点：

- 小白做简单 Tab：独立身份 → 插件构建 → 预检 → 开发者侧载 → 重启验证。
- 技术人员做库存或消息能力：正确 API、所有权、失败恢复与游戏验收。
- 复杂游戏功能：评估 Mod，未经授权不下载/启用外部 skill。
- 缺 Python/Git/gh、游戏引用或网络：按阶段给实际替代与指导，不把本地开发卡在发布账号上。
- 宿主太旧、不支持新 DI 或侧载：检测版本，不把新工作区工具写成旧发行版已有功能。
- 本地同版本修订、重复包、正式包同 ID 冲突、模式撤销、已安装与当前加载摘要不同、启停/卸载同步。
- DLL 正式发布与工坊索引两条路线，以及 main 固定旧工具但本地工具较新的情况。
- main 构建失败、同提交重试、Release 已有但 Index 尚不可见：不覆盖资产、不跳审核。

不得为验证安装外部 skill、发布 Release、提交 Index 或修改远端。没有真实游戏验证时如实写明，不将场景演练冒充执行结果。

交付：skill 文件结构、结构和场景验证结果、依据的文档/源码版本、工作区与正式发行差异，以及仍待游戏验收或 CI 引用更新的事项。检查并保留并行修改，不自动提交或推送。完成后停止，等待下一批安排。
