# 旧客户端接入 Rework 服务端：单插件兼容评估

评估日期与规划修订：2026-10-05。范围是源码评估与实施边界，尚未实现兼容插件，也未进行游戏内联机验证。

总体顺序见 [后续实施计划](./后续实施计划.md)。登录/聊天原型用于检验共享契约，再推进物理拆仓；交易发布受独立交付政策约束，不等待或依赖客户端全量 DI。

## 结论

可以由一个服务端兼容插件承接旧协议，并复用现有 Chat/Trade 业务。
认证与用户目录的协议已经一致；聊天适配可行；交易可以翻译旧包，但完整可靠交付与完整物品状态不能仅靠服务端插件保证。

当前公开扩展接口尚不足以直接实现上述方案。需要先补齐通用服务端传输、会话验证、入站派发和出站接收者接口，并将 Chat/Trade 服务接口放入各自 Contracts。
这些是所有插件都能使用的通用能力；旧模块名、protobuf 包、字段翻译、旧客户端识别、降级规则和兼容交付记录全部留在一个插件内。
不能把“现有新客户端连接旧服务端的 adapter”误当成“新服务端已能接受旧客户端”。

## 客户端实际要求

| 环节 | 旧客户端行为 | 服务端适配要求 |
| --- | --- | --- |
| 连接 | LiteNetLib，连接 key 为 `Phinix`，模块字符串后接 protobuf `Any`，ReliableOrdered | 保留同一外层；`Any.TypeUrl` 必须是 `Phinix/Chat.*` 或 `Phinix/Trading.*` 等旧完整名 |
| 认证、用户目录 | Authentication/UserManagement 模块；收到 Hello 后认证，成功后发送 Login | 核对的所有认证、用户 protobuf（含枚举、字段类型/编号）与 Rework 相同；沿用原会话验证，不伪造用户身份 |
| 会话续期 | 使用 `ExpiresIn`；同时兼容旧 `Expiry` | Rework 已发送 `ExpiresIn`，无需专属认证分支 |
| 聊天发送 | 先创建本地 pending 消息，以 `OriginalMessageId` 查找回执，更新为 `NewMessageId` | 发真实 `ChatMessageResponsePacket`；不要再把同一消息作为广播回送发送者，否则会多一条记录 |
| 聊天历史 | 接收 `ChatHistoryPacket`；重连清空本地历史 | 登录后由插件主动同步；不等待旧客户端发送 Framework hello/history request |
| 创建交易 | 接收 `CreateTradeResponsePacket` 后才创建本地交易 | 两个参与者均需收到与自身视角匹配的创建/同步包 |
| 报价更新 | 本地物品暂时 despawn；只有成功回执的匹配 Token 才销毁托管物品 | Token 与请求一一关联；业务确认后才回成功；请求拒绝必须回失败，普通快照不能携 Token 冒充确认 |
| 空报价与双方视角 | 空 Items 是清空；Items 为本方，OtherPartyItems 为对方 | 原子清空；分别构造双方视角，不能直接转发发送者列表 |
| 接受/取消 | 状态包含 Accepted、OtherPartyAccepted、Cancelled | 保留状态语义；成交交付对方物品，取消返还本方物品 |
| 完成包 | 收到 CompleteTradePacket 就触发物品交付，随后移除本地交易；没有业务 ACK，也没有重复完成包检查 | 不能伪造 Framework completion ACK；断线/重启重放可能重复交付 |

旧消息命名空间属于 wire contract，不能因为 C# 类型放在插件命名空间而改变 protobuf descriptor 的完整名。

## 单插件设计及当前缺口

建议目录为 `Extensions/LegacyCompatibility/Server`，发布一个 `LegacyCompatibility.Server.dll`。
依赖使用通用契约和 Chat/Trade Contracts，通过普通 `IPhinixExtensionModule` 的 Register、Activate、Shutdown 路径加载。
旧 protobuf 类型可编入此 DLL；保留原 proto package，通过 `csharp_namespace` 区分 C# 命名空间，并走正常生成路径。不要手改生成源码。

| 当前缺口 | 建议的通用补齐方式 | 必须留在兼容插件内 |
| --- | --- | --- |
| HostContext 没有公开网络模块传输服务或认证会话服务 | 提供可注册/注销任意模块、发送字节、连接事件的 endpoint 抽象，以及会话认证/连接身份查询；实现放在 Server endpoint | 注册 Chat/Trading，解析旧 Any，校验字段与能力 |
| `IFrameworkServerPacketDispatcher` 只有出站 Send，没有入站入口 | 提供任意插件均可用的入站派发接口，统一认证、用户绑定和管线执行；不能默认信任插件包内 UUID | 把旧请求翻译为标准消息/命令，并维护 Token 关联 |
| 广播在执行出站 interceptor 前已 `Where(isConnectionFrameworkCapable)` | 出站管线向 interceptor 提供完整目标集合；只有通用最终传输按已注册协议路由 | 识别旧连接、选出旧接收者、发旧回执/历史/状态；其余继续原流程 |
| 登录早于 Framework hello，暂时无能力不能证明是旧客户端 | 提供通用协商状态/连接事件；已知旧模块请求是正证据，只有“暂未 hello”仍属 Unknown | 管理 Unknown/Legacy/Framework 状态、超时与重连，不误判新客户端 |
| `IFrameworkChatServerApi`、`IFrameworkTradeServerApi` 定义在 Server 实现文件 | 移至所属插件 Contracts；兼容插件解析这些接口或走标准管线，不依赖实现类 | 旧包与业务结果的翻译；不建立第二份聊天/交易权威仓库 |

禁止调用 `PhinixServer.Server.Connections` 等静态字段、反射修改 Host、直接复用旧 ServerTrading 创建独立交易库，或在业务主体里添加 `if (legacyClient)`。
插件停用/缺失时，应完整撤销模块 handler、事件订阅和连接缓存；原 Framework 客户端路径继续可用。

现有入站入口还要求 Framework capability 已协商；旧客户端不会发该 hello。通用派发契约必须能表示经过认证的其他协议来源，明确限制可调用的消息/命令，并执行同一业务管线，不能靠伪造 Framework hello 绕过授权。
登录后历史同步需要定义协商等待与补发策略，因为空闲旧客户端不会主动发 Chat 请求。超时只是兼容策略而非版本证明；Unknown 状态不得用于放宽交易物品准入或认定交付成功。

## 两个无法从服务端消除的交易边界

### 1. 交付确认与重放

旧 `ClientTrading.completeTradePacketHandler` 在每次收到完成包时都触发交付事件，没有先核对 activeTrades 是否仍有该交易，也不回 ACK。
旧服务端以通知尝试处理 PendingNotification，并不能证明物品已经在地图上交付。
Rework 则保留待通知结果，等待 `CompletionAckRequest`。直接连接两者会使完成包在下次登录重放，存在复制物品风险。

服务端插件无法同时保证“不丢失”和“不重复”：发包后记已交付可能丢失，保留并重发可能重复；LiteNetLib 的传输确认也不是地图物品落地确认。
如果要求完整可靠交易，必须让旧客户端增加交付去重、持久记录和业务 ACK，或使用具有明确人工核对流程的旧客户端交付模式。
兼容模式的记录应放在插件独立存储中，保留结果未知状态和审计，不能用虚构 ACK 删除 Trade 的权威待交付记录。后者若需要操作，必须先定义一般性的交付状态契约。
这是待设计的能力边界，不能将关闭交易后宣称全面兼容，也不能降低现有 Framework 的确认标准。

### 2. 物品状态与客户端缺失 Def

旧 ProtoThing 仅含 DefName、StackCount、StuffDefName、Quality、HitPoints、InnerProtoThing。
`TradingThingConverter` 用 ThingMaker 创建新对象，再填这些字段。它没有完整 Thing/ThingComp、pawn、基因、装备等状态。
`Client.cs` 完成/取消交付会将 UnknownItem 过滤掉，服务端无法观察到过滤或补救。

现有 `__PHINIX_STATEFUL_ITEM_V1__` 隧道适用于“新客户端经旧服务端传递状态”；原版旧客户端不会还原该隧道，不能据此认为反向兼容已解决。
服务端也不能从物品预览重建完整状态。混合新旧客户端交易必须在报价提交前检查对端表示能力，整批拒绝无法无损表示的物品，绝不静默过滤或去掉 state payload。
旧客户端没有完整 Def 清单协商，即使简单物品也需运营侧共同 Mod/Def 范围约束；服务端单独不能保证对方安装了某个 Def。
只要求服务端单插件且客户端完全不改时，可验证协议互通和受限旧格式物品；无法保证任意复杂物品完整性。

## 实施顺序与验收

1. 先补通用挂载点、服务契约和完整出站接收者上下文；用普通第三方测试插件验证可用，Host 不引用 LegacyCompatibility。
2. 单插件先实现认证后的 Chat 入站、真实回执和登录历史；验证新旧聊天共存，身份/会话不匹配时拒绝。
3. 明确交付政策，并先修通用交易完整性与持久提交约束；定义可表示物品准入，整批拒绝缺失 codec、损坏、过大/过深或部分不可表示的物品。
4. 前置条件通过后实现 Trading 入站、双方视角、报价、成交、取消、离线完成与重连；未能核对的记录保留结果未知，不自动返还。
5. 内存传输 harness 覆盖新新、旧旧、新旧聊天/交易；包含空报价、拒绝/重复/过期 Token、重复完成、断线与重启、停用插件、持久化失败、旧客户端缺 Def。
6. 直接链接旧客户端的游戏无关模块核对包处理行为，并在 RimWorld 实测物品实际所有权、存档及重连。仅编译通过不能视作联机验收。

实施前还应解决既有 `ResolveOfferItems` 在 ItemPacketRef 缺失时只告警并继续部分列表的问题，以及权威交易状态在报价成功回执前的持久化顺序。
这些属于通用交易完整性/持久化约束，应作为独立修复处理；不能藏在旧协议插件里，也不能用兼容性为理由绕过。

## 分阶段支持声明与交易决策门槛

| 阶段 | 可验证的支持范围 | 进入条件与发布限制 |
| --- | --- | --- |
| L0：通用能力 | 普通第三方测试插件可注册模块、查询已认证身份、派发与注销 | Host 无兼容插件强引用；未认证、身份伪造、重复注册和清理失败有测试 |
| L1：登录/聊天 | 指定原版源码的认证、用户目录、聊天回执与历史，新旧客户端共存 | idle 旧客户端与延迟 Framework hello 均有验证；阶段发布明确声明仅此范围 |
| L2：交易原型 | 旧包翻译、双方视角、整批准入及拒绝行为 | 通用完整性与持久化约束通过；仅协议原型不代表可靠物品交付 |
| L3：交易发布 | 选定交付政策内可核对的报价、完成、取消与恢复 | 确认、去重、物品表示和停用/重启证据齐全；未满足前不宣称完整兼容 |

默认继续按原版客户端不改动评估，不将补丁方案视为已授权或已经实现。若要求与新客户端相同的可靠交付，应另行决定客户端持久去重、业务 ACK 和物品 codec 改造；即使补 ACK，也不能自动获得完整物品表示能力。若保留原版客户端并接受受限人工核对，需要先设计可执行的未知结果处置，不以运输确认代替业务确认。

## 契约、记录与停机补充

- 入站上下文包含已认证身份、连接代次、协议来源与允许能力；UUID 来自受信会话映射，旧包只提供待核对字段。保留统一授权/限额，不因兼容路径跳过其他管线政策。
- 协议状态随连接重建，超时仍不能证明客户端版本。Unknown 的历史补发策略不能授予交易能力，迟到 Framework hello 的清理和去重需要确定性测试。
- 出站按接收者选择表示形式，保留完整目标集合与发送结果；未知、旧、Framework 接收者不会相互冒用能力。受限旧物品策略在报价被接受前执行。
- 兼容记录至少关联稳定服务器/用户/交易/操作身份、连接代次、协议版本、状态、尝试与核对证据。身份持久锚点不能只依赖可修改的服务器显示名。
- Trade 保持唯一业务权威，兼容存储只维护翻译关联、交付尝试和核对证据。需要操作权威交付记录时，通过一般性契约设计，不能复制一套 ServerTrading 或直接改内部文件。
- 兼容插件停止先关闭新请求，再处理在途任务、撤销模块与订阅。未决交易和记录继续保留；缺少插件时明确停止旧协议处理，不能自动完成、退款或删除证据。
- 重启或升级核对记录版本与身份，迁移失败保留记录并停止对应业务路径。客户端无持久去重时不自动重放结果未知完成包；取消包涉及返还，同样需要所有权核对。
- 控制输入尺寸/深度、请求频率、Token/关联缓存容量和记录保留；清理缓存不等于删除未决交付证据。具体数值由基线与试点决定，不沿用无界旧实现。

新增验收覆盖：插件缺失/停止/升级且有未决交易、延迟 hello 与 idle 客户端、恶意 UUID、重复注册、持久写入失败、完成或取消发出前后崩溃、 mixed peer 不可表示物品、重连重复 Token、缺 Def 与旧数据恢复。纯协议 harness、真实旧模块行为测试、RimWorld 物品所有权验证分别记录结果，不互相替代。

本轮仅完善实施规划，L0—L3 均未因此标记通过。
