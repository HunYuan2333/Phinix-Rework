# 统一库存功能可行性与架构方案

> **已废止（2026-09-13）**：本文中的 `BigInteger`、小额自动空投和软依赖结论已被新的产品决策覆盖。当前评估见 [库存插件客户端架构与持久化评估.md](库存插件客户端架构与持久化评估.md)。保留本文仅用于追溯旧方案，不应据此实现。

> 调查日期：2026-09-09  
> 调查范围：最新《LegacyRedPacket 性能、稳定性与设计审查》、当前 Trade/LegacyRedPacket 客户端实现、扩展框架生命周期与设计哲学。  
> 本文只做方案调查，不代表已经开始实现。

## 1. 结论先行

建议新增一个内置的 `builtin.inventory` 客户端扩展，统一保存“已获得但尚未交付到地图”的 `Thing` 物品；Trade、LegacyRedPacket 以及未来其他功能通过库存契约写入，玩家再按需提取。白银等通常被称为“货币”的资源，在 RimWorld 中同样是可堆叠的 `Thing`，不另设货币通道。

库存的业务语义、账本、提取 UI、RimWorld `GameComponent` 和物品编解码都应归库存扩展所有。Host 只提供已经存在的通用能力，例如扩展发现、API 注册、主线程调度和通用存储路径，不直接认识“库存”“红包”或“交易”。

库存从第一版开始就定义为**当前存档私有数据，永久不做跨存档自动继承**。这不是暂缓项，而是兼容性边界：如果今天按存档设计，未来再把库存改成全局继承，会改变数据归属、重复领取风险和玩家对存档的预期，属于破坏性更新。因此本方案不预留“以后自动跨存档”的产品语义或迁移承诺。

这个方案可以保持普通用户当前看到的交互：普通交易和普通红包仍然可以立即空投；只有大额、无法安全一次性实体化或玩家主动选择暂存的奖励进入库存。

## 2. 最新审查文件与当前状态

最新审查文件将红包问题分为两条链路：

1. **收到即卡**：接收阶段曾经存在主线程无界排空、重复状态更新、通知风暴、Relay 大响应和 UI 全量绘制风险。当前 Phase 1、Phase 3、Phase 4 已完成相关边界修复。
2. **点击领取后卡崩**：`SpawnReward` 仍可能按 `stackLimit` 无界创建大量 `Thing`，并且 Phase 2（有界实体化、虚拟账本、失败安全交付）仍然延后。

因此，当前代码已经封住了若干明确的接收路径资源风险，但没有现场遥测时，不能把“单个 `TotalCount` 很大”认定为收到即卡的唯一根因。库存功能主要解决第二条链路，同时可以让交易、红包和未来模块共享同一套有界交付机制。

### 2.1 游戏原生大数支持调查

已对本地 `GameDlls/Assembly-CSharp.dll` 和现有协议代码做静态核对：

- `Verse.Thing.stackCount` 的字段类型是 `System.Int32`；
- `Verse.ThingDef.stackLimit` 的字段类型是 `System.Int32`；
- Trade 的 `TradeItemSnapshot.StackCount` 是 `int`；
- `FrameworkItemPacket` 和旧版交易协议中的 `stackCount` 也是 `int`。

这意味着 RimWorld 原生物理层支持的单个堆叠上限受 `Int32` 和具体 `ThingDef.stackLimit` 双重约束，不能通过库存扩展把一个真实 `Thing` 的 `stackCount` 改成 `long` 或 `BigInteger`。超过原生堆叠上限的数量，必须表现为多个真实 `Thing`，或者继续作为非实体化库存数量保存。

因此“尽可能支持大数字”的正确目标不是让游戏世界出现一个超大 `Thing`，而是：

1. 网络入口按既有协议支持到 `int` 范围；
2. 库存聚合和存档不受 `int`/`long` 溢出限制；
3. 物理提取严格按 `int` 堆叠、`stackLimit`、单次实体预算和主线程预算执行；
4. 超出物理表达能力的部分永久保留为当前存档内的逻辑库存余额。

## 3. 现有代码可复用点

### 3.1 扩展框架已经支持所需的解耦方式

当前框架已有：

- `IPhinixExtensionModule` 的发现、注册、激活、关闭生命周期；
- `ExtensionApiRegistry` 的跨扩展 API 注册与解析；
- `IClientMainThreadDispatcher`，可把 Verse/Unity 操作放回主线程；
- `IItemCodec` 与 `FrameworkItemPayload`，可用编解码器保存物品而不是直接保存 `Thing` 引用；
- `IExtensionStorageProvider`，可提供扩展自己的文件路径。

这些能力足以让库存成为独立扩展，不需要把库存业务硬塞进 Host。

### 3.2 当前 Trade 的直接交付点

`PhinixDefaultTradeBehaviour` 在 `OnTradeCompleted` 和 `OnTradeCancelled` 中将 `TradeItemSnapshot` 转换成 `Thing[]`，然后调用 `DropPods`。这说明库存的第一处接入点明确：

```text
交易完成
  → 生成/接收中立物品载荷
  → 写入库存账本
  → 默认立即提取（保持当前空投交互）
  → 无法立即安全提取时留在库存
```

为了支持自定义 `IItemCodec`，长期不应只依赖已经降级过的 `TradeItemSnapshot`。建议在交易完成事件中增量暴露原始 `FrameworkItemPayload`，旧调用方继续使用现有 `Items` 属性，避免破坏兼容性。

### 3.3 当前红包的直接交付点

红包领取最终进入 `SpawnReward`，其中 `CreateThingsFromTemplate` 按堆叠上限拆栈并创建真实 `Thing`。这正是库存最有价值的接入点：

```text
本地领取结果通过校验
  → 以 (packetId, claimerUuid) 幂等写入库存
  → 普通数量走快速提取
  → 大数量建立有界提取任务
  → 剩余数量继续留在库存，不丢失、不截断
```

发送者正在发送的红包仍然可以在第一版继续使用现有 `StoredThings` 托管。发送中、超时归还和领取完成后的物品转库存可以分阶段迁移，避免一次性改动过大。

## 4. 功能边界与可行性

| 能力 | 可行性 | 第一版建议 | 主要风险 |
|---|---|---|---|
| 当前存档内物品库存 | 高 | 作为首发范围 | 存档加载时需要校验坏数据 |
| Trade 完成后进入库存 | 高 | 先保留立即空投，再提供暂存开关 | 旧事件只有快照，需保留 codec 信息 |
| 红包领取后进入库存 | 中高 | 与 Phase 2 一起实现 | 需先修复 assign 因果校验和幂等入账 |
| 大额数量完整保存 | 高 | 任意精度逻辑数量 + 有界提取 | 不能承诺一次生成同等数量的实体 |
| 任意 Mod 物品 | 中 | 依赖 `IItemCodec` | 未注册 codec 的物品只能降级或拒绝提取 |
| 物品自定义 Comp 完整保真 | 中低 | 先按现有 codec 能力支持 | 当前 Trade 快照本身不覆盖所有 Comp 状态 |
| 白银等“货币”物品 | 高 | 按普通 `Thing` 进入同一库存 | 仍需遵守 Def、堆叠和实体预算 |
| 自动跨存档继承 | 不纳入范围 | 永久不做 | 会改变存档归属和已有用户预期，属于破坏性更新 |
| 显式导出/导入凭证 | 不纳入库存本体 | 不提供 | 仍然会形成跨存档转移语义，超出本功能边界 |

“库存”定义为**`Thing` 物品托管账本**。白银、药品、资源和其他可交易物品全部走同一条物品路径；本方案不区分“货币物品”和“普通物品”。非 `Thing` 的声望、研究进度、权限或其他游戏状态不属于库存功能范围。

## 5. 推荐的数据模型

库存不能保存大量真实 `Thing` 实例，也不能为巨大数量预先创建等量列表。推荐使用“少量记录 + 数量”的模型：

```text
InventoryEntry
  EntryId              唯一记录 ID
  CodecId              物品编解码器 ID
  Payload              中立物品载荷（JSON/bytes）
  Quantity             任意精度的非负逻辑数量，不直接等于已创建实体数
  Source               trade / redpacket / other
  SourceTransactionId  来源幂等键
  SchemaVersion        记录版本
```

同一 `CodecId + Payload` 且语义上可堆叠的物品可以合并数量；品质、Stuff、耐久、内含物等会影响相容性的字段必须进入载荷或稳定哈希，不能只按 `DefName` 合并。

### 5.1 数量类型与保存格式

`long` 不作为库存数量的最终模型。虽然当前 v1 红包字段是 `int`，但库存会合并多个来源、多个交易和多个红包；一旦未来允许继续聚合，64 位整数仍然会成为人为上限，而且溢出会直接破坏账本正确性。

推荐采用三层表示：

```text
内存运算：System.Numerics.BigInteger
扩展契约：InventoryQuantity 值对象（只允许非负值）
存档格式：规范十进制字符串，例如 "0"、"75"、"2147483647"
```

本地 Verse 暴露的 `Scribe_Values.Look<T>` 虽然是泛型签名，但这不代表任意 .NET 类型都具备稳定的原生值序列化支持。存档和日志不要直接传入 `BigInteger`，也不要使用 `double`、`float` 或可能发生舍入的 `decimal`。在 `GameComponent.ExposeData` 中按字符串保存；加载时使用不变文化解析、去除前导零、拒绝负号和非法字符，再转换为内部 `BigInteger`。

任意精度不等于无限输入。为了防止恶意存档或旧插件构造超长数字导致 CPU/内存消耗，仍应设置 `MaxQuantityDigits`（建议首版 256 位十进制数字，已经远超正常游戏规模）和单条记录总载荷上限。这个限制是输入/存档防护，不是 RimWorld 物理堆叠上限；超出上限的记录隔离并记录诊断，不得截断后继续发放。

物理提取时只把 `BigInteger` 分解为不超过 `ThingDef.stackLimit` 且不超过 `Int32.MaxValue` 的 `int` 批次；绝不能先把巨大数量转换成 `int`、`long` 或列表长度。数量扣减也必须先验证余额，再以任意精度执行，成功交付后才提交扣减。

同时保留有界的交易记录：

```text
InventoryTransaction
  TransactionId
  Source
  SourceKey
  Add/Withdraw
  Status
  CreatedAtUtc
```

`SourceKey` 用于防止重复事件重复入账。红包至少使用 `(packetId, claimerUuid)`；Trade 至少使用 `tradeId + participantUuid + completionKind`。交易记录也必须有容量上限和淘汰策略，不能用另一个无限增长集合替代当前问题。

## 6. 提取模型与性能边界

提取需要分成两个阶段：

1. **账本操作**：只修改中立数据，数量运算使用 `BigInteger`，在主线程上以常数级记录规模完成。
2. **物理交付**：按 `ThingDef.stackLimit` 计算实际堆数，每 Tick 只创建有限数量的 `Thing`，创建、DropPod、地图访问和 UI 更新全部遵循主线程预算。

建议保留三层边界，并把快速提取上限做成可配置项：

- `MaxEntries`：库存记录数上限；
- `MaxThingsPerTick`：本 Tick 最多创建的实体数，由系统硬上限保护；
- `MaxThingsPerExtraction`：一次自动提取或手动提取允许使用的实体预算；
- `QuickExtractionThingLimit`：普通交易/普通红包自动快速提取的目标上限，由玩家配置。

`QuickExtractionThingLimit` 只影响“是否走立即交付”以及一次快速交付的规模，不改变红包金额、库存总量或手动提取能力。配置值必须经过范围夹紧，例如：

```text
用户配置：1 ～ 设定的系统硬上限
默认值：较小的安全值（建议 32 个 Thing）
实际值：min(用户配置, MaxThingsPerExtraction, MaxThingsPerTick 的累计预算)
```

系统硬上限不能被配置项绕过；用户把快速提取上限调高时，仍然不能突破单 Tick 时间预算、单次实体预算和库存记录容量。建议在库存设置中提供“快速提取实体数”选项，并显示说明“较高数值可能增加单帧负载”。

数量本身不应被简单截断。一个 `stackLimit` 很高的 Mod 物品可能可以安全提取；一个 `stackLimit = 1` 的物品，即使逻辑数量不大，也可能超出实体预算。超过预算的部分继续作为库存余额，下一 Tick 或下一次用户提取再处理。这里的余额使用任意精度数量，不受 `long` 上限约束，但受十进制位数和记录大小硬上限约束。

这就是“虚拟仓储/余额凭证”在现实工程中的对应做法：用常数级记录保存完整逻辑数量，把昂贵的物理对象创建变成受预算约束的消费过程。:codex-annotation{index="1"}

## 7. 存档策略比较

### 7.1 随当前存档保存：首选

实现方式：库存扩展提供一个 `GameComponent`，在 `ExposeData` 中保存版本号、库存记录和有界交易记录。加载时执行字段长度、数量、codec、Def 可用性和记录数校验。

优点：

- 和 RimWorld 的存档语义一致；
- 不需要修改服务端或网络协议；
- 不会把一个存档的物品带入另一个完全不同的世界；
- 可以沿用 `TalentTradeGameComponent` 已验证的“扩展自行拥有 GameComponent”模式；
- 迁移和回滚范围清楚。

注意事项：

- 游戏关闭、切换存档和异常退出时要保证账本由 Scribe 保存；
- 扩展禁用时 `GameComponent` 仍可能被 RimWorld 自动实例化，必须像 TalentTrade 一样检查运行时激活状态；
- 不应在 `ExposeData` 中创建 Thing、发空投或触发网络副作用。

### 7.2 跨存档继承：明确永久不做

本功能不使用全局 profile，也不把库存写入与存档无关的共享文件。即使技术上可以通过 `StorageProvider` 实现，也不采用，原因是：

- 物品归属会从“某个世界”变成“某个本地账户”，改变现有存档语义；
- 同一个账户同时打开多个存档时会产生并发、重复消费和回滚问题；
- Mod、Def、codec 或存档版本变化可能使旧库存无法安全还原；
- 云同步、复制存档和卸载扩展时难以解释哪个库存才是权威；
- 未来再从 per-save 切换为全局继承必然需要数据迁移和用户行为改变，属于破坏性更新。

因此，库存数据结构、设置文案和 UI 都必须明确标注“仅当前存档”。不能添加隐藏的全局备用文件、账户级缓存或“以后可开启继承”的开关。

`ExtensionHostContext.StorageProvider` 仍可用于扩展级配置、诊断或缓存，但不能用于保存库存余额；库存唯一权威来源是当前 RimWorld 存档中的 `GameComponent`。

### 7.3 明确排除的替代方案

本方案也不提供导出/导入凭证、跨存档兑换码或手动搬运库存。它们虽然比自动继承更容易控制，但仍然会建立跨存档转移语义，并把物品所有权和安全审计扩展到本功能之外。若将来出现类似需求，应另立全新功能和迁移协议，不能把它视为本库存的兼容升级。

## 8. Extension 还是 Host

### 8.1 做成 Host 内容的优点与问题

优点是所有扩展都可以直接使用，生命周期看起来统一。

问题是它会让 Host 认识“物品库存”这一业务概念，进而出现：

- Host 引用 Trade/RedPacket 的业务数据或 codec；
- 通用 Host 被迫承担 RimWorld `Thing`、地图、空投和库存 UI；
- 新业务必须修改 Host，违反“新增业务能力不应要求 Host 改动”的原则；
- 插件禁用、替换或第三方扩展接入时，边界变得模糊。

因此不建议把库存实体、库存 UI 或红包/交易适配代码放进 Host。

### 8.2 做成独立 Extension 的优点

库存扩展可以独立拥有：

- `builtin.inventory` 生命周期；
- `IClientInventoryService` 和中立 DTO；
- per-save `GameComponent`；
- 物品 codec 适配；
- 库存 Tab、提取窗口和徽标；
- 交易/红包来源的幂等账本；
- 有界交付队列和失败重试状态。

Trade 与 LegacyRedPacket 通过 API Registry 解析库存能力，不需要 Host 知道双方的业务细节。

### 8.3 推荐的混合边界

最终边界建议如下：

```text
Host
  ├─ 扩展发现、依赖和生命周期
  ├─ API Registry
  ├─ 主线程调度器
  └─ 通用存储路径/配置基础设施

builtin.inventory Extension
  ├─ 库存领域模型与中立契约
  ├─ GameComponent 与 per-save Scribe
  ├─ 账本、幂等、预算和提取队列
  ├─ 库存 UI
  └─ ItemCodec 适配

Trade / LegacyRedPacket Extensions
  ├─ 保留各自协议和业务状态
  ├─ 在完成/领取点提交库存载荷
  └─ 库存不可用时按兼容策略回退旧 DropPod
```

也就是说：**库存是 Extension；调度和基础存储是 Host 能力；业务语义不进入 Host。**

## 9. 依赖与兼容策略

建议扩展 ID 为 `builtin.inventory`，并采用两阶段依赖策略：

1. 首次发布时作为默认启用的软能力。Trade/红包发现库存 API 后使用库存；发现不到时回退现有直接空投，保证旧配置和异常环境可用。
2. 库存稳定、所有交付路径迁移完成后，再考虑把 Trade/红包声明为硬依赖。硬依赖前必须定义“库存扩展被禁用时”的明确提示，而不是静默丢物。

库存契约不应引用 `TradeItemSnapshot` 或红包类型。建议新建独立的 `Inventory.Contracts`，只依赖框架中立的 `FrameworkItemPayload`、数量、来源和结果类型。这样未来 Chat、任务、邮件或其他扩展可以接入，不形成 Trade → Inventory → Trade 的循环引用。

旧插件和 v1 Relay 不需要升级。旧版发来的大额红包仍然可以被接收和展示；客户端在本地领取结果落账、提取和物理实体化阶段执行预算。发送端限制仍只属于提前提示，不是安全边界。

## 10. 保持普通交互不变的流程

### 10.1 普通交易

```text
交易完成事件
  → 库存登记（幂等）
  → 立即提取
  → 原有 DropPod/Letter
```

用户仍看到“交易完成并收到空投”，只是物品先经过一个可靠的本地托管点。

### 10.2 普通红包

```text
点击领取
  → 现有领取算法与结果提示
  → 奖励完整写入库存
  → 预计实体数在预算内时立即提取
```

### 10.3 超大红包或地图暂不可用

```text
点击领取
  → 奖励完整写入库存
  → 显示“已存入库存”
  → 用户在库存 Tab 中按数量提取
```

这里改变的是失败时的兜底方式，不改变红包的金额、分配算法或旧协议交互。

### 10.4 交付失败

物品先处于 `PendingDelivery` 或库存余额状态，只有实际创建并成功交付后才减少库存。没有地图、codec 失败或单批预算不足时不能把领取标记为已完成后直接丢失物品。

## 11. 分阶段实施建议

### Phase A：库存基础层

- 新建 `Inventory.Contracts` 和 `builtin.inventory`；
- 建立中立载荷、任意精度 `Quantity`、幂等键和版本化记录；
- 使用 per-save `GameComponent` 保存和加载；
- 实现有界提取队列，但先不改 Trade/红包的默认交互；
- 加入库存 Tab，至少能查看记录、数量和失败状态。

### Phase B：Trade 接入与迁移

- 给交易完成事件增加原始 `FrameworkItemPayload` 的兼容字段；
- Trade 完成和取消分别定义来源语义，避免同一批物品重复入账；
- 将 `PhinixDefaultTradeBehaviour.OnTradeCompleted` 的直接 `Thing[] → DropPods` 改为“载荷入库存 → 按 `QuickExtractionThingLimit` 尝试快速提取”；
- `OnTradeCancelled` 保留“物品归还原持有者”的语义，同样先写入库存，再按配置快速提取，不能把取消误记为交易所得；
- 迁移期间保留旧 DropPod 回退：库存扩展未启用、载荷无法入账或迁移失败时，继续走原有 `DropPods`，并记录一次限频警告；
- 旧 Trade 会话和已打开窗口不迁移历史状态，只从迁移启用后的完成/取消事件开始接管，避免重复处理已经交付过的物品；
- 验证 vanilla、Minified、品质、Stuff、未知 codec 和自定义 codec。

### Phase C：LegacyRedPacket 接入与迁移

- 先完成审查文件中 Phase 2 的 create/assign 校验；
- 领取结果以 `(packetId, claimerUuid)` 幂等写入库存；
- 将 `SpawnReward` 的物理创建部分改为库存提取任务，不再按金额执行无界同步循环；
- 普通红包领取按 `QuickExtractionThingLimit` 尝试快速交付；超过上限的部分仍完整留在库存；
- 迁移第一版不改发送者在途红包的 `StoredThings` 托管方式；只有领取成功、超时归还或明确失败恢复时，才把可安全转化的奖励接入库存；
- 对迁移前已存在的红包：继续由旧状态机完成原有生命周期；迁移后的新领取结果才写入库存，避免同一红包同时由旧交付和库存交付；
- 若旧状态机已经把奖励标记为成功但尚未能确认物理交付，不能自动猜测并重复入账，应通过明确的待交付记录或人工恢复入口处理；
- 将无地图、转换失败和超预算统一变成库存中的可重试状态；
- 普通红包保留即时空投，大额红包自动进入库存。

### Phase D：存档边界验收

- 验证新建、保存、加载、复制和切换存档时库存严格隔离；
- 验证删除、禁用扩展或缺失 Mod 时不会读取其他存档的库存；
- 验证不存在全局库存文件、账户级余额或隐式导入路径；
- 将“仅当前存档”写入设置、帮助文本和迁移文档，作为稳定产品契约。

## 11.1 两个现有插件的迁移顺序

建议按“先旁路、再接管”的方式迁移，避免一次切换影响现有用户：

1. **Inventory 扩展先上线但默认只观察**：建立 GameComponent、库存 UI、配置和诊断指标，不改变 Trade/红包交付。
2. **Trade 旁路接入**：完成事件同时生成库存入账预览和旧 DropPod 结果，验证载荷、数量、幂等键及快速提取耗时；预览期间不重复发放。
3. **Trade 正式接管**：库存入账成功后按配置快速提取；只有库存不可用或入账失败才回退旧 DropPod。
4. **LegacyRedPacket 先接领取结果**：不改发送端和在途 `StoredThings`，只把通过本地校验的最终奖励交给库存。
5. **LegacyRedPacket 再接超时/失败恢复**：确认库存交付成功后，逐步替换 `SpawnReward` 和原有直接掉落路径。
6. **观察期结束后清理旧分支**：保留旧分支作为兼容回退，不在首个版本删除；至少经过一个完整版本周期和存档回归后再评估移除。

迁移必须使用稳定的来源幂等键。Trade 不得只用物品内容作为键，因为两次合法交易可能包含完全相同的物品；红包不得只用 `claimerUuid`，必须绑定 `packetId`。所有“入库存”和“快速提取”都要有可观测结果，避免迁移失败时既无法判断是否入账，也无法安全重试。

## 12. 验收标准

- 收到单个超大红包不会按数量创建 `Thing`；
- 任意合法 v1 `int` 数量都能完整写入本地库存账本；
- 多个来源聚合到超过 `Int64.MaxValue` 的逻辑数量时仍能正确加减、保存和加载；
- 256 位以内的合法十进制库存数量保存后字面值不变，前导零会被规范化；
- 任何真实 `Thing` 的 `stackCount` 都不超过 `Int32.MaxValue` 和对应 `ThingDef.stackLimit`；
- 单 Tick 和单次提取的实体创建量都有硬预算；
- 重复 Trade 完成、重复 assign、断线重连不会重复入账；
- 普通交易和普通红包的可见交互仍是即时空投和原有提示；快速提取数量由设置控制，但默认行为保持不变；
- 无地图、未知 codec、存档加载坏记录不会静默丢物；
- 库存记录、交易日志和提取队列都有容量上限；
- 禁用库存扩展时有明确兼容回退，不会让 Trade/红包失去交付路径；
- 不修改服务端、不修改 v1 wire format、不要求旧插件升级；
- per-save 模式通过存档切换、复制、加载、保存、崩溃恢复和 Mod 缺失回归测试；不同存档之间不得出现库存串读或继承。

## 13. 最终决策

当前最稳妥的工程决策是：

1. **新增 `builtin.inventory` 内置扩展，而不是 Host 内容。**
2. **库存永久只属于当前存档，不做跨存档自动继承、导出/导入或账户级共享。**
3. **库存保存中立载荷和任意精度逻辑数量（内存 `BigInteger`、存档十进制字符串），不保存海量真实 `Thing`。**
4. **普通流程自动提取，大额或异常流程按需提取。**
5. **Trade、LegacyRedPacket 先软接入并保留旧 DropPod 回退，稳定后再考虑硬依赖。**
6. **把库存作为审查文件 Phase 2 的实现载体，但单独立项，避免把“收到即卡”的已完成接收修复和大规模新功能混在同一补丁中。**
7. **快速提取上限开放为用户配置，但始终受系统硬上限和动态主线程预算约束。**
8. **Trade 与 LegacyRedPacket 采用分阶段迁移，先保留旧 DropPod 回退，再逐步让库存成为唯一交付入口。**
