## Pre-fix findings

1. **P1 — Receiving a market pawn lacks a matching transaction/authenticated sender gate.** `TalentTradeManager.cs:846` `HandleMarketSell` compares the payload buyer UUID with the local UUID, then removes a pending ID and queues pawn materialization. It does not first require that the ID exists in pending purchases or bind the seller to an authenticated event origin and the expected listing. Message processing does maintain in-session deduplication (`:532–648`), but deduplication is not sender authentication or a proof of an authorized purchase. If unauthorized or modified messages can reach the relay stream, unsolicited delivery/data processing is possible. No remote attack or exploit was performed, and server-side identity protections are unknown.

2. **P1 — Plain HTTP and no client-side authenticated event origin.** `TalentTradeTransport.cs:13–15` uses an HTTP endpoint/shared room with an empty key. GET/POST have no TLS; outgoing sender identity is a client-supplied header, while the receiving path forwards decoded payload text without an authenticated sender context. Protocol handlers compare UUID fields from that text; no cryptographic message verification was found in this client. These facts establish absent client protections, not that the server permits arbitrary internet writes or administrative access. Server authentication, source filtering and rate limits require the original operator's evidence. [OWASP REST security guidance](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html) recommends HTTPS and bounded payload handling.

3. **P1 — Unbounded input reads and GZip expansion.** `TalentTradeTransport.cs:150–157` Base64-decodes and expands compressed data with `ReadToEnd`; the response body at `:274–278` is also read without a byte cap. Fetch count and queue length limits do not bound each message or decompressed pawn XML. Oversized or highly compressed input can exhaust memory or stall game-thread parsing. `PawnDeserializer.cs:73–103` loads expanded XML then invokes game Scribe. The review does not establish arbitrary code execution or an XML external-entity exploit; explicit XML reader/expansion limits still need verification and implementation.

4. **P1 release gate — Item/pawn ownership still relies on legacy trust and incomplete recovery evidence.** `HandleMarketPaid` at `TalentTradeManager.cs:887–891` explicitly leaves payment confirmation unimplemented/trust-based. Transport overflow drops the oldest message, retries can reorder work, and initial fetch covers only 20 minutes. Return-ledger improvements preserve ambiguous pending data but are not a complete acknowledged, durable purchase/delivery protocol. Actual missing-package resaving/late component discovery and independently installed pawn ownership recovery remain unproven. These are existing legacy risks, not newly caused by making the repository public.

5. **Data exposure boundary.** `PawnSerializer` serializes the selected Pawn through Scribe, then GZip/Base64. This transfers character state, not an encrypted payload or a verified whole-save upload. Trade/rental messages also contain participant identifiers/names and compatibility Def metadata. The service operator can receive these messages; HTTP exposes transit data to on-path observers. Pending-return audit records are bounded/escaped IDs and outcomes, without serialized pawn data. Legacy debug/error logs can contain IDs, names and exception details; they are not automatically equivalent to credential leakage.

## Original recommendations (implementation status above)

- Ask the original service maintainer whether HTTPS is available, how writing/sender identity/rooms are authorized and rate-limited, and what event retention/acknowledgement guarantees exist. Do not replace the legacy endpoint or alter interoperability without that clarification.
- Locally bound response bytes, encoded/decoded bytes, GZip output, XML size and parsing work; preserve all-or-nothing item semantics. Validate expected pending purchase, seller/listing identity and payload before removing records or queueing delivery. Add regressions for unsolicited/wrong-party delivery, oversized payloads, expansion limits and failure retention. UUID matching or hashing alone does not authenticate a remote sender.
- Keep the existing source/static CI evidence separate from game/server security acceptance. Do not add `plugin-approved` automatically or describe v1.0.0 as production-security approved. Resume normal intake after the relevant local fixes and service/game gates are recorded; approval remains the user's action.

This initial audit batch only read source and official security guidance and wrote bilingual audit/planning records. It made no protocol/endpoint/business-code changes, did not contact the legacy relay, and ran no attack or in-game tests. Builds/runtime harnesses were not repeated because code was unchanged. Main dirty-tree changes remain uncommitted. No secret value was logged or added to this document.
