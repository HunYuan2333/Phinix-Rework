## 当前限制

当前 `GitHubRepositoryAccess.OriginOperation.Repository` 只接受匿名可访问的公开仓库；准入机器人的 `GitHub.verify_origin` 也要求公开发行来源、精确仓库/所有者/Release/tag/commit/资产身份，且固定 commit 中有真实 C# 源码。版本监控同样要求公开来源。私有源码仓库不能直接作为现有商店发行来源；公开的纯二进制仓库也需要明确改准入政策。不能塞一个假的 `.cs` 绕过检查，也不能给玩家客户端放仓库 token。

GitHub 的 [Release API 文档](https://docs.github.com/en/rest/releases/releases)和[token 权限表](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)说明访问边界。单独增加 CF 回源 token 权限，不会让匿名 GitHub 直连与之对等，也不会自动满足现有仓库/源码检查。

private 减少新源码直接公开，但公开 DLL 中硬编码的服务 IP 和客户端参数仍能被分析出来。主体公开仓库中已有副本/历史也不会因新仓库私有而消失；本批不改变主体可见性或重写历史。

## 后续发行路线和顺序

1. 两个源码仓库保持 private，保留旧服务行为；先完成红包未决发送/历史核对和人才晚加载/缺包保存保留。
2. 为这两个旧插件设计单独的**公开二进制发行来源**，只提供版本说明、changelog、明确来源记录和不可变 ZIP。新建公开发行仓库及上传资产是另一次公开发布动作，不由私有源码推送授权涵盖。
3. 加入明确审阅过的私有源码/旧插件准入政策，仅覆盖维护者批准的这两个包；普通发布者保留公开源码路径。区分公开发行 tag/commit 与私有构建源码 commit，记录源码快照、manifest、ZIP 摘要，明确由谁核对私有源码及构建来源。静态 DLL 校验不等于证明源码与二进制一致。
4. 保持索引、GitHub 直连和 CF adapter 使用相同目录与资产身份协议。游戏客户端无 token 读取公开发行来源，CF 缓存同一份已批准公开字节；私有源码权限只用于维护者及受控构建，与玩家下载凭据分开。
5. 验证准入、来源/tag/hash 不匹配拒绝、版本监控和 GitHub/CF 下载一致，再走正常 Issue 审批与目录发布。真实托管安装、重启、卸载重装、存档及所有权恢复通过后，才移除主体内置产品。

若将来连二进制资产也要求 private，匿名 GitHub 直连将无法工作，需要另外明确设计服务端代取及玩家访问方式，不能由 CF 悄悄引入另一套默认行为。这是方案记录；准入/来源改造和公开二进制发行来源尚未实现，不先推进其他专项。
