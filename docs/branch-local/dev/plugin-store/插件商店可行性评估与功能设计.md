## 1. 结论与范围

术语按 [术语与功能分层](术语与功能分层.md) 理解：**基础功能通过内置功能模块解耦；本轮规划让红包、人才等可选扩展通过独立包按需分发，两者共享技术契约。** 本文的“插件商店”保留既有名称；实现商店的代码称商店功能模块，商店内的下载对象称扩展包/模组。Chat、Trade、Inventory、LegacyAdapter 的基础功能定位不等于 Host/Core 实现或新的不可禁用政策。

**可行，建议采用“商店功能模块 + GitHub 审核索引 + 工坊/GitHub 双渠道 + 显式包依赖清单”的方案。** 工坊条目在 Steam 游戏内浏览器打开，由玩家自行订阅；商店不下载工坊内容，其前置依赖交给 Steam。GitHub 条目索引作者仓库与固定 Release 资产，可自动下载、校验和安装。GitHub 包作者声明版本号与依赖，商店依此解析 GitHub 依赖链，不解析工坊的递归前置。插件仍通过原有模组加载及适用的 Phinix 扩展生命周期生效。

已由用户明确的要求：

- 首版面向游戏内客户端；服务端暂时手动安装。
- 从 GitHub 获取列表；源可配置，并有默认源。
- 默认源由 Phinix 维护，是经过审核的插件索引仓库。
- 评估自动解析和下载依赖，包括传递依赖链。
- 特殊网络环境下允许配置**仅插件商店使用**的 HTTP、SOCKS5 等代理。
- 本阶段只做评估与功能设计，保存文档，不实际实现。
- 工坊模组索引工坊链接；轻量 GitHub DLL 包索引 GitHub 链接，评估类似 AstrBot 的自动化。
- 官方仓库发布审核后的索引，DLL 由作者仓库发布；首次入库人工批准，后续版本自动检查后更新索引。
- 默认源允许任何作者申请，审核后收录；GitHub 插件必须有可审查源码，无源码 DLL 不收录。源码存在不等于已证明源码/产物一致或代码安全。
- 开发者友好：提供完善的开发/发布指南与文档，评估配套 AI 指引，使非计算机专业者能在 AI 帮助下开发、测试并发布简单插件。
- 使用版本号表达版本；GitHub DLL 包由插件作者显式声明版本和依赖。工坊只提供链接，前置依赖利用工坊自身机制；后续评估聚焦具体软件工程，不扩大产品指标或运营体系设计。
- 工坊链接通过 Steam 游戏内浏览器（Steam Overlay）打开，由玩家在页面自行订阅；不由商店下载或自动订阅。
- 后续将红包、人才贸易改为可下载的官方插件；本轮已确认 Chat、Trade、Inventory、LegacyAdapter 暂时继续随主包发布。

当前推荐、尚未由用户明确确认的产品决策：

- 首版支持两种来源；GitHub 首选轻量标准 ZIP，纯 DLL + 明确清单可评估生成最小本地模组壳。安装结果优先保持标准模组身份，不直接写 Phinix/Workshop 目录。
- 安装与启用分开：新包默认不启用，玩家在原生模组列表中启用、排序并重启；不承诺当前游戏热加载。
- 首版优先提供浏览、搜索、依赖计划、新包安装、缓存及代理；升级覆盖、卸载和自动修改模组列表进入后续阶段。

| 能力 | 可行性 | 主要条件或限制 |
| --- | --- | --- |
| 默认/自定义 GitHub 索引 | 高 | 约定索引格式，缓存与限流，显示来源 |
| 下载客户端插件包 | 高 | 下载编译好的 Release asset，校验后安装 |
| 工坊条目展示与跳转订阅 | API 路径可行，游戏接入待实测 | 索引包含工坊 ID；打开 Steam 游戏内浏览器，玩家订阅，Steam 下载 |
| 自动补齐直接及传递依赖 | GitHub 链可行 | 作者显式清单；工坊仅链接提示，前置交给 Steam |
| 首次人工入库、后续自动更新索引 | 高 | 绑定发布者身份和发行规范，通过检查后自动收录 |
| 任意现有 DLL 自动推导完整依赖 | 低，无法可靠保证 | 程序集引用不能描述资源、模组依赖和下载位置 |
| HTTP 代理访问 HTTPS GitHub | 高，需游戏运行时验证 | 商店专用 handler、CONNECT、认证、重定向 |
| SOCKS5 代理 | 有条件可行，主要技术风险 | net472/Unity 兼容传输实现，远端 DNS 与认证验证 |
| 当前进程内即时加载、升级、卸载 | 不适合首版承诺 | 程序集、Defs、资源、静态状态及生命周期限制 |
| 客户端安装后自动具备服务端功能 | 不成立 | 服务端插件与协议能力需管理员另行部署 |

## 3. 分发来源与本地加载形态分别设计

用户后续要求工坊与 GitHub DLL 两类条目，本节相应调整。**不再要求所有作者都只发布标准 ZIP**；前一版推荐保留为本地安装形态建议。来源有工坊/GitHub，载荷有标准包/纯 DLL，加载方式有 Phinix 扩展/普通 RimWorld patch 模组，三者不是同一维度。具体清单与安装路径见补充评估。

### 3.1 两种方案的取舍

| 维度 | 标准 RimWorld 独立模组包（推荐） | 裸 DLL / 专用插件目录 |
| --- | --- | --- |
| 内容 | 可完整携带 About、语言、Defs、贴图和多个 DLL | 还需自行定义资源位置与加载方式 |
| 身份 | RimWorld packageId、插件模块 ID、商店包版本各自明确 | 需要另建身份与包边界 |
| 发现与启用 | 使用已有模组与扩展加载入口 | 任意专用目录目前未被自动探测；需要增量宿主能力 |
| 安装位置 | 玩家本地 `Mods` 的独立目录 | 不宜写入 Phinix 或 Workshop；用户目录还需探测契约 |
| 多 DLL 与 Contracts | 一个完整包，清单规定归属 | 平铺目录容易出现同名程序集和版本覆盖 |
| 使用成本 | 玩家需启用并重启 | UI 可能更省步骤，但要承担新加载模型的成本 |
| 更新与恢复 | 每包有清晰文件边界 | 需追踪每个 DLL 的归属、共享库和资源 |

**推荐理由**：Phinix 扩展包可以在一个 RimWorld 模组中提供多个扩展模块和 DLL。独立包与开发者指南推荐的分发方式一致，能够保留资源和标准模组身份，并避免 Steam 更新覆盖商店写入的内容。它也更方便手动安装、排查问题和第三方发布；普通 patch 模组则可以只使用游戏入口。

安装包格式与是否“一键启用”是两个独立决策。采用标准包不会阻止未来增加启用辅助；首版不自动改模组列表，主要是控制依赖、排序与存档影响。

### 3.2 GitHub 标准 ZIP 的建议包约定

- ZIP 根目录直接包含 `About/About.xml` 和 `phinix-package.json`，不允许随机多层外包装目录。普通顶层 `Assemblies` 作为首版支持基线；复杂 `LoadFolders.xml` / 版本资源布局需专门适配和验收。
- 使用稳定且唯一的 RimWorld `packageId`；声明 Phinix 模组依赖及加载顺序。额外模组依赖也必须写入 About，不能只存在于商店索引。
- 清单列出包提供的所有 ExtensionId、包依赖、必需外部模组、运行环境与程序集身份。
- 不重复分发 Phinix 核心 DLL、RimWorld/Unity 参考 DLL；依赖其他插件 Contracts 时由明确的所属包提供，不能每包各带一份不同版本。
- 普通第三方运行库可随包分发，但需声明归属、许可证与程序集身份；不能从 DLL 名称猜测 NuGet 包并在线下载。
- 模组之间的加载顺序由模组声明与玩家排序决定；单个模组内 DLL 顺序仍需按现有工具链要求打包。模块依赖图无法修复发生在反射之前的程序集加载失败。
- 首版不支持安装脚本、编译源码、执行仓库命令或任意安装钩子。

GitHub 包安装目标为已确认可写的本地 RimWorld `Mods` 根目录下的商店管理目录，例如 `Mods/PhinixStore_example.notes/`。前缀只用于目录归属，不改变 About 的 packageId。不能根据 Phinix 所在目录推导可写位置，因为它可能位于 Workshop。纯 DLL 需要审核清单和已验证加载入口，再生成最小 About/Assemblies 壳；工坊内容由 Steam 管理，不复制到此目录或改写工坊文件。

此处建议是**每包一个直接位于本地 Mods 根下的独立模组目录**，不是把文件下载进仓库源码 `Extensions/` 或主包 `Common/Extensions`。红包、人才贸易拆分及现有探测/注册/编号的具体影响见 [专项评估](插件安装目录与发现加载及官方插件拆分评估.md)。最终包布局尚需确认与游戏验证。

## 4. 架构边界与接入方式

商店功能通过 `IPhinixExtensionModule`、`IActivatablePhinixExtensionModule` 实现，走统一发现、注册、激活和关闭流程；自身发行形态当前建议是标准独立模组。官方默认源是商店配置默认值，不是宿主给商店的特殊权限。

建议逻辑分层：

```text
商店 Tab / 独立窗口 / 设置面板
              ↓ 用户意图与只读状态
CatalogService → DependencyResolver → InstallCoordinator
       ↓                ↓                    ↓
GitHubSource       本地包快照          DownloadTransport
       ↓                                     ↓
索引缓存                              校验 → 暂存 → 安装日志
```

- GitHub 适配器、HTTP/代理、安装目录操作属于客户端商店实现，不放进 Common，也不经 Phinix 联机传输层发送 HTTP。
- GitHub HTTP 请求是外部内容获取；设计哲学关于 Message/Command/Item 管线的要求适用于与 Phinix 服务端通信，不意味着所有互联网 HTTP 必须塞进游戏协议。
- 包模型与解析器先作为商店内部、无游戏依赖的逻辑；未来确有复用需求再抽独立契约/库，不提前增加框架负担。
- 商店不引用 Client/Server 宿主工程、不读取 `Client.Instance`、不直接调用宿主私有 Loader 入口。
- 通过 `IMainTabProvider` 提供商店 Tab；通过 `IClientSettingsPanelProvider` 和可选快捷设置面板提供入口与网络设置，使用 `IClientWindowService` 打开商店窗口。设置入口不要求先登录服务器，主菜单 Mod Settings 路径也应可访问。
- `Register` 只注册对象；`Activate` 注入服务、创建客户端及取消上下文；`Shutdown` 取消任务、解绑事件、释放连接和文件句柄，阻止迟到回调更新已关闭 UI。
- Verse 模组信息在主线程读取为快照；网络、哈希、解压及包解析在后台进行。翻译、开窗、共享 UI 状态通过现有 dispatcher；进度合并后更新，不能每个数据块都占用主线程队列。
- 商店首次安装仍需随官方发行版提供或由玩家手动安装自身，不存在“未安装商店却从商店安装商店”的启动路径。

### 4.1 可能需要的通用框架增量

现有激活策略只提供禁用查询，不是完整的模块状态和安装包目录 API。首版可使用商店本地记录和 Verse 的已安装模组快照做安装计划，精确运行状态则不能假装已有公开查询能力。

若需要可靠显示“运行中 / 注册失败 / 宿主与契约版本”，评估增加通用只读 `IClientExtensionCatalog`、`IClientRuntimeInfo` 一类接口（名称待设计），放入 ClientExtensionAbstractions，并提供宿主适配。它们对所有插件开放，不含 GitHub、下载或商店业务。旧接口保留，遵守增量兼容原则。

因此，“基础浏览和新包安装可以主要在普通插件内完成”可成立；“完整运行状态、全部路径和版本信息零宿主改动保证可得”尚不能成立。复杂包探测、热加载和启动前更新另行论证。

## 5. GitHub 索引与版本来源

### 5.1 推荐获取方式

默认维护一个**独立审核索引仓库**。GitHub 包文件放在各作者仓库的 Releases；工坊模组保存工坊定位。官方只发布索引，不统一构建/重托管第三方 DLL，不代替 Steam 发布工坊内容。

配置字段建议：源 ID、`owner/repository`、索引入口路径、跟踪分支或固定提交、显示名称、信任状态。默认仓库的实际地址尚未提供，本文不虚构已经存在的默认源。

首版支持单个当前源，允许切换默认/自定义源、恢复默认。多源聚合后续再做；切换源不自动替换已安装包的归属。依赖只从当前计划允许的源解析，禁止索引悄悄引入新源。

建议采用小入口文件 + 按提交固定的完整目录快照：

1. 默认拉取已发布 stable 入口，得到索引 Release/tag、目录快照 commit 和内容摘要；不直接把开发中的 main 分支当正式目录。自定义源可显式指定 ref。
2. 本次安装计划只使用该 commit 下的包版本记录；如拆成多个文件，它们全部来自同一提交。
3. 保存快照标识、原始内容摘要与获取时间，避免解析过程中分支变化产生混合版本。
4. 浏览阶段不逐个访问每个作者的 Releases；选定包后才获取必要资产信息或使用已审核的固定下载定位。

GitHub Contents API 支持 `ref` 指定提交、分支或 tag，也支持 raw 内容。其返回的下载 URL 可能过期，因此缓存仓库定位与 commit，不持久依赖临时下载 URL。[GitHub Contents API](https://docs.github.com/en/rest/repos/contents)

### 5.2 缓存、限流与离线

- 仅在首次打开、用户刷新或缓存过期时请求；Draw 不发起网络操作。建议缓存有效期 30 分钟，最终参数可调整。
- 缓存按源身份、索引路径和 ref 隔离；保存 ETag/Last-Modified，支持条件请求，离线仍可浏览上次有效目录并明确标记时间。
- GitHub 公共 REST API 的未认证主限额为每来源 IP 每小时 60 次；多人共享代理出口可能共同消耗额度。[GitHub REST 限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- 识别限流响应与 `Retry-After` / reset 信息，不无限重试；普通认证失败、源不存在与限流必须区别显示。[GitHub API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- 默认支持公共源，不要求 GitHub 账号。私有源/token 可后续增加；绝不能内置共享 PAT。
- 原始索引无效时保留上一份有效缓存；未来不支持的 schemaVersion 拒绝安装，不尝试忽略关键字段。
- 首版离线安装只接受已有锁定计划且哈希匹配的完整缓存；离线时不能声称已获得最新撤回信息。

### 5.3 索引管理与审核

作者通过官方索引仓库 Issue 表单提交；bot 做格式、来源、依赖与载荷初审，生成可审阅的元数据 PR，首次由维护者批准入库。后续监测已批准来源的新版本，检查通过后自动更新索引。索引 tag 触发正式目录发布，作者 tag/Release 是独立的二进制发布过程。详见 [自动审核发布评估](插件商店双渠道索引与GitHub自动审核发布评估.md)。

审核侧校验 schema、标识唯一性、依赖闭包可满足性、环境声明和包结构；检查是否包含框架/游戏 DLL及不允许的文件。AI 报告只是初审参考。工坊条目需显示审核的对象与时间，不把条目首次批准等同于之后每次 Steam 自动更新内容都已审核。

索引应提供正常、撤回、停止维护等状态。撤回版本禁止新安装；已经安装的版本显示提示，不能自动删代码或清持久化数据。普通发布标签并不等于不可变内容；若作者启用 GitHub immutable releases，可增加资产稳定性，仍保留商店自己的固定哈希。[GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)

## 6. 清单模型与依赖解析

### 6.1 必须区分的身份

| 身份 | 示例 | 用途 |
| --- | --- | --- |
| SourceId | `phinix.default` | 来源、缓存和信任边界 |
| 商店包 ID | `example.notes` | 依赖解析、安装记录与发布归属 |
| RimWorld packageId | `example.phinixnotes` | 模组启用、加载顺序、Workshop 重复检查 |
| ExtensionId | `example.notes.main` | Phinix 模块运行时依赖 |
| 包版本 | `1.2.0` | 商店选择、升级及版本范围 |
| 程序集身份/版本 | `Example.Notes.Client` / `1.2.0.0` | CLR 类型及程序集冲突检查 |

一个包可以提供多个 ExtensionId 和 DLL；DLL/模块名称不能唯一推导 GitHub 包地址。安装记录须固定源与包身份，同时对 RimWorld packageId、ExtensionId 和程序集 simple name 检查全局冲突。

### 6.2 清单提案

每个包版本描述至少包含：

- 包 ID、包版本、名称、作者、简介、项目地址、许可证、维护/撤回状态。
- RimWorld packageId、提供的模块 ID、各模块必需的模块 ID。
- 客户端目标运行时、RimWorld 支持版本、Phinix/Contracts 兼容范围；需要原生库时列 OS/架构。
- 必需包依赖及版本范围、可选依赖、外部模组依赖、已知冲突。
- `distribution.kind`、`payloadKind` 与 `integrationKind`：分发来源、载荷形态、是否参与 Phinix 生命周期分别声明。
- GitHub：固定 artifact 仓库/tag/commit/asset 定位、SHA-256、下载大小和布局；工坊：publishedFileId、链接、作者、审核时间与版本可验证性，不捏造固定 Release/hash。
- 是否需要服务端配套插件、服务端版本/能力要求。元数据只用于说明，不能当成已完成服务器协商的证据。

如下为概念示例；仓库、版本兼容范围与哈希均是占位，不可作为可安装清单。字段尚未冻结：

```json
{
  "schemaVersion": 1,
  "packageId": "example.notes",
  "version": "1.2.0",
  "distribution": { "kind": "github-release", "payloadKind": "rimworld-mod-zip" },
  "integrationKind": "phinix-extension",
  "rimWorldPackageId": "example.phinixnotes",
  "modules": [
    { "id": "example.notes.main", "dependsOn": ["example.storage.main"] }
  ],
  "compatibility": {
    "side": "client",
    "targetFramework": "net472",
    "rimWorldVersions": ["1.6"],
    "phinixRange": ">=0.9.7 <0.10.0"
  },
  "dependencies": [
    { "packageId": "example.storage", "versionRange": ">=2.0.0 <3.0.0", "optional": false }
  ],
  "externalMods": [],
  "serverRequirement": { "required": false },
  "artifact": {
    "repository": "EXAMPLE_OWNER/EXAMPLE_REPO",
    "tag": "v1.2.0",
    "assetName": "example.notes-client-1.2.0.zip",
    "sha256": "REPLACE_WITH_64_HEX_CHARACTERS",
    "sizeBytes": 1048576
  }
}
```

完整发行规范还需加入包内 `phinix-package.json` 与目录的交叉校验；索引控制选择与期望哈希，包内自述不能反过来覆盖索引身份、路径、依赖或版本。

### 6.3 可以解析什么，不能推导什么

1. **商店包依赖**：可自动递归下载，例如 A → B → C；清单明确指定包 ID 与版本范围。
2. **模块依赖**：现有 DependsOn 仍负责 Register/Activate 顺序和缺失阻断。索引提供模块 → 包映射，确保包依赖闭包实际提供全部必需模块。
3. **程序集依赖**：只反映 CLR 引用，不能说明哪个仓库/资产提供它，也不能覆盖 Defs、翻译和动态反射加载依赖。解析 PE 元数据可作审核补充，不能代替作者清单。
4. **RimWorld 模组依赖**：About 声明和商店清单需一致；作者声明且在选定源中明确提供的 GitHub 包可以下载。工坊前置仅提供作者声明的链接提示，其递归依赖交给 Steam，商店不监控订阅/下载状态或保证工坊精确版本。DLC/付费内容只检查和指引，不自动从未知地址补齐。
5. **宿主与随发基础包**：Phinix/游戏视为环境前置，不由依赖链自动升级；Chat、Trade、Inventory、LegacyAdapter 暂留主包。红包、人才贸易计划独立发布，应由清单映射到各自包，不能按 `builtin.*` 前缀推定仍内置。旧主包仍含副本时先处理迁移，不下载同名 DLL覆盖主包。
6. **可选依赖**：默认不自动加入；缺失时作者必须能降级。编译时无条件引用一个并未提供的 Contracts DLL，不能仅在商店标为 optional 就保证降级。

首版只承诺清单明确且在允许源中存在的 GitHub 依赖可自动下载。遇到工坊前置时停止商店的递归展开，显示链接与启用提示；GitHub 文件安装成功不表示全部模组运行条件已满足。历史包无清单时可由维护者补元数据，标记仅手动安装；不在运行进程中 `Assembly.Load` 待检查包去猜依赖，以免验证阶段就加载了插件代码。

### 6.4 解析与安装计划

```text
固定目录快照和目标版本
  → 获取本地已安装/已启用/来源/已加载身份快照
  → 过滤运行环境不兼容、撤回、预发布候选
  → 展开必需依赖并合并各路径版本约束
  → 选择版本，必要时有限回溯
  → 检查环路、外部模组、模块提供者及程序集冲突
  → 生成锁定计划和依赖优先顺序
  → 玩家确认一次完整计划
  → 下载、校验、暂存、提交安装
```

选择规则建议：

- 定义固定 SemVer 2.0 子集：首版只支持 `>=x.y.z <x.y.z` 和精确版本，预发布默认不选。不能使用字符串大小比较版本；程序集四段版本只作程序集信息。
- 一个 packageId 只选一个版本；共享依赖合并约束。先保留已经满足条件、可验证的安装版本，再选择最高可兼容稳定版；选择顺序固定以保证可复现。
- 单纯拓扑排序不能处理版本冲突。例如 A 要求 B `<2.0.0`，C 要求 B `>=2.0.0` 时不存在合法交集；应报出两条依赖路径，不能选一个“最新版”继续安装。
- 先前版本候选可能有不同依赖，所以需要有限回溯；达到节点、候选或耗时上限时报出无法完成解析，不伪称“没有版本”。
- 首版不给已安装包自动升级、降级或覆盖；依赖只能通过变更已有包满足时阻断计划并给出明确原因。后续增加升级时，必须重算所有受影响已安装包的约束，不能只算当前目标的子树。
- 本地手动 GitHub 包只有可信包版本元数据时才参与商店版本约束，不能用 AssemblyVersion 猜包版本。Workshop 来源只提供链接提示，不纳入商店版本求解。
- 已安装但未启用或被 Phinix 禁用的依赖，不需要重复下载，却仍需明确启用提示。安装计划满足不等于运行图已经满足。
- 重复 RimWorld packageId（特别是本地与 Workshop 两份）、模块 ID 或程序集名称必须先处理；不默默采用后发现的文件。

建议保护限额：计划最多 64 包、依赖深度 32、每包最多 32 个候选版本，解析耗时上限 5 秒。它们是待实验调整的初值，不是性能测试结论。

安装计划展示新增包、已满足依赖、需启用的模组、来源、版本、总下载/解压大小、服务器要求和阻断原因。确认后锁定目录快照、全部版本及哈希；源或代理配置变更后需重新生成计划，不能后台换版本。

## 7. 特殊网络环境：商店专用代理

### 7.1 产品范围与配置

代理覆盖商店自行发起的索引、元数据、GitHub 插件与依赖包请求，包括 Release 重定向。商店预览图若首版支持，也使用同一策略。工坊页面在 Steam 游戏内浏览器打开，其访问和实际工坊下载使用 Steam 自身网络配置，均不由商店 HTTP/SOCKS5 客户端控制；其他外部网页由所用浏览器决定代理。不能向用户承诺商店代理能解决 Steam 页面访问或下载问题。

配置模式建议：明确直连、显式跟随系统代理、HTTP 代理、SOCKS5 代理。默认明确直连；不静默继承环境变量或其他模组的全局网络配置。“HTTP 代理下载 HTTPS 文件”和“通过 TLS 连接到 HTTPS 代理服务器”需要在 UI 中区别。

| 字段 | 建议语义 |
| --- | --- |
| 类型 | Direct / System / HTTP / SOCKS5；HTTPS proxy 单列能力状态 |
| 主机、端口 | 默认示例为本地地址；校验合法主机和 1–65535 端口，支持 IPv6 |
| 认证 | 无认证或用户名/密码；不将密码拼进日志中的代理 URL |
| DNS | SOCKS5 默认由代理解析目标域名；本地 DNS 为显式选项 |
| 超时/重试 | 连接、请求和停滞超时；可取消，有限次重试 |
| 连接测试 | 分别测索引、资产及重定向，不仅测端口可达 |
| 失败策略 | 显式代理失败时保留错误，默认不退回直连 |

使用专用网络客户端/传输实例。禁止修改 `WebRequest.DefaultWebProxy`、进程级默认代理、全局证书验证回调、系统代理或 Phinix 联机网络配置。凭据仅绑定所选代理；原站认证、代理认证与下载重定向分别处理。

### 7.2 客户端运行时可行性

客户端目标是 net472，实际运行于 RimWorld 的 Unity/Mono 环境；服务端 net10 的能力不能当作客户端能力。Microsoft 文档支持在 `HttpClientHandler.Proxy` 上为单个 handler 配置代理。[HttpClientHandler.Proxy](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclienthandler.proxy?view=netframework-4.8.1)

Microsoft 将 HttpClient SOCKS 支持列为 .NET 6 新增能力，示例使用 `SocketsHttpHandler`。由此不能推定 net472/Unity 的现有 handler 接受 `socks5://` 并正确工作。[.NET 6 SOCKS 支持](https://devblogs.microsoft.com/dotnet/dotnet-6-networking-improvements/)

推荐策略：

1. **HTTP 代理**：优先用兼容的 HttpClientHandler/WebProxy 实例，经 CONNECT 获取 HTTPS 内容；验证无认证及用户名/密码认证。企业 NTLM/Kerberos 与 PAC 不作为首版跨平台保证。
2. **SOCKS5**：定义商店内部 DownloadTransport 边界，选用经维护与许可证审查、兼容 net472/Unity 的实现，再验证远端 DNS、认证、TLS/SNI、流式大文件和取消。尚未选定具体库，本评估没有已验证可用的库结论。
3. **传输库不可用时**：专门实现/维护 SOCKS5 隧道是技术上可行的备选，但不仅是 SOCKS 握手，还需正确集成 HTTP、TLS、重定向、连接池和流式读取，成本明显增加。优先复用成熟传输实现，避免自写完整 HTTP 栈。
4. **HTTP 本地入口作为兼容路径**：用户已有代理软件若提供 HTTP 或 mixed 端口，可通过该入口使用；这不等于已满足纯 SOCKS5 支持，不能把它作为取消 SOCKS5 要求的理由。
5. **HTTPS proxy**：目标站是 HTTPS 并不要求代理地址是 `https://`。若确需 TLS-to-proxy，作为单独的兼容性验证项，不能把 HTTP CONNECT 的成功外推为 HTTPS proxy 成功。

SOCKS5 是用户要求的一部分。首版发布门槛应包含其验证结果；若唯一 SOCKS5 入口不可用，应明确标为阻断项并重新评估，不用“设置框已提供”冒充功能支持。实际支持能力取决于传输适配器，不仅取决于 URI 格式。

### 7.3 DNS、重定向与诊断

- SOCKS5 远端 DNS 必须实际把目标域名交给代理；不能先在本地解析成 IP，再仅在 UI 显示“代理 DNS”。代理服务器自身域名的解析是另一个问题，可允许填 IP 避免本地 DNS 依赖。
- HTTP CONNECT 使用目标域名建立隧道，TLS 验证仍针对最终 HTTPS 主机；不能因为代理环境复杂就关闭证书校验。
- GitHub 资产下载 API 可能直接返回内容或返回 302；两种都要处理。重定向后的资产域名同样必须走所选代理。[GitHub Release assets API](https://docs.github.com/en/rest/releases/assets)
- 限制重定向次数（建议最多 5 次），禁止 HTTPS 降级到 HTTP；源策略明确允许下载主机，拒绝任意不可信跳转。允许的 CDN 主机需按实际请求验证，不凭空写死一个域名就声称覆盖全部 GitHub 下载。
- 跨主机不转发原站 Authorization；Proxy-Authorization 只能发送给代理。临时签名资产 URL 不长期缓存，查询参数不写完整日志。
- 显式代理不采用目标本地地址自动绕过、不静默回退直连。下载目标与重定向目标拒绝本地/私网等非预期端点；本地代理地址允许使用 loopback，两种地址不能混为一谈。
- 连接测试读取少量实际索引与测试资产内容，检查格式/哈希及重定向。测试只请求固定受信目标，不把任意 URL 输入变成通用网络探测器。
- 错误分类：代理连接失败、407/认证失败、SOCKS 协商失败、DNS 失败、TLS 失败、GitHub 限流、下载中断、校验失败。仅“连上代理端口”不能显示下载可用。
- 配置变化只影响新任务；运行中的任务固定网络策略，先取消或完成再切换。索引与包下载默认共用一份商店策略，避免依赖下载遗漏代理。

代理密码默认仅在当前进程保存，普通设置只存类型、主机、端口与用户名。如果以后提供“记住密码”，用平台凭据存储并明确支持范围；不假定 Windows DPAPI 在 Linux/macOS 可用。不保存到仓库、普通 JSON、安装锁文件或游戏存档。远程 HTTP/SOCKS5 的基础用户名/密码认证不保证客户端到代理链路加密，应在配置说明中准确表达其能力。

## 8. 下载、安装、持久化与恢复

### 8.1 GitHub 下载校验

- 只下载索引指定的编译产物，不拉源码 ZIP 后现场构建。
- 流式落盘和 SHA-256 校验；不能把整包读进内存。检查实际字节数，拒绝 HTML 错误页、大小异常与哈希不匹配。
- SHA-256 校验防止包内容偏离审核索引，但不证明插件代码安全；索引与资产同时被篡改时，仅靠同源哈希不能提供独立真实性保证。默认源仍需仓库权限、审核与发布保护；签名索引/离线信任密钥可在加强阶段引入。
- 默认源审核不等于沙箱：插件 DLL 最终以游戏进程权限执行。自定义源界面明确显示信任来源，不允许用同包名覆盖默认源既有归属。
- 解压前后阻断绝对路径、`..`、符号链接、跨平台路径碰撞、重复文件和压缩炸弹；XML 解析禁用外部实体/DTD。
- 建议初值：索引 2 MiB、单包下载 128 MiB、解压 512 MiB、最多 10,000 文件、最多 2 个并发下载；超限拒绝并显示原因。更大内容需要明确扩展策略。
- 校验 ZIP 内 About、package manifest、依赖与程序集归属；程序集元数据检查不执行插件入口。无法证明清单一致时拒绝安装，不静默丢文件。
- 中断首版允许整包重试；断点续传后续增加，必须验证资产身份、Range 行为与完整哈希，不能拼接不同资产版本。

### 8.2 推荐状态机

```text
Idle → Resolving → AwaitingPlanConfirmation
                 → Blocked
AwaitingPlanConfirmation → Downloading → Verifying → Staging → Committing
                                                               → InstalledPendingEnable
中间阶段 → Cancelled / Failed
提交开始后异常 → RecoveryRequired → RolledBack / InstalledPendingEnable
```

解析、网络、解压和提交均有取消/超时边界；进入文件提交后不能靠直接中止线程取消，需完成当前原子步骤再回滚。UI 观察状态，不能在 Draw 中推进安装或直接改磁盘状态。

建议连接超时 15 秒、索引请求 30 秒、下载停滞 30 秒、单包总下载上限 15 分钟、最多重试 2 次并退避。代理认证错误、清单错误、哈希失败和不兼容不作无脑自动重试。参数需在慢速网络实验后调整。

### 8.3 GitHub 本地包的暂存与提交边界

1. 获取安装目标锁并检查可写空间、包身份及目录不存在；首版只安装新包。
2. 在插件数据目录缓存下载；在目标文件系统、RimWorld 不扫描的位置准备 staging。staging 的非扫描性需实测，不能只靠目录名以点开头就假定隐藏。
3. 完整依赖闭包下载并校验成功后才提交；中途失败时不把剩余半包当作成功。
4. 写持久化事务日志，记录新目录、已提交步骤、包锁与内容摘要。逐包以同文件系统目录 rename 提交，在每一步之后记录进度。
5. 全部成功后持久化安装记录，显示“已安装，待在模组列表中启用”。不得自动改 `ModsConfig`、调用 Loader 或宣布已经 Active。
6. 可恢复失败时仅移除/退回本事务创建且归属、摘要仍匹配的目录。外部已经修改的文件不自动删除，进入 RecoveryRequired。

上述事务只覆盖商店管理的 GitHub 本地包。工坊链接之外的订阅、下载和前置由 Steam/玩家处理，不属于该文件事务；GitHub 包失败不影响玩家的工坊订阅。

**单个目录 rename 与整个依赖链事务不同**：跨多个模组目录不天然具备 ACID 原子性。崩溃可能留下部分已提交新目录，需根据持久化日志恢复。首版所有新包未启用，降低下一次启动的影响；不能保证玩家手动启用不完整包后仍安全。RimWorld 模组扫描早于商店功能模块恢复，商店不具备通用启动前恢复特权。

若未来需要替换已加载 DLL、自动升级完整依赖链或启动前恢复，则需另设退出后的安装器/启动前组件，或通用宿主阶段设计。不能假定商店在 Activate 时就能安全替换已经加载的包。Microsoft 说明 .NET Framework 无法只卸载单个程序集；RimWorld/Unity 的实际行为仍需在游戏验证。[程序集加载与卸载](https://learn.microsoft.com/en-us/dotnet/standard/assembly/load-unload)

### 8.4 持久化记录与生命周期

- 插件专属存储保存 sources、目录缓存、安装记录、版本锁及事务日志，schema 可迁移，损坏时提示并保留原文件。
- 版本锁记录源身份、快照 commit、精确包版本、依赖边、artifact 定位与哈希；安装记录附加 RimWorld packageId、模块 ID、目录及文件归属。
- 写入临时文件、刷盘、替换和备份策略由商店负责，StorageProvider 不自动提供这些语义。
- 商店禁用后已安装模组仍由 RimWorld/Phinix 正常加载；商店不是其他插件运行的必需依赖。
- 卸载商店不自动卸载其下载的模组。后续卸载功能也只管理代码与安装文件，不删除其他插件数据、存档、待交付记录或库存。
- 文件回滚不等于业务数据/存档回滚。升级、降级、禁用业务插件可能造成 codec 缺失或恢复能力变化，尤其涉及库存和交易时不能把“文件操作成功”当作物品安全证明。
- 首版不改变 Legacy/V2 协议、交易确认、持久化迁移或物品所有权。服务器需要配套插件时只显示部署条件，客户端商店不冒充服务器能力确认。

## 9. 功能与交互设计

建议有三个页面：

1. **浏览**：搜索、兼容筛选、名称/作者/版本/渠道、审核范围；详情包含依赖、运行环境、许可证、项目与服务端要求。工坊按钮是“在 Steam 中打开”，说明将在 Steam 游戏内浏览器打开条目并由玩家订阅；GitHub 按钮是“下载并安装”。不能给工坊跳转显示下载已完成。
2. **本地与任务**：已安装/未启用/版本未知、下载与校验进度、失败原因、重试/取消、待重启提示；运行状态通过通用查询契约或明确标记未知。
3. **源与网络**：默认/自定义源、恢复默认、直连/系统/HTTP/SOCKS5、认证、DNS、分阶段连接测试、缓存清理。密码输入不回显。

GitHub 链交互：点击安装 → 查看完整计划 → 一次确认必需包 → 下载/校验/安装 → 列出应启用模组及顺序 → 玩家启用并重启。涉及工坊前置时列出链接提示，商店不建立 Steam 下载等待流程，不把 GitHub 包安装完成显示为全部模组已可运行。不静默升级已有包；官方索引自动收录新版本与玩家本地升级是两个功能。

依赖图示例：

```text
Example Notes 1.2.0          新安装
└─ Example Storage 2.1.0     新安装
   └─ Phinix Rework          环境前置，已满足

需启用：Example Storage → Example Notes
服务器要求：无
```

窄屏详情降级为单栏/子页；列表虚拟滚动，长名称与译文可截断配 Tooltip。使用现有响应式几何、主题和屏幕安全区工具，缓存布局及翻译，异常路径恢复 GUI 全局状态。任务进度不能占用每帧大量分配或阻塞主线程。

### 9.1 工坊入口：Steam 游戏内浏览器

已确认的流程是：点击工坊条目 → 请求 Steam Overlay 浏览器打开对应页面 → 玩家自行订阅 → Steam 处理下载与前置 → 玩家在游戏模组界面启用。商店只负责链接入口，不记录订阅完成，不等待工坊下载，也不根据关闭覆盖层推断依赖已经满足。

技术上可调用 Steamworks 的 `ISteamFriends::ActivateGameOverlayToWebPage` 打开完整 URL。该接口返回 `void`，调用正常返回不构成页面加载、订阅或安装成功的证据。具体 C# 封装签名须以 RimWorld 1.6 实际引用为准，本文不假定已有同名游戏方法。[Steamworks 网页入口](https://partner.steamgames.com/doc/api/ISteamFriends#ActivateGameOverlayToWebPage)

入口建议只接收有效的十进制 `publishedFileId`，在通过 UInt64 范围与非零校验后生成 `https://steamcommunity.com/sharedfiles/filedetails/?id=<id>`；索引中的展示链接必须与之匹配。拒绝任意协议、主机或脚本链接。条目所属 RimWorld 的验证由收录校验负责，客户端不为打开链接增加 SteamUGC 查询。

调用前检查游戏现有 Steam 上下文和覆盖层可用性；`ISteamUtils::IsOverlayEnabled` 可检查覆盖层是否可访问，但游戏刚启动时可能暂时返回 false，应允许用户稍后重试。[覆盖层可用性](https://partner.steamgames.com/doc/api/ISteamUtils#IsOverlayEnabled)

覆盖层依赖 Steam 启动及实际运行环境，应验收 Steam 启动、覆盖层关闭、非 Steam 环境和网页访问失败。`GameOverlayActivated_t` 仅反映覆盖层开关，不能作为订阅完成回调。[Steam Overlay 条件与回调](https://partner.steamgames.com/doc/features/overlay)

建议覆盖层不可用时保留条目，说明原因并提供“重试”；可另外提供“复制工坊链接”作为降级建议，是否纳入首版尚待确定。默认跳转路径保持游戏内浏览器，不静默改为外部浏览器。网络断开时页面可能无法访问，商店不能仅凭 API 调用结果判断该网页错误。

## 10. 开发者友好：让新手在 AI 帮助下开发并发布简单插件

### 10.1 可行性与适用范围

**可行，但降低门槛需要经过验证的模板、清楚的文档和能理解的错误反馈共同支撑。** 仅提供一份长接口指南或让 AI 自行拼工程，仍会把引用版本、程序集布局、线程和发布规范等问题留给新手。

用户要求把“非计算机专业者可借助 AI 完成简单插件并发布”纳入设计目标。首批推荐围绕现有通用扩展点选题，例如显示固定帮助内容的 Tab、本地设置项或只读信息展示；通过自然语言说明需求，基于最小模板逐步修改。具体例子需先验证实际接口和游戏入口，不把尚未存在的能力写成可用 API。

不将任意复杂 Harmony patch、交易/库存所有权、存档迁移或新服务端协议包装为新手的一键任务。遇到这些需求，应说明新增边界并转入进阶指南。AI 辅助可以减少编码负担，但作者仍需在游戏中确认行为并对发布内容负责；生成成功、编译通过和审核通过是不同阶段。

现有 [附属 Mod 开发者指南](../../../Phinix附属Mod开发者指南.md) 是接口参考；[扩展开发体验增强设计](../扩展开发体验增强-设计方案.md) 曾提出 Starter 模板，可借鉴目标和组织方式，不能直接把历史示例当作当前已验证模板。新的新手路径应使用指定框架版本的真实契约和模块 ID，并纠正旧示例与当前实现的差异。

### 10.2 文档按任务组织，接口参考作为后续查询

建议提供以下文档组合。名称和拆分是未来交付建议，本次不创建这些尚未验证的教程或工具：

| 文档/材料 | 面向读者与主要内容 | 应给出什么结果 |
| --- | --- | --- |
| 快速入门 | 从零解释模组、源码、DLL、packageId、扩展 ID；环境准备、模板创建、第一次构建与游戏验证 | 能看到自己的最小插件运行，知道如何关闭和恢复 |
| 简单插件教程 | 一个完整小功能，逐步修改、设置/翻译/生命周期示例 | 不靠猜测即可复现功能，并理解关键边界 |
| 开发参考 | 当前公共 API、依赖 Contracts、线程要求、版本兼容与数据目录 | 能查到真实签名和适用版本，避免重复拷贝多套说明 |
| GitHub 发布指南 | 可审查源码、对应 commit、编译产物、清单、许可证、tag/Release 资产、首次申请与机器人报告 | 能发布一个可被索引检查的候选，知道如何修复拒绝原因 |
| 工坊发布指南 | 标准模组布局、工坊条目链接/身份、About 依赖及真实验证 | 提交工坊条目，理解条目审核不等于逐版代码审核 |
| 更新、撤回与常见问题 | API/依赖变更、资源缺失、加载失败、坏版本、凭据误提交和恢复 | 能区分编译、加载、网络、审核问题并采取下一步 |
| AI 项目指引 | 当前版本、架构约束、可用能力、构建/验证步骤、发布检查 | AI 能基于本项目事实工作，作者能检查其结果 |

教程以清晰的步骤、预期画面/输出和失败时的处理为主；技术术语首次出现时解释。错误报告应包含“哪里有问题、为什么、下一步怎么修”，不要只显示堆栈或评分。可复制的示例和命令必须注明支持平台，不能把 Windows 专用流程写成跨平台保证。

开发教程引用统一的契约参考和 schema，避免把完整 API/清单定义复制进每个教程。与版本绑定的内容随框架/模板发行维护；中英文材料在有对应版本时同步，过期页面显式标明版本。

### 10.3 从需求到入库的完整路径

1. **描述需求和边界**：作者说明想显示什么、是否保存数据、是否联网及是否需要其他插件；模板/AI 帮助判断是否属于简单客户端扩展。首个练习尽量只使用已有扩展点。
2. **准备环境并建立独立仓库**：指南明确所需 SDK、net472 编译支持、框架契约版本和合法获得的游戏引用。初始模板固定匹配版本，填入作者自己的 packageId/扩展 ID，不要求修改 Phinix 源码。
3. **在模板上小步修改**：先运行原始最小示例，再加一个功能；AI 查询真实契约而非臆造接口，记录依赖与敏感行为。新增文件时确认工程编译项。
4. **构建并在游戏验证**：分开记录编译结果、模组启用/排序、重启后发现、实际功能与退出/重入。首次测试使用备份或测试存档；从脱敏日志定位问题，不把参考程序集构建当作游戏测试。
5. **打包并本地校验**：产物布局与清单来自同一组元数据，检查 About、版本、依赖、程序集、资源及禁止随包分发的游戏/宿主引用。不提交凭据、私人配置或整份日志。
6. **由作者发布自己的发行物**：GitHub 发布定位到可审查源码及固定 Release 资产，轻量标准 ZIP 优先；纯 DLL 加清单按已讨论的规范处理。工坊走标准模组发布。作者 tag 可用于其自身构建/发布，但官方索引 tag 由索引流程维护。
7. **申请并处理报告**：把发行信息提交到默认源 Issue 表单，按机器人可读报告修正；首次由维护者人工批准。以后正常版本自动检查收录，异常则保持旧稳定记录。AI 帮助整理申请，不代替审批，也不凭一句“已测试”伪造验证结果。

模板中可规划构建/打包/本地校验入口及作者仓库的发行工作流，但这些在当前尚未实现。初始版本可以提供清楚的手动发布步骤，再将成熟路径自动化；官方索引机器人不接收作者的发布密钥，也不为了新手体验在高权限环境执行其构建脚本。

### 10.4 配套 AGENTS.md / agent.md 的设计

建议在未来独立插件模板中提供 AI 可读的项目指引，可沿用本仓库的 `AGENTS.md` 命名；如果所用工具要求 `agent.md` 或其他格式，提供等价说明或手动加载步骤。是否自动读取需按目标工具验证，不能声称放一个文件就能约束所有 AI。

这份指引应记录模板对应的框架/契约版本、入口/目录、稳定 ID、公开 API 参考、确实存在的构建与校验入口，以及需要询问作者的需求边界。不要把开发机器的绝对路径、GitHub token 或发布密码写进模板。长参考材料以链接引用，不将全部框架源码塞进提示词。

以下为未来模板的**指引内容草稿**，在本设计文档中展示，不创建新的仓库级 `AGENTS.md`，也不改变现有代理指令：

```text
目标：帮助作者完成一个独立、简单的 RimWorld 1.6 / Phinix 客户端插件。
先阅读模板固定版本的开发参考、快速入门和发布指南；不猜测 API。
需求不清楚，或涉及存档迁移、物品所有权、协议与额外联网时，先询问作者。
使用公共契约和现有扩展点，不修改 Phinix 宿主、游戏 DLL 或工坊安装目录。
客户端维持 net472/游戏兼容语法；新增源文件须确认工程编译项。
模块 ID、packageId、程序集名和依赖清单保持一致；不随包覆盖宿主/Contracts。
游戏 API 与翻译经主线程使用；事件、后台任务和资源按生命周期清理。
先构建，再按指南在游戏中测试；无法测试的项目明确列出，不伪造通过记录。
源码、清单和发行物指向同一版本；不提交密钥、玩家数据或游戏参考 DLL。
发布前让作者检查产物、兼容声明和验证记录，明确授权后才向外部发布。
```

真实模板应把上述参考替换为可访问、对应版本的文件，并填入已验证的命令；不能向新手交付仍含未解析占位符的“可直接发布”模板。指引应适用于独立作者仓库，而不是照搬 Phinix 主仓库的服务端构建命令和禁止编辑区域。

AI 指引是协作约定，不能强制限制 DLL 权限，也不能证明 AI 生成的源码或产物安全。默认源 GitHub 插件仍需有可审查源码、首次人工批准及后续检查，不因使用官方模板或 AI 而免审；技术限制详见 [安全评估](插件商店安全性与维护成本评估.md)。

### 10.5 与小规模维护成本的取舍

优先维护“一份小模板 + 一条完整简单教程 + 两渠道发布指南 + 一份 AI 指引 + 可读诊断”，比大量半成品样例或自动生成长文更容易保持有效。模板复用现有公共契约，不为新手模板增加宿主特例，不先建设云端编译/在线 IDE。

作为额外设计预算，小模板、入门/发布指南和 AI 指引的编写及首次验证约 3–5 工作日，新手试用与纠错约 1–2 工作日；合计约 4–7 工作日，部分与原有文档和发行校验工作重叠。可发布模板工程、校验工具和作者 CI 若需新实现，须单独评估，不包含在“写指南”的工时内。此预算不是当前已执行工作或排期承诺。

持续成本来自契约变化后重验示例、模板依赖版本更新和常见问题整理。模板与指南应有明确版本及维护者，并将高频问题修回文档，避免每个作者都需要一对一辅导。少量用户也可能带来大量 AI 生成申请，不能默认机器人或维护者能无限接纳。

### 10.6 开发者体验的验收标准

后续交付应找未参与框架开发、非计算机专业的试用者，以一个简单功能检验完整路径：能按指南配置环境、让 AI 完成修改、看到游戏内结果、生成正确发行资产并提交入库申请。记录卡住的步骤、失败原因和需要额外人工解释的位置，不仅看教程作者本人是否能成功。

最低应验证：原始模板能构建且真实游戏可加载；ID/版本/About/清单一致；错误有明确修复步骤；源码与发行资产可定位；禁用/重启和数据边界讲清；GitHub/工坊两条发布路径没有互相混用；AI 指引不引用过时接口或不存在的命令。具体支持平台、教程选题和模板仓库地址留到实施前确定。

## 15. 工程实现评估：最小可交付路径与实际技术风险

### 15.1 综合判断与职责划分

**没有发现必须改变 Rework 插件架构才能实现的障碍。** Steam 仅打开页面，使工坊侧的工程范围明显缩小；主要不确定性集中在游戏的 Steam 接口接入、GitHub DLL 的真实加载以及 Unity/Mono 的 SOCKS5 传输。依赖解析、安装记录和索引校验属于可单独验证的常规工程，仍需把失败路径写清。

| 工程问题 | 当前判断 | 最小实现建议 | 尚需取得的证据 |
| --- | --- | --- | --- |
| Steam 游戏内浏览器 | Steam 官方 API 支持；本仓库尚无对应入口 | 复用游戏已初始化的 Steam 上下文，封装打开条目和可用性检查 | RimWorld 1.6 的公开封装/程序集引用，以及覆盖层实际打开 |
| GitHub DLL 加载 | 现有活跃模组程序集发现路径可复用；纯 DLL 不天然可加载 | 优先独立最小模组壳，安装后由玩家启用、重启 | DLL 被游戏加载并进入原有发现/注册/激活路径，普通 patch 入口同样有效 |
| 清单与依赖 | 明确声明后可解析；现有 DependsOn 不包含包下载与版本语义 | 单一清单规范、有限版本规则、固定索引快照、确定安装计划 | 链、菱形、环路、缺失、版本冲突及本地版本未知的可解释结果 |
| 专用代理下载 | HTTP 有候选路径；SOCKS5 不能直接套用现代 .NET 能力 | 商店内部独立传输实例，先选兼容库再验收 | net472/Unity 下真实 HTTP/SOCKS5、DNS、TLS、重定向、取消 |
| 安装与失败恢复 | 新包安装可行；多目录提交不天然原子 | 完整暂存校验、逐包提交、短事务日志、只清理本次新建目录 | 取消、磁盘满、进程退出和用户改动文件后的恢复行为 |
| 作者发行与索引发布 | GitHub 工作流可组织；当前仓库尚未提供 | 作者发布固定资产，官方校验后生成索引快照并发布 | 候选身份不漂移，错误版本不进入正式索引，发布事件链可运行 |

商店功能模块内部可划分 CatalogReader、DependencyPlanner、DownloadTransport、PackageInstaller 和 WorkshopLinkOpener 等职责，用接口隔开网络、文件系统与游戏入口，方便故障测试即可；不必拆成大量独立工程或引入服务端商店。UI 通过现有 Tab/设置/主线程调度契约接入，宿主不引用具体商店功能模块。Steam 逻辑留在客户端，公共 Common 不新增 Steam 端点依赖。

### 15.2 Steam 接口接入：小范围功能，先核实可调用入口

当前 [Settings.cs](../../../../Client/Source/Settings.cs) 使用 `SteamUtility.SteamPersonaName`，说明已有游戏 Steam 工具调用，但不能证明它公开了覆盖层浏览器方法。[ChatMessageList.cs](../../../../Extensions/Chat/Client/ChatMessageList.cs) 的 `Application.OpenURL` 也没有证据能满足本次指定的游戏内浏览器要求，不能直接沿用并宣称完成。

实施前先查看真实游戏参考程序集：若有可用的游戏公开包装方法，优先复用；否则评估游戏已有 Steamworks C# 绑定能否安全引用，以一个客户端适配器隔离调用。仅在多个插件确有共同需要时再讨论通用抽象，不为商店预先建设宿主专属 Steam 服务。不得随插件打包另一套 Steam 托管/原生 DLL 或重复初始化、关闭游戏的 Steam API。

按钮事件在游戏主线程发起，后台任务的 UI 结果经现有 dispatcher 返回；异常只影响此入口。验收范围是“正确条目在游戏覆盖层浏览器打开”和“不可用时解释原因”，不包含自动订阅、下载进度、安装完成判断。无需为这个入口单独建设 Steam 回调管理系统。

### 15.3 DLL 与程序集兼容：轻量不等于没有加载约定

建议仍优先最小标准模组壳：About 提供 packageId、兼容版本与前置，Assemblies 放作者 DLL；纯 DLL 发行物由经过校验的清单补齐这些元数据。专用探测目录会涉及加载时机、模组启用、依赖定位与卸载行为，只有最小壳确实无法满足时才扩大框架。最终包约定仍需确认，并以真实样例验证。

[ExtensionAssemblyLoader.cs](../../../../Common/Utils/Framework/ExtensionAssemblyLoader.cs) 使用同进程程序集加载，并按已加载程序集名称避开重复加载；不能靠每个插件独立目录实现依赖 DLL 的版本隔离。安装前至少检查框架/游戏 DLL 禁带、主程序集重名、同 packageId 的工坊/本地副本，以及作者声明的共享依赖版本；未识别到的运行时冲突仍可能发生。不同库版本不能只换文件名就视为已解决。

Phinix 扩展应走原有模块生命周期；仅 Harmony/RimWorld patch 模组可走游戏自身入口，不能要求它伪装成 Phinix 扩展。首个样例应分别验证两种入口。安装完成只代表文件就绪，插件启用策略也不构成第三方 DLL 的执行沙箱；安全边界继续见独立安全评估。

### 15.4 清单和依赖：先把错误结果做确定

版本号是用户已确定的基础；第 6 章的精确版本和简单范围是实现提案，具体语法仍待规范确定。建议拒绝不支持的表达式，避免一开始兼容各种包管理器语法。统一处理可选的 tag 前缀与规范版本，使用版本解析比较，不能字符串排序；版本号也不能替代 RimWorld/契约兼容声明。

固定一次索引快照后，先收集全部必需 GitHub 依赖和约束，再选具体版本，验证环路、缺失与冲突，生成固定版本/哈希计划。小规模目录可使用有数量/时间上限的候选搜索，不必引入通用 SAT 求解服务；若存在可满足组合，不能因为贪心只选最新版本就误报无解。报错应给出例如“A 要求 B <2.0.0，C 要求 B >=2.0.0”的冲突来源，而非仅显示安装失败。

本地已有但版本未知的依赖应显示待确认/阻断，不能猜为满足。遇到工坊依赖输出打开入口和人工启用提示，不进入 GitHub 版本求解。下载确认后若索引更新，当前计划仍使用原快照；候选被撤回或资产失效时报告失败，不临时改成另一版本继续安装。

### 15.5 代理与下载：优先关闭 Unity 运行时风险

第 7 章已有网络设计；这里的工程判断是：**在真实 Unity/Mono 中通过验证之前，SOCKS5 属于未关闭的关键风险。** 先比较兼容传输实现的维护状态、许可证、额外 DLL 和依赖冲突，再验证，不因服务端 net10 测试通过而接受客户端方案。避免同时维护自写 HTTP 栈和 SOCKS 隧道。

每个任务固定代理配置，所有索引/资产/重定向共用该策略；配置变更只作用于新任务。任务取消应终止网络读取并关闭文件流，不能只是隐藏进度。使用流式写盘与哈希，后台处理网络与解压，主线程只接收限频状态更新；关闭商店窗口与取消任务的关系须在 UI 中明确，插件 Shutdown 必须终止任务并释放资源。

最小实测覆盖：HTTP CONNECT 和 SOCKS5 的无认证/用户名密码认证、SOCKS5 远端 DNS、资产跨主机重定向、慢速网络取消及 TLS 失败。若纯 SOCKS5 未通过，HTTP mixed 端口只能作为可说明的兼容路径，不能宣布已满足要求。Steam 游戏内浏览器和工坊下载不进入这个传输实例。

### 15.6 安装失败与恢复：只承担可证明归属的文件

建议首版限于新包安装，沿用第 8 章状态机：整个 GitHub 依赖计划下载和校验后才提交，暂存区经验证不会被游戏扫描，逐目录 rename 与持久化日志配合。可共用一个后台安装队列和目标锁，不必引入通用事务框架。

重点区分下载失败、提交前取消和提交中异常。前两者清理暂存；后者根据记录恢复，仅处理本事务创建且归属可核对的目录。日志损坏、目录被用户修改或无法确认归属时提示人工处理，不能按前缀批量删除。rename、日志落盘和进程崩溃之间仍有窗口，要用中断样例验证，而不是仅靠正常安装成功推导可靠。

此范围不覆盖已加载 DLL 替换、游戏启动前的自动恢复、存档/插件数据回滚或 Steam 订阅回滚。若首版要自动升级已装插件，应先重新评估退出后安装和恢复机制，不能把它作为新包安装的顺带功能。

### 15.7 发行与索引：复用校验规则，固定批准对象

作者仓库负责构建和发布 DLL/包；官方索引负责元数据、固定资产及检查记录。建议一份清单 schema 配一组正负样例，作者发布前检查与官方机器人使用同一版本的规则；客户端依同一规范再检查下载内容。可共享纯逻辑，运行时与 GitHub API 适配分别实现，不要求 net472 游戏直接调用现代 CI 工具。

首次人工批准必须对应具体候选的仓库身份、源码 commit、tag、asset 与 SHA-256。批准前候选被替换就重检；后续自动收录仍要核对源码可访问、资产内容与依赖闭包，失败保留上一份正式索引。记录 sourceCommit 和构建链接有助于追溯，但没有额外证据时仍不能证明 DLL 与源码一致，不能将此项写成已解决的安全问题。

发布索引时生成固定快照，再更新稳定指针；多包更新若依赖尚未满足则等待或拒绝该候选。工作流明确调用发布步骤，不依赖机器人创建 tag 后一定再触发另一工作流。具体权限与事件限制沿用双渠道评估，不建设新的全量作者构建平台。

### 15.8 建议的验证顺序与范围控制

后续实施建议按以下顺序取得证据；本次不执行原型或游戏测试：

1. **先验证游戏边界**：一个工坊入口确实在 Steam 游戏内浏览器打开；一个最小 GitHub 扩展和一个简单 patch 模组经原有入口加载。确认覆盖层不可用、禁用/重启、重复程序集的结果。
2. **验证网络边界**：在目标游戏运行时完成 HTTP/SOCKS5、DNS、重定向和取消样例，决定可复用传输方案。这一步通过后才稳定下载层工期。
3. **验证纯逻辑和文件边界**：用 A→B→C、菱形冲突/环路样例检查计划；用哈希失败、磁盘满和提交中断验证不留下可误认为完整的新包，不误删用户文件。
4. **连通发布链**：用测试作者仓库从 Release 到候选检查、首次人工批准、后续自动更新和索引发布；故意替换资产/提交错误清单，确认正式快照保持可用。
5. **完成最小 UI 与作者指南**：只暴露已有且验收过的能力，明确工坊自行订阅、GitHub 安装后启用和专用代理范围；再让新手按第 10 章指南完成一个简单插件。

工坊改为覆盖层链接后，主要新增工作是客户端接入与条件验证，可并入双渠道 UI 的既有预算；不能直接计为已完成，也不再按 SteamUGC 下载状态机估算。现有工期是粗略设计预算，若实际游戏没有可调用绑定、SOCKS5 库冲突或要求升级覆盖安装，需据实重估；本次不把这些不确定性包装成精确总工期。

### 15.9 下载目标与官方插件拆分：保留注册流程，加强 DLL 解析

详见 [安装目录、发现加载与官方插件拆分评估](插件安装目录与发现加载及官方插件拆分评估.md)。推荐下载到独立本地模组的 Assemblies，而非主包 Common/Extensions；现有活跃模组探测路径可复用，但版本目录、来源路径和类型加载失败诊断需要核实。

源码已经通过 `ExtensionDependencyGraph.GetStableTopologicalOrder` 按 `DependsOn` 注册模块，并沿此顺序激活、逆序关闭；无需为独立发布的官方可选扩展另建注册通道。文件名前缀只参与 DLL 探测排序，不能代替程序集身份/引用解析。建议先建立完整候选索引与解析器再加载，明确同名版本冲突；现有主包编号暂作兼容，不在缺乏 RimWorld 更早加载阶段证据时直接删除。

红包和人才贸易后续独立发布，Chat、Trade、Inventory、LegacyAdapter 暂留主包。拆分需同步四个业务 DLL 的发布目标、语言资源、产物检查和旧副本迁移；建议保持原有模块/程序集/数据身份，分别验证红包托管库存记录与人才贸易存档中的待返还 pawn。发行位置变化不能证明对历史存档和物品所有权没有影响。

### 15.10 本轮源码复核：补充两个缺口，收束后续评估

本轮判断：**已有评估足以确定主要实现方向，不需要再增加一轮全面架构设计。** 新发现的两个具体缺口是持久化根路径的稳定性和任务终态的可靠传递；版本识别补充实际代码依据。它们影响安装记录/恢复和 UI 正确性，值得在实施前明确，而非扩展成新平台或另一套插件框架。

**缺口一：现有扩展存储位置不等于稳定的用户数据目录。** [Client.cs](../../../../Client/Source/Client.cs) 传入相对路径 `framework-extensions/client`，而 [FileSystemExtensionStorageProvider](../../../../Common/Utils/Framework/FrameworkTypes.cs) 在构造时用 `Path.GetFullPath` 转成绝对根。该实例创建后根不再随工作目录变化，但不同启动方式若工作目录不同，下一次构造得到的根可能不同；目录创建也不能保证玩家对该位置始终有写权限。这是源码可见的前提风险，不表示已经复现了记录丢失。[Microsoft 相对路径行为](https://learn.microsoft.com/en-us/dotnet/api/system.io.path.getfullpath?view=netframework-4.7.2)

商店缓存、安装记录和事务日志需要可确定、可写且跨启动可定位的存储根；本地 Mods 根则是另一个目录。建议通过框架统一存储/通用路径能力明确根位置，并在安装前验证实际写入和恢复所需文件操作，不能先提交模组后才发现日志不可写。若只用现有存储服务，须先验证启动位置与权限前提，不能宣称持久化边界已关闭。若未来调整宿主存储根，必须考虑其他模块已有记录的迁移，尤其红包托管数据；不在本轮自动迁移或默认更改所有模块根目录。

**缺口二：主线程队列不保证每个完成回调都执行。** [ClientMainThreadDispatcher.cs](../../../../Client/Source/Framework/ClientMainThreadDispatcher.cs) 最多保留 500 个动作，满时丢掉最旧动作，每帧最多执行 100 个；这些是当前源码常量，不是商店性能结论。仅限频进度消息仍不足以保证“安装完成/取消/失败”回调永不丢失。若持久化或任务状态只在该回调中完成，会出现文件已提交但 UI 一直下载中，或恢复记录未完成的问题。

建议安装任务拥有可线程安全读取的权威状态快照，完成后先记录实际结果，UI 主线程读取快照；dispatcher 用于提示刷新和必须在主线程执行的游戏/UI 操作。避免让后台写入任务依靠有损 UI队列获得完成确认。只能在主线程执行的关键步骤，若以后需要可靠确认，另评估通用可靠调度契约；当前首版不为文件提交引入此依赖。验收应模拟回调遗漏、关闭后重开窗口、迟到回调和退出中断，不能靠增大队列长度解决可靠性。

**已知版本问题的代码依据补充。** 当前 [Client AssemblyInfo](../../../../Client/Source/Properties/AssemblyInfo.cs) 与 [Utils AssemblyInfo](../../../../Common/Utils/Properties/AssemblyInfo.cs) 声明 `0.9.7.0`，[ClientExtensionAbstractions AssemblyInfo](../../../../Client/ClientExtensionAbstractions/Properties/AssemblyInfo.cs) 声明 `1.1.0.0`；`Client.Version` 取宿主程序集版本。这些值不能直接当作所有商店包的发行/兼容版本。实施前把清单中的 Phinix 兼容版本对应到明确的主包/契约信息，复用第 4.1 节通用运行信息提案；无法取得时标记未知，不用最新 GitHub tag 或协议版本号代替当前本地版本。本轮不另建复杂版本治理体系。

**已经得到源码支持、无需重做的入口。** 主菜单 Mod Settings 通过 `IClientSettingsPanelProvider` 收集面板；[RootPatch.cs](../../../../Client/Source/Patches/RootPatch.cs) 调用 `Client.Update` 消费主线程队列，没有当前存档或登录检查；扩展发现/激活也发生在宿主构造而非登录之后。由此支持“无需登录或先载入存档即可进入商店”的设计方向。商店面板需保持离线可见，不给自身声明 Chat/Trade 等无关业务依赖；真正的窗口打开和主菜单行为仍需游戏验收，源码不代替实测。
