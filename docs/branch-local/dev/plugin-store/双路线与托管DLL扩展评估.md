# 双路线与托管 DLL 扩展评估

> 实施进展：M1–M3 宿主加载/恢复/管理及 M4a 目录 v2/托管 ZIP 校验已有本地实现；M4b/M4c 安装/联网和游戏验收待做，详见[分步实现](托管DLL分步实现.md)。

[English](ManagedDllRoutes.md)。日期：2026-10-04；分支：`dev`。用户已明确产品方向；本文保留早期源码评估与计划；当前实现进展以上方更新及分步记录为准。

## 1. 结论与当前方向

可行，且与现有插件平权架构一致。商店提供两类条目：

| 条目 | 商店职责 | 下载、加载与管理 |
| --- | --- | --- |
| 完整 RimWorld Mod | 展示索引、作者、说明和工坊链接 | 用户自行订阅；Steam 下载，RimWorld 管理启用和游戏资源 |
| Phinix DLL 扩展包 | 展示索引、规划依赖、下载、校验和安装 | Phinix 在独立托管目录发现；通过通用扩展管理启用、停用、卸载 |

GitHub 是 DLL 包的发布权威源，CF endpoint 的既有固定回源与缓存负责客户端分发。条目不能仅凭来源网站推断安装行为，须显式区分发行形态/管理路线。一个作者可以同时提供两种发行方式；禁止同一模块、程序集或包的两个副本同时装载。

托管 DLL 不生成 About，不改 ModsConfig，不注册成 RimWorld Mod。ZIP 可以继续用作 DLL 与清单的运输容器；“DLL 包”不等于必须下载一份裸 DLL。需要 Def、Patch XML 或游戏原生内容发现的完整 Mod 走工坊路线。DLL 可以经游戏 API 实现 Tab、按钮、白银操作及代码补丁；原生 Languages/Textures 等资源不能因为放进托管目录就自动成为游戏模组资源。首批样例使用包内文本/代码，通用资源接口后续按真实需求增加。

本文覆盖旧评估中“GitHub 包安装成独立本地 Mod”“DLL 生成最小 Mod 壳”的建议。旧 ZIP 事务代码和 Playtest 1.1.0 发布记录保留为历史实现证据，不代表新路线已经完成。

## 2. 源码依据与实际缺口

- `Client/Source/Client.cs` 的 `GetExtensionProbeDirectories` 已探测主包 `Common/Extensions` 和活跃 Mod 的 `Assemblies`；随后统一扫描模块、建立依赖图并运行注册/激活。Chat、Trade 与第三方不需要不同业务启动分支。
- `Common/Utils/Framework/ExtensionAssemblyLoader.cs` 当前先加载 DLL，再挂解析器；候选缓存按文件名，慢路径还会扫描晚加入文件。不能直接加入一个下载目录后声称托管加载完成。
- `StaticActivationPolicy` 在程序集加载后控制模块激活。托管包停用要在加载前生效：从静态清单建立候选集合，停用、待卸载、未核验或有冲突的包不得进入 Phinix 托管解析候选。该控制不是同进程安全沙箱；其他 Mod 或插件直接调用 CLR 加载 API 不受它隔离。
- `ClientEnvironmentCapture` 当前仅通过 RimWorld Mod 根目录推导程序集、模块归属；独立目录中的 DLL 会导致 `ModuleOwnershipUnknown`。应增加通用包来源/管理类型，保留真实 Mod 事实，不能伪造 Mod 根来绕过完整性检查。
- 当前扩展管理主要展示已发现模块。未加载的停用包、待重启安装包、加载失败包也必须由静态包目录提供管理条目；包级加载状态与模块级激活状态分开显示。一包可含多个 DLL/模块，不能假定一 DLL 等于一模块。
- 商店中的 `ManagedInstallation` 已有摘要核验、暂存、归属凭据、日志和恢复代码，但目标目录及删除前置仍按本地 Mod 设计。通用事务机制可复用，路径、状态和启动恢复时机需适配。

## 3. 目录与职责建议

建议根目录为 `<SaveData>/Phinix/ManagedExtensions/`，包含 `packages/`、`state/` 和 `transactions/`；稳定包目录使用来源/包 ID 的确定性哈希，不能直接使用展示名称。临时下载/暂存/隔离目录与加载候选分离，并保持目录提交所需的同文件系统约束。插件运行数据保留原有数据身份和存储契约，卸载不删除设置、存档或业务恢复数据。

不要把下载文件写入主包 `Common/Extensions`：主包仍在该目录发行内置模块，托管包独立保存，主包更新不应覆盖它们。这里只提议目录布局，路径 API 与迁移格式尚未冻结。

宿主/通用框架负责读取静态库存、恢复启动事务、提供加载和管理状态；商店负责联网索引、下载授权和发起安装请求。宿主不引用商店具体类型或某个业务扩展。安装收据与静态清单由通用层读取，不能要求商店先加载，才能找到下载的其他插件。关闭商店后，已装扩展仍能在后续启动加载和管理。

启动顺序建议：读取包状态与恢复意图 → 核验候选及依赖 → 建立程序集身份索引/解析器 → 加载允许的程序集 → 统一发现模块 → 依赖排序 → Register/Activate。恢复失败的包不进入候选，保留诊断；基础模块和不相关扩展仍可正常启动。游戏与翻译相关状态捕获仍遵守主线程边界。

## 4. 安装、停用与卸载的体验

首版继续采用重启生效，避免把关闭业务模块误认为已经卸载 DLL。

1. 安装：确认依赖计划 → 下载并静态校验 → 提交包及收据 → 显示“已安装，重启后启用”。安装确认明确授权计划中新包启用；安装完成不在本次游戏中执行新 DLL。
2. 停用/启用：扩展管理保存期望状态，展示当前状态和“待重启”。内置模块沿既有激活策略；托管包关闭时，下一次启动直接排除其 DLL。依赖检查不静默关闭其他包。
3. 卸载：核对所有权、文件摘要和反向依赖。未加载且未被使用的包可直接事务移除；已加载的包保存“待卸载”意图，提示重启。下一次宿主启动在加载前重新核验依赖/归属，隔离并移除目标，再建立候选集合；移除失败保持排除加载并提供恢复诊断，不能把失败显示为已卸载。

无需用户先到 RimWorld Mod 列表禁用。包级启停决定是否加载，模块级启停控制该包已允许加载后哪些模块激活；存在多个模块/共享程序集的依赖时，两级状态需分别校验。首批样例使用一包一模块，管理契约不能因此把二者身份合并。

DLL 与游戏对象共享当前 AppDomain；现有生命周期 Shutdown 不具备程序集卸载能力。Microsoft 的[程序集加载与卸载](https://learn.microsoft.com/en-us/dotnet/standard/assembly/load-unload)说明 .NET Framework 中卸载需卸载所在 AppDomain；与当前 Unity 对象/契约共用域的模型采用重启边界，并在目标 Mono 游戏实测。未知程序集请求应返回 null，禁止递归按名加载，见[程序集解析规则](https://learn.microsoft.com/en-us/dotnet/standard/assembly/resolve-loads)。

## 5. 依赖与协议

包依赖、CLR 引用和模块 DependsOn 保持独立。内置模块作为宿主提供的依赖，不下载重复框架/游戏 DLL。完整 Mod 作为外部前置时，只检查游戏当前事实并给出订阅提示，不由商店下载工坊内容。反向依赖检查至少覆盖托管包、当前内置模块与可识别的活跃 Mod 扩展；旧 Mod 不会自动声明新包格式，无法识别的原生游戏依赖不假装有完整覆盖。

同名不同内容/版本、重复模块 ID、框架/游戏 DLL 冒充、缺失依赖均有明确包级失败。禁用的托管 DLL 不得被 Phinix 的解析慢路径捞回来；同时核对 CLR LoadFrom 的自动邻目录依赖解析，不能把未核验 DLL 留在允许加载的目录里。目标 Mono 上需要实测隐藏引用和跨包加载，不能只测试自定义解析回调。不承诺隔离第三方自行执行加载代码。

当前 catalog v1 强制 `rimWorldPackageId`，`dll-with-manifest` 以 `.dll` 资产和旧模组壳建议为背景，不能原地修改成新的 ZIP/托管含义。下一批先设计带版本和能力声明的托管包契约，显式区分工坊条目与托管扩展；传输层 stable/published 固定身份和摘要机制能复用，不必因此重做 CF 缓存。旧客户端应拒绝不支持的新 schema/路线，不能误装成 Mod。当前静态 DLL 校验器需补托管布局及声明一致性检查。

旧 `installation-v1` 本地 Mod 凭据和新托管状态分开读取。旧已安装副本不自动搬迁或删除；检测到重复时要求用户按旧路线卸载/清理后改装新包。Playtest 新路线发布新的版本和不可变资产，保留现有 1.1.0 和旧目录摘要。

## 6. 接下来的实施与验收

按依赖顺序推进，不先增加完整界面再修加载基础：

1. 冻结托管清单/来源、启用意图、归属和事务状态；新增通用路径与只读库存契约。
2. 先实现宿主启动恢复、静态候选检查和受限程序集解析；回归停用包绝不由 Phinix 加载、重复身份/缺失引用/损坏收据失败、商店停用后已装包仍可用。
3. 扩展管理接入包库存，支持待重启安装、启停、失败及待卸载；保持内置模块现有能力和设置恢复入口。
4. 复用下载/校验/安装事务，增加托管目标及恢复路径；保留旧凭据的只读识别和旧包卸载兼容。
5. 发布新的 DLL Playtest 样例：安装重启后出现 Tab、计数及确认给 100 白银；停用重启后消失、管理仍可见；卸载重启后文件/条目移除、数据保留；重新安装能重新注册。工坊链接路线另做平台验证。

日志覆盖包/source/version/hash、事务与启动关联 ID、candidate/resolve/discover/register/activate/remove 阶段、最终结果和稳定错误码，不输出凭据。对跨程序集失败保留详细内部诊断与安全的 UI 提示。

本轮只评估源码和修改计划，未改变运行时代码、发布资产或 Worker，也未运行新增功能测试。旧安装/校验与 585 项回归是复用基础的证据，不能作为托管 DLL 路线的验证。
