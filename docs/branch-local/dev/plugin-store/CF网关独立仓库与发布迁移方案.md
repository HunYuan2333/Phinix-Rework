# CF 网关独立仓库与发布迁移方案

[English](CfGatewayRepositoryMigration.md) · 2026-10-06 · 状态：评估和待执行计划。

当前投入顺序见[商店专项收尾](商店专项收尾顺序.md)：本专项属于商店，接着完成红包/人才拆包及正式发行，全部完成后再看主三仓等其他专项。

2026-10-06 已执行：[独立仓库、正式发布接管及主仓库撤出验收](CF独立发布接管与验收.md)。下文保留原设计与门槛，不再表示该专项尚未实施；旧 PoC 永久删除仍独立待批。

本方案把“跟主 Phinix 发布”理解为源码归属、构建和发布节奏。建议插件商店的 CF 网关独立维护和部署，同时继续作为 Phinix 官方服务。它不需要随 Mod 版本一起发布，也不需要玩家自行部署。此次只写方案，不创建远端仓库、不迁移源码、不部署或删除云资源。

## 1. 结论与取舍

建议建立 `Phinix-Plugin-Gateway` 独立仓库（名称待实施时确认），迁入当前 `Extensions/PluginStore/RepositoryWorker/`。客户端商店继续随 Phinix 客户端交付；插件目录、准入审核与发布机器人继续归 `Phinix-Plugin-Index`。

| 选择 | 收益与代价 | 判断 |
| --- | --- | --- |
| 留在主仓库，独立部署 | 仓库少，跨端修改方便；Node/云部署工具和游戏构建混在维护入口 | 可作为迁移期间的安排 |
| 放进 Index 仓库 | 都属于商店基础设施，少一个仓库；索引写入机器人与云服务部署凭据、权限和故障处置混在一起 | 首选不采用 |
| 网关独立仓库 | 云服务可独立测试、发布、回滚，清晰隔离凭据；多维护一个仓库，需要固定跨仓协议样例 | 推荐 |

独立仓库不是独立建立一套索引或发行规则。GitHub 仍是权威源，CF 仍是协议适配和访问加速入口。修复 CF 回源、日志或限流通常不需要玩家更新 Mod。目录/清单格式变化仍需联合验证客户端、机器人和网关。

源码换仓不会增加玩家请求、包体或 CF 流量；本方案复用现有 Worker，不新建在线副本，也不启用 R2/DO。迁移验证会产生少量探测请求。这是结构判断，不是费用或免费额度保证。

## 2. 当前源码核查

- `Phinix.sln` 只包含商店的 `PluginStore.Client` .NET 项目，没有 Worker 工程。
- `PluginStore.Client.csproj` 只复制商店 DLL 和语言资源到 `Output/phinix-rework`，不复制 Worker、Node 依赖或云配置。
- 主仓库 `.github/workflows/docker.yml` 发布服务端镜像，没有 CF 部署步骤。
- 但 Dockerfile 会 `COPY Extensions/`，而当前 `.dockerignore` 没有单独排除 Worker 和其 `node_modules`。这些文件可能进入 Docker 构建上下文及构建阶段；最终镜像只复制 .NET 发布产物。拆出可以减少这类无关输入，不能把它说成现有镜像运行了 Worker。
- Worker 的正式入口是 `src/read-only.mjs`，使用 Node/Wrangler 工具链，不依赖 RimWorld 或 .NET 程序集。
- **测试仍有真实跨目录依赖**：`tests/helpers.mjs` 读取主仓库 `Tests/PluginStoreRuntimeTests/Fixtures/chain.catalog.json`；`tests/localized-display.test.mjs` 读取其中 `localization-display/cases.json`。直接搬目录会让测试失败，必须先带走并锁定样例。
- 当前 `git ls-files Extensions/PluginStore/RepositoryWorker` 没有结果，整个商店目录仍是主工作区未跟踪内容。不能只从已有 Git 提交克隆/提取历史，声称迁到了完整最新源码。

正式配置已在[域名迁移记录](CF正式入口迁移与退役记录.md)核实：正式地址 `https://plugins.hunyuan2333.com`，旧 staging 地址暂时是同一服务的别名；底层服务名仍为 `phinix-plugin-repository-staging`。生产绑定不含 R2、DO 或管理 RPC；现有限流是各 CF 节点的聚合限制，不是全账号计费硬上限。

## 3. 文件和职责归属

| 内容 | 目标归属 | 处理方式 |
| --- | --- | --- |
| 正式网关、GitHub 回源、协议检查、流式校验、审计、元数据缓存 | Gateway | 迁入 `src/`，保留现有行为 |
| Worker 的 package/lockfile、Wrangler 配置、Node/Python 测试 | Gateway | 固定依赖，消除主仓库相对路径 |
| 网络探测、审计查询、内部缓存运维工具及说明 | Gateway 的运维目录 | 保留用途隔离，不发布为游戏组件，不加入正式公开管理路由 |
| 历史 R2/DO/PoC 源码和故障恢复测试 | Gateway，明确标记实验/历史 | 首轮保持路径以减少变量；生产部署只选正式配置，后续再整理目录 |
| 商店 UI、GitHub/CF 客户端访问适配、安装/更新及本地校验 | 当前主仓库；将来 Client 仓库 | 不随 Worker 搬走 |
| 托管扩展运行时与通用宿主契约 | 原有框架工程 | 不引入对 Gateway 的代码依赖 |
| 目录、作者准入、受信校验和自动发布 | Index | 不因拆网关而更改审核权限、历史记录或已发布资产 |
| Example/Playtest 作者源码 | 各自插件仓库 | 不复制到 Gateway 的正式目录 |

网关的独立版本描述服务实现；Mod 版本描述客户端/框架；目录快照描述已发布内容。三者不要求同号。Gateway 不加入 Client/Common/Server 的 submodule，不新增协议协调仓库或 SDK 发布管线。

## 4. 迁移顺序与退出条件

### M0：冻结可审阅输入

1. 在隔离临时目录生成源文件白名单、逐文件 SHA-256 和来源说明，包含当前未跟踪代码、锁文件、必要样例、许可证及中英运维文档。
2. 排除 `node_modules`、`.wrangler`、`.dev.vars`、`.env`、日志、账号认证文件、私有备份、构建产物及游戏 DLL。公开配置中的账号/域名属于部署定位信息，逐项审阅，不把它们误当作可用凭据。
3. 记录现有正式 Worker 版本、入口、两条域名、secret 名称、绑定和限流 namespace；不读取或导出 secret 明文。
4. 先在原路径跑窄范围基线。过去已通过的测试不等于拆仓后通过。保留当前工作区，不执行整仓提交、清理或强制历史重写。

退出条件：迁移清单完整，可追溯到实际文件字节；正式部署保持原状。

### M1：建立可独立获取的源码和 CI

1. 以审阅快照建立新仓库。未跟踪文件注明快照来源，不能捏造其提交历史；已经提交的内容若需保留历史，在临时副本按白名单提取。
2. 把两个外部 JSON 样例放进网关 `tests/fixtures/`，修改读取路径。样例的规范维护入口先保持当前主仓库的协议测试，未来随客户端测试归 Client；网关和 Index 消费指定版本/摘要的样例副本，更新有同步记录，禁止三边手改成不同标准。
3. CI 从干净检出安装锁文件依赖，跑 Node 测试、Python 工具测试、production dry-run 和原生 workerd 测试。不依赖兄弟目录、私有本机路径、游戏 DLL 或云账号。
4. 原生测试仍覆盖历史缓存/内部 RPC。它依赖 default/ops/production 三份本地 bundle，不能删掉实验配置就认为 `test:native` 仍完整。
5. 默认开发命令明确是本地测试；部署入口只选正式配置。PoC 和管理 bridge 配置不得被默认线上发布误用。

退出条件：单独克隆 Gateway 能跑完整适用测试；本阶段没有云部署凭据、没有线上写入。

### M2：接管现有服务的发布入口

1. 新仓库配置受保护的正式发布入口：部署限定可信分支/固定提交，先验证，再由维护者触发；不因作者 Issue、外部 PR 或示例插件发布自动部署 CF。
2. 部署用 CF 凭据与网关中的 GitHub 只读回源凭据分开管理。CF 凭据按部署需要收窄权限；不把索引机器人现有凭据复制过来。首次部署身份设置由维护者完成，凭据不进聊天、源码或普通日志。
3. **部署到同一个现有 Worker 名称**，继续使用原有 `GITHUB_TOKEN` secret、正式域名及暂留别名、限流 namespace 和绑定。移动文件不需要换 DNS；不借此改名创建新服务或做 secret 轮换。
4. 部署记录关联网关提交、bundle 摘要、Worker 版本、BUILD_ID、配置摘要、测试结果和操作人。首轮保留旧版本及原路径，先演练可执行的回滚操作说明，再做有界在线验证。

退出条件：新仓库可维护现有服务；旧部署入口停止新增发布，避免两个仓库争抢配置。发布切换与改名/删资源是不同操作。

### M3：协议与在线验收

1. 从固定输入检查 stable、published、catalog 和 ZIP 的摘要链、来源身份、长度及本地静态校验；GitHub 与 CF 返回同一个固定快照的内容字节。测试期间若目录更新，锁定快照后比较，不能把“当前最新”两次读取误判成适配器差异。
2. 覆盖 ETag/304、未知来源、错误方法/query/Range、限流、超时及流中断；公开管理操作仍被拒绝。
3. 核对审计 requestId、BUILD_ID 和真实部署版本；日志保留定位信息并隐去凭据和签名下载地址。
4. 使用当前 .NET/Mono 下载检查工具验证真实传输。它仍归客户端测试，只在网关发布验收时显式检出固定客户端提交运行，不把整个客户端当作 Gateway 本地构建前置。
5. 人工游戏检查只需：选择 CF 刷新；与 GitHub 切换后目录一致；已安装 Example 和设置保留；需要时安装/更新后重启正常。纯源码换仓不需要重跑所有玩法和存档用例；若同时改变协议、客户端或资源绑定，扩大相应验收。

退出条件：自动测试与人工检查记录分开；失败时恢复之前核实的正式只读版本及配置，不指向旧 PoC。

### M4：撤出主仓库并收尾

1. 新仓库发布入口和回滚确认后，才在主仓库移除迁出的 Worker 源码。留下短入口文档，链接新仓库、协议样例和部署说明；修正有关旧相对路径的说明。
2. 检查 Docker 上下文、solution/csproj、产物脚本和文档链接。主 Mod 构建不需要安装 Node/Wrangler，也不包含云部署文件；服务端镜像只发布自己的图。
3. 主仓库或 Index 可以调用无凭据的协议联测，但不持有网关部署权；普通 Mod/目录发布不联动部署 CF。
4. 分别给主仓库移除改动和 Gateway 发布留可回滚提交。撤回源码迁移不改变插件安装记录、用户设置或目录资产。

退出条件：一个明确的正式部署所有者，主仓库无遗留构建/测试路径依赖。

## 5. 需要防止混入本次迁移的工作

- **旧 PoC 永久退役仍待具体授权。** 当前公开入口已关闭，但 Worker、R2、DO 和 secret 副本保留；自动审批此前拒绝删除，DO 完整账本备份缺失。源码换仓不授权删除，按独立[退役记录](CF正式入口迁移与退役记录.md)处理。
- 保留当前 staging 域名别名直到正式入口验收；它不是独立测试环境。将来真要 staging，再创建隔离资源和独立凭据，另行评估。
- 不同时启用 R2、重写缓存策略、改 schema、改来源身份、改安装路径、改官方插件边界或重写所有 README。
- 当前开源仓库文案整理仍交给用户安排的另一模型；AI 作者工具按既有计划另做。作者无需拥有 CF 部署权限。

兼容性风险主要是协议三端漂移、样例遗漏、误用旧配置覆盖路由和双发布入口。仅迁移源文件不涉及游戏存档、玩家数据、交易 ACK 或物品归属。云端状态删除的不可逆风险属于独立退役操作。

## 6. 与主 Phinix 拆仓计划的关系

与[Client/Common/Server 三仓计划](../Repo-Split-Plan.md)并行：Gateway 属于分发基础设施，不属于其中 Server 仓库的多人游戏服务器，也不放入 Common。它已有独立工具链，可先拆出，不需要等三仓方案完成；三仓方案不因此变成四个互相引用的源码消费者。

建议下次实施先做 **M0 + M1**，交付独立可测试的候选仓库和文件清单，然后接 **M2 + M3**，最后执行 **M4**。新仓库创建、源码公开发布和受保护部署配置在实施时按确认后的范围办理；本次没有执行这些操作。

本轮仅核查代码/配置和文档链接，没有重跑编译、自动测试或游戏验证；上述验收项均是迁移实施的要求。
