# 术语与功能分层

日期：2026-10-02。分支：`dev`。状态：命名与文档表达建议，不改变运行时行为。

本文为 [商店设计文档](README.md) 提供统一词义，也可作为后续架构说明和开发者指南的术语底稿。依据为 [设计哲学](../../../Design-Philosophy.md)、[开发者指南](../../../Phinix附属Mod开发者指南.md) 及现有扩展契约。本轮沿用现有接口、模块 ID、目录与启用策略；具体 UI 名称和稳定文档的全面迁移尚未实施。

## 1. 推荐的对外解释

> **Phinix 的基础功能以模块化方式实现；商店用于分发可选扩展。**

基础功能中的聊天、交易、库存和协议兼容被拆成独立模块，是为了减少耦合、便于维护和替换。用户安装 Phinix 主包即可获得这些功能，不需要先理解“插件机制”。开发者则通过统一扩展契约实现它们，使基础功能与外部扩展都能复用同一发现、注册、激活和关闭流程。

红包、人才贸易在本轮规划中属于可选扩展：由官方维护，后续独立发布和安装。它们目前仍随主包打包，发行拆分尚未实施；**打包位置变化，不改变原有模块身份与数据归属。**

## 2. 按使用场景选择词语

| 推荐术语 | 含义 | 适用场景 |
| --- | --- | --- |
| 基础功能 | Phinix 标准产品提供的功能 | 面向玩家介绍聊天、交易、库存、兼容支持 |
| 内置功能模块 | 随主包提供、采用扩展机制实现基础功能的模块 | 架构说明、基础功能维护文档 |
| 可选扩展 | 玩家按需获取的附加功能；可增加新功能，也可调整或增强既有行为 | 商店介绍、扩展选择与使用指南 |
| 官方可选扩展 | 由 Phinix 官方维护的可选扩展 | 后续独立发行的红包、人才贸易 |
| 社区扩展 | 由社区作者维护的可选扩展 | 第三方功能介绍；审核状态另行说明 |
| 运行时扩展模块，简称扩展模块 | 参与 Phinix 扩展契约和生命周期的代码单元 | `IPhinixExtensionModule`、依赖图、注册/激活、ExtensionId |
| 扩展包 | 可独立发行、安装、记录版本与文件归属的单位 | 下载、哈希、清单、安装与卸载 |
| 商店条目 | 索引中描述来源、兼容性、版本与检查范围的记录 | 列表、收录审核、索引更新；条目不是代码本体 |
| 商店功能模块 | 实现浏览、索引、下载和安装界面的模块本身 | 描述商店实现；避免与“商店里下载的扩展”混淆 |

“插件”可保留在现有标题“插件商店”、历史文档和既有代码注释中；精确说明时使用上述术语。避免继续把“官方内置插件”作为总称，或把“商店插件”同时用来指商店实现、条目和下载包。可选扩展也不限于小幅增强，所以不统一叫“增强插件”。

此处“基础功能”是产品角色，不是“不可禁用”的新技术标记。当前扩展禁用能力和依赖传播保持现状；产品是否以后隐藏某些开关、设哪些默认项或要求必须启用，需要另行决定。

## 3. 产品角色、发行方式和维护者分别表达

这几项是描述维度，不必为命名统一新增一套复杂权限或清单系统：

| 维度 | 回答的问题 | 例子 |
| --- | --- | --- |
| 产品角色 | 它提供基础功能还是可选功能？ | 基础功能 / 可选扩展 |
| 发行方式 | 文件随主包提供还是独立安装？ | 随主包发布 / 独立扩展包 |
| 维护者 | 谁开发并维护内容？ | Phinix 官方 / 社区作者 |
| 获取渠道 | 用户在哪里获取它？ | 主包 / GitHub Release / Steam 工坊 / 手动安装 |
| 集成方式 | 是否进入 Phinix 模块生命周期？ | Phinix 扩展模块 / 普通 RimWorld 模组 |

“内置”只说明随主包提供；“官方”只说明维护归属；“商店收录”只说明存在条目和相应检查记录。它们不能互相替代：社区作者的作品收录进官方索引后，仍是社区扩展；官方可选扩展也不会因为独立下载而变成第三方作品。

| 当前对象 | 推荐产品表述 | 发行状态 | 技术实现 |
| --- | --- | --- | --- |
| Chat、Trade、Inventory、LegacyAdapter | 内置基础功能；分别为聊天、交易、库存和兼容支持 | 已确认暂时随主包发布 | 内置功能模块，走统一扩展机制 |
| 红包、人才贸易 | 官方可选扩展 | 当前随主包打包，计划改独立扩展包 | 保留现有扩展模块和身份 |
| 社区 Phinix 功能包 | 社区可选扩展 | 通常独立发行，可从商店或手动获取 | 可提供一个或多个 Phinix 扩展模块 |
| 商店收录的普通 patch 模组 | 按需安装的 RimWorld 模组 | GitHub 包或工坊条目 | 可只使用游戏自身入口，不必有 Phinix 模块 ID |
| 商店本身 | 官方商店功能，交付层级类似 Trade | 后续随主包发布；当前独立包用于开发预览 | 独立工程/DLL，通过统一扩展机制接入；保留禁用能力 |

LegacyAdapter 提供协议兼容基础能力，但不是每个连接场景都必须启用；Chat/Trade/Inventory 的“基础”定位也不自动证明每项功能是宿主启动的硬依赖。基础功能之间的运行条件仍以实际依赖契约为准。

## 4. 基础功能模块不属于宿主基础设施

为了表述方便，推荐把技术层次写成：

| 技术层次 | 职责 | 例子 |
| --- | --- | --- |
| 基础设施与宿主 | 提供业务无关的通信、认证、通用服务、扩展生命周期与 UI 壳 | Common 基础能力、Client/Server Host |
| 契约与扩展点 | 定义可实现、可注册和可调用的接口 | ClientExtensionAbstractions、扩展契约、业务 Contracts |
| 功能实现 | 使用上述契约实现具体功能 | 内置功能模块、外部 Phinix 扩展模块 |

**Chat 是基础功能，并不意味着 Chat 的业务实现应移回 Host/Common。** 基础功能模块仍处于功能实现层，宿主不强引用其具体工程，不为官方模块建立专用启动分支。可选扩展可以依赖相关功能的公开契约；模块之间的实现耦合仍按原架构边界评估。

原文中的“插件平权”在这里准确解释为：**扩展模块共享契约、发现入口和生命周期，不设官方特权。** 它不要求所有功能具有相同产品角色、打成相同发行包、全部进入商店，或允许相互覆盖文件。

当前模块 ID中的 `builtin.*` 与仓库/发布目录中的 `Extensions` 都是已有代码身份和物理约定。不得用字符串前缀推断基础/可选、官方/社区、可信/不可信；这次术语澄清也不把现有接口改名成 BasicFeatureModule，不迁移 ID、程序集名、数据键或目录。

## 5. 包、模组、DLL、模块和扩展点

| 对象 | 定义与边界 |
| --- | --- |
| 扩展包 | 安装与发行单位，有包 ID、包版本、来源、清单和文件归属；可含多个 DLL与模块 |
| RimWorld 模组（Mod） | 游戏识别的内容/启用单位，有 About packageId 和资源布局；主包或独立扩展包可采用这种形态 |
| DLL / 程序集 | 编译后的代码容器，有程序集身份与引用；也可能只是契约库或辅助库 |
| Phinix 扩展模块 | 在运行时提供模块 ID及 Register/Activate/Shutdown 等契约的代码单元；不等于一整个包或一个 DLL |
| 扩展点 / provider / handler | 模块注册的 Tab、设置面板、API、消息处理器等能力；不是另一个可安装包 |
| Contracts | 供合作代码编译/调用的业务契约；引用契约不代表运行时已有对应实现 |
| 索引源 | 提供商店条目列表的配置来源；默认官方索引可指向社区作者资产 |
| Release 资产 | 作者发布的具体下载文件；与官方索引的 tag/Release 是不同发行物 |

例如一个红包扩展包可包含 Contracts DLL、Client DLL和语言资源，提供 `builtin.legacy-redpacket` 模块；该模块又注册 Tab、设置面板和库存 codec。这些对象不会因为都叫“插件”就具有相同更新、禁用或卸载边界。

商店包 ID管理发行单位，packageId 管游戏模组身份，ExtensionId 管模块依赖，AssemblyName 管代码引用。包版本、程序集版本、契约兼容版本和索引快照版本分别使用，不能根据其中一个推定其他值。具体字段沿现有清单提案，不在本轮冻结新格式。

## 6. 状态与顺序也要分层说明

| 说法 | 可以证明什么 | 不应推定什么 |
| --- | --- | --- |
| 条目已收录 / 版本检查通过 | 索引存在条目，且记录了对应范围的检查 | 官方开发、无恶意、当前本地已安装 |
| 工坊页面已请求打开 | 商店发起了覆盖层网页入口调用 | 页面加载、玩家订阅或下载完成 |
| 包已下载 / 已安装 | 资产已获取，或文件完成安装检查和提交 | DLL已执行、模组已启用、模块已激活 |
| 模组已启用 | 游戏配置选中了模组 | 当前进程已加载，或全部运行依赖满足 |
| 程序集已加载 | DLL进入进程且可供解析 | 模块已注册/激活，或代码安全 |
| 模块已注册 / 已激活 | 完成相应 Phinix 生命周期阶段 | 网络业务成功、服务器确认或物品交付成功 |

安装计划按包依赖确定版本与下载集合；游戏按模组声明处理加载条件；程序集解析按代码引用与身份工作；模块按 `DependsOn` 注册/激活；handler 的 `Priority` 排处理管线，TabOrder 等排 UI。它们不是同一种“插件加载顺序”。开发者指南中用 Priority 概括插件差别的历史表述，不能作为全部生命周期顺序的定义。

基础功能和可选扩展都可能在游戏进程内执行代码。术语分类不提供权限隔离；“官方维护”“官方索引收录”“检查通过”也必须区分，安全结论继续以 [独立安全评估](插件商店安全性与维护成本评估.md) 为准。

## 7. 文档和界面的应用建议

文档开头先用第 1 节的一句话说明产品，再在技术章节使用“内置功能模块 / 外部扩展模块”。维护者与获取渠道需要时追加，不每次堆出四五层名称。历史标题“插件商店”和现有文件名先保留，文中解释其面向可选扩展和相关模组的作用。

面向玩家，建议基础功能页使用“聊天、交易、库存、兼容支持”等功能名，商店条目使用“可选扩展”并分别标注作者、来源与检查范围。以后若调整扩展管理 UI，可区分“基础功能”和“可选扩展”；“模组未启用”“模块注册失败”“缺少依赖”使用实际状态。此为界面建议，本轮没有修改 UI或基础模块禁用能力。

依赖计划中的主包提供项建议写“基础功能：库存，由 Phinix 主包提供”，独立包写“需安装扩展包：某扩展 1.2.0”，工坊项写“在 Steam 中订阅”。不把基础模块当作商店里的独立下载包，不按 `builtin.*` 自动安装，也不把索引更新显示为本地功能已经升级。

新手指南开头应包含第 5、6 节的短版，让作者先知道自己创建的是一个扩展包、其中哪些类是运行时模块、DLL怎么装载以及如何验证；AI 指引采用同一词表。不要让命名便利形成错误承诺，例如“编译成功即完成插件”“禁用模块即卸载模组”。

本轮在商店文档中补充术语说明，并将“官方基础插件”“商店插件”等关键歧义表述改为建议术语；既有代码符号、历史研究引用及“插件商店”标题保留。现有设计哲学和开发者指南中的 plugin/插件是技术广义表述，阅读时按本词表区分产品角色；稳定后再统一中英文架构文档和开发者指南，不把仍在讨论的命名建议写成已经改变的运行时规范。

这里只厘清概念，不新增 mandatory/不可禁用标记、专属加载入口、商店专属权限或清单强制字段。基础功能范围与红包/人才独立发布沿用户已确认方向，具体 UI命名、默认开关和发行方案仍按相关评估决定。
