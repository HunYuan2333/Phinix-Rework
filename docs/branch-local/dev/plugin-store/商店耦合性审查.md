## 问题与处理建议

### C1 · P2 · 通用清单解析写死官方业务程序集

证据：`Common/Utils/Framework/ManagedExtensions/ManagedExtensionManifestReader.cs:15` 的 protectedNames 包含 ChatExtension、TradeExtension、InventoryExtension 及 LegacyAdapter.Client；`:63` 和 `:78` 在解析时拒绝这些名称及文件别名。它将当前内置分配策略固化到共享格式解析器；以后把这些功能独立发行，必须改通用源码，与普通插件平等及发现式要求不符。

建议：保留游戏/CLR/框架基础设施的保留名边界；官方业务程序集的占用由实际宿主事实和维护者 host profile 提供。运行时 `ManagedExtensionCandidatePlanner.cs:130`、安装服务 `ManagedExtensionInstallationRuntime.cs:118` 与发布闭包已检查真实名称冲突。调整前补文件别名、真实宿主冲突、未知模块和第三方可用性的测试，不直接删除全部保留名或降低冲突检查。这是维护耦合，不是目前已证实的安装故障。

### C2 · P2 · 共享校验源码副本存在无明确分类的差异

证据：本地与索引 `Validator/production-provenance.json` 各声明 24 个冻结文件。全部副本符合各自记录的摘要，但与当前主仓库源文件比较，本地有 5 个差异、索引有 7 个差异。两个额外的线上差异是宿主引用升级规则：索引 `ManagedExtensionCandidatePlanner.cs:155` / ManagedExtensionMetadata 仍是旧版本；其他差异涉及 replacement/事务管理和 staging→official 配置。

重要区别：固定可信验证器快照是合理发布边界，不应让候选源码或联网拉取的“最新 Common”决定生产验证。当前 `Validator/Program.cs:18` 的 publication 入口调用 PublicationClosure；payload 入口调用 ManagedStorePayloadValidator，**没有调用旧 CandidatePlanner**。因此不能把这两个冻结差异写成“当前索引拒绝 Harmony 升级”。安装事务差异也不自动意味着 ZIP 检查规则不同。

建议：按调用闭包缩小独立校验器源码，明确哪些必须与客户端保持相同格式/校验语义、哪些是宿主实现或独立部署配置。提供显式刷新/核对工具和自动一致性检查；保留固定来源/摘要与测试，不简单复制整个 runtime。下一批先处理这项，使 C1 的格式边界调整能可靠同步到索引及作者工具。

### C3 · P2 · 已退役的完整 Mod 安装器仍被编入商店

证据：`PluginStore.Client.csproj:43` 编译 `ManagedInstallation.cs`。该类 `:82` 管理 installation-v1、`:419` / `:470` 处理 About.xml 与 phinix-package.json。当前正式注册、View 和 ManagedStoreController 没有该类调用；真正 DLL 安装走 IManagedExtensionInstallationService，Workshop 路线只打开订阅链接。

建议：将旧完整 Mod 安装器从正式编译范围撤出，保留专项测试所需源码或移入明确开发工具项目。确认相关公共辅助类的现行调用后再缩小，不把 CatalogReader/PayloadValidator 等仍被 v3 使用的边界工具一并删除。不自动删除玩家历史记录或未知文件。本项是产物/维护收口，不要求重新测试旧 Mod 路线。

### C4 · P3 · Gateway 正式只读路径与 PoC/R2 路径仍共享处理器

证据：`src/read-only.mjs:6` 调用 createGateway；`gateway.mjs:13` 仍调用 authorizePoc，`:66`–`:83` 包含 R2/DO 路径。正式入口在 beforeOrigin 中严格拒绝启用这些配置，生产没有缓存绑定；144 个离线测试通过。没有证据表明生产会进入这些缓存业务。

建议：将缓存、测试鉴权和运维能力限制在显式 adapter/策略组合，正式入口只组合所需能力。保留运维恢复代码及历史证据，不以审查为由删除云资源。优先级低于 C1–C3；不需要为了这个结构问题重新部署服务或增加缓存费用。

### C5 · P3 · 索引仓库身份已有常量，但一处 owner 又写死

证据：`scripts/bot.py:16` 的 INDEX 定义固定可信仓库；`scripts/admission.py:15` 从它构造 PREFIX；`scripts/publisher.py:77` 的旧 workflow_dispatch 审批证明路径另外写死 HunYuan2333。迁移 owner 时可能改漏。当前标签审批会先进入 label_admission.proof，未证实普通标签流程受影响。

建议：从同一固定 INDEX 派生 owner，保持 repositoryId/ownerId 等身份锁；不能用候选输入替代维护者配置。此项可随索引维护切片处理，不是自助开放任意来源。
