# 多仓库文档更新任务书

2026-10-06 · 供用户交给其他模型执行 · 工作安排，不是公开 README 草稿

## 目标、顺序与权限

将 Phinix 的公开文档整理为玩家、插件作者和维护者可以实际使用的说明。先核查代码，交提纲供用户审查，用户确认后才改正文。不是润色旧 README，也不是将开发日志搬到首页。

本轮只做文档，不修改代码、工作流、权限、云配置、Release 资产、标签、审批或审计记录。不要部署 Worker、触发插件发布、替用户批准申请或自动合并 PR。每仓单独文档分支和草稿 PR。

建议顺序：Rework → Index → Gateway → Example → TalentTrade → RedPacket → PoC。最后统一术语、双语内容和跨仓链接。AI 作者 AGENT/skill、无 git/gh 环境下的自动发布工具是后续专项，本轮不实现、不宣传已支持。

## 事实核查要求

**以当前代码、项目文件、生效工作流、固定发行资产和实际目录为准。Rework README 长期未更新，不能作为现状依据。** 设计文档、计划和旧 README 都需要与代码交叉核对。

记录各仓检出分支、提交和目标公开版本。远端默认分支与用户本地开发代码可能不同：目标分支没有的功能，不写成公开版默认能力；先列差异，等代码同步。README 面向实际可获得的版本，开发构建单设入口。

## 各仓库正文大纲

### Phinix-Rework

1. **用途**：一句话介绍用途、适用 RimWorld 版本和真实联网能力，避免暗示不存在的同步功能。
2. **获取和安装**：实际下载入口、前置 Mod、安装位置、加载要求。没有公开主包 Release 时写实际获取方式，不虚构按钮；普通安装与开发构建分开。
3. **第一次连接**：实际 UI 入口、填写信息、连接成功表现、常见失败及求助入口。
4. **商店和扩展**：打开商店、安装/重启、更新提示、启用/停用/卸载、GitHub 直连与 CF 加速手动切换。普通路线不出现测试源、PoC ID、规划器、运维字段。
5. **主包与插件关系**：依实际打包规则说明默认能力。红包/人才是否仍内置须核对目标代码和产物，不能抄历史列表。区分托管 DLL 插件与 Workshop 完整 Mod；后者由玩家订阅，仍由 RimWorld 管理。
6. **开发与贡献**：链接设计哲学、开发者指南、CI/构建和 Issue，不将完整 API 表搬到首页。

深层指南放已有 `docs/`。核对 SDK、目标框架、合法本机游戏引用、构建命令、输出和 CI 覆盖范围；不能把全部平台客户端构建说成 Actions 已覆盖。游戏 DLL 不公开分发。

`AGENTS.md` 本轮仅核对失效入口和事实矛盾，保持工程规则定位，不扩写成用户教程。面向用户的“许愿编程并自动发布”工具另做。

### Phinix-Plugin-Index

README 最短路线：准备插件 → 提交申请 → 维护者审核 → 自动发布结果。作者和维护者分节，不能让作者以为应给自己的申请加批准标签。

1. **用途**：目录、准入记录和机器人，不是运行游戏插件的服务。
2. **作者提交**：现行模板入口、必填字段、可通过当前解析器的示例。版本、固定资产、摘要、依赖、兼容范围、多语言名称/简介/更新说明的来源分别说明；schema 以代码为准，不拼旧格式。
3. **审核**：静态检查反馈、人添加标签后的 PR/合入/发布/关闭过程；拒绝、关闭、撤销的实际行为由脚本确认。
4. **失败排查**：格式错误如何修改；异常标签、workflow 链接、修复和重试。区分提交检查与发布失败，不建议无依据反复加标签。
5. **更新边界**：自动源更新究竟修改什么、什么时候重新审批、何时锁定版本和摘要；不要将目录自动发布写成客户端自动安装。
6. **维护者配置**：Host module profile、依赖闭包、来源、排除规则和权限。说明这是维护者配置，不是作者自行降低校验。

优先整理已有 `GitHubBotGuide*`、`ControlledPublication*`、`SourceUpdates*`、`HostModules*`；README 作为导航。`packages/README.md`、`reviews/README.md` 与数据布局对齐，避免新建重复教程。

读 `.github/workflows/` 和 `scripts/` 的真实调用，核对事件、labels、权限、幂等、重试和成功判定。本轮不得触发真实发布或代人审核。

### Phinix-Plugin-Gateway

1. **作用与协议关系**：GitHub 是权威目录和固定资产来源；CF 提供适配访问、缓存及请求治理。核对两入口的协议/校验是否对等，不承诺网络绝对可用。
2. **公共入口与验证**：当前生产入口、只读请求、错误和诊断编号，不将 PoC 运维路径作为普通用户入口。
3. **部署**：README 链接已有 `DEPLOYMENT*`；配置项按真实 Wrangler 文件/代码列出账号、域名、绑定、allowlist、权限、秘密注入，不抄历史测试资源名。
4. **维护与回滚**：只读状态检查、日志、GitHub 回源与 Worker 故障区分、选择已验证版本回滚。写步骤，不执行部署/回滚。
5. **限制与成本**：真实生产是否启用 R2、DO、预算/限流；哪些代码只是实验，不能因存在源码就称已启用。

保留 `AUDIT*`、`ops/README*`、fixture 文档的证据；首页链接即可。区分现行维护路线与历史实验，不删除未知恢复资料。

### Phinix-Example-Plugin

1. **用途**：展示当前真实示例功能；不要沿用 Playtest “生成白银”说明。
2. **玩家体验**：安装、重启、Tab、设置、计数等实际操作。
3. **源码导览**：入口、发现/注册、生命周期、Tab、设置、语言、存储分别在哪个文件，用小表，不逐文件机械复述。
4. **最短开发路线**：改文本/名字 → 构建 DLL → 打包 → 校验 → 固定发行 → Index 申请。命令按实际项目/脚本，不复制 Rework 全量构建。
5. **包结构**：真实目录树，区分开发目录、ZIP 内布局和安装后目录；说明 manifest、DLL、Resources、语言和摘要。
6. **本地化**：单语言也有效；多语言按当前 resolver 选择和回退。区分目录元数据和插件 UI 文案；缺 key、格式参数行为按代码说明。
7. **改成自己的插件**：包 ID、模块 ID、程序集/命名空间、资源作用域、版本必须改哪些；宿主 DLL 只引用不随包分发。

Example 提供可复制短路线；完整协议/审批链接 Index，框架 API 链接 Rework，避免三仓重复大段格式。

## 写作与中英文要求

首页开头一两句回答“是什么、谁会用”，接着最短使用路径、常用操作、必要限制、求助和开发入口。不要让徽章、巨大目录、架构宣传挡住安装步骤。玩家、作者和维护者的内容逐层链接；既不全藏，也不全堆首页。

用行为和条件写句子，少用口号。去掉无依据的“生产级、零配置、全自动、绝对安全、开箱即用”；不要将“本批、阶段 S2、C1/C2、通过 N 条断言”搬到用户文案。日期流水账、commit 和测试数量归 PR/维护记录。

不重复总结、不堆形容词、不层层嵌套列表；章节名用“安装、使用、开发、排查”。顺序操作用编号，比较/字段用表格。自然表达不能删掉限制、依赖、旧服务归属、署名、许可证和恢复注意事项。

| 避免 | 建议 |
| --- | --- |
| 打造生产级可扩展生态 | 在商店安装 Phinix 插件，重启后使用插件功能。 |
| 全链路自动化闭环 | 维护者批准后机器人发布目录，失败信息留在申请 Issue。仅在代码确认时使用。 |
| 双源无缝智能加速 | 可手动切换 GitHub 直连与 CF 加速，两种方式读取同一目录。 |
| 1693 条断言证明稳定可靠 | 首页不写；PR 说明实际检查及尚未做的游戏测试。 |

两语言结构、能力、限制、命令、链接一致；英文自然表达，不机械逐字翻译。术语统一：Phinix managed plugin/Phinix 托管插件，extension manager/扩展管理，GitHub direct/GitHub 直连，CF acceleration/CF 加速。UI 名称以实际语言资源为准。

命令、schema key、ID、文件名不翻译。公开命令用 `<path-to-repository>`、`<RimWorld-managed-directory>` 占位符并解释替换方式，不贴个人 `/home/...`/Steam 路径。示例版本不是永久兼容承诺。

## 用哪些 CLI 工具

| 工具 | 用途 | 本轮限制 |
| --- | --- | --- |
| `git` | 检出、分支、diff、提交、推送 | 新工作目录，保留用户脏工作区。 |
| `gh` | 查仓库/Release/Issue/PR/CI，创建草稿 PR | 不改权限、不审批、不合并、不触发发布。 |
| `rg` | 搜索实际代码/入口/过时说明 | 按文件范围搜索，避免打印敏感配置。 |
| `python3` | 相对链接、文件存在、双语结构及 JSON 检查 | 仅辅助文档验证。 |
| `dotnet` | 必要的 C# 构建/工具参数验证 | 缺游戏依赖时只核查源码/参数，明确未运行。 |
| `node`/`npm` | Gateway 现有本地检查 | 按 lockfile 和已有脚本，不盲目升级依赖。 |
| 项目自带 `wrangler` | 配置/帮助核对、编写部署指南 | 不上传秘密、不部署、不迁移/删除资源。 |

当前机器已找到 git、gh、dotnet、python3、node、npm。其他模型的机器自行检查。GitHub CLI 是主要远端工具，不需要 computer use，也不需要 CF 写权限。

`gh auth status` 用于登录检查；禁止 `gh auth token` 或打印环境变量全集。代理沿用用户配置，只报告可达/错误类型，不展示认证代理 URL。没有 git/gh 可说明缺项并让用户安装或用 GitHub 网页交付，不在文档任务中发明自动发布工具。网络受限就注明无法核查的状态。

## 单仓操作流程与命令

以下以 Example 为例，逐仓替换名字。选择新的父目录，已有同名目录先停下核查，不覆盖。默认分支通过 API 确认，不靠猜。

```sh
git --version
gh --version
gh auth status
gh repo view HunYuan2333/Phinix-Example-Plugin --json nameWithOwner,defaultBranchRef,url
gh repo clone HunYuan2333/Phinix-Example-Plugin Phinix-Example-Plugin-docs
cd Phinix-Example-Plugin-docs
git status --short
git rev-parse HEAD
git switch -c codex/docs-user-guide
gh release list --repo HunYuan2333/Phinix-Example-Plugin --limit 5
gh run list --repo HunYuan2333/Phinix-Example-Plugin --limit 5
rg --files -g '*.md' -g '*.csproj' -g '*.py' -g '*.yml' -g '*.json'
```

先交提纲/事实表。用户确认后改文档，再检查：

```sh
git diff --check
git diff --stat
git diff -- README.md README.zh-CN.md
git status --short
```

确认文档修改和 PR 交付获授权后，仅逐个暂存审阅过的文件，不用 `git add .`：

```sh
git add README.md README.zh-CN.md
git diff --cached --stat
git diff --cached
git commit -m "docs: clarify installation and plugin development"
git push -u origin codex/docs-user-guide
gh pr create --repo HunYuan2333/Phinix-Example-Plugin --draft \
  --title "docs: clarify installation and plugin development" \
  --body-file /tmp/phinix-example-docs-pr.md
```

PR 说明先写到文件，包含范围、事实依据、实际验证和待确认事项。Rework 暂存 `.github/README*`，其他深层文档按批准清单加入。本任务书没有执行推送、创建 PR 或合并。

验证相对链接和图片从文件所在目录计算，特别是 `.github/README*`；检查双语互链、跨仓目标和 GitHub 渲染。不存在的文档标待补，不生成虚假链接。不要安装与文档无关的依赖或跑全套游戏测试。

教程命令优先核对帮助和源码。只读检查可运行；本地打包/构建用隔离输出。发行、审批、部署、回滚写成步骤但不执行。依赖游戏/身份而无法验证时，明确只做参数核对，不谎称运行成功。

## 两轮交付与验收

第一轮：每仓读者/问题/拟改文件；章节提纲与内容迁移；事实表及分支/提交；本地/远端差异；必要待确认事实；最终双语/术语/链接校验方案。等用户审查再改正文。

第二轮：每仓独立草稿 PR、简短改写说明、实际验证、未核实事实。陌生读者能从文档完成自己的最短路线，能力与目标代码/公开版本一致，是验收标准；不以篇幅、排版或“已去 AI 味”的自评替代。
