## 修复前基线发现

1. **P1：收到市场人才时缺少匹配交易和可信发送者门槛。** `TalentTradeManager.cs:846` 的 `HandleMarketSell` 核对消息里的买方 UUID 是否等于本地 UUID，然后删除一个待购 ID 并入队物化 Pawn。它没有先要求该 ID 确实存在待购记录，也没有把卖方绑定到可信事件发送者及预期挂牌。消息入口已有进程内去重，不能把它当成鉴权或主动购买证明。若未授权/被修改的消息能进入中继，可能触发非主动请求的数据处理或交付。未做远程攻击验证，服务端是否另有身份保护未知。

2. **P1：HTTP 明文，客户端没有可信消息来源验证。** `TalentTradeTransport.cs:13–15` 使用 HTTP、共享房间和空 key。GET/POST 没有 TLS；出站身份是客户端填写的头，入站只传递解码后的正文，没有经验证的发送者上下文。业务处理核对正文 UUID，未发现客户端密码学验签。可确认客户端缺少这些保护，不能据此断言服务器允许任意公网写入或管理员访问。鉴权、来源限制及限流须向原服务方确认。[OWASP REST 指南](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)建议 HTTPS 和载荷上限。

3. **P1：响应和解压数据缺少字节上限。** `TalentTradeTransport.cs:150–157` Base64 解码和 GZip 解压后直接 `ReadToEnd`；`:274–278` 的网络响应也是不限字节读取。拉取条数、队列条数上限不能限制一条消息或解压后 XML 的大小。异常大或高压缩率的数据可能耗尽内存，或卡住游戏主线程解析。`PawnDeserializer.cs:73–103` 随后加载 XML 并进入 Scribe。本次没有证实任意代码执行或 XML 外部实体漏洞，仍须明确限制 XML/解压大小和解析工作量。

4. **P1 发行门槛：人才/物品所有权仍有旧版互信及恢复证据不足。** `TalentTradeManager.cs:887–891` 的 `HandleMarketPaid` 明确没有完成付款确认，市场仍依赖互信。传输队列溢出丢最旧消息，重试可能改变顺序，首次只取最近 20 分钟历史。已做的返还台账保留不确定记录，不等于完整、权威确认且持久的购买/交付协议。真实缺包重新保存、晚加载组件以及独立安装后的人才恢复仍未证实。这些是原有协议风险，不是仓库公开才产生。

5. **数据边界。** `PawnSerializer` 用 Scribe 序列化所选 Pawn，再 GZip/Base64；会传输人物状态，不是加密，也未发现整份存档上传。交易/租赁消息还包含参与者标识、显示名和兼容 Def 信息。服务方能收到这些消息，HTTP 链路也存在被途经节点读取的风险。新返还审计只记录有界/转义后的 ID、结果，不记录 Pawn 载荷；旧调试/异常日志可能包含 ID、名称和异常细节，不能一概称为凭据泄露。

## 接下来怎么处理

- 向原服务方确认 HTTPS、写入/身份/房间鉴权及限流、历史保留和确认保证；确认前不擅自换端点或改变旧客户端互通。
- 客户端可先补响应、编码/解码字节、GZip 输出、XML 大小/解析工作的限制；删除记录或入队交付前检查真实待购请求、预期卖方/挂牌和完整载荷，保持整批语义。加非主动交付、错误对方、超限/解压膨胀和失败保留回归。比较 UUID 或算 hash 本身不能证明远端身份。
- 源码/静态 CI 与游戏、服务端安全验收分开记录；不代加 `plugin-approved`，不把 v1.0.0 宣称为已获生产安全验收。相应本地修复和服务/游戏门槛记录后再继续正常准入；标签仍由用户亲自添加。

最初审计批次只读源码和官方安全指南，写入双语审计/计划记录。没有改协议、端点或业务代码，没有访问旧中继，也没有攻击或游戏测试；代码未变，不重跑构建/回归。主体脏工作区未提交，没有在本文记录任何密钥值。
