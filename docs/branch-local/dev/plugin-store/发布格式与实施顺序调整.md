## 哪些需要改

分发链继续使用作者 GitHub Release 固定资产 → 受校验目录快照 → CF 固定来源网关 → 客户端。语言只影响展示，不改变包 ID、模块 ID、程序集身份、依赖标识、资产摘要或安装归属。

| 层 | 改动与原因 |
| --- | --- |
| 目录格式 | 给各版本增加多语言显示名称、简介和 changelog，定义默认语言、逐字段回退及大小限制。现有 v2 严格拒绝额外字段，必须显式升级格式。 |
| 客户端 | 改目录模型、stable/published 格式分派、网络与缓存读写/连续性校验，以及列表、搜索、详情、语言切换后的显示缓存。仅接受新 v3，不实现旧 v2 读取或迁移。 |
| 发布工具 | 作者元数据输入、目录生成器和发布前检查产生相同格式；描述中的 catalogSchemaVersion、目录摘要/字节数同步更新，仍最后发布 stable。 |
| CF Worker | 接受明确的新目录版本，并正确按托管包模式选择资产。目前 selectedPackage 仅将 schemaVersion=2 识别为托管路线，单独放宽版本白名单会选错包格式。固定路由与资产身份检查继续保留。 |
| GitHub 机器人 | 更新可信校验器源码快照及来源摘要、申请表/示例、语言有效性和发布检查；A1 的现有 v2 检查继续有效，不表示它已支持新格式。 |
| 通用客户端抽象/宿主 | 增加按包隔离的资源与翻译能力，让内置、官方和第三方插件用同一接口获取 UI 文本；商店停用不影响其他已装插件的翻译。 |

第一批拟采用显式目录 v3；最终字段名和版本号在 R1 冻结。stable/published 外层 v1 与 `/v1/sources/...` 路径没有仅因多语言而升级的必要，升级的是它们声明/接受的 catalogSchemaVersion。托管 manifest v1 已有 Resources 文件声明，优先用它承载语言资源；语言文件的解释与宿主能力单独定义，只有现有声明确实无法表达必要信息时才讨论 manifest 升版。

## R1：先冻结展示与语言契约

- 作者按语言提供 JSON，含 display 与 UI strings；发布工具提取 display 到 localization.translations[locale] 的 name/summary/changelog，加可选 defaultLocale。manifest 规范信息与显示名分开，不保留目录旧顶层 name/summary 的兼容映射。
- 一种语言即有效，允许仅 en-US、仅 zh-CN 或其他支持的标识。不要求英语/中文齐全；可选默认语言必须实际存在。
- 精确匹配 → 合适的同语言变体/基础语言 → 可用英语 → 作者默认 → 稳定顺序的可用内容；逐字段/逐 key 回退。规范化后重复标识要拒绝，地区/文字体系规则写清楚。
- UI 资源格式、key/占位符与长度规则、宿主游戏语言映射和生命周期边界一起确定。译文不成为保存、协议、审计或身份字段。
- 产物为中英文格式说明、单语言/多语言/非法数据样例和验收矩阵。开发期旧输入按新结构重建，不做兼容过渡。

## R2：贯通新旧格式的解析和发布检查

按最新决定，先完成下一节宿主语言核心/应用，再同步客户端纯数据解析、缓存、目录生成/校验、CF 版本分派和可信机器人校验器。客户端只接新 v3；旧缓存作无效浏览缓存处理，不实现 v2 读取或迁移。固定资产、摘要、资源归属与事务检查保留。

开发环境读写两端一起替换，更新样例和测试来源。用同一组语言样例核对宿主、商店、Worker 与机器人，验单/多语言、无目标语言、被篡改/超限数据、离线新格式缓存及发布失败保留有效指针。

多语言元数据可以为已有不可变 ZIP 发布新的目录快照，不重写原版本资产/manifest，也不改变其摘要。首次增加包内 UI 语言文件则发布新的包版本与新 ZIP。

## R3：完成通用 UI 本地化并做一次游戏验收

本节优先于 R2 数据链实施；把 M6b 的通用资源/本地化部分提前；人才贸易的存档迁移仍保留在拆包前置阶段。契约放在 ClientExtensionAbstractions，宿主只提供通用服务，不依赖商店实现。验证已声明资源的有界读取、包隔离、逐 key 回退、主线程游戏语言读取、语言切换通知与 shutdown 清理。

通过新增可选服务契约接入，不给现有第三方必须实现的接口增加成员。使用新服务的包声明相应最低宿主版本；旧包继续走原有发现/注册路径，不放松程序集引用检查来伪造兼容。

先让 Playtest 使用通用接口，单语言包和多语言包均测试 Tab、按钮、提示、切语言、重启以及商店关闭后插件显示。沿用已经通过的基本安装/卸载线路，测试重点是新增的资源与翻译行为。本阶段需要游戏测试。

## R4：统一商店交互与界面

在稳定模型与翻译接口上做同包版本分组/选择、单“安装”入口、依赖确认、字节/阶段进度、简介/changelog、清晰的错误/待重启状态与布局。加入启动后台更新提示：只查受校验元数据，不自动下载或更新。游戏验收版本选择、无/有依赖安装、确认/取消、进度、断网/重试、语言切换和离线启动。

“有新版”提示与正式版本替换分开交付。当前安装器不支持原位升级；暴露“更新”按钮前另做版本替换事务、依赖变化、归属校验与中断恢复验收，数据兼容不能由代码回退推定。

## R5：完成机器人收录与受控发布，再开启自动版本监控

保留已上线 A1。R1/R2 格式冻结后，机器人开发可与 R3/R4 独立推进：

1. A2：维护者批准固定候选指纹/来源政策，机器人产出条目 PR 与永久审核记录；补写权限及仓库保护。
2. A4 受控发布：先人工触发可信发布器，串行核验批准输入、生成完整目录、上传/核验固定 Release，最后更新 stable；验并发/失败恢复和隔离来源上的真实客户端下载。此时不需要先开启 A3 无人值守监控。
3. A3：在已批准来源/政策内监控普通新版本，用同一检查器/发布器自动处理；身份、同版本字节或政策变化进入复核。受控发布验收通过后才开启无人值守发布。

A 编号保留原功能划分，工程实施顺序调整为 **A2 → A4 受控链 → A3 自动化**。首次上架与政策变化仍有人判断，正常版本通过既定规则后不要求逐版人工批准。
