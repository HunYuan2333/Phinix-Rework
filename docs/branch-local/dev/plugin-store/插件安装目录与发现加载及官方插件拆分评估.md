本文补充 [商店总体设计](插件商店可行性评估与功能设计.md)，回答 GitHub DLL 包安装位置、当前发现/注册/加载顺序是否需要修改，以及红包、人才贸易作为官方可选扩展改为独立发行的工程边界。依据为 [设计哲学](../../../Design-Philosophy.md)、[开发者指南](../../../Phinix附属Mod开发者指南.md)、[兼容与恢复边界](../../../Compatibility-Boundaries.md) 及下列源码。建议不表示已决定包布局或已经完成迁移。

## 1. 结论

本文“官方插件拆分”的准确产品语义为：**两个官方可选扩展从随主包打包改为独立发布**；基础功能继续由内置功能模块提供，二者都是统一机制中的扩展模块。文件名中的历史称呼保留；产品角色、发行状态和技术对象详见 [术语与功能分层](术语与功能分层.md)。不因术语变化改变现有禁用、注册或数据身份。

**建议下载成独立本地 RimWorld 模组，不写进当前 Phinix 的 `Common/Extensions`。注册流程已有依赖排序，可复用；DLL 解析和冲突诊断需要加强。** 红包、人才贸易已经是独立扩展工程，拆出发行包可行，但还需改构建发布、资源归属和旧版迁移，不能只停止复制两个 Client DLL。

| 问题 | 判断 | 建议改动规模 |
| --- | --- | --- |
| GitHub 下载到哪里 | 优先玩家本地 `Mods/PhinixStore_<包标识>/`，每包独立 About、Assemblies 和资源 | 商店安装器新增；下载目录不是仓库源码 `Extensions/` |
| 是否用当前 `Common/Extensions` | 保留为现有主包中基础功能模块的发布位置，不作为自动下载目标 | 不直接改写 Phinix/工坊主包 |
| 插件发现 | 已扫描活跃独立模组并发现已加载模块，基本路径可复用 | 核对加载时机、版本目录、源身份与反射失败诊断 |
| 注册/激活 | 已按模块 `DependsOn` 拓扑排序，关闭逆序 | 不重做生命周期；校验依赖声明并保留失败传播 |
| DLL 加载顺序 | 当前文件排序只提供探测顺序，不能代替程序集依赖解析 | 先建立候选索引/解析器，再加载；用程序集身份而非编号管理依赖 |
| 红包/人才贸易拆包 | 业务入口已有，发行边界尚未独立 | 分包构建、清理旧残留、资源迁移、数据与存档回归 |

文件名编号可在现有主包启动链中暂时保留兼容用途；**不能继续要求商店所有作者申请全局 `17+` 编号，也不能直接删除所有编号后宣称已解决加载问题。** RimWorld 先于 Phinix 宿主执行的加载阶段需要另行验证。

## 2. 当前实际运行链路

### 2.1 三种“Extensions 目录”不是同一个东西

- 仓库 `Extensions/`：插件源码工程目录，不是玩家机器上的下载目标。
- 发布包 `<PhinixRoot>/Common/Extensions/`：目前由各插件工程 AfterBuild 写入的平铺 DLL 目录。
- `framework-extensions/client`：宿主传给扩展存储提供者的业务数据根，不是当前 DLL 探测目录，也不能直接当成安装目录。

当前仓库没有商店的下载/安装实现。[Client.cs](../../../../Client/Source/Client.cs) 在构造宿主时调用 `GetExtensionProbeDirectories` 和 `ExtensionAssemblyLoader.LoadAssemblies`；目录来自宿主程序集位置或模组根、主包 Common 目录、应用基目录，以及 `ModLister.AllInstalledMods` 中活跃模组根下的 `Assemblies/`。它不是递归扫描任意下载目录的机制。

第三方模组探测条件是 `mod.Active`，源码没有检查“必须排在 Phinix 之后”；开发者指南中相应描述比这段代码更强。实际游戏加载仍应在 About 中声明 Phinix 前置与 `loadAfter`，但不能把这些声明与这段目录筛选逻辑混为一谈。

### 2.2 DLL 加载与模块注册已分开

```text
RimWorld 模组加载阶段：About / LoadFolders / Assemblies
  → Phinix Client 构造：补充探测 DLL
  → 扫描 AppDomain 中已加载的候选程序集和模块类型
  → ExtensionDependencyGraph：重复 ID / 缺失依赖 / 环路检查
  → 激活策略：禁用项和依赖禁用项不实例化模块
  → 依赖优先实例化并 Register
  → 按已登记模块顺序 Activate
  → Shutdown 反向顺序
```

[PhinixExtensionRegistry.cs](../../../../Common/Utils/Framework/PhinixExtensionRegistry.cs) 读取已加载程序集中的候选类型；[ExtensionDependencyGraph.cs](../../../../Common/Utils/Framework/ExtensionDependencyGraph.cs) 根据特性中的模块 ID 和 `DependsOn` 建图，`GetStableTopologicalOrder` 决定 Register 顺序。无依赖约束的节点使用类型全名作为稳定次序，不按 DLL 文件名决定业务优先级。Activate 沿已成功登记的模块列表执行；Shutdown 逆序。

因此，**文件名前缀问题主要发生在类型可见之前的 DLL 加载层。** 模块依赖图不能拯救尚未加载成功、因缺 DLL 而无法枚举的类型；反过来，先加载一个 DLL 也不表示它的模块已经先激活。

## 3. 安装位置：推荐独立模组包

### 3.1 首选布局与文件归属

以下是建议布局，目录标识和 packageId 需在发行规范中最终确定，不是已经创建的文件：

```text
<已确认可写的 RimWorld 本地 Mods 根>/
  PhinixStore_<红包包标识>/
    About/About.xml
    Assemblies/LegacyRedPacketExtension.dll
    Assemblies/LegacyRedPacketExtension.Client.dll
    Languages/<语言>/Keyed/LegacyRedPacketExtension.xml
  PhinixStore_<人才贸易包标识>/
    About/About.xml
    Assemblies/LegacyTalentTradeExtension.dll
    Assemblies/LegacyTalentTradeExtension.Client.dll
    Languages/<语言>/Keyed/LegacyTalentTradeExtension.xml

<Phinix 主包根>/Common/Extensions/
  Chat / Trade / Inventory / LegacyAdapter 的现有 DLL
```

纯 DLL Release 可以在有完整元数据时生成最小 About/Assemblies 壳；这两个官方插件都有自己的契约和语言内容，建议直接发布轻量 ZIP，减少运行时拼装。它们独占的 Contracts DLL 随各自包发布；框架、游戏和已由主包提供的共享依赖不能再随下载包复制一份。

商店先缓存和完整校验，再在目标文件系统的非扫描暂存位置准备包，最终提交到每个独立目录。用户随后在 RimWorld 模组列表启用并重启；当前设计不直接激活刚下载的 DLL。缓存、业务数据与最终模组目录分别记录，不把暂存文件置于主包的探测范围。

**不要把 `<PhinixRoot>/Common/Extensions` 当作“主包同级 Mods 根”的定位依据。** Phinix 可能安装在工坊目录；本地 Mods 根应来自已核实的游戏路径 API或用户明确选择，并校验是否属于可写本地模组根。若必须新增路径信息接口，应是客户端通用只读能力，不向宿主加入商店专属安装方法。

### 3.2 其他方案的代价

| 位置 | 主要问题 | 本轮建议 |
| --- | --- | --- |
| 当前 Phinix `Common/Extensions` | 主包/工坊更新可能覆盖；没有独立模组启用边界；同名 DLL 与文件归属难管理 | 仅兼容已有手动投放，不作为商店默认写入点 |
| 独立本地模组的 `Assemblies` | 游戏会参与加载，需要 About 前置、启用和真实游戏验证 | 首选；复用当前第三方入口 |
| 用户数据下自建 `Plugins/<id>/<version>` | 当前不扫描；没有原生模组身份/资源加载；一般 patch 和 GameComponent 不能仅靠扩展加载器保证行为 | 仅在独立模组路径确实不能满足时另立方案 |

目录隔开可以简化文件回滚和卸载，但程序集最终仍在同一游戏进程，不构成版本隔离或安全沙箱。选定源、包 ID、版本、packageId、模块 ID、程序集身份和文件摘要均需记录；本地目录名不代替这些身份。

## 4. 发现机制需要哪些修改

**无需为了两个独立模组新增“官方专属发现路径”。** 已有活跃模组 `Assemblies` 探测和 AppDomain 类型扫描可复用；首批官方包建议使用根 `Assemblies/` 的简单布局。

需要在独立发布前核实或加强以下通用行为：

1. **加载时机与有效目录**：当前补充探测只拼根 `Assemblies`，不按第三方 `LoadFolders.xml` 求版本目录。游戏已经加载的版本目录 DLL可被后续 AppDomain 扫描发现，但“已加载”与“该目录得到补充解析支持”不同。根目录与 `1.6/Assemblies` 两种布局都要实测；如需增量，应基于游戏实际生效目录/已加载模组程序集建立索引，而非递归扫描所有版本。
2. **失败可见性**：`getLoadableTypes` 捕获 `ReflectionTypeLoadException` 后只保留可用类型，没有把各 `LoaderExceptions` 转成完整模块诊断。商店可能出现“文件在、插件不见”的情况。建议报告包、程序集及缺失引用，不通过重复改文件编号猜原因。
3. **来源归属**：`ResolveModPackageId` 按程序集路径 `StartsWith(rootDir)` 匹配，没有目录边界检查，且 `Assembly.Location` 可能为空。建议用规范化的目录边界判断和游戏模组程序集归属记录；商店安装记录只作补充证据，不伪造运行状态。
4. **发现与下载解耦**：下载完成写安装记录，下一次正常启动发现模块。商店关闭或卸载不影响已装插件正常启动。运行状态查询可沿主文档的通用只读目录提案，不能由商店直接操纵宿主私有注册器。

当前注册扫描覆盖 AppDomain 中符合条件的已加载程序集，文件探测的 `Active` 筛选并不等于运行时沙箱。若未来限制模块来源，应独立设计与第三方兼容的通用策略；本轮不增加默认来源白名单或官方特权。

## 5. 加载顺序：保留已有模块图，加强程序集解析

### 5.1 四层依赖各管什么

| 层 | 依据 | 解决的问题 |
| --- | --- | --- |
| 商店安装计划 | 包清单中的版本/包依赖 | 应下载哪些包，版本约束是否可满足 |
| RimWorld 模组加载 | About 前置、loadAfter、有效 LoadFolders | 哪些模组启用、游戏加载与资源可用条件 |
| DLL 解析加载 | 程序集真实身份及引用元数据 | 哪个物理 DLL 满足某个 CLR 引用 |
| Phinix 模块生命周期 | ExtensionId、DependsOn | Register/Activate 顺序、禁用/失败传播和逆序关闭 |

商店包版本与 DLL 的 AssemblyVersion 不是同一个字段；下载一条包依赖也不自动增加模块 `DependsOn`。清单/About/程序集引用/模块声明应一致校验，但不能合并为一个万能依赖图。

### 5.2 当前加载器的具体限制

[ExtensionAssemblyLoader.cs](../../../../Common/Utils/Framework/ExtensionAssemblyLoader.cs) 的现状：

- 每个探测目录只读顶层 `*.dll`，按文件名忽略大小写排序；目录之间没有程序集引用排序。
- 首次调用先 `tryLoadAssembly` 全部候选，再重建缓存和注册 `AssemblyResolve`。第一次加载所需的解析支持可能尚未就绪，失败是否发生取决于运行时何时解析引用，不能假定必现，也不能保证没问题。
- 缓存按文件名或剥掉数字前缀的名称建立，不是按 DLL 的真实 `AssemblyName` 建立；同键候选会被覆盖，没有明确报告冲突。目录集合和文件枚举不提供跨目录冲突的可靠优先规则。
- `AssemblyResolve` 主要按请求的简单名称找文件，没有核对完整身份、请求方与兼容版本。同名不同版本不能仅靠换目录或换前缀解决。
- 已加载程序集只要简单名称相同就跳过，不报告其版本、路径或是否与候选内容一致；旧主包副本可能遮住新下载副本。
- 缓存只在首次挂接解析器时重建，后续新增目录虽有慢路径，但快路径可能保留旧归属；当前设计并无可靠热更新保证。

这些限制支持用户对“编号不可靠”的判断。但这不是“现有 Register 也靠编号”或“任何无编号 DLL 必定失败”的证据。

### 5.3 推荐的有限加载器增量

1. **先完整收集，再加载**：收集允许探测目录，读取候选程序集身份/引用与归属，建立索引，并在首次候选加载前挂接解析器。单个坏 DLL 不能让整个候选清单建立失败。
2. **按真实程序集身份解析**：至少记录 Name、Version、Culture、PublicKeyToken、规范路径及包归属，使用请求方帮助定位。读取未安装包的引用元数据采用静态 PE/元数据工具，不通过执行插件入口验证。
3. **冲突明确失败**：同身份、同摘要的重复文件可诊断为重复；同名且不同版本/内容不选“枚举碰巧最后一个”，报告涉及包。已由游戏加载的程序集也要比对；冲突不能卸载单个 DLL修复，应停止受影响模块并要求退出处理。
4. **依赖优先加载只是辅助**：可按候选引用关系生成稳定顺序，已由游戏/框架提供的依赖视为外部已知项；涉及程序集循环不能直接套模块环路规则，要给出诊断并依据实际解析策略处理。可靠解析器和身份一致性比维护全局数字队列更重要。
5. **限制解析器职责**：只处理已识别候选，未知请求返回 null，避免递归解析和抢占其他模组绑定。明确处理缓存更新，不向游戏全局注册无限目录或扫描器。

Microsoft 的说明支持使用 `AssemblyResolve` 在正常绑定失败时解析已知引用，并可利用 `RequestingAssembly`；不应接管未知程序集或递归调用导致再次失败的按名加载。[程序集解析规则](https://learn.microsoft.com/en-us/dotnet/standard/assembly/resolve-loads) 多版本与加载上下文可能造成类型身份冲突，独立文件夹不能自动隔离。[程序集加载实践](https://learn.microsoft.com/en-us/dotnet/framework/deployment/best-practices-for-assembly-loading) 这些是 CLR 设计依据，仍需在目标 Unity/Mono 验证。

**范围限制**：上述增量发生在 Phinix `LoadAssemblies` 阶段，不能倒过来修复 RimWorld 更早的程序集加载和类型枚举。现有主包基础 DLL 编号和包内少量编号先作为兼容措施保留；只有真正通过“不依赖文件名前缀”的游戏验证后，才能调整发行规范。不要把排序替换成一个拓扑函数就声称彻底解决。

## 6. 注册流程：保留入口与依赖拓扑

**无需增加 DownloadedPlugin.Register 或 OfficialPlugin 特殊通道。** 两个插件继续实现 `IPhinixExtensionModule`/`IActivatablePhinixExtensionModule`，沿原有特性、构造、Register、Activate、Shutdown。保留重复 ID、环路/缺失依赖、禁用依赖传播与注册回滚。

红包入口已有 `[PhinixExtension("builtin.legacy-redpacket", DependsOn = ...)]`，依赖 `builtin.trade` 与 `builtin.inventory`；在 Activate 解析库存 API并注册自身 codec/展示器。人才贸易当前只声明 `builtin.legacy-talent-trade`，主要从 HostContext 取通用服务，不能因为同样是交易功能就随意加 `builtin.trade` 依赖。

商店安装元数据应表达所需主包及兼容版本，红包还要检查基础模块存在并启用；主包自带依赖已满足时不重复下载 Trade/Inventory。服务器能力或外部中继可用性仍是运行条件，不因包存在就视为成立。人才贸易现有独立中继联网也不受商店专用代理配置控制。

**建议保留两个现有 ExtensionId、程序集名、命名空间和数据键。** `builtin.*` 只是现有身份字符串，不强制代表物理内置；不要因发行位置变化而改成 `official.*`。新增独立 RimWorld packageId 与商店包 ID即可；如果未来确需改旧身份，另做显式迁移，不顺手改名。

## 7. 两个官方可选扩展的拆包评估

### 7.1 已有条件与必须处理的差异

| 项目 | 红包 | 人才贸易 |
| --- | --- | --- |
| 当前入口 | [BuiltInLegacyRedPacketClientExtension.cs](../../../../Extensions/LegacyRedPacket/Client/BuiltInLegacyRedPacketClientExtension.cs) | [BuiltInLegacyTalentTradeClientExtension.cs](../../../../Extensions/LegacyTalentTrade/Client/BuiltInLegacyTalentTradeClientExtension.cs) |
| 模块 ID | `builtin.legacy-redpacket` | `builtin.legacy-talent-trade` |
| 独占发行 DLL | LegacyRedPacketExtension + Client | LegacyTalentTradeExtension + Client |
| 基础依赖 | 模块 Trade/Inventory；工程还直接引用 Trade.Client | 通用客户端契约、Utils、UserManagement；Harmony 游戏补丁 |
| 生命周期特点 | 库存 codec/展示器注册、事件、发送托管与未决状态 | Activate 挂补丁和定时器，Shutdown 解除；GameComponent 有额外游戏生命周期 |
| 持久化风险 | ExtensionId 下的 inventory-send 记录、`legacy-redpacket.template` codec、库存中已有载荷 | 存档中的挂牌 ID、pawn 数据、saveToken、待返还状态 |

两者不是宿主中的专用启动分支，本轮在宿主、客户端抽象和保留基础功能模块代码中未检出对它们的类型/模块名引用；各自工程也没有直接引用 Client 宿主 csproj。命名空间 `PhinixClient.*` 的出现不等于工程依赖宿主，需按实际程序集归属判断。

红包 [客户端工程](../../../../Extensions/LegacyRedPacket/Client/LegacyRedPacketExtension.Client.csproj) 直接引用 `TradeExtension.Client`，这是插件实现之间的现有耦合，不是 Host 反向依赖；主包暂留 Trade 时不阻断拆包，但兼容范围必须覆盖其 Client DLL。当前 codec 使用该程序集中的 `StatefulTradeItemProtocol`。将稳定常量/契约移入合适 Contracts 是后续解耦建议，不作为这次发行拆分的必做重构。

### 7.2 构建和资源归属必须一起改

两个插件的 Client 和 Contracts 工程 AfterBuild 都把产物复制到主包 `Common/Extensions`；红包 Client 还再次复制 Trade/Inventory 契约及 Trade.Client。未来应拆分“编译依赖”和“发行复制”：保留所需编译引用，独立官方包只装自己的文件，基础主包独立保障共享依赖。

至少同步四类发行规则：

- 四个插件工程的发布目标不再把红包/人才 DLL塞入主包，生成独立包产物；源码留在同一仓库并不影响插件平权，无需为了拆包强制拆仓库。
- 主包不包含这四个业务 DLL及其独占资源；[check-artifacts.ps1](../../../../.github/scripts/check-artifacts.ps1) 目前将四个 DLL列为主包必备项，未来改为主包禁止残留、独立包校验完整内容。
- [mono.yml](../../../../.github/workflows/mono.yml) 当前上传 `Output/phinix-rework/`；独立包增加单独产物和作者侧 Release 定位，官方索引仍只发布元数据。
- 两组中英文 Keyed 语言文件目前在 `Client/Languages`，主包复制所有语言资源；独占文本随各插件迁移，共用资源留主包，防止重复定义。Defs、贴图、版本通知与 Harmony 引用按实际使用清点；本轮未证明存在需要迁移的独占 Def/贴图，不凭文件名称批量移走资源。

**不能只改 AfterBuild 而复用旧 Output 发包。** 已存在的四个旧 DLL不会因为停止复制自动消失，应使用干净发行目录，并验收主包不含残留。最终包也不得携带游戏、Unity、框架或主包共享 DLL。

### 7.3 旧版主包迁移与业务数据

商店发现旧主包仍含同名程序集时，阻止并列安装新下载副本，说明需退出游戏并迁移主包；按简单名称跳过新 DLL不能视为更新成功。不能在运行中删除旧 DLL、自动停掉托管业务或改写工坊目录。工坊主包更新由 Steam 完成；手动主包建议换用干净新包，不在旧目录上只追加解压。

红包的 [发送记录](../../../../Extensions/LegacyRedPacket/Client/RedPacketInventorySendStore.cs) 属于未决物品托管；[codec](../../../../Extensions/LegacyRedPacket/Client/RedPacketInventoryCodec.cs) 解析既有库存载荷。保留模块 ID、codec ID、版本及存储路径规则，迁移不删除这些数据。插件缺失时原始载荷必须保留并提示缺少恢复能力，不能回退成普通物品或自动返还结果未知的发送。

人才贸易的 [TalentTradeGameComponent.cs](../../../../Extensions/LegacyTalentTrade/Client/TalentTradeGameComponent.cs) 保存待返还 pawn 等存档数据；它并非仅在 Phinix Activate 中创建。保留程序集/类型身份、Scribe 字段和设置键，还需实测老存档带新独立包加载。未安装插件就打开并重新保存旧存档，可能影响组件数据与后续恢复；不能宣称“取消内置只是入口变化，对存档零影响”。缺包存档的处置方案属于迁移决策，未在本轮默认启用自动修复。

建议发行前给已有用户清楚的先后顺序：退出游戏 → 备份主包安装与相关数据/存档 → 获取干净的新主包及两份独立插件 → 启用前置和所需插件 → 重启核对数据与功能。此为迁移建议，不表示商店首版已支持覆盖安装或已具备安全的通用存档迁移器。

## 8. 最小改动顺序与验收

建议分开验证而非同时重写加载系统和业务插件：

1. 为两个官方插件建立独立包清单、About、资源归属和发布目标，暂留主包基础 DLL编号；只改变发行边界，保持模块身份和业务行为。
2. 用干净主包＋独立包在真实 RimWorld 1.6 验证发现、注册、激活、禁用和老存档；先取得最小模组壳可用证据。
3. 对通用加载器做“先索引解析器、后加载”及身份/冲突诊断增量，旧入口保持兼容；再验证打乱文件名顺序、目录顺序和无前缀插件，不提前承诺全链无编号。
4. 接上商店下载与新包安装，按安装清单识别主包提供的依赖和旧残留，确认退出重启前不执行新插件。

| 场景 | 验收重点 |
| --- | --- |
| 干净主包，不安装两个可选插件 | 基础功能正常，不因缺可选业务 DLL导致宿主/基础模块加载失败 |
| 单独安装红包；Trade/Inventory 禁用或缺失 | 依赖优先、清晰阻断；不半注册 codec，不改变已有库存记录 |
| 单独安装人才贸易 | 通用服务可用，补丁/定时器随 Activate/Shutdown，不额外绑 Trade 模块 |
| 随机文件名顺序、根/版本目录、首次与后续解析目录 | 不将偶然加载顺序视为依赖满足；说明实际支持布局 |
| 旧主包残留与新独立包同名 DLL/重复模块 ID | 安装前阻断，启动诊断明确指出版本/路径冲突 |
| 重复共享依赖或版本不匹配 | 不悄悄任选 DLL，不复制主包 DLL补洞 |
| 老设置、红包未决发送/库存载荷、人才待返还 pawn 存档 | 身份与数据保留，不重复交付、不吞掉无法恢复内容 |
| 新发行包检查 | 主包无业务残留；独立包完整；全部产物无游戏/Unity 参考 DLL |

[Phase35RuntimeTests](../../../../Tests/Phase35RuntimeTests/Program.cs) 已有依赖优先注册/激活、反向关闭、缺失/环路及注册失败回滚的断言，未来改框架时沿最近 harness 扩展；程序集解析的文件候选、首次解析、重名冲突则补对应加载测试。红包/库存/交易的最近 harness 加迁移和缺 codec 场景，实际人才存档和补丁生命周期在游戏验收。这里说明应测内容，本次没有运行这些测试。
