Talent previously cleared pending records after enqueueing and overwrote them during saving. The return ledger now retains unresolved loaded records and merges them with current active-listing snapshots. Withdrawn current listings do not leave stale backups. Removal requires the local drop-pod API to return normally. Preparation/deserialization failure retains data; exceptions at the ownership boundary retain raw data with uncertainty and block automatic replay on reload. Duplicate IDs and malformed pairs are retained without materialization. Missing live cache retains previously captured data but marks ownership uncertain, never authorizing replay from cache absence; unavailable data retains its listing ID and a diagnostic.

Callbacks check active state and exact Game/component ownership; stale work cannot enter another save. Queue overflow rejects new work instead of evicting accepted ownership callbacks; rejected returns retain their payload. Cosmetic failures after delivery cannot create a retry. Structured `talent.pending_return` audits include bounded/escaped IDs, save token, time and reason; abnormal outcomes are warnings and never contain serialized pawn data.

Keep existing identities and dependencies. RedPacket depends on actual Trade/Inventory APIs and Trade.Client, its own Contracts, abstractions/UserManagement/Utils; only its own DLLs/resources belong in a future package. Preserve module/codec/settings/storage IDs. Talent has no invented Trade dependency, retains its assembly/type/Harmony/GameComponent/settings identities and old Scribe fields, and adds `pendingReturnUncertainIds`.

The uncertainty field is save-local recovery state, not a separate durable transaction journal; queueing/marking does not prove disk persistence.
