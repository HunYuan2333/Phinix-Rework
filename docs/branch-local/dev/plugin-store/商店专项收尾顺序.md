### 正常用户体验的收口

普通用户不能看到测试源、旧开发迁移入口和手动解析/下载不安装的前置操作；保留必要错误原因、排查编号、取消/重试、待重启、版本选择和作者 changelog。现有实现先核查，只有剩余问题进入 S0/S5，不另开全量 UI 重写。

列表/详情的易用性、长文本、窗口缩放和状态反馈属于商店收尾。纯视觉再设计按实际反馈控制范围，首版继续不加远端图片。已完成的全量响应式迁移不重做。

## 3. 安全门槛与不阻塞事项

- 商店所需安全修复前移：线程错误、失败清理、日志凭据泄露、发送未知结果、重复交付/返还、丢物品或 pawn，一经证实先修。不能为赶拆包而删掉恢复状态或前置检查。
- 宿主只提供通用挂载点；模块、业务状态和协议细节仍归插件。生命周期、确认及数据归属遵循[设计哲学](../../../Design-Philosophy.md)与[兼容边界](../../../Compatibility-Boundaries.md)。需要新公共能力时同步中英指南和最接近的回归。
- S3/S4 每个包发布前，当前代码必须满足该包的持久托管、权威确认、资源及存档门槛。可以继续现有实现，不要求先引入 Autofac/Polly/Stateless/SQLite；编译或 Tab 注册不能证明业务安全。
- **旧 PoC 永久删除独立处理。** 自动审批此前拒绝具体删除，DO 完整备份缺失；当前已停用公开访问，保留资源不会阻塞 S1—S5 功能交付。未经具体批准不删除、不绕过拒绝、不把删除标成完成。
- 仓库发布、源码公开和索引准入按实际可审阅范围办理。作者工具不能替维护者批准首次收录；人测也不能由自动 harness 结果代替。

## 4. 商店完成判定

必须分别记录：S0 增量验收、S1 独立源码与正式发布所有权、S2 资源/存档能力、S3/S4 两个真实独立包及正规上架、S5 干净发行/升级和适用人测。每批记录输入提交或文件摘要、实际命令/结果、包内容、审计、回滚点和剩余限制。

**红包和人才仍在主包里时，不能称本轮商店相关工作全部完成。** 两包独立可用、主包残留清理和旧数据保护均通过后，才转入其他专项。旧 PoC 删除待批、暂留域名别名或未声明平台的覆盖缺口单列状态，不能隐藏，也不等同于必需功能未交付。

## 5. 本轮不启动的后续候选

主 Common/Client/Server 三仓、全面宿主/DI 重构、HTTP/状态机换库、全面测试 runner 迁移、旧客户端服务端兼容专项、SQLite、聊天图片/WebP、AI 作者 CLI/API 与 AGENTS/skill，均保持计划，不插入当前主线。商店确实需要的最小宿主修复及业务恢复工作仍属于 S2—S4。

多仓 README 风格整理仍由用户安排其他模型；现行技术入口随实际迁移修正，不代做整套文案重写。商店全部收尾后，再复评[其他专项顺序](../后续实施计划.md)，不把旧表中的顺序当成现在的实施授权。

**当前下一步是 S2/S4：已交付人才保护的人测、购买/存档持久恢复，以及红包所需的通用 Host 模块准入政策。** Issue #22 已可审阅，代理不加批准标签。不先拆主三仓、不先换库；后续人测随对应可用构建明确告知。

## 拆分后必须做的耦合审查

两插件独立发行后，按设计哲学检查新加的 Store、托管运行时、索引机器人和 Gateway：Host/抽象/插件依赖方向、发现/注册/生命周期平等性、策略与数据归属、来源 adapter、主线程快照/派发、持久化恢复及校验器生产快照重复。定位通用代码里的业务 ID/路径和来源专用分支，适合的改为发现或维护者配置；先给证据和局部修复，再转其他专项。可配置不等于绕过真实宿主可用性与依赖校验。
