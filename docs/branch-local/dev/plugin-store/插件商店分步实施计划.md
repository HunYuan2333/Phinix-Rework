| P6：官方拆包与作者交付 | 红包/人才独立包、历史数据验收、中英文指南/模板/实际 AGENTS.md | 加载与资源归属证明；正式拆包仍取决于旧存档/物品所有权验收；失败继续原发行布局，不阻塞商店文件逻辑 | 可先准备资源/包布局；完整指南跟随冻结的真实发布链 |
| P7：整体验收与候选放量 | 本地/线上全链、实际游戏/Steam/代理、网络样本、额度和故障记录；干净发行物 | P1 平台硬边界及大陆/套餐验证、P2–P6 各自验收；CF 架构 §13 的数值/样本仍是建议门槛，正式放量前确认适用范围 | 失败修复局部重测，不用成功编译替代游戏证据 |

发布协议采用“先最小测试草案、后用 PoC 结果冻结正式 contract”，不是等自动审核平台全部完成才测试下载。索引正式 Release 只发布索引相关数据；作者字节仍来自作者 Release。测试发布不等于正式上架或生产 stable。

### 0.3 本次重新评估的关键取舍

1. **CF 不是可选的客户端提速开关。** 自动数据链统一为客户端→CF→边缘/R2/GitHub；GitHub 跳转只在 Worker 内处理。GitHub direct 只作为测量基线或玩家主动手工下载，不实现生产自动 fallback。Steam 及主动打开项目链接保持原边界。
2. **先复用 v1，避免在第一批同时重写所有清单。** v1 原始 catalog 可以经 CF 返回并由现有代码校验；stable/发行描述另有自己的格式版本，不向严格 v1 塞新字段。provider-neutral v2 是尚未批准的升级建议，CF 本身不强制要求它。正式发行前明确是否继续 v1；若要承诺无客户端升级换 provider，则先做 v2，并同步 manifest/生成器/中英文规范，不能靠统一 URL 宣称已解耦。
3. **签名是正式信任模式的决策，不阻塞本地 PoC。** 未签名模式信任 endpoint/TLS；同链摘要不能独立证明 CF 没改批准记录。若正式目标包含防 gateway 伪造，签名必须在 GitHub 发布侧，客户端固定信任根。未决定前不宣传已具备这项保护，也不先强制每位作者维护钥匙。
4. **R2 协调不是一段淘汰脚本。** 优先评估一个覆盖受控桶的 SQLite Durable Object，只记录容量、写入预留、同键任务和操作预算。官方文档确认 Free 可用 SQLite DO，但其请求、时长、读写也有自身限额；已用于隔离 PoC，不能由免费可用推断整个组合零费用。[DO 定价](https://developers.cloudflare.com/durable-objects/platform/pricing/)、[SQLite 事务 API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
5. **预留到期不能直接当物理空间已释放。** R2 与协调账本不是同一事务。必须覆盖 put 已成功但确认丢失、删对象后记账失败、旧任务在租约过期后仍写入、账本丢失的测试；不确定的对象/写入仍计占用或预留，阻止重复填充并复核。只能证明账本拒绝迟到提交，不能据此宣称 R2 没有写出对象。恢复查询/清理也耗预算，无法确认则停填充，可继续经 Worker 回源服务。
6. **浏览 freshness 与安装授权分开。** 30 分钟浏览缓存、300 秒 stable 共享 freshness 是设计起点；确认和提交前重新核对完整闭包。离线缓存先只用于浏览；是否开放显式离线安装留作产品决策。无有效 body 的 304 要重新取，无效刷新保留旧有效缓存并标记过期。
7. **收窄第一条验收链。** 首次用一个 ZIP 跑通固定发布定位→CF→客户端缓存/校验；随后补 A→B→C 与普通 patch。DLL 静态校验保留，但实际下载需要伴随 manifest 的受审 assetId/名称/大小定位，关闭缺口后交付；暂不加 Range 续传、全量镜像、永久归档或撤回同步删除系统。

新增关键工作集中在发布 contract、CF/R2 故障一致性及实际游戏传输，不能继续沿用旧评估“索引与源缓存 3–5 人日”的范围估计。P0 已有草案实现，P1 隔离试验继续补证据后再估后端工作量；大陆观察期与开发并行，不把未知平台结果折算成确定发布日期。

## 1. 目标、边界和交付顺序

最终交付是游戏内客户端商店：通过统一 repository endpoint 浏览默认或自定义受信源的 GitHub 权威索引，打开工坊页面供用户订阅，下载并安装 GitHub 扩展及其依赖；配套作者发布指南、首次人工入库和后续正常版本自动更新索引的流程。红包、人才贸易成为独立发行的官方可选扩展。

沿用已确认方向：

- 默认索引由 Phinix 维护，允许任何作者申请；GitHub 条目必须提供可审查源码。
- 官方仓库发布索引，作者仓库发布扩展包。首次入库人工批准，后续正常版本自动检查后更新索引。
- 工坊只打开 Steam 游戏内浏览器，不下载、不代订阅、不解析其前置；GitHub 依赖由作者声明版本和依赖关系。
- 商店自动请求只访问配置的 CF repository endpoint；边缘未命中读私有 R2，再未命中由 Worker 回源 GitHub，不向客户端转交外部 Location，不在 CF 失败时客户端直连 GitHub。
- R2 按需保存固定字节、容量不足优先淘汰旧版本；初始容量目标为十进制 9 GB，操作预算及协调实现仍待 PoC。它不保存批准权，不全量同步，也不保证账号零费用。
- HTTP/SOCKS5 代理只作用于客户端商店到 endpoint 的请求；Worker 内部 GitHub 重定向另受 origin adapter 的逐跳限制。
- Chat、Trade、Inventory、LegacyAdapter 暂留主包；只拆红包和人才贸易，保留原有模块、程序集和数据身份。
- 继续使用统一发现、注册、激活和关闭流程；商店不建立官方模块的特殊通道。

当前首版按两条路线交付：**完整 Mod 由用户通过工坊订阅并由 RimWorld 管理；GitHub 托管 DLL 包由 Phinix 下载到独立保存目录，通过扩展管理控制，重启生效**。不改 ModsConfig，也不把下载包写入主包 Common/Extensions。此前本地 Mod ZIP 安装为已完成候选的历史路径，事务/摘要/归属与日志恢复机制将复用，加载与状态边界按新方案调整。2026-10-03 用户要求后续商店达到类似 Trade 的级别，本计划按随主包交付的正式官方功能模块落实：保持独立工程/DLL，以通用发现和生命周期注册主 Tab、设置与服务，并保留禁用能力。当前独立本地预览包继续用于本轮游戏验证；后续正式主包包含商店 DLL 和翻译，玩家安装主包即可获得商店，不需先从商店下载商店本身。业务协作需要时再抽取 Contracts，CF/R2 分发后端独立推进。新托管包清单、加载前库存与通用管理契约优先冻结；不复用 v1 的 RimWorld 身份作为虚构包归属。

首版不安排已装包自动覆盖升级、热加载、无人确认的自动卸载、修改游戏启用列表、服务端商店、多源聚合、完整沙箱或强制 AI 审核。索引自动更新与客户端自动升级是两件事。若需要扩大这些范围，先调整安装与恢复方案。
