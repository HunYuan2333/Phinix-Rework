# 插件商店安全性与维护成本评估

日期：2026-10-02。分支：`dev`。状态：独立安全评估与建议，未实现。

配套文档：[商店可行性与功能设计](插件商店可行性评估与功能设计.md)、[双渠道索引与 GitHub 自动审核发布评估](插件商店双渠道索引与GitHub自动审核发布评估.md)。本文评估这些功能带来的风险及维护负担，不是对框架、所有插件或 GitHub 仓库完成全面安全审计的声明。

## 1. 结论、确认事项与决策边界

**第三方 DLL 一旦在游戏中运行，风险上限是游戏进程所拥有的本机权限，而不是某个 Phinix API 的权限。** 当前 Rework 没有针对不可信插件的运行时安全沙箱。因此商店只能通过控制来源、审核具体发行物、规范安装和及时撤回，降低风险；不能保证已加载的恶意模组被框架限制住。

对可能只有少量用户、少量维护者的项目，建议投入优先放在确定性校验、官方账户/发布流程保护、可追溯的发行记录及简单的撤回流程。插件权限弹窗、强制 AI 审核和复杂沙箱平台如果没有可靠边界，容易花费更多维护时间，却无法兑现安全承诺。

用户本轮已确认，本文保留：

- 允许任何作者提交申请，审核后收录；不改成邀请制，也不等于自动接纳全部申请。
- 首次入库人工批准；后续版本自动检查，通过后更新索引。
- 默认源的 GitHub 插件必须提供可审查源码；只有 DLL、没有可审查源码的申请不收录。工坊的条目审核单独评估。
- 官方只发布索引，作者发布 DLL；工坊与 GitHub 两个渠道继续分别处理。
- 本阶段仅写评估，不修改代码、GitHub 配置或实际收录政策。

当前没有真实的使用人数、每月申请量、更新次数或可投入维护时间，不能编造事故概率或用“人少”证明风险可忽略。本文对工时和规模的数值仅作情景假设。

**源码准入已由用户明确确认。** 这不自动要求官方重编译每个插件，也不表示用户确认了逐版人工审核或特定开源许可证。其余措施均明确为设计建议，不视为已批准实施。

## 2. 要保护什么，以及商店新增了什么风险

按 [术语与功能分层](术语与功能分层.md) 区分内置功能模块、官方可选扩展、社区扩展与商店条目。“基础功能”是产品定位，“官方维护”是维护归属，“收录/检查通过”是检查记录，均不构成权限隔离。本文关于同进程代码的技术限制同样适用于内置功能模块；商店新增的是分发与安装链风险。

需保护的对象包括玩家存档和模组配置、Phinix 登录凭据和会话、代理凭据、本机中游戏进程可读写的数据、服务器正常运行，以及官方索引仓库/机器人凭据。只关注游戏是否崩溃，会漏掉账号和本机数据风险。

原生 RimWorld 模组已经能够在游戏进程内运行代码。商店未创造这种执行能力，但会降低安装门槛、递归引入依赖，并让“官方收录”看起来像一种背书。索引和自动发布如果被控制，攻击者可能同时影响多个玩家，而非仅诱导一次手动下载。

主要风险来源不只包括故意提交恶意插件的作者，还包括善意作者的账号失陷、第三方依赖被替换、源码与发行 DLL 不一致、错误安装包、官方自动化处理不可信输入，以及普通代码缺陷。

| 场景 | 可能后果 | 商店能降低的部分 | 仍无法保证的部分 |
| --- | --- | --- | --- |
| 恶意或被攻陷的作者发布 DLL | 读取凭据/文件、联网、破坏存档、干扰其他模组 | 初审、具体资产绑定、异常暂停、追踪和撤回 | 同进程内阻止已运行代码的全部行为 |
| 首次版本正常，后续加入恶意代码 | 自动进入可信列表的新版本 | 固定来源、版本记录、危险变化提示与抽查 | 身份稳定和哈希正确不证明新版本无害 |
| 主插件正常，依赖有问题 | 玩家一并安装另一作者的代码 | 展示完整闭包，逐项校验来源和发行物 | 父插件的审核不能代替依赖审核 |
| 索引/发布账户被控制 | 用攻击者提供的条目和哈希引导安装 | 账户保护、权限隔离、审计、独立签名可进一步加强 | 同源索引和哈希同时改写时仅有 SHA-256 不够 |
| ZIP 路径、符号链接、解压体积异常 | 安装阶段越界写入、覆盖文件、资源耗尽 | 在执行插件前拒绝，约束路径、格式和大小 | 安装规范无法限制 DLL 启用后的文件操作 |
| 普通 bug、排序/版本冲突 | 崩溃、存档损坏、业务恢复错误 | 兼容/依赖检查、未启用安装、测试说明 | 静态检查无法证明所有游戏组合正常 |
| CI 执行申请者脚本 | 偷取官方凭据、修改发布物 | 默认只做静态检查，不给不可信执行环境写权限 | 可信工具自身也可能有缺陷，需维护 |

表中描述风险能力和影响，不表示已发现作者恶意行为，也不宣称已经证实仓库存在对应可利用漏洞。没有可靠数据支持发生概率排序；恶意代码和索引接管属于需优先防范的高影响情景。

## 3. Rework 与游戏模组的技术边界

### 3.1 API 抽象约束合作代码，不约束恶意代码

[设计哲学](../../../Design-Philosophy.md) 的插件平等、接口解耦、最小侵入和边界校验有助于降低误用、耦合及恢复错误，但它们是工程约定。恶意 DLL 可以绕过接口调用 .NET 文件/网络 API、反射访问同进程对象，或使用游戏现有的 patch 能力。

[Harmony 官方说明](https://harmony.pardeike.net/articles/intro.html) 展示了运行时修改方法及使用反射的能力。不能把 `private`、命名空间、只有只读接口、或“代码不允许引用宿主”当作攻击者无法绕过的权限边界。Harmony 有适用限制，本文也不假设它能任意修改所有原生方法。

**能力声明如“联网、读取存档、访问文件”可以供作者披露用途，当前不能宣称由框架强制执行。** 实现一个仅检查框架接口调用的权限开关，不能拦住直接 .NET 调用或其他模组入口。

### 3.2 当前加载与禁用机制的真实作用

| 当前机制和代码依据 | 确实提供什么 | 安全限制 |
| --- | --- | --- |
| [Client.cs](../../../../Client/Source/Client.cs) 先加载程序集再扫描/激活；探测活跃模组程序集 | 标准发现入口与加载顺序 | 未建立每包独立 OS 权限；不以商店审核作为全部模组的启动条件 |
| [ExtensionAssemblyLoader.cs](../../../../Common/Utils/Framework/ExtensionAssemblyLoader.cs) 在当前 AppDomain 调用 `Assembly.LoadFrom` | 程序集探测和依赖解析 | 不可信 DLL 没有由此获得受限执行环境 |
| [PhinixExtensionRegistry.cs](../../../../Common/Utils/Framework/PhinixExtensionRegistry.cs) 在模块实例化前咨询激活策略 | 被禁用模块不实例化、不执行其 Register/Activate | DLL 已进入加载范围；不能约束普通 Mod 构造、独立 patch 和其他入口 |
| [StaticActivationPolicy.cs](../../../../Client/Source/Framework/StaticActivationPolicy.cs) 使用启动时禁用快照 | 静态启用策略和依赖禁用 | 不是即时卸载，也不是已运行恶意代码的终止按钮 |
| Registry 的异常捕获与注册回滚 | 部分正常插件失败不会中断其他生命周期 | 无法隔离死循环、内存耗尽、进程退出或任意外部副作用 |
| [FrameworkTypes.cs](../../../../Common/Utils/Framework/FrameworkTypes.cs) 的 StorageProvider 校验根目录 | 规范 API 返回路径，减少误写/路径穿越 | 不强制所有文件访问经 Provider；不能据此隔离插件数据 |

准确说法是“禁用能阻止这个 Phinix 模块通过标准生命周期运行”，不能说“禁用完全没有作用”，也不能说“禁用后这个模组必然没有代码执行”。`Assembly.LoadFrom` 本身也不等于立刻执行该 DLL 的每个静态构造函数；风险来自整个模组加载和实际调用过程。

独立本地模组目录、最小 DLL 模组壳和包归属记录方便卸载/恢复，不构成权限隔离。手动放入 Phinix 目录的 DLL、工坊模组及未经过商店的本地模组仍可能被游戏/框架加载。商店无法垄断 RimWorld 的全部安装入口。

### 3.3 已存在的会话、设置和传输能力

[客户端抽象](../../../../Client/ClientExtensionAbstractions/Framework/IClientExtensionAbstractions.cs) 的 `IClientSessionContext` 暴露会话 ID；`ILegacyModuleTransport` 支持按模块名发送/注册原始消息处理器。[Client.cs](../../../../Client/Source/Client.cs) 向扩展提供这些服务，[NetClientLegacyTransportAdapter.cs](../../../../Client/Source/Framework/NetClientLegacyTransportAdapter.cs) 转交到真实连接。

这些接口有合法兼容用途，但当前不能作为“插件只能访问自己的网络消息”的证明。[ClientSettingsContextAdapter.cs](../../../../Client/Source/Framework/ClientSettingsContextAdapter.cs) 的通用键读写也未体现按调用插件强制鉴权。增加通用命名空间和访问约束可以减少合作插件误用，不能阻止同进程恶意代码绕开。

此外，[ClientAuthenticator.cs](../../../../Common/Authentication/ClientAuthenticator.cs) 的凭据保存路径直接将 CredentialStore 序列化到文件；[Credential.proto](../../../../Common/Authentication/Credentials/Credential.proto) 包含用户名/密码字段。此路径未体现磁盘加密。二进制 protobuf 格式不是加密。本文只检查代码，没有读取任何实际凭据文件。

由此应把登录凭据、会话和代理凭据列入影响评估，而非仅提示“插件可能让游戏崩溃”。即便后来使用 OS 凭据存储或磁盘加密，也不能承诺对已经在同一游戏进程运行的插件隐藏运行时所需秘密。不让商店持有官方发布 token、避免日志泄露凭据，仍是有效的基本措施。

### 3.4 net472/Unity 客户端与 .NET 10 服务端不同

客户端项目目标为 .NET Framework 4.7.2，但游戏运行时由 RimWorld/Unity 决定，不能据编译目标假定 Microsoft CLR 的所有隔离 API 都可用。[Unity 文档](https://docs.unity3d.com/Manual/overview-of-dot-net-in-unity.html) 说明了其 .NET 兼容层及平台差异，实际 API 仍需按游戏版本验证。

不能把 .NET 10 的 AssemblyLoadContext 移植到客户端就当作解决方案。它主要解决程序集加载/版本问题，也不是不可信代码沙箱；[Microsoft 插件教程](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support) 明确建议用 OS 或虚拟化边界隔离不可信代码。这一现代 .NET 说明不替代对旧 CLR 的全部能力判断；本文的客户端结论主要依据当前代码未建立任何受限执行环境。

服务端插件也运行在服务端进程内，管理员手动安装只减少自动分发入口，不会消除执行风险。服务端可通过独立低权限账户/容器减少整台机器的影响范围，但这通常仍不能隔离同一服务中的不同插件。

真正隔离一个插件需要独立进程加 OS 权限约束、容器或虚拟机；仅开一个同账户的子进程也不够。需要访问 Verse/Unity 对象和直接 Harmony patch 的普通模组难以放入此模式，必须重做受限协议及功能范围。Rework 无法仅靠商店替已有任意游戏模组补上一层可靠沙箱。

### 3.5 多人协议和物品权威也有边界

恶意客户端模组可以改变本地 UI、状态和发出的消息。因此服务器必须把客户端输入视为不可信，按认证身份、长度、业务权限和状态校验；“来自官方索引插件”不是授权依据。具体协议是否已充分防护需要单独服务端审计，本文不以本次阅读宣称全部安全。

[兼容与恢复边界](../../../Compatibility-Boundaries.md) 要求真实回执、幂等性、整批转换和结果未知保留。这些规则应继续保留，但主要约束正常实现和故障恢复，不能证明恶意客户端从未篡改本地物品。当前涉及服务端原样转发的 opaque 游戏载荷，也不能据此声称服务器可验证全部游戏实体来源。

关闭/撤回插件或回退 DLL 不自动逆转存档、库存、已确认交易或待交付记录。不能为了安全撤回而直接删数据、返还结果未知物品或降低所有权规则。

## 4. 各种常见安全措施的实际收益

| 措施 | 实际防护 | 不能据此承诺 |
| --- | --- | --- |
| HTTPS 与正常证书校验 | 降低传输窃听/篡改；代理下也保留目标 TLS 验证 | 作者/官方账户未失陷，代码没有恶意行为 |
| SHA-256 与固定资产身份 | 检测下载内容偏离已接受发行物、同版本资产被替换 | 已接受字节安全，索引与哈希同时被改时仍可信 |
| 索引签名，客户端固定信任公钥 | 在密钥管理正确时验证来源与内容，增加独立验证路径 | 签名 DLL 无害；签名密钥和发布凭据一起失陷时仍有保护 |
| GitHub immutable releases | 限制已发表 tag/资产被改写 | 攻击者不能发布新的恶意版本 |
| 可审查源码/源码差异 | 让初审、异常调查和责任追踪有依据 | 发行 DLL 必然对应源码，所有危险行为均被发现 |
| 构建证明/可复现构建 | 在信任工具链和验证成立时加强来源与产物对应 | 被编译的源码本身无害 |
| AI/静态扫描/杀毒 | 提供有限线索，部分已知问题可检出 | 未报告问题就是安全，未知/延迟触发恶意逻辑会被检出 |
| 声明权限与安装确认 | 告知用途和新引入的作者/依赖，让用户作决定 | 框架强制禁止声明外行为 |
| 不热加载、不静默升级、新包不自动启用 | 保留启动前检查机会，减少未经玩家操作的执行 | 玩家启用后的运行时被隔离，Steam 不会自行更新 |
| 独立目录和安装回滚 | 防止商店误覆盖、降低正常安装失败损失 | 自动撤销已执行代码和存档迁移 |

Microsoft 特别指出 [.NET strong name](https://learn.microsoft.com/en-us/dotnet/standard/assembly/strong-named) 主要用于程序集身份，不能作为安全保证。不要把 DLL 的强名称、文件名前缀或“作者已验证”徽章混同于安全审核。

[GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) 是可选加强措施；作者不启用时仍可使用固定记录与下载哈希检测变更。独立签名值得后续比较，但如果每次自动发布都把签名密钥放在同一高权限任务，它对该任务被控制的防护有限；真正独立审批/离线签名又会增加逐次人工工作，不能隐瞒它与无人值守更新的取舍。

## 5. 小规模项目值得做的基本措施

以下是**建议的最低措施组合**，不代表本次已决定实际上线或增加新准入限制。多项在前两份设计已有，安全评估确认其价值，不应重复计算为全新建设成本。

### 5.1 默认源要求 GitHub 源码，首次审核要看具体内容

开放申请不等于自动信任新作者。人工至少核对来源/作者联系方式、加载入口、明显联网/文件/进程启动行为、所声明依赖、兼容说明和具体发行资产。申请与批准绑定同一候选指纹，申请编辑/资产更改后旧批准不能继续使用。

对可审查源码，先集中阅读启动入口、敏感行为和依赖变化，不承诺逐行审计。报告注明具体 commit、覆盖范围和未验证项；隐藏逻辑、严重混淆、无法解释的敏感行为或复杂度超出维护能力，建议保持待审或拒绝，而不是给形式上的“通过”。收录标准需要用户另行确认，不能仅由自动评分设定。

用户已经选择第一条路线；第二条仅保留为被放弃选项的取舍比较，不是实施建议：

| 路线 | 收益 | 成本和限制 |
| --- | --- | --- |
| GitHub DLL 必须有可审查源码（已确认） | 降低纯黑盒初审负担，便于看差异和事件调查 | 排除不提供源码的作者；仍有源码/产物不一致风险 |
| 允许无源码 DLL 单独人工判断（不采用） | 接纳更多作者 | 初审证据更少；反编译不保证完整可读，工时更不确定 |

具体发行版本须能定位到相应可审查源码，不能仅给一个与候选版本无关的仓库链接。自动更新时也检查源码 commit 可获取、清单声明与发行记录关联；缺少必要源码时保持待检查，不能自动收录。这里的“可审查”不擅自扩大为强制特定开源许可证，但分发授权仍需核对。源码和 DLL 是否一致属于另一条证据链，未做可复现/可信构建验证时必须注明尚未证明。

工坊暂按条目审核，不能因为未要求所有工坊作者附源码，就把同样的“代码检查通过”徽章套到工坊上。

### 5.2 保留自动更新，但不把机器通过称为重新人工审核

对已批准身份的新版本做结构、兼容、依赖、实际哈希、版本及来源检查；保留旧稳定记录，来源/所有者变化、已接受版本内容变化等异常暂停。新版正常通过可自动收录，客户端仍仅获得可用更新提示。

建议生成源码差异摘要和敏感行为变化提示，供维护者抽查。若确定性检查发现越界或明确高风险变化，进入异常队列，而非默默重新计算哈希放行。异常暂停不要求每个正常发行再批准一次，保留用户已确认的自动更新路径。

但新增恶意行为完全可能符合 schema、版本和哈希规范；不能以“后续每次都有检查”掩盖无人逐次阅读代码的残余风险。是否抽查、频率和异常分级应根据实际流量确定，本文不擅定固定等待天数或逐版本签字制度。

### 5.3 依赖同样是执行代码的来源

完整计划列出每个必需插件、作者、来源、版本及审核范围，GitHub 下载资产逐项校验。建议默认源的自动安装闭包仅使用已收录条目，不接受一个清单中的任意 URL 作为可信依赖，也不默默跨入自定义源或自动覆盖宿主 DLL。

本地本来就有的模组标记“本地已有”，不升级成“官方审查过的资产”。按用户确认的简化边界，工坊条目在 Steam 游戏内浏览器打开，由玩家自行订阅；商店不下载内容，前置交给 Steam，不将点击链接表示为已安装/已满足。一个 GitHub 条目的入库批准不会传递给它以后新增的未知作者依赖。

### 5.4 先保证安装器不会造成额外损害

暂存位置不属于游戏加载目录；不在游戏进程内加载候选 DLL 来做检查。使用静态元数据解析，并约束解析器/压缩处理的输入大小和执行时间。

路径规范化、拒绝越界/绝对路径/符号链接、控制压缩炸弹和文件数量，限定每包独立目录；同名程序集/身份冲突、现有目录归属不明则停止。不同平台的路径大小写、重解析点和重定向行为需要测试，不能只检查字符串是否含 `..`。

不执行安装脚本、不要求管理员权限、不写 Phinix/Workshop 基础目录、不调用 Loader 热加载。只回滚本次拥有且仍匹配记录的文件，保留存档及插件数据。建议游戏及服务端使用普通低权限账户运行；这降低整机影响上限，仍不会隔离该账户能够访问的数据。拒绝不符合格式的脚本/可执行安装器能缩小安装面，但不意味着被接受的托管 DLL 不能启动进程或调用原生 API。

### 5.5 官方账户和自动化保护优先于复杂扫描

建议独立索引仓库、维护账户启用强认证并保存恢复方式、减少写权限成员、保护重要分支/工作流变更，Actions 固定可信版本并按任务授予最小权限。[GitHub 账户认证说明](https://docs.github.com/en/authentication/securing-your-account-with-two-factor-authentication-2fa/about-two-factor-authentication) 和 [Actions 安全指南](https://docs.github.com/en/actions/reference/security/secure-use) 可作为实施依据。

官方发布任务不执行/构建申请者的代码；Issue 和报告按不可信数据处理，不拼进 shell，不由 AI 文本决定审批。检查和发布权限隔离；隔离构建如以后加入，不能持有官方凭据或共享高权限环境。`contents: write` 无法只限某个目录，独立仓库与可信路径校验很重要。

准备一个可手动关闭的监控/发布入口。维护者不在线或检查故障时保留旧稳定快照，新申请排队，不降级到“检查失败也发布”。无需为少量申请建设复杂运维平台。

### 5.6 下载代理和本地秘密

坚持 HTTPS，不提供为了代理可用而关闭证书校验的常规开关；跨域重定向不转发原站认证，代理密码不出现在日志/索引/报告。显式代理不隐式直连回退，目标地址和重定向校验不能与允许本地代理地址混淆；细节沿用主文档。

公有索引优先不要求玩家填写 GitHub token，商店从不接收官方写权限 token。确需玩家私有源凭据时属于额外设计，不以公共商店需求隐含增加秘密存储负担。

商店代理仅控制商店请求，不限制第三方模组自行联网，也不控制 Steam 游戏内浏览器访问或 Steam 下载。同进程恶意 DLL 能访问的范围不能靠商店代理配置缩小。

### 5.7 一条简单但真实的撤回路径

索引保存撤回状态、原因、影响版本、来源与联系入口。事故时可暂停自动跟踪并发布撤回记录，阻止新安装；已有用户在商店可访问时收到提示。无需承诺全天候响应或远程强制卸载。

已运行可疑 DLL 时，索引撤回不是有效的进程内“杀毒”。建议提示关闭游戏，在下次启动前禁用整个相关模组/隔离文件，保留必要记录；若有凭据泄露迹象，通过相应服务更新凭据/会话。具体应急操作需按事件确认，不自动删除存档、不返还未确认物品、不宣称重启即可恢复所有损害。

自定义源单独展示来源和审核状态；默认源的撤回记录不保证其他源也撤回。玩家离线、长久不打开商店或被恶意代码干扰时，也可能收不到提示。

## 6. 不建议首版为安全投入的重型措施

| 措施 | 不作为首版基础的原因 | 何时再考虑 |
| --- | --- | --- |
| 给任意 DLL 做“权限沙箱” | 当前同进程架构无法兑现；需要改变插件模型 | 另设不能直接操作 Verse/patch 的受限插件类型 |
| 每次扫描全部源码/每版 AI 强制通过 | 输入量、误报和模型维护费高，不能保证产物安全 | 有明确覆盖目标、预算及异常处理能力时作为辅助 |
| 每个作者 DLL 在官方环境重新构建 | 任意构建代码带来 CI 风险与跨版本工具链成本 | 少数重要插件有可复现配方和隔离验证环境时 |
| 每版离线签名或多名维护者签字 | 提高人工负担，可能取消已确认的正常版本自动更新 | 威胁/采用规模值得投入，且用户重新确认流程时 |
| 上传所有 DLL 到多个第三方扫描服务 | 外部隐私/许可证/配额和结果处理成本；仍可能漏报 | 作者授权和收益明确，不将“无检出”视为保证 |
| 远程运行时强制停用/自动删除 | 对同进程恶意代码不可靠，且可能破坏持久化恢复 | 针对正常插件的受控维护，不作为安全隔离承诺 |
| 自建镜像、下载网关和遥测平台 | 增加托管、隐私、更新和事故责任 | 有实际网络与规模需求后单独论证 |

这个取舍不意味着减少 ZIP、来源或权限检查。应优先去掉不能兑现的复杂安全功能，而非去掉基本边界校验。

## 7. 使用人数较少时，维护成本如何计算

### 7.1 成本更多随申请和更新量增长

用维护工时而非下载量估算：

```text
每月人工维护时间 ≈ 新申请数 × 首次审核时间
                 + 异常版本数 × 复核时间
                 + 抽查次数 × 单次抽查时间
                 + 自动化日常维护时间
                 + 实际事故处理时间
```

自动检查的机器开销随请求/资产大小增加，首次人工审核不因用户少而消失。开放申请还可能有与真实玩家数量无关的垃圾提交；建议限流、排队、同来源去重和明确维护能力，不能靠机器人“秒批”减少负担。

供估算的小插件情景：首次针对敏感路径阅读约 1–3 小时；技术异常复核约 15–60 分钟。复杂/混淆插件可能需要数日，不能仍按小插件报价。这些时间不是完整安全审计的预算，也不包含游戏组合测试。

### 7.2 示例仅用于比较，不预测本项目流量

假设一位维护者、约五个已收录小插件，每月一个新申请、六个常规更新、一次异常：首次审查取 2 小时，异常复核取 0.5 小时，工具日常维护取 1 小时。

| 方案 | 示例每月时间 | 得到/失去什么 |
| --- | --- | --- |
| 已确认的首次人工、正常更新自动检查 | 约 3.5 小时，另加抽查和事故 | 日常可持续，但普通更新未必有人读代码差异 |
| 每个更新再人工看 0.5 小时 | 约 6.5 小时，另加事故 | 多看部分差异，仍不构成完整审计；不是本次采用方案 |
| 索引仅展示链接、不做 GitHub 自动安装 | 来源审核仍需时间，客户端安装器维护减少 | 降低项目新增安装责任，便利性下降；需用户另行决定 |

若每月新申请从一个变为五个，首次审查部分由 2 小时变为 10 小时，即使仍只有少量用户也会显著增加维护负担。没有可靠事故率数据，不给“预计每年只出一次问题”的结论；一次凭据/索引事件可能超过数月日常维护，还可能有不可恢复损失。

### 7.3 初期建设与持续负担分开

前两份设计已经包含路径/哈希/依赖检查、发布隔离和恢复，不把它们再完整累加一次。若从未实现起步，安全方案不是给现有下载器加几个开关；基础安装与发布边界本来就是功能实现的一部分。

作为设计预算，首次审核记录/报告和简单撤回说明约 1–2 工作日，安全异常状态与来源变更处理约 1–2 工作日，针对性负面测试和应急演练约 2–4 工作日；三项合计约 4–8 工作日，部分与前文自动化/安装验证重叠。实现后根据实际流量记录维护小时，再决定是否加 AI、签名和更深审核，不能机械地加到旧总工期上。

源码/产物验证、独立签名、受限进程模型与跨平台秘密存储都需单独预算，不能声称已包含在这个基础增量中。

### 7.4 是否值得建设的条件

若插件很少且长期没有安装需求，展示链接加清晰审核范围可能已解决主要问题；自动下载器的便利收益未必足以覆盖维护工作。它是备选路线，不在本次擅自替换用户已讨论的商店功能。

若继续建设自动安装商店，建议至少有人负责首次审核、能暂停发布并处理撤回，基础安装/发布边界能经过验证。如果这些条件无法满足，建议推迟自动安装范围，而不是承诺“机器人能替代维护者”。人数少可以降低建设规模和响应承诺，不能降低 DLL 的权限上限。

## 8. 工坊的特殊风险与官方审核范围

工坊订阅/下载由 Steam 管理；订阅模组可能在 Steam 管理下更新，独立于 Phinix 的索引 tag。[Steam Workshop 实施指南](https://partner.steamgames.com/doc/features/workshop/implementation?language=english) 描述了订阅与内容获取流程，但不能据其 API 认定第三方代码已由 Phinix 审核或获得运行时沙箱。

首版工坊条目只能诚实显示“条目经过收录审核”，附审核日期、来源与可核对信息。此标记不表示当前下载内容、所有未来版本或依赖的代码都已审查。GitHub 条目显示具体被接受发行资产的检查结果；两类结果不可混用。

“工坊发布”本身不是代码安全证明；“GitHub DLL 较小”也不是低风险证明。工坊链接能减少商店自己的下载/文件写入责任，但不会减少工坊 DLL 在游戏中的执行能力。

红包、人才贸易后续从主包拆出，具体 [安装与迁移评估](插件安装目录与发现加载及官方插件拆分评估.md) 建议独立模组目录、保持旧模块/程序集/数据身份并阻断旧副本并列安装。独立目录不增加运行时隔离；官方来源也不改变权限。缺少红包 codec 或人才存档组件会影响既有数据恢复，文件回滚不能代替库存托管或 pawn 返还的业务验证。

打开入口应从校验过的工坊 ID 生成固定 HTTPS 条目地址，而不是直接执行自定义源提供的任意 URL/协议。复用游戏已有 Steam 上下文，不引入第二套 Steam DLL 或更改 Steam 配置；覆盖层不可用时说明原因。游戏内浏览器只是用户访问条目的位置，不构成模组沙箱或额外代码审核；玩家自行订阅后的内容风险仍适用本章。

## 9. 需要验证的基本安全场景

以下是后续实现的针对性验收建议，不在本次运行攻击测试，也不写实现或测试代码。

| 验证点 | 期望行为 |
| --- | --- |
| 已接受版本远端资产被替换 | 哈希不匹配停止安装，保留原记录，不能自动改摘要 |
| 申请编辑/仓库转移/审批候选被修改 | 原批准失效或来源更新暂停 |
| 依赖清单带任意 URL、自定义源同名包 | 不被默认源闭包自动信任，不替换既有包归属 |
| 越界 ZIP、符号链接/重解析点、大小写冲突、压缩炸弹 | 暂存/校验时拒绝，不能触及包外数据 |
| 检查或发布任务中断 | 保持旧稳定索引，不发布未完成候选 |
| Issue 注入 shell 文本、AI 报告含执行指令 | 只按数据处理，不执行、不获得批准或凭据 |
| 代理认证/跨域重定向/证书失败 | 无秘密日志/跨域泄露，不能以关闭 TLS 校验绕过 |
| 包不兼容、同名程序集、安装中途崩溃 | 不热加载、不错误清理他人文件，保留恢复状态 |
| 正常版本自动检查通过 | 自动进入索引，但不静默更新已运行/已装插件 |
| 安装版本被撤回或玩家离线 | 阻止后续新安装、可访问时提示；不冒充已强制隔离运行代码 |
