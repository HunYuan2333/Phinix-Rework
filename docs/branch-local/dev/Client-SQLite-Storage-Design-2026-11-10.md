# 客户端通用 SQLite 存储设计

日期：2026-11-10。状态：待实现。库存是第一个消费者，本设计不依赖库存模型。

## 目标与边界

提供普通客户端模块都能使用的 SQLite 基础设施：稳定路径、连接生命周期、事务、schema 版本升级、错误分类和一致备份。模块自己定义业务表、SQL、唯一键及领域行为。使用者不需要引用 Inventory，不需要库存处于激活状态。

基础设施不解释物品、交易、Game、存档、预留或旧 journal，也不统一接管所有插件现有数据。当前只接入库存；其他模块需要时按同一入口申请数据库。

## 依赖方向

| 层 | 负责 | 依赖 |
| --- | --- | --- |
| 中立存储合同 | 逻辑库描述、schema 升级步骤、数据库租约和错误结果 | BCL；不引用 SQLite provider 或业务程序集 |
| Client/Storage.Sqlite | provider/native 依赖、连接与事务、schema runner、持久化配置、备份 | 中立合同、选定 SQLite provider |
| Host 组合根 | 创建并注册通用存储服务，在消费者停止后关闭 | 通用服务；不引用库存合同 |
| Inventory/Storage | 库存表、SQL、数量及幂等约束、库存 repository | 中立存储合同、库存领域模型 |
| Inventory/LegacyMigration | 旧存档解析、一次导入、迁移回执和旧字段清理 | 库存 repository、历史格式 reader |

服务通过现有通用组合/服务机制提供给同级插件，不增加 builtin.inventory 专属通道。native SQLite 依赖只有基础设施包负责分发，库存及后续消费者不各带一套。

## API 形状

以下是职责草案，实施时按现有合同命名收敛：

- `IClientDatabaseService.Open(ownerId, logicalName, schema)`：取得模块拥有的逻辑库租约。owner 从模块作用域取得或验证；禁止把任意绝对路径直接当作普通打开参数。
- 数据库租约提供短生命周期连接/工作单元。使用标准 `System.Data.Common` 的 `DbConnection`、`DbCommand`、`DbTransaction` 表达查询和事务，不公开某个 provider 的连接类型。
- 通用层统一连接初始化、超时与资源释放；SQL 参数化、reader/command 释放及业务事务边界由使用者落实。可以提供薄的事务执行帮助方法，不再包一套自定义 SQL 语言或 ORM。
- `DatabaseSchema` / `DatabaseMigration`：模块声明目标版本和有序升级步骤，通用 runner 在模块表可用之前执行。迁移 SQL/代码位于模块内。
- 最小错误分类：Busy、Unavailable、Corrupt、UnsupportedSchema、MigrationFailed。模块决定展示方式；通用层不自动删库、退款、重投业务操作。

写事务中的业务回调不能被通用层自动重放。锁等待可有界处理，但包含外部副作用的操作不能因重试而再次执行。写提交结果无法确认时返回不确定错误，使用者按其操作 ID 查询，不能报告确定成功或无条件再执行。

## 数据库组织

默认每个模块使用自己的逻辑库，通过同一服务访问。例如库存申请 `builtin.inventory / inventory`，后续模块申请自己的逻辑库。物理路径由通用层映射到稳定的用户数据目录；存档名称、模组安装路径和账号临时会话不参与库存数据库身份。

复用的是连接/事务/升级基础设施；不同业务不必挤进同一个物理文件，避免共用版本号、锁与升级顺序。若以后确有共享事务需求，再由参与模块声明共同 schema owner；本轮不增加跨模块共享表、跨库原子提交或全局万能数据仓库。

每个库只由一个 schema owner 管理：

| 记录 | 所有者 | 内容 |
| --- | --- | --- |
| `__database_meta` | 通用层 | databaseId、schema owner、基础设施格式版本 |
| `__schema_migrations` | 通用 runner | schema owner、版本、迁移标识/校验、完成时间 |
| `inventory_meta` | Inventory | 库存领域版本、revision、业务元数据 |
| `inventory_entries` 等 | Inventory | 库存自己的业务表、索引与约束 |
| 旧存档导入回执 | Inventory | 来源、幂等键、导入结果；不写进通用 schema 历史表 |

通用 schema migration 表达“表结构升级”；库存 migration receipt 表达“这个旧档已导入”。两者不能混用。同名数据库被其他 schema owner 打开、迁移历史不匹配、目标版本低于已安装版本时，拒绝继续写入并保留文件。

## 最小工程规则

- 数据类型、主键/外键、唯一键、非空与数量范围按实际表契约定义。SQL 使用参数，不用任意 JSON 键值表代替所有关系结构；opaque 物品 payload 可独立按原字节保存。
- 选定一个实际支持目标运行时的 provider 并锁定版本；程序集与 native 库只在通用存储项目及打包层声明。公共合同不携带 NuGet provider 类型。
- schema 升级按序执行，在可事务化范围内原子提交迁移和版本记录。升级失败不推进版本；需要非事务步骤时显式拆分，不能假定任意数据库管理命令都可放在同一事务中。
- 连接和 reader/transaction 不能挂在 UI 或跨线程长期共享；以短工作单元使用，关闭按模块租约/Host 生命周期成对执行。主线程只应用业务结果，通用层不触碰 Verse/Unity 对象。
- 统一制定并验证持久化、锁等待和备份配置；不追求自建 WAL、业务日志重放、复制协议或分布式事务。
- 备份使用 provider/SQLite 支持的一致快照方式，不让模块随意复制仍在写入的单个文件。文件缺失或损坏与首次创建要有可区分的诊断。

## 可用性取舍

数据库内部维持正常事务与唯一约束。数据库外的世界保存、网络结果或物理物品操作，不承诺任意崩溃后自动恢复。

事故处理允许丢弃尚未完成的业务操作并通知玩家。决定哪些操作可放弃、如何处理相关余额，由业务 owner 负责；通用层不能静默删业务记录。保留足够的操作 ID/终态用于防重，无需无限保存完整操作历史。一个不确定操作不应让无关库存长期只读。

正常迁移仍遵循提交后清理：导入事务失败不能删除玩家旧库存。允许放弃事故恢复不等于允许升级过程先删源数据。

## 实施顺序与验收

1. 通用合同、provider 实现及打包：用独立测试 schema 验证，不引用任何 Inventory 类型。
2. schema runner 与事务：验证首次创建、升级、重复打开、升级失败、较新 schema 拒绝、锁/磁盘错误及重启后持久化。
3. 生命周期：验证消费者租约、释放顺序和并发访问，异常不会泄漏连接或重放外部副作用。
4. 库存 repository 定义自身表和 SQL，接入普通通用服务，再迁移旧存档。
5. 用第二个简单测试模块申请另一逻辑库，证明无需 Inventory、互不污染表/版本和路径；不为此新增实际产品模块。

当前不实现 ORM、通用领域 repository、消息总线、跨库事务或多种数据库后端。通用性体现在清楚的所有权与依赖方向，保持当前实际需求所需的最小接口。
