# 客户端持久化与 SQLite 简评

日期：2026-10-03；规划修订：2026-10-05。基于源码静态阅读，未做性能基准、SQLite 接入或游戏内验证。

执行顺序见 [后续实施计划](./后续实施计划.md)。SQLite 保留为独立的后置候选，不与三仓、DI 或状态机迁移捆绑。

## 结论与优先级

服务端使用较少，SQLite 迁移暂缓；已有定期保存和覆盖写入风险仍存在，但不作为当前主要投入方向。

客户端值得改善持久化，但现阶段不建议全面换 SQLite。优先补齐交易、红包的持久托管与恢复链，再改善库存日志增长。SQLite 最有价值的落点是库存的增量账本、幂等回执和操作记录；配置、凭据、聊天缓存不需要为了统一而迁移。

## 当前客户端情况

| 区域 | 代码现状 | 评估 |
| --- | --- | --- |
| 库存 | 游戏存档嵌入完整账本；外部日志每次追加完整新状态，校验并 `Flush(true)` 后才发布成功 | 已有可靠提交边界，主要问题是重复数据、长期增长和同步写入成本 |
| 库存恢复 | 以 SaveId 和规范化存档路径隔离；较新日志须玩家确认；损坏只读、残缺尾部隔离 | 这些语义必须保留，数据库不能直接用“最新状态”覆盖旧存档 |
| 交易报价托管 | 库存预留已落盘；地图物品仍由窗口的 `pendingItemStacks` 持有运行时对象，token 跟踪也在内存 | 地图物品待确认记录与重启核对更值得优先处理；数据库不能直接持久化活 Thing |
| 交易待交付 | `pendingCompletions` 是内存字典，Stop 时清空；库存成功入账有稳定 DepositId 去重 | Legacy 服务端无持久交付确认，客户端本地待交付记录尤其重要 |
| 红包发送托管 | 每个预留一份带校验的记录，临时文件强制刷盘后替换；重启后保守标记 uncertain | 基础保存已较稳，首要缺口是中断后的中继历史核对，而非文件格式 |
| 设置、凭据 | 设置使用 RimWorld Scribe；客户端凭据使用小型 Protobuf 文件直接覆盖 | 设置继续沿用游戏机制；凭据可先补原子替换，单独引入数据库收益低 |

## 库存迁移的实际收益

`InventoryJournal` 的单条序列化 payload 上限为 8 MiB，日志文件上限为 128 MiB。追加完整账本时还会再做 Base64 封装；加载和追加会把每个历史状态放进 `recovered`，包含重复的物品载荷。正常保存路径目前没有日志压缩或历史状态淘汰，已完成的幂等回执、预留也会继续进入后续完整快照。

这意味着成本取决于“账本大小 × 操作次数”，并不只取决于当前物品数。若日志封装后的每次记录平均为 1 MiB，约 128 次追加就会触及文件上限；这是容量示例，不是实测。一次库存提取至少需要预留、完成两次提交；大载荷和分堆提取会更快消耗空间。达到限制会拒绝写入，不能靠无限提高上限解决。

SQLite 配合按记录增量更新，可以避免重复写入不变的 payload，按稳定操作 ID 查询回执，并把数量变更、预留和回执放进同一事务。只把整份 JSON 快照改存数据库仍会保留大部分序列化与复制成本；`InventoryLedger` 自身的完整状态克隆、线性查找也不会自动消失。数据库历史、WAL 和幂等记录仍需有明确保留策略。

当前没有真实用户日志、载荷分布和写入耗时，不能断言已经造成卡顿，也不能承诺性能提升倍数。

## SQLite 无法代替的恢复工作

- 游戏世界、游戏存档、客户端数据库、远端服务器/中继不能由一个 SQLite 事务统一提交。落地物品后崩溃、旧存档回滚、发送已接受但回执丢失，仍需证据核对和 uncertain 状态，不能自动重发或返还。
- 交易待托管记录应先脱离窗口，保存稳定操作 ID、服务器/用户/存档身份、完整 opaque payload、状态及确认依据；地图物品还需设计 Scribe 保存和本地托管交接，避免世界和外部记录各保留一份可交付物品。
- 红包库存预留与发送托管目前分两次提交。各自改成 SQLite 不会形成跨插件事务；应先明确可恢复的交接协议，再决定是否需要通用事务能力，不能让库存直接依赖红包类型。
- 红包记录当前上限为 2048 份、128 MiB，每次保存扫描同目录检查容量，未见已结算文件的清理路径。数据库能改善查询和更新，但安全归档、跨旧存档的去重和中继核对仍需业务规则。

## 接入成本与建议边界

客户端目标是 net472 / RimWorld Unity 运行环境。必须验证候选 .NET provider、原生 SQLite 的平台/架构、加载路径和其他 Mod 依赖共存；不能将 net472 编译通过或 .NET 10 下测试通过当作游戏运行兼容。当前库存打包只复制两份指定 DLL，接入后必须补齐托管、原生依赖和产物检查。[原生依赖说明](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/custom-versions)。

使用 `Microsoft.Data.Sqlite` 时，Async 方法仍同步执行，不能靠改成 async 消除游戏主线程等待。若采用后台写入，必须传入纯数据、串行控制提交顺序，并在真实提交完成后回到主线程确认，不能把入队当成功。[异步限制](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async)。

若后续试点，建议先只替换库存内部持久化实现，保持公开 API、codec 与 Legacy wire format；保留游戏存档内的完整快照，外部数据库用于后续操作恢复。继续按现有存档身份隔离，保留拒绝恢复时的分支记录，不做全局账户库存。导入旧日志须校验完整性、保留旧文件且可回退；SQLite 不可用时明确只读，不能静默切换到另一份空账本。若使用 WAL，运行中备份不能只复制主数据库文件。[WAL 与备份边界](https://sqlite.org/wal.html)。

单人熟悉代码、含必要回归的粗估：

| 范围 | 工作量 |
| --- | --- |
| provider / 原生依赖的游戏内兼容试点 | 2–4 个工作日，取决于可用测试平台 |

| 完整交易地图物品托管、红包中断核对 | 单独评估，不包含在库存迁移估算中 |

## 推荐执行顺序

1. 先补客户端交易持久托管、待交付记录和红包恢复核对；存储后端可先沿用文件，成功标准不变。
2. 记录真实日志大小、账本大小、加载内存与提交耗时；检查大载荷和连续分堆提取。日志历史可先减少内存驻留；压缩必须以可靠的完整存档成功检查点为依据，不能在 `ExposeData` 中直接删日志，也不能随意删除去重凭据。
3. 真实使用出现容量压力，或下一轮账本改造本就需要增量存储时，做 SQLite 兼容试点，通过后迁库存。红包按收益决定是否随后迁移，设置和凭据继续使用轻量文件。

迁移验收至少覆盖：磁盘满/写入失败、提交中断与重启、旧存档/复制存档/另存为、重复操作与冲突 ID、未知回执、缺失 codec 原字节保留，以及实际游戏内多平台加载。此次未运行构建或测试，仅新增评估文档。

代码依据：`Extensions/Inventory/Client/{InventoryJournal,InventoryLedger,InventoryGameComponent,BuiltInInventoryClientExtension}.cs`、`Extensions/Trade/Client/{TradeWindow,PhinixDefaultTradeBehaviour}.cs`、`Extensions/LegacyRedPacket/Client/{RedPacketInventorySendStore,RedPacketInventorySending}.cs`、`Common/Authentication/ClientAuthenticator.cs`、`docs/Inventory.md`、`docs/Compatibility-Boundaries.md`。

## 试点、导入与采用门槛（2026-10-05）

10 月 4 日库选型更积极的原因是接受较大重构，不是新增性能证据。本轮统一为：先证明恢复语义与实际增量存储收益，再决定 SQLite，不因库选型表写了候选就承诺迁移。

1. 固定代表性旧日志与存档样本，覆盖小账本、大 opaque 载荷、连续分堆操作、未决预留和回档分支；先测记录增长、峰值内存、提交与恢复耗时，事先明确可接受预算。
2. provider 试验分别记录支持的平台/架构、托管与原生版本、游戏加载路径和同名依赖共存情况。不支持的平台必须明确，不能用单台机器推断多平台。
3. 先定义 schema/version、写入负责人、存档分支和恢复证据，再在临时数据库导入。对条目、数量、完整载荷、预留和幂等回执进行核对，不只比较文件数或总金额。
4. 导入完成后才切换唯一权威存储，保留原文件与切换记录；中断后的再执行能识别已完成阶段，不能重复存入。迁移验证可以只读比较，不长期双写两个权威账本。
5. 数据库打开失败、schema 不支持、磁盘满、锁等待、WAL/备份恢复失败都应有可观察且保守的处理。原文件副本不能在新数据库产生业务提交后自动成为可写回退账本。
6. 首版保留游戏存档完整快照与现有拒绝恢复分支。外部数据库与游戏存档分别提交；复制/另存为、跨机器搬档、数据库缺失或较新时，沿用明确核对，不自动重放所有物品。
7. 有完整的中断/恢复、旧数据、备份和产物验证后才采用。真实收益不足或原生分发不可接受时，继续完善文件日志，不阻塞既有恢复改进。

本轮只补充规划，未采集样本、测量性能、执行导入或运行上述验证；现有工作量粗估不是排期承诺。
