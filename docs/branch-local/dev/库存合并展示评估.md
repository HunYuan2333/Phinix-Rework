# 库存合并展示评估

截图中的多行“大地懒肉 ×75”属于 Trade 的完整状态条目。`TradeInventoryCodec.GetAggregationKey` 明确返回 null，每份 `FrameworkItemPayload` 保持独立；右侧“×1”是状态条目数量，不是肉的数量。左侧标题又包含入账时的堆叠数，容易让玩家把两个计量单位混为一谈。

可实施的首选是展示分组：相同物品、材质、品质及来源的条目显示为一组，例如“大地懒肉 · 共 511 个（7 堆）”，展开后查看各堆详细状态。底层 EntryId、载荷、来源事件、预留与提取日志保留独立，不重写存档所有权。不同腐烂进度或烹饪原料可以在同一展示组中保留子行，不能让分组名称暗示它们状态相同。

泛用库存不能按名称解析 payload，也不能从名称末尾的 ×75 猜数量。应由 codec 的增量展示契约提供实际物品数与分组信息；缺失该能力的第三方条目继续使用原有独立展示。汇总在账本版本或语言改变时重建，不在 Draw 中反复物化全部物品。

组提取须明确输入按“实际物品个数”计量，并把选择映射回各 EntryId。当前不可分条目只有整份提取能力，部分提取需增加 codec 支持的无损拆分事务，不能先扣整份再丢弃余数。每日计划也需要稳定组身份、调度顺序和失败后的逐条余额记录。

真正合并载荷需要额外证明：除可变化的堆叠数量外，所有 Thing/ThingComp 状态均等价。腐烂时间、原料、毒物、衣物颜色、编码和绑定、人格/武器词条以及第三方 Comp 都可能阻止合并。名称一致、相同 Def 或普通 CanStackWith 均不足以证明任意 Mod 的完整序列化状态等价。现有来源事件也参与聚合身份，不应为了缩短列表而丢失追溯。

因此采用展示分组，底层状态合并仍须 codec 明确授权。已实现契约版本 5 的可选 `IInventoryItemPresentationCodec`、Trade/红包元数据展示器与可展开库存分组。子行显示实际物品数量，整份提取和每日计划明确注明每份数量。汇总排除已预留余额，来源事件和条目独立保留；第三方没有展示能力时保持单独行。本次不做组提取或载荷合并。库存回归新增分组计数、来源/品质隔离、预留变化、未知格式、身份碰撞和溢出场景。
