# 红包（RedPacket）插件移植与适配实施方案

> 2026-07-31，基于原 submod（Steam Workshop 3627190048，PhinixRedPacket）源码与 Phinix-Rework 代码库实测编写。
>
> **本文档是方案文档，不是已实施记录。**

**决策记录**：
- **通信与状态：保留老方案** —— v1 文本协议（`PHXRP|v1`）+ 第三方 HTTP 中继 + 客户端确定性复算状态机，**与老 submod 客户端保持互通**。
- **物品交互：走新流程** —— 原 `Trading.ProtoThing` / `TradingThingConverter`（旧 mod 类型）替换为 Rework `TradeItemSnapshot` / `TradeItemConverter`（TradeExtension 契约），插件声明 `DependsOn = builtin.trade`。
- **UI：走新流程** —— `IMainTabProvider` / `IBadgeProvider` / `IClientSettingsPanelProvider` / `Window` / `IClientMainThreadDispatcher`，删除全部 Harmony 补丁与硬编码挂点。
- **解耦原 mod 耦合** —— 不再直接引用原 `Client.Instance` 内部（Uuid / Online / TryGetDisplayName / DropPods / Settings / GetChatMessages），改用 `ExtensionHostContext` 通用服务与插件间 API。
- **服务端**：不新增服务端权威记账（老方案无服务器参与，红包状态在客户端复制）。插件为 **Client 单端**。
- **中继属"Legacy 协议适配器"例外**（《设计哲学》§3.7）——老协议流量不经过框架管线，不向框架聊天管线注入任何协议文本。

---

## 0. TL;DR

| 改动 | 可行性 | host 改动 | 插件改动 | Proto 改动 | 风险 |
|------|--------|-----------|----------|------------|------|
| **插件工程（Contracts + Client，单端）** | 🟢 高 | 零（仅构建链 + DLL 编号） | 新增 | 零 | 低 |
| **协议 + 中继迁移（v1 线格式不变）** | 🟢 高 | 零 | 迁移 `RedPacketProtocol` / `RedPacketRelayTransport` | 零 | 低 |
| **状态机迁移（行为不变）** | 🟢 高 | 零 | 迁移 `RedPacketManager` → 适配 Rework API | 零 | 中（确定性金额必须保持一致） |
| **物品模型新流程** | 🟢 高 | 零 | `TradeItemSnapshot` / `TradeItemConverter` + 空投解耦 | 零 | 低 |
| **UI 新流程** | 🟢 高 | 零 | Tab / 详情窗 / 设置面板 / 角标走框架挂载点 | 零 | 低 |
| **解耦原 mod 内部引用** | 🟡 中 | 可能补 1-2 个通用服务 | 替换 `Client.Instance.*` 为框架服务 | 零 | 中 |

## 1. 背景与目标

### 1.1 触发需求

原 Phinix 有一个红包 submod（PhinixRedPacket，Steam 3627190048），允许玩家把游戏物品打包成"红包"，其他玩家可领取，物品以空投舱送达。实现方式：

- 协议消息 `PHXRP|v1|...`（pipe 分隔文本）经**第三方 HTTP 中继**（`http://39.96.216.77/rp`，API key 硬编码，房间 `phinix-global`）在客户端间广播；
- 红包状态在每个客户端**全量复制**，靠确定性幸运算法（FNV-1a）与相同的过期时间保持同步；
- UI 通过 **Harmony 补丁**硬注入原 mod 的 `ServerTab`、`Root.Update`、`Client` 未读计数与聊天列表过滤；
- 物品与掉落直接使用旧 mod 的 `Trading.ProtoThing` / `TradingThingConverter` / `Client.Instance.DropPods`。

Rework 采用插件化架构。本方案把红包功能移植为 Rework 插件，**保留老协议与中继以兼容仍在使用老 submod 的客户端**，同时把物品交互、UI 和资源访问切到 Rework 新流程，并解掉对原 mod 内部的硬编码耦合。

### 1.2 老方案保留什么、替换什么

| 保留（兼容性红线） | 替换（现代化） |
|--------------------|----------------|
| v1 线格式 `PHXRP|v1|create/claim/assign/timeout` | 物品模型：`Trading.ProtoThing` → `TradeItemSnapshot` / `TradeItemConverter` |
| HTTP 中继（同一 room / API key，与老客户端同总线） | UI：Harmony 补丁 + 硬编码 tab index → 框架挂载点 |
| 客户端确定性复算状态机（金额、过期、扣减、掉落语义不变） | 资源访问：`Client.Instance.*` → `ExtensionHostContext` 服务 / 插件 API |
| 零宽字符聊天内嵌编解码（协议库保留，兼容历史报文） | 日志：`Verse.Log` / 无分级 → `hostContext.Log`（§3.8） |
| | 线程：自建 `MainThreadQueue` → `IClientMainThreadDispatcher` |

### 1.3 目标（按优先级）

| 优先级 | 目标 | 衡量标准 |
|--------|------|----------|
| **P0** | 与老 submod 客户端互通 | 老客户端 A 创建红包，新插件客户端 B 可领取，双方状态一致（同一中继房间） |
| **P0** | **双向收发（硬性验收）** | ① 新插件能**发送**：创建红包、发送领取请求，老客户端可收；② 新插件能**接收**：接收老客户端的创建/领取广播并完整处理（状态机 + 掉落 + 信件）；③ 新↔新 双向同样成立 |
| **P0** | 物品交互走新流程 | 选物品/记账/掉落全部基于 `TradeItemSnapshot` / `TradeItemConverter`，不引用旧 `Trading` 类型 |
| **P0** | UI 走新流程 | Tab / 详情窗 / 设置 / 角标走框架挂载点，零 Harmony 补丁 |
| **P1** | 解耦原 mod 耦合 | 插件源码中不再出现 `Client.Instance.Uuid / Online / DropPods / Settings / GetChatMessages` 等直接引用 |
| **P1** | 确定性算法单测 | 同输入（packetId/claimerUuid/remaining）→ 与 v1 完全一致的金额 |

### 1.4 非目标

- **不做服务端权威记账** —— 老方案中红包状态在客户端复制，服务器不参与；改动会破坏与老客户端的互通。
- **不改线格式、不引 protobuf** —— v1 文本协议即线格式，新增字段按"向后兼容追加"处理（解析时容忍缺省字段）。
- **不修老方案的已知局限** —— 两客户端并发 claim 同一红包时，因广播到达顺序不同可能产生金额分叉（老方案固有行为，文档注明，不"顺手修掉"）。

## 2. 原 submod 现状精确定位

### 2.1 组件清单

| 组件 | 职责 | 本方案处理 |
|------|------|------------|
| `RedPacketProtocol` | v1 文本协议 build/parse、零宽字符编解码、字段 base64 | **迁移保留**（线格式与兼容库） |
| `RedPacketRelayTransport` | HTTP 中继轮询/发送队列（700ms / 80ms、重试、断线清理） | **迁移保留**，按 §3.6/§3.8 加固 |
| `RedPacketManager` | 客户端状态机：HandleCreate/Claim/Assign/Timeout、确定性幸运算法、过期结算、掉落、信件、显示名缓存 | **迁移保留**，适配 Rework API |
| `RedPacketTab` / `RedPacketDetailWindow` | Tab UI 与详情窗（Patch ServerTab 注入 index 2） | **重写**：`IMainTabProvider` + `Window` |
| `ChatFilterPatches` ×4 | 聊天列表/未读/渲染过滤协议消息 | **删除**（新插件不把协议塞进聊天） |
| `RootUpdatePatches` | 每帧驱动中继/过期/主线程队列 | **删除**（主线程调度走 `IClientMainThreadDispatcher`） |
| `UnreadMessagePatches` | 未读计数排除协议消息 | **删除**（无聊天污染；角标用 `IBadgeProvider`） |
| `RedPacketSettings` + Mod 设置页 | 通知/聊天公告/未知物品抑制 | **重写**：`IClientSettingsPanelProvider`（Order 130） |

### 2.2 v1 线格式（保留，即线格式）

payload = `PHXRP|v1|{create|claim|assign|timeout}|...`（pipe 分隔）。中继传输的是**纯文本 payload**；零宽字符（U+200C=0 / U+200D=1，哨兵 U+2060×4）编码仅用于历史报文/聊天内嵌场景，解析库需兼容。

```
create : PHXRP|v1|create|id|senderUuid|defName|stuffDef|quality|hp|totalCount|totalPackets|type|createdTicks|expiresTicks|senderDisplayName(b64)[|luckyAlgoVersion]
claim  : PHXRP|v1|claim|packetId|claimerUuid|claimerDisplayName(b64)
assign : PHXRP|v1|assign|packetId|claimerUuid|amount|remainingPackets|remainingCount
timeout: PHXRP|v1|timeout|packetId|claimerUuid|utcTicks
```

> **注意**：原实现只广播 create 与 claim，`assign`/`timeout` 为死代码。新插件保留这四个类型的解析与构建（assign/timeout 可用于手动同步/补发场景），但默认行为与老客户端一致（仅 create/claim）。

### 2.3 状态机现状（实测，行为红线）

- 领取：claimer 广播 claim → 每个客户端用确定性 FNV 哈希（种子 = packetId、claimerUuid、remainingCount、remainingPackets）计算**相同金额** → 各自本地记账。
- 发送者本地持有 `StoredThings`（真实 Thing），按金额扣减；领取者本地 `SpawnReward` 空投。
- 过期：每个客户端本地在同一 `ExpiresAtUtc` 结算；发送者执行返还/特殊结算（Wastepack/GoldenCube：50% 袭击、25% 双倍返还、25% 销毁）。
- 完成：发送者收信件汇总（领取明细、耗时、返还数量）。
- 反压：pending claims 20s 超时、入站消息 200 条上限、掉落每组 ≤100 空投舱。

## 3. 目标架构（老方案 + 新流程）

### 3.1 总体

```
RedPacketExtension.Client（Rework 插件，单端）
┌────────────────────────────────────────────────────┐
│ 兼容层（老方案，行为红线）                            │
│  ├─ RedPacketProtocol   ：v1 文本协议 build/parse    │
│  ├─ RedPacketRelay      ：HTTP 中继（同 room/API key）│
│  └─ RedPacketStateMachine：确定性复算状态机           │
├────────────────────────────────────────────────────┤
│ 新流程层（现代化）                                    │
│  ├─ 物品：TradeItemSnapshot / TradeItemConverter     │
│  ├─ UI  ：RedPacketTab(IMainTabProvider)             │
│  │        RedPacketDetailWindow(Window)              │
│  │        RedPacketSettingsPanel(IClientSettingsPanelProvider)
│  │        RedPacketUnreadBadge(IBadgeProvider)       │
│  ├─ 服务：IClientSessionContext / IClientUserDirectory
│  │        / IClientMainThreadDispatcher / hostContext.Log
│  └─ 入口：[PhinixExtension("builtin.legacy-redpacket", DependsOn=["builtin.trade"])]
└────────────────────────────────────────────────────┘
```

- **通信**：保持老方案 —— 插件直接与中继通信（§3.7 的"Legacy 协议适配器"例外），**不向框架管线注入红包协议文本**，聊天管线零污染。
- **物品**：走新流程 —— 所有物品快照使用 `TradeItemSnapshot`，转换用 `TradeItemConverter`（TradeExtension.Client）。
- **UI**：走新流程 —— 全部通过框架挂载点注册，零 Harmony 补丁。
- **解耦**：资源访问全部经框架服务（见 §3.5 映射表）。

**收发双路径（P0 验收）**：

```
发送路径（出站）：
  创建：Tab UI 选物品 → TradeItemSnapshot → RedPacketStateMachine.BuildCreate → 中继 POST
  领取：Tab UI 点领取 → RedPacketStateMachine.RequestClaim → BuildClaim → 中继 POST

接收路径（入站）：
  中继轮询 GET → RedPacketProtocol.TryParse → RedPacketStateMachine.HandleXxx
  → 状态机记账 →（领取者）SpawnReward 空投 /（发送者）扣减 StoredThings + 信件
```

两条路径缺一不可：只发不收或只收不发都不满足验收。Phase B（中继迁移）完成后即以"新→老、老→新、新↔新"三个方向做连通性验证。

### 3.2 兼容层：协议与中继（迁移）

- `RedPacketProtocol` 原样迁移（含零宽编解码），作为线格式唯一实现。
- `RedPacketRelayTransport` 迁移，加固点：
  - 队列有界（§3.6）：发送/接收队列设上限（如 512），超出丢最旧并记 Warning；
  - 日志走 `hostContext.Log`（§3.8）：轮询/发送失败 WARNING，重试成功 INFO，路由细节 DEBUG；
  - 异常隔离（§3.5）：单次请求失败不中断，按原逻辑退避重试；
  - 清理：`Shutdown` / 断线时清空队列与游标（对应原 `Clear()`）。
- **与老客户端互通条件**：同一中继地址、同一 room（`phinix-global`）、同一 API key。API key 硬编码问题保留（与老客户端一致才能互通），但集中在插件内一个常量处并注明安全风险。

### 3.3 兼容层：客户端状态机（迁移，行为不变）

`RedPacketManager` 迁移为 `RedPacketStateMachine`（或保留原名），**逻辑逐行对齐**：

- `HandleCreate` / `HandleClaim` / `HandleAssign` / `HandleTimeout`：字段解析、幂等去重（`ProcessedProtocolKeys`）、显示名缓存逻辑不变；
- 确定性金额：`DeterministicRangeInclusive` + `MixSeed`（FNV-1a）种子输入不变，保证与老客户端同金额；
- `StoredThings` 扣减 / `SpawnReward` 空投 / 过期结算 / 特殊物品（Wastepack、GoldenCube）逻辑不变；
- 信件（`QueueSenderSummary`）、到期返还、袭击触发逻辑不变。

**适配点**（仅替换实现依赖，不改行为）：

| 原引用 | 替换为 |
|--------|--------|
| `Client.Instance.Uuid` | `IClientSessionContext.Uuid`（宿主服务） |
| `Client.Instance.Online` | 服务组合或宿主新增"在线状态"通用服务（见 §3.5） |
| `Client.Instance.TryGetDisplayName` | `IClientUserDirectory.TryGetDisplayName` |
| `Client.Instance.Settings.BlockedUsers` 等 | 不涉及（无聊天过滤） |
| `Trading.ProtoThing` | `TradeItemSnapshot` |
| `TradingThingConverter` | `TradeItemConverter` |
| `Client.Instance.DropPods` | 独立空投帮助类或 Trade 客户端掉落 API（见 §3.4） |
| 自建 `MainThreadQueue` | `IClientMainThreadDispatcher.Enqueue` |
| `Verse.Log.*` / 无分级 | `hostContext.Log`（§3.8） |
| `PhinixRedPacketMod.Settings` | 插件设置（`IClientSettingsPanelProvider` 读写） |

### 3.4 物品交互新流程

- **模型**：发送者 UI 选物品 → `TradeItemConverter.ConvertThingFromVerse(thing)` → `TradeItemSnapshot` → 存入红包模板；`create` 报文中的物品字段（defName/stuffDef/quality/hp）从快照序列化。
- **领取**：领取者收到 claim 后 `TradeItemConverter.ConvertThingFromSnapshotOrUnknown(snapshot)` → `Thing` → 空投。
- **空投**：抽成独立 `RedPacketDropHelper`（基于 Verse `DropPodUtility` / `DropCellFinder`，组数上限 100，地图选择逻辑与 Trade 的 `dropCurrentMap` 语义一致），不依赖 `Client.Instance.DropPods`。
- **依赖**：插件 `DependsOn = new[]{"builtin.trade"}`，通过 TradeExtension 契约解析转换器/掉落能力（插件间协作，§3.3 设计哲学）。

### 3.5 解耦清单：原 mod 耦合 → 框架服务

| 原耦合 | 框架替代 | 状态 |
|--------|----------|------|
| `Client.Instance.Uuid` | `IClientSessionContext.Uuid` | 已有服务 |
| `Client.Instance.TryGetDisplayName(uuid, out name)` | `IClientUserDirectory.TryGetDisplayName(uuid, out name)` | 已有服务 |
| `Client.Instance.Online` | `IClientSessionContext.SessionId` + `IFrameworkClientLifecycle.CompatibilityMode` 组合；如语义不完整，宿主新增 `IClientConnectivityState` 通用服务 | 需评估（可能新增 1 个通用服务，属 host 增量，§6） |
| `Client.Instance.Settings.ChatMessageLimit / BlockedUsers / DropCurrentMap` | 不涉及 / 插件自身设置 / Trade 设置 | — |
| `Client.Instance.GetChatMessages()` | 不涉及（无聊天过滤） | — |
| 每帧 `Root.Update` | `IClientMainThreadDispatcher` + 定时检查（沿用原 1s 过期节流，不依赖每帧） | 已有服务 |
| `PhinixRedPacketMod` 静态入口 | `IPhinixExtensionModule` 生命周期（Register/Activate/Shutdown） | — |

### 3.6 UI 新流程

| 原组件 | 新组件 | 挂载点 |
|--------|--------|--------|
| `RedPacketTab`（Patch ServerTab） | `RedPacketTab : IMainTabProvider` | `RegisterApi<IMainTabProvider>`，TabOrder 1100 |
| `RedPacketDetailWindow` | `RedPacketDetailWindow : Window` | UI 自行打开（`IClientWindowService`） |
| 未读计数（Patch Client） | `RedPacketUnreadBadge : IBadgeProvider` | `RegisterApi<IBadgeProvider>` |
| Mod 设置页 | `RedPacketSettingsPanel : IClientSettingsPanelProvider` | Order 130 |
| `ChatFilterPatches` ×4 | 删除 | — |
| `UnreadMessagePatches` | 删除（红包未读由插件自身统计） | — |

UI 渲染遵循 §8.3：Tab Draw 缓存红包列表与翻译，无每帧分配。

## 4. 设计哲学合规要点

| 哲学条目 | 约束 |
|----------|------|
| **§1.1 插件平权** | 红包与 Chat/Trade 同级注册；宿主无专用分支 |
| **§1.2 host 不依赖插件** | 只引用 `ClientExtensionAbstractions` + TradeExtension 契约；`Client.csproj` 不新增 ProjectReference |
| **§3.7 通信走管线** | 红包协议经中继（Legacy 协议适配器例外，同 LegacyAdapter 的定位）；**不向框架聊天/命令管线注入红包文本**，也不绕过管线发框架包 |
| **§3.5 错误隔离** | 单报文解析失败跳过；中继请求失败退避重试，不中断；反序列化 try-catch |
| **§3.6 资源边界** | 中继队列、pending claims、StoredThings 有上限；定时器 `IDisposable`，Shutdown 释放；事件订阅配对退订 |
| **§3.8 日志** | 全部经 `hostContext.Log` / `ILoggable` 分级；异常带完整 Exception；API key 等敏感信息不进日志 |
| **§8.3 UI 性能** | Tab Draw 路径零分配 |
| **§6 增量** | 不修改既有接口/签名；如需"在线状态"通用服务，新增接口 + host 增量实现 |

## 5. 实施阶段

每阶段独立可编译、可运行、可验证。

### Phase A：工程骨架
- 新建 `Extensions/RedPacket/Contracts`（消息 DTO + v1 解析库）与 `Extensions/RedPacket/Client`（插件入口）。
- 参考 Chat/Trade 的 csproj 结构与 AfterBuild 拷贝规则；DLL 编号按依赖顺序（如 `13-LegacyRedPacketExtension.dll`、`14-LegacyRedPacketExtension.Client.dll`，参考《设计哲学》§5.1）。
- 注册进 `Phinix.sln`；新增中英翻译键文件 `RedPacketExtension.xml`。

### Phase B：兼容层迁移（协议 + 中继）
- 迁移 `RedPacketProtocol`（含零宽编解码）。
- 迁移 `RedPacketRelayTransport`，按 §3.2 加固（有界队列、日志分级、异常隔离、Shutdown 清理）。
- 验证：可与老 submod 客户端同房间互通（创建/领取报文收发）。

### Phase C：状态机迁移
- 迁移 `RedPacketManager` 全部逻辑为插件内状态机，行为逐行对齐（确定性金额、过期、特殊物品、信件）。
- 用框架服务替换直接引用（见 §3.3 适配表，除物品/UI 外先做最小替换）。

### Phase D：物品交互新流程
- 替换 `Trading.ProtoThing` → `TradeItemSnapshot`；`TradingThingConverter` → `TradeItemConverter`。
- 抽 `RedPacketDropHelper`（空投、地图选择、组数上限），移除 `Client.Instance.DropPods`。
- 声明 `DependsOn = builtin.trade`，解析 Trade 契约能力。

### Phase E：UI 新流程
- `RedPacketTab : IMainTabProvider`、详情窗、设置面板、`IBadgeProvider` 角标。
- 主线程调度切换为 `IClientMainThreadDispatcher`；删除全部 Harmony 补丁。

## 7. 测试要点

### 7.1 功能测试

| 测试项 | 方法 | 预期 |
|--------|------|------|
| 创建 → 领取 → 空投 | 新插件客户端 A 发包，新插件客户端 B 领取 | B 空投舱收到物品；A 扣除 StoredThings；双方 remaining 一致 |
| 新→老 发送 | 新插件客户端创建红包 + 发送领取 | 老 submod 客户端收到创建广播、可领取；新客户端收到老客户端的 claim 并正确记账/扣减 |
| 老→新 接收 | 老 submod 客户端创建红包 + 发送领取 | 新插件客户端收到创建广播并显示、可领取；老客户端收到新客户端的 claim 并正确记账 |
| 新↔新 双向 | 两个新插件客户端 | 创建/领取/掉落/信件全流程正常 |
| 重复领取 | B 连续两次 claim | 幂等拒绝（ProcessedProtocolKeys） |
| 自领 | A 领取自己的红包 | 拒绝 |
| 过期结算 | 短过期不领取 | 返还/袭击/销毁 + 信件 |
| 特殊物品 | Wastepack 红包过期 | 50% 袭击 / 25% 双倍返还 / 25% 销毁 |
| 断线重连 | 中继请求失败后恢复 | 队列退避重试，不丢包不崩溃 |

### 7.2 已知局限（老方案固有，不做"修复"）

| 场景 | 行为 |
|------|------|
| 两客户端同时 claim 同一红包 | 广播到达顺序不同可能导致金额分叉（与老客户端行为一致） |
| 客户端离线期间红包过期 | 以本机时钟结算（与老客户端一致） |
| 中继服务不可用 | 红包功能整体不可用（与老客户端一致） |

### 7.3 UI 性能（§8.3）

- Tab 打开/滚动无每帧分配（缓存红包列表与翻译）。
- 大列表（100+ 红包）滚动流畅。

## 附录 A：v1 消息保留清单

| 消息 | 用途 | 本方案 |
|------|------|--------|
| `create` | 创建红包（广播） | 保留，行为不变 |
| `claim` | 领取意图（广播，各端确定性复算） | 保留，行为不变 |
| `assign` | 分配同步（原死代码） | 解析/构建保留，可用于手动补发，默认不主动广播 |
| `timeout` | 过期结算（原死代码） | 解析/构建保留，默认由各端本地过期逻辑驱动 |

**字段追加规则**：解析时对新增字段取默认值，保证新字段出现在报文尾部时老客户端仍可解析（老客户端 `Split('|')` 后按索引读取，尾部追加兼容）。
