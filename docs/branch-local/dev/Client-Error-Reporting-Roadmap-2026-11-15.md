# Rework Client 统一错误窗口与堆栈保留 Roadmap

日期：2026-11-15。状态：E0 已完成；E1/E2/E3 代码及自动验证已完成，真实游戏交互和发行验收待 E5；E4 代码迁移、逐位置审阅及自动验证已完成；M1 本地整合与自动验证已完成；E5 进行中，联合白盒及测试候选已完成，真实游戏与发行验收待完成。详见 [E0/E1 实施记录](Client-Error-Reporting-2026-11-15/IMPLEMENTATION.md)与 [E2 实施记录](Client-Error-Reporting-2026-11-15/E2-IMPLEMENTATION.md)。

依据：[源码评估报告](../audits/Client-Error-Observability-2026-11-15/REPORT.md)及其错误位置清单。当前用户决定优先于报告中较宽泛的首版恢复系统建议。

## 1. 已确定的产品目标

普通玩家遇到需要关注的错误时，看到一个能理解的窗口，点击“复制错误详情”就能向维护者提供插件身份、出错步骤、完整异常原因链和堆栈；原本需要交给 RimWorld 的异常继续按原堆栈传播。

第一版的核心路径：

```text
故障发生
  → 统一入口立即保存异常详情，生成错误编号
  → 将需要提醒的故障交给 Host 主线程通知窗口
  → 按原边界继续抛出 / 隔离并返回失败 / 清理并终止任务

玩家打开窗口 → 复制已保存的错误详情 → 显示“已复制” → 可关闭窗口
```

记录和异常传播不等待玩家点击。关闭窗口不代表问题恢复，也不代表交易取消、成功、退款或物品交付完成。

第一版只提供“复制错误详情”“关闭”，不增加通用重试、自动退款、插件热重载、远端遥测或独立业务恢复框架。已有安全重试和恢复机制仍归原插件管理。

## 2. 必须固定的边界

### 异常如何交给 RimWorld

| 边界 | 统一出口后的行为 | 验收要求 |
|---|---|---|
| 当前同步调用明确应继续交给游戏的异常 | 保存详情、安排窗口，然后在原 catch 中原样重抛 | 原始调用帧和 inner 保留；不等待 UI，不改成新异常 |
| 已有插件隔离边界，如 event/task/handler | 保存详情，按该边界隔离、返回失败或取消；经现有日志桥接进入 RimWorld 日志 | 不为制造红字而额外抛出；无关插件与后续任务继续运行 |
| 网络、Timer、后台 Task/线程入口 | 在实际执行处观察异常，记录并标记失败/停止相关工作；主线程只负责通知 | 不把后台异常延迟扔到游戏线程，不让它逃出工作线程 |
| 预期取消、输入拒绝、缓存 miss | 保持原有正常结果，必要时做轻量记录 | 不每次弹窗，不人为构造异常 |
| 错误窗口、剪贴板、日志出口自身失败 | 保留原始故障，记录次级故障，停止递归通知 | 不覆盖原异常，不连续弹出“报错窗口又报错” |

“记录到 RimWorld 日志”和“重新抛出异常”是两种不同处置，实施和测试必须分别登记，不能互相冒充。第一版不增加 AppDomain 全局异常继续运行补丁、不通过 Harmony 拦截所有其他 Mod 的错误。

### 窗口与复制内容

- 标题：“Phinix Rework 遇到问题”。正文说明插件/功能、失败操作和影响；无法确认结果时明确写“结果暂时无法确认”，不能笼统声称“未执行”或“已安全恢复”。
- 主要按钮：“复制错误详情”；次要按钮：“关闭”。复制后窗口保持打开并显示“已复制，可粘贴给维护者”；复制失败显示“复制失败，请重试”，不丢原报告。
- 玩家正文不直接使用任意 `Exception.Message`；采用 Host 通用提示或插件提供的本地化安全提示。
- 复制内容：错误编号、时间、Host/游戏版本与运行时、插件 ID/版本、操作/阶段、必要关联 ID、已知操作结果、异常类型/原因链/堆栈。版本事实缺失标“未知”，不依赖完整环境采集成功。
- 保留 AggregateException 分支与 ReflectionTypeLoadException.LoaderExceptions。消息和本机路径按策略脱敏；保留定位所需的类型、方法调用帧和原因结构，不以脱敏为由删除整条堆栈。
- 默认不复制凭据、session、secret、packet/body、SQL 参数、聊天全文、存档内容或完整 Mod 配置。不同于删除任意异常字符串中的所有敏感信息，脱敏能力需要测试，不能假定只过滤 token 这个单词就足够。
- 同类故障合并次数、首次/末次时间；同一故障沿调用链重复上报复用错误编号。最多一个错误窗口，新故障更新/汇总到当前窗口，已关闭的重复故障不每帧重新弹出。
- 保存近期有界记录；初始建议 64 个故障组，记录总大小与异常树深度也设上限。达到限制明确标注淘汰/截断，不静默删除中间帧或原因；常规异常详情必须完整。具体预算在第一阶段根据样本确定并纳入测试。
- 窗口关闭后可从 Host 设置中的“最近错误”重新打开；插件商店缺失、禁用或启动失败不影响该入口。初版记录限本次进程，跨重启使用原有 RimWorld 日志，不额外建设持久诊断数据库。

## 3. 实施阶段

每阶段独立可审阅、附检查结果；状态完成必须有对应证据，不以“接口已存在”视为整条链路完成。

### E0：锁定接入合同与迁移清单

状态：已完成。目标：把本路线图落成最小技术合同，随后立即实现第一条完整路径。

- 定义中立的故障上报入口、模块身份、错误编号、只读详情、通知级别；优先复用现有 HostLogEntry / IExtensionLogger 的异常能力。
- 共享 Common 仅放无游戏依赖的采集合同/挂点，Host 实现记录、窗口和剪贴板；游戏 API 留在对应客户端适配层。服务可供内置与第三方同样使用。
- Report 只采集和通知，不替业务决定重抛/重试，不设计“返回 handled 即恢复”的总开关。不强制 BCL 异常继承自定义异常，不先批量引入新异常子类。
- 明确 Report 自身不应向调用者抛错；采集和记录先于外部日志出口，递归时保留原故障及有界次级摘要。
- 以评估清单为基线，建立逐位置处置登记：文件/位置、原行为、目标行为、是否保留栈、是否弹窗、是否重抛、验证与完成状态。catch 和 throw 都要登记，正常校验不机械改写。
- 开工重新核验文件指纹和未提交修改，不覆盖正在进行的 SQLite/Trade 工作；共享源码在 Common 正式修改并由客户端精确 pin，不改 vendor/protobuf。

完成门槛：最小合同、归属与预算确定；明确无需改动的公开合同与确需新增/变更的 ABI，明确发行组合。E0 不单独发布。

### E1：先完成“出错 → 窗口 → 复制 → 原堆栈传播”的完整路径

依赖：E0。状态：代码及双运行时白盒验证完成，真实游戏窗口/剪贴板待验收。目标：尽早得到玩家能直接使用的功能。

- 实现 Host 故障记录、详情格式化和通知控制器；线程安全地接收故障，主线程打开单一窗口。
- 使用现有窗口服务和对应游戏版本的剪贴板实现；不在中立合同里引入 Verse/Unity 类型。窗口尽量少依赖可选插件、动态贡献者和复杂业务呈现，避免呈现系统坏掉后无法报错。
- 实现中英文正文、复制反馈、关闭、重复合并、最近错误入口。
- 从一个真实 Host 同步入口接入，演练原样重抛；从生产 dispatcher 接入，演练任务被隔离而后续任务继续。两条路径都能复制到原始故障帧。
- 覆盖启动早期收集：窗口服务尚未就绪时暂存通知，主线程可用后再展示。记录必须先于模块加载/激活建立。
- 通知不得被业务任务队列满或 scope 结束静默删除。优先在现有 Host 更新流程处理一个有界通知状态，避免新建第二套业务任务调度器；Host 无法继续更新/退出进程时只能保证已有日志路径尽力保留，不能承诺弹窗必达。

完成门槛：非 DevMode/Release 情况下，玩家无需打开日志或理解代码即可复制完整报告；复制与关闭不影响异常传播或操作状态；错误窗口自身失败不会递归。

### E2：修复共享加载层与公共回调边界

依赖：E1。状态：代码与双运行时定向验证完成；Common 本地修改需在发行前提交并固定 gitlink，实际游戏仍待验收。目标：第三方和内置插件共同经过的入口不再先丢掉异常。

接入顺序：

同一主异常和清理异常必须全部保留；正常继续隔离的路径不统一改成 rethrow。不必为关联 ErrorId 扩大修改所有公共 snapshot/result：先复用既有服务查询/内部映射，确有需要时单独记录 ABI 改动。

完成门槛：相同故障注入到内置和第三方样例，报告质量与隔离规则一致；新插件无需 Host 业务特例。旧插件内部主动吞异常仍是明确覆盖限制。

## 4. 验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 主线程同步异常 | 原始栈进入记录；安排弹窗后原样传播，不等待点击 |
| task/event/插件 handler 异常 | 单次失败可复制；无关任务/订阅者继续，不额外抛到游戏线程 |
| constructor/Register/Activate/Shutdown 及依赖失败 | 插件身份/阶段准确，原异常、LoaderExceptions 和清理失败均可追踪 |
| 后台网络/Timer/Task 异常 | 实际入口观察故障、相关工作失败/停止，主线程通知，不崩溃式转抛 |
| 非 DevMode 的 Release | 原因链与堆栈仍被采集，玩家可直接复制 |
| 复制/剪贴板不可用、窗口绘制失败 | 原报告仍在；有可理解反馈；没有递归或二次业务提交 |
| 每帧同类错误及大量不同错误 | 单窗口、合并计数、有界资源；抑制/淘汰/截断明确可见 |
| 同一异常穿过多个 catch | 一个主要错误编号，首次原栈保留，新增清理故障单独关联 |
| 启动早期、队列满、切 Game、模块停止 | 不持有旧 Game/插件回调，不将通知交付误当业务恢复，不无痕丢记录 |
| 取消、超时、能力缺失、坏包/缓存 miss | 分类符合原行为；正常拒绝不连续弹窗；实际故障可查 |
| NotSent / Unknown / 已提交后刷新失败 | 玩家提示与事实一致，无自动重发、物化、退款或伪造确认 |
| 凭据、payload、路径与敏感异常消息 | 复制样本完成脱敏，类型/调用帧/原因结构仍可排查 |
| 中英文、小窗口与长堆栈 | 按钮可用、正文可读、报告复制完整，不依赖屏幕能显示所有堆栈 |

自动检查只拦截明确危险模式：新增具名重抛、无 inner 换异常、实际故障只记 Message/类型而无诊断引用等。正常取消、预期 TryParse/缓存 miss、单纯回滚重抛需要审阅依据，不能用正则“一刀切禁止 catch”。

## 5. 首版范围与后续恢复

E0–E5 加 M1 联合整合门槛构成首版。E1 是第一个可体验里程碑，E2 是插件公共覆盖里程碑，E5 才是发行完成。当前 E0 已完成，E1/E2 仍缺实际游戏验收与统一发行闭合，不能把公共边界落地视为全量错误处理迁移或发行完成。

后续若具体功能有需要，再增加“重新打开视图”“刷新”“重连”等 owner 提供的安全动作；每个动作单独证明 scope、结果和幂等性。统一窗口的“关闭”和错误被记录都不能作为恢复成功依据。跨重启故障历史、远端遥测和完整自动恢复另立任务，不阻塞首版。
