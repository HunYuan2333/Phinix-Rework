# Host 能力缺口与统一插件日志审计

> 审计日期：2026-09-13  
> 范围：当前 `dev` 分支的 Client Host、Server Host、共享扩展框架、官方扩展及开发者文档。  
> 性质：独立的 Host 现状审计、适用性判断和整改顺序，不是已实现功能说明，也不针对某个具体业务插件。

## 1. 结论

当前 Host 已经具备扩展发现、注册、静态启用、API 注册、部分管线、主线程派发、基础存储路径和扩展管理界面，足以承载普通 UI 与消息类插件；但若把开发者指南描述的依赖顺序、失败隔离、统一日志和持久化暗示当成已实现保证，实际运行会出现明显偏差。

用户关于“插件日志是不是还没有统一”的判断成立。插件调用 `hostContext.Log` 后只进入 RimWorld 或服务端日志出口，并不会自动进入客户端扩展管理器的 300 条日志缓冲。直接调用 `Verse.Log`、`Console.WriteLine`、`Debug.WriteLine` 的路径也仍然存在。因此现在同时存在多个互不完整的日志面，无法按插件追踪一次操作。

更严重的 Host 缺口集中在生命周期和依赖执行：依赖图没有参与拓扑排序；循环依赖只警告不阻断；缺失、注册失败或激活失败的依赖不会可靠阻止下游插件；注册失败的模块仍可能执行 `Activate()`；已注册的 API 和处理器不会回滚；客户端也没有实际调用框架的 `Shutdown()`。这些行为与中英文开发者指南里的承诺不一致。

整改不应把 Host 扩张成数据库、业务协调器或热加载容器。判断一项能力是否应进入 Host，只看它是否是多个插件共同需要、能保持业务无关、能由 Host 统一实施，并且其收益足以覆盖兼容成本。其余能力应留在插件或延后。

## 2. 已经做到的能力

| 能力 | 当前状态 | 证据与边界 |
|---|---|---|
| 扩展发现 | 已实现 | 扫描已加载程序集中的 `IPhinixExtensionModule` 并实例化，见 `PhinixExtensionRegistry`。 |
| 三段式接口 | 接口已实现 | 有 `Register`、`Activate`、`Shutdown`，各阶段也有局部异常捕获。执行顺序和状态约束仍不完整。 |
| 静态禁用 | 已实现 | `StaticActivationPolicy` 读取启动时快照，重启后生效。 |
| API 注册和多提供者解析 | 基础实现 | 可注册和解析接口；多个提供者时保留第一个并警告。没有跟随插件状态撤销。 |
| 消息、命令、物品管线 | 已实现 | 有拦截器、默认处理器、观察者和优先级排序。Legacy 仍有旁路。 |
| 主线程派发 | 基础实现 | 有容量 500 的队列和逐项异常隔离。超限策略不适合事务工作。 |
| 扩展管理界面 | 基础实现 | 展示扩展状态、依赖提示和最多 300 条框架日志。这里的日志并非统一插件日志。 |
| 服务端扩展持久化 | 基础实现 | `RegisterPersistent` 在服务端会被 `LoadExtensionState` / `SaveExtensionState` 消费。缺少单扩展错误隔离和原子写保证。 |
| 客户端存储路径 | 基础实现 | 插件可取得一个文件路径。它只是路径分配，不是持久化事务服务。 |

## 3. 统一插件日志：当前没有完成

### 3.1 日志入口和管理器缓冲是两条断开的链

`ExtensionHostContext.Log` 的类型是 `Action<string, LogLevel>`。客户端把它连接到 `Client.Log(new LogEventArgs(...))`，最终写入 `Verse.Log`。扩展管理器的日志缓冲则只在 `PhinixFrameworkClient.RaiseLogEntry()` 中调用 `appendExtensionLog()` 时更新。

结果如下：

- 插件规范地调用 `hostContext.Log`，日志能进 RimWorld 日志，但通常不进扩展管理器；
- `PhinixFrameworkClient` 自己调用 `RaiseLogEntry`，日志能进管理器，订阅建立后也会进 RimWorld 日志；
- 构造期间为了同时照顾两个出口，部分诊断分别调用 `RaiseLogEntry` 和 `hostContext.Log`，形成重复发送逻辑；
- 管理器中的“扩展日志”实际是部分框架日志，名称会让使用者误以为它覆盖所有插件。

因此 300 条容量上限本身已经实现，但它限制的是一个不完整的数据源。

### 3.2 日志记录缺少插件身份和结构

`LogEventArgs` 只有可变的 `Message` 与 `LogLevel` 字段；`hostContext.Log` 也没有模块上下文。现状无法稳定记录：

- `ExtensionId`、程序集或来源 Mod；
- 事件类别和稳定的 EventId；
- 一次跨线程或跨组件操作的 CorrelationId；
- 原始 `Exception` 对象及内部异常；
- 线程、游戏存档标识、游戏 tick；
- 可安全筛选的结构化字段。

插件只能把这些内容拼到字符串中。前缀容易漏写或写错，日志系统也无法可靠筛选、聚合和脱敏。服务端把所有插件的 `hostContext.Log` 都以 `typeof(Server)` 作为 sender，最终的 `sender.GetType().Namespace` 不能表示真实插件来源；对空 sender 也没有防御。

### 3.3 仍有多个旁路

已确认的旁路包括：

- `LegacyChatProtocolAdapter` 大量直接调用 `Verse.Log`；
- Client 启动、认证、用户事件、设置面板异常直接调用 `Verse.Log`；
- `ClientMainThreadDispatcher` 和主题加载器直接调用 `Verse.Log`；
- 共享序列化和扩展扫描部分错误写入 `Debug.WriteLine`；
- 服务端控制台命令使用 `Console.WriteLine`，命令异常和插件运行日志没有统一来源模型。

这些日志不会同时出现在管理器、游戏日志和服务端持久日志中，也无法按插件启停状态统一处理。

### 3.4 已发现敏感字段风险

`LegacyChatProtocolAdapter.SendChatMessage` 的普通日志包含 `sessionId` 和用户 UUID。SessionId 属于认证会话信息，不应写入可复制、可上传的游戏日志。统一日志系统必须先做字段分类和脱敏，不能只把现有字符串转发到更多出口。

### 3.5 300 条缓冲仍缺少运维能力

客户端缓冲在 Release 构建中直接丢弃 DEBUG 记录，并逐条保留最近 300 条。它目前没有：

- 按插件、等级、事件类别筛选；
- 搜索、复制诊断包或导出；
- 丢弃计数和速率限制，单个插件可刷掉其他插件记录；
- 跨启动的可选诊断文件；
- CorrelationId 视图；
- 对重复日志的合并；
- 日志 sink 失败的降级与自监控。

DEBUG 是否输出应由运行时配置和 sink 策略决定，不应在写入共享内存缓冲前由条件编译永久删除。

### 3.6 建议的统一日志模型

长期可增加由扩展注册过程绑定身份的 `IExtensionLogger`，插件不能自行填写 `ExtensionId`：

```text
HostLogEntry
  TimestampUtc
  Level
  ExtensionId / HostComponent
  EventId
  Category
  Message
  Exception
  CorrelationId
  Fields (受控键值，进入 sink 前脱敏)
```

同一条 `HostLogEntry` 由一个聚合器分发到多个 sink：客户端 `Verse.Log`、扩展管理器环形缓冲、服务端 Logger，以及用户显式启用的诊断文件。聚合器负责等级过滤、脱敏、限速、重复合并和 sink 失败隔离。

兼容迁移期间必须保留 `hostContext.Log`。第一步只需让它与 `RaiseLogEntry` 汇入同一个聚合出口，保证插件上报在 Verse 和管理器各出现一次；之后再以新增服务提供带 ExtensionId 的 logger。所有直接 `Verse.Log`、`Console.WriteLine` 和 `Debug.WriteLine` 逐步改走聚合器，只有最终 sink 可以直接写目标日志系统。完整结构化字段、诊断文件和导出属于后续增强，不是修复“管理器看不到插件日志”的前置条件。

## 4. 生命周期和依赖关系缺口

### 4.1 依赖图没有控制执行顺序

`ExtensionDependencyGraph` 记录直接依赖和反向依赖，并用 DFS 检测循环，但循环只产生 warning。注册顺序仍是模块类型全名的字母序，激活顺序沿用同一个列表，关闭也是正序遍历。

这与开发者指南声称的“DAG 拓扑注册、拓扑激活、逆序关闭、循环模块 Failed 并跳过”不一致。任何声明了依赖关系的插件都无法获得指南承诺的执行顺序。

### 4.2 失败模块可能继续激活

模块在调用 `Register()` 之前就被加入 `discovered.Modules`。如果 `Register()` 抛异常，结果被标记为 `Failed`，但 `ActivateExtensions()` 不检查结果状态，仍遍历模块并调用 `Activate()`。

此外，`Register()` 抛异常前写入的 API、处理器、codec、UI provider 和持久化注册不会回滚。`Activate()` 失败后这些注册项也继续可解析。Host 因此可能呈现“状态 Failed，但部分功能仍在运行”的半启用状态。

### 4.3 依赖失败不会传播

静态策略只检查用户明确禁用的直接依赖。它没有完整处理：

- 声明的依赖根本不存在；
- 依赖初始化、注册或激活失败；
- A 依赖 B、B 依赖被禁用的 C 这种传递关系；
- 重复 ExtensionId 导致的歧义；
- 循环依赖。

重复 ExtensionId 当前只记录 warning，两个模块仍可继续注册和激活。

### 4.4 客户端 Shutdown 的实现与既定生命周期不一致

`PhinixFrameworkClient.Shutdown()` 会注销网络处理器、释放计时器并调用扩展关闭，但 Client 侧没有找到任何对 `frameworkClient.Shutdown()` 或 `Dispose()` 的调用。已经确定客户端扩展采用进程级生命周期，启停重启生效，所以不应在退出存档时调用它，也不需要为了这条死路径引入运行时重载。

正确处理是把 Shutdown 限定为客户端进程结束时的对称清理，以及测试中的显式 Host dispose。若 RimWorld/Unity 的可靠退出回调不能保证执行，插件持久化仍不能依赖 Shutdown 才落盘；开发者指南需要明确这一限制。

运行时启用/禁用目前本来就是“改设置后重启”，API provider 列表又被 Client 永久缓存。管理器不能被视为真正支持热卸载或热加载。

### 4.5 应建立明确状态机

建议状态流：

```text
Discovered -> DependencyValidated -> Registering -> Registered
           -> Skipped/Failed
Registered -> Activating -> Active
           -> Rollback -> Failed
Active     -> Stopping -> Stopped
```

只有 `Registered` 能进入激活，只有 `Active` 能对外解析 API 和接收管线调用。注册阶段先写入扩展私有 staging area，成功后一次性提交；失败则丢弃。激活失败要撤销已提交注册并执行一次有界清理。关闭按成功激活顺序逆序执行且保证幂等。

依赖解析必须先校验唯一 ID、缺失依赖和循环，再得到稳定拓扑序。任一必需依赖失败，其下游标为 `DependencyFailed` 并禁止注册或激活。

## 5. 持久化和本地存储缺口

### 5.1 客户端 `RegisterPersistent` 没有执行者

`ExtensionHostContext.RegisterPersistent()` 和 `Persistents` 位于共享契约中，但只有 `PhinixFrameworkServer` 遍历它们执行 Load/Save。客户端没有对应消费代码。因此它不能被描述为客户端插件持久化服务。

客户端的 `StorageProvider` 只返回 `framework-extensions/client/<extension>/<logicalName>` 路径。它没有关联当前 RimWorld 存档，也不提供打开、锁定、提交、刷盘、恢复、迁移、配额或清理语义。

### 5.2 文件路径隔离不严格

路径清理只替换 `Path.GetInvalidFileNameChars()`。`.` 与 `..` 并非 Windows 非法文件名字符，恶意或错误的 extensionId / logicalName 仍可能逃出预期子目录。返回路径前也没有对规范化绝对路径做根目录包含校验。

根路径由相对路径构造，实际位置依赖进程工作目录；这对备份、权限、便携安装和诊断都不清晰。

### 5.3 服务端持久化也不是事务服务

服务端会依次直接调用每个插件的 `Load(path)` / `Save(path)`，但循环本身没有逐插件异常隔离。一个插件抛错可能阻断后续插件加载或保存。Host 没有临时文件、fsync、原子替换、校验和、旧版本保留或崩溃恢复协议，最终可靠性取决于每个插件自己实现。

因此 `RegisterPersistent` 更准确的名称是“持久化生命周期回调注册”，不能暗示原子性、隔离性或耐久性。

## 6. 主线程、队列和背压缺口

`ClientMainThreadDispatcher` 有 500 条上限，但满载时无条件丢弃最旧动作。调用者得不到成功、失败或被丢弃的结果，也没有所有者、优先级、取消、截止时间和重试语义。任何插件若把不可丢失的状态变化放入这条队列，旧动作都可能被静默替换，日志之后也无法关联到原操作。

队列每帧一直消费到空，没有条数或耗时预算。一次积压最多执行 500 个任意插件动作，可能造成明显卡帧。动作异常被捕获后直接写 `Verse.Log`，调用者无法观察失败。

声音队列使用无容量上限的 `List<SoundDef>`。它在主线程消费且有锁，但后台生产快于消费时仍可能增长。

建议把 UI 通知队列和可靠工作队列分开：

- UI、声音等允许丢弃或合并，并向指标记录丢弃数；
- 不可丢失的工作使用插件自己的状态机，或使用未来新增的可靠工作接口；
- 每帧按耗时或条数预算消费，跨帧继续；
- 每个扩展设置公平配额，避免单插件占满全局队列。

## 7. 程序集加载和插件隔离缺口

加载器会枚举探测目录顶层的全部 DLL，按文件名排序并调用 `Assembly.LoadFrom`。全局静态探测目录、文件缓存和匿名 `AssemblyResolve` 处理器会留在 AppDomain 生命周期内。

当前缺少：

- 插件 manifest 和 Host API 版本范围预检；
- RimWorld 版本、目标框架和必需依赖的加载前诊断；
- 重复程序集版本的确定性冲突策略；
- 完整性或来源信息；
- 卸载隔离；
- 对 AssemblyResolve handler 的解除注册；
- 插件目录与普通依赖 DLL 的明确区分。

数字文件名前缀仍参与实际加载顺序，说明运行时发现已经插件化，但打包和程序集解析仍依赖人工顺序。.NET Framework AppDomain 的不可卸载限制可以继续接受；manifest、完整性校验和来源管理只有在第三方插件分发规模扩大后才有足够收益，当前只需把程序集冲突报告清楚。

## 8. Host 与业务边界仍有泄漏

Client Host 向所有插件注册了 `ILegacyModuleTransport`，其接口明确允许发送、接收任意模块原始字节。设计哲学本意是只让 Legacy 协议适配器拥有这条例外，目前服务容器没有能力范围或调用方身份，任何插件都能绕开 Framework 管线、能力协商、统一日志和审计。

Host 还用裸 `Action` 表示“打开设置”，用裸 `Action<bool>` 表示“更新是否接受交易”。后者是交易业务进入 Host 服务容器；类型本身也没有语义，未来再注册同类型服务会覆盖。`IClientSettingsContext` 同时包含通用键值设置和 Chat 专属的屏蔽用户字段，`ITradeRequestApi` 也放在通用 Client abstractions 中。

建议：

- 将 `Action` 改为有名称的 `IClientSettingsWindowService`；
- 将接受交易状态移入 Trade 契约和 Trade 插件拥有的服务；
- 将屏蔽用户状态移入 Chat 契约，通用设置接口只保留命名空间化键值能力；
- 只向明确标记为 Legacy adapter 的扩展发放按模块名限制的 transport capability；
- Host 的类型和设置不再认识具体业务。

## 9. API 注册和运行时可观测性缺口

API registry 在多个实现存在时固定返回第一个注册者。它没有版本协商、优先级、唯一提供者约束、启用状态过滤、撤销和作用域。选择结果会受程序集与类型排序影响，warning 不能消除歧义。

Host 目前也没有统一健康快照，例如：插件各阶段耗时、最近错误、队列深度、丢弃计数、活跃订阅、持久化最后成功时间、恢复次数。扩展管理器展示静态状态和不完整日志，无法判断一个 `Active` 插件是否已经失去网络处理器或持续失败。

短期只需维护当前状态、状态变化时间、最后错误和全局队列丢弃计数。注册资源数量、每插件队列、持久化 checkpoint、诊断包等指标应由实际排障需求驱动，不应为了“平台完整”一次性引入。

## 10. 开发者指南建议的必要性与目标适配评估

本节只评估开发者指南中与 Host API、生命周期、依赖、日志、持久化、加载和管理界面有关的建议，不评估插件 UI 写法或具体业务示例。表中也列出几项容易从指南继续推导出的平台能力，用于明确排除过度建设。

开发者指南的方向大体符合“插件平权、Host 只提供通用能力”的目标，但其中混合了三类内容：真正的宿主不变量、尚未实现却写成事实的能力、以及没有当前需求支撑的平台增强。不能把指南中的每条理想描述都直接转成开发任务。

| 指南中的建议或承诺 | 是否符合目标 | 当前是否必要 | 结论 |
|---|---|---|---|
| 官方与第三方插件走同一发现、注册、激活、关闭路径 | 符合，是插件平权的核心 | 必须 | 保留并补齐实际执行语义。Host 内置管理 UI 可以特殊注册，但业务插件不能走私有路径。 |
| `Register -> Activate -> Shutdown` 三阶段 | 符合，能区分声明资源和运行时副作用 | 必须 | 接口无需重做；要修正状态检查、失败回滚和关闭顺序。 |
| `DependsOn` 使用 DAG 拓扑顺序，缺失或循环依赖失败 | 符合，属于 Host 才能统一保证的通用能力 | 必须 | 指南描述合理，代码没有做到。实现稳定拓扑排序，无依赖模块维持原有相对顺序。 |
| 单个插件失败不影响其他插件 | 基本符合 | 必须，但要改写含义 | “不影响无关插件”才正确；依赖失败的下游必须停止，不能为了表面隔离继续运行。 |
| 所有插件日志进入 300 条管理器缓冲 | 符合，且是管理界面的基本可信度要求 | 必须 | 先汇合现有日志链即可，不要求先建设完整结构化日志平台。 |
| 插件从 `hostContext.Log` 全量迁移到 `ILoggable` | 具体机制不是产品目标 | 不必要 | 目标是统一入口、来源和异常；可以新增 logger，也可以保留兼容桥，不应为了接口统一而破坏插件。 |
| Release 编译时删除 DEBUG | 部分符合性能目标 | 不宜作为固定契约 | sink 可以按运行时等级过滤；管理器是否保留 DEBUG 应可配置。无需立即修改。 |
| `GetStoragePath` 提供插件专属路径 | 符合通用 Host 能力 | 必须保留并加固 | 它只保证安全路径，不应被描述为自动、原子或按存档持久化。 |
| Host 自动替所有插件完成事务持久化 | 超出当前 Host 目标 | 不必要 | 当前没有这一明确需求。插件拥有其数据格式和恢复策略；Host 只提供安全目录或生命周期回调。 |
| 扩展管理器运行时开关插件 | 只有真的支持卸载时才符合 | 当前不必要 | 维持“修改后重启生效”。在资源撤销和缓存失效完成前，不引入热加载。 |
| 所有队列都具备背压和上限 | 符合稳定性目标 | 必须保留原则，按队列实现 | UI 队列可以有损；可靠工作不能进入有损队列。无需把通用 dispatcher 升级成任务调度平台。 |
| Legacy adapter 可使用原始 transport | 符合兼容边界中的例外 | 当前必要 | 保留旧兼容能力；长期按 adapter/模块范围收窄，不能突然移除公共接口。 |
| manifest、插件签名、完整健康指标、诊断包 | 方向可接受 | 当前不必要 | 等第三方分发、冲突或排障量证明需求后再做。 |
| 真正的运行时卸载和程序集隔离 | 与 net472/AppDomain 成本不匹配 | 当前不必要 | 不应进入当前整改范围，也不应在指南中暗示已经支持。 |

### 10.1 客户端 Shutdown 的确定语义

当前代码有 `PhinixFrameworkClient.Shutdown()`，但 Client 没有调用点。客户端 Mod 和插件随进程存在，退出某个存档不等于卸载 Host；绑定到存档退出会让回到主菜单后的扩展永久停止或重复激活。

正式定义为：客户端扩展是进程级生命周期，启停只在重启后生效；不支持运行时 Host 重置或热卸载；退出存档不触发 Shutdown。Host 可以在可靠的客户端进程退出回调中做一次逆序、幂等清理，但业务正确性和持久化不得依赖该回调必然执行。开发者指南应删除“Host 重置时关闭”的承诺，并写明进程退出清理的限制。

## 11. 破坏性更新评估与兼容策略

这里的“破坏性”分为四类：二进制兼容、源码兼容、运行行为兼容，以及协议/持久化数据兼容。Host 完善应优先做内部修正和新增式扩展，不把架构清理成本转嫁给现有插件。

### 11.1 可以兼容完成的修正

| 修正 | 兼容性判断 | 实施约束 |
|---|---|---|
| 让 `hostContext.Log` 同时进入 Verse 和管理器 | 非破坏性 | 保留委托类型和调用方式，确保每个 sink 只写一次。 |
| 删除或脱敏 SessionId 日志 | 非破坏性 | 只改变日志内容。 |
| 安全规范化存储路径 | 对合法 ID 非破坏性 | 合法现有路径保持不变；只拒绝越界、设备名等原本就不安全的输入。 |
| Register 失败后不再 Activate | 行为修正 | 只会影响已经失败却依赖半初始化副作用的插件；应在发行说明中明确。 |
| 依赖缺失、循环、失败时停止下游 | 行为修正 | 这是现有 `DependsOn` 公开语义应有的结果。状态和原因必须可见。 |
| 稳定拓扑排序 | 有限行为变化 | 仅对声明依赖的模块调整先后；无依赖模块保持当前全名排序和相对顺序。 |
| Shutdown 对 Active 模块逆序且幂等 | 有限行为变化 | 仅用于进程退出或显式测试 dispose；不对从未 Active 的模块调用，不绑定到存档退出。 |
| 服务端逐插件隔离 Load/Save 异常 | 非破坏性 | 不改变 `IPersistent` 签名；继续处理其他插件并记录来源。 |

### 11.2 当前不应直接实施的破坏性改动

以下做法虽然能让代码表面更整洁，但会破坏已编译插件或现有调用方式：

- 把 `ExtensionHostContext.Log` 的类型从 `Action<string, LogLevel>` 直接改成新 logger；
- 给现有公共接口新增必须实现的成员，或修改 `Enqueue`、`Register`、`Activate` 等签名；
- 删除 `ILegacyModuleTransport`，或突然限制现有插件已经能访问的模块；
- 把 `ITradeRequestApi`、设置相关成员等公共类型直接搬到另一程序集；.NET 类型身份包含程序集，单纯改 namespace 或项目引用不能保持二进制兼容；
- 全局禁止 API 多提供者；主 Tab、侧栏等本来就需要多个实现；
- 把 API 统一改成“只有 Active 才可解析”而不区分启动阶段，这可能让依赖插件在 `Activate` 中无法解析已经成功 Register 的依赖；
- 修改现有文件位置、格式或 wire protocol 来配合 Host 清理；本审计没有提出协议更新。

### 11.3 推荐的渐进迁移规则

1. 现有公共接口只修实现，不删成员、不改签名、不换程序集。
2. 新能力以并行接口或可选 Host 服务加入，例如新增 logger factory，同时让旧 `hostContext.Log` 继续桥接。
3. 注册资源按 ExtensionId 跟踪。Register 期间保持当前可见性，失败后撤销该模块本轮写入；成功依赖的 API 可供下游 Activate 解析，失败模块的 API 对正常运行态不可见。
4. 多提供者策略按 API 类型声明：UI 集合允许多个，单一服务可拒绝歧义；不能使用一个全局规则。
5. 业务接口迁移先新增新契约，再由旧接口适配到新接口并标记弃用。至少跨一个正式版本保留桥接，移除只放在明确的主版本更新中。
6. 原始 transport 先增加更窄的新能力并迁移官方 adapter；旧接口保留、记录弃用诊断，确认第三方使用情况后再决定主版本移除。
7. 文档承诺与实现必须在同一版本同步；未实现能力明确标为规划，不让第三方依赖虚假保证。
8. 保存一组用旧版 Contracts 编译的插件二进制，作为加载、Register、Activate、日志和 Shutdown 的兼容回归样本。
9. Host 内部重构不得顺带改变 wire protocol、服务端确认语义或现有持久化格式。若未来确需改变，单独设计版本协商与迁移。

## 12. 整改优先级

### P0：先让现有契约名实相符

1. 实现依赖校验和稳定拓扑序，缺失、循环、失败依赖必须阻止下游激活。
2. 修正生命周期状态机：Register 失败不得 Activate；失败注册可撤销；Shutdown 只处理 Active 模块并按逆序执行。
3. 让现有 `hostContext.Log` 与管理器缓冲真正汇合，保留原签名，并立即移除 SessionId 日志。
4. 加固存储路径的规范化和根目录包含校验，不新增事务存储抽象。
5. 同步纠正中英文开发者指南中尚未实现的描述。

### P1：以新增方式改善诊断和稳定性

1. 新增可选的带 ExtensionId、Exception 和 CorrelationId 的 logger，同时保留旧日志桥。
2. 为主线程派发增加每帧预算和丢弃指标；声音等辅助队列设上限。可靠队列等有实际消费者时再新增。
3. API registry 增加按拥有者撤销和按契约声明的多提供者策略，不改变现有公共签名。
4. 服务端持久化增加逐插件异常隔离并准确标记日志来源。
5. 以兼容桥逐步清理通用 abstractions 中的业务接口及裸 `Action` 服务。

### P2：有需求证据后再做

1. 插件 manifest、Host API 兼容范围、签名或完整性机制。
2. 完整结构化日志、诊断包和细粒度健康指标。
3. Host 级事务持久化或可靠工作队列。
4. 真正的运行时启停、程序集隔离或热加载。

## 13. 文档需要纠正的承诺

中英文开发者指南目前把以下能力写成了已实现事实，必须在代码完成前改成“规划中”或准确描述当前限制：

- DAG 拓扑 Register / Activate；
- 逆依赖顺序 Shutdown；
- 循环依赖标记 Failed 并跳过；
- 缺失依赖导致 Failed；
- 扩展管理器的 300 条日志是完整扩展运行日志；
- 客户端可通过共享持久化注册获得自动 Load/Save（若任何章节造成这种暗示）。

设计哲学里已经较诚实地写明插件日志仍通过 `hostContext.Log`，未来再迁移到统一 `ILoggable`；但还应补充当前管理器缓冲和 Host 日志出口没有汇合，避免开发者误判可观测性。

## 14. 验收标准

Host 整改不能只以“编译成功”为完成。至少要有独立回归场景验证：

1. A 依赖 B，程序集文件名让 A 排在 B 前，仍保证 B 先 Register/Activate、A 先 Shutdown。
2. 缺失依赖、循环依赖、依赖 Register 失败、依赖 Activate 失败时，下游从未运行。
3. Register 写入若干 API 后抛异常，所有写入均不可解析，管线也不调用它。
4. 旧插件只调用一次 `hostContext.Log`，Verse 与管理器各出现一次；使用新 logger 的插件还能看到一致的 ExtensionId、异常和 CorrelationId。
5. 日志含 SessionId 或声明为 secret 的字段时，所有 sink 均为脱敏值。
6. 单插件刷日志时不会挤掉所有其他插件记录，并能看到限速/丢弃计数。
7. 模拟客户端进程退出或测试显式 dispose 时，所有 Active 插件恰好 Shutdown 一次且顺序正确；退出存档不触发 Shutdown。
8. 主线程普通队列溢出时记录丢弃计数，并按帧预算消费；文档明确它是有损队列。
9. 存储逻辑名为 `..`、绝对路径、保留设备名或超长名字时无法逃出插件根目录。
10. 服务端某插件 Load/Save 抛错时，其余插件仍执行，错误带正确 ExtensionId。
11. 使用旧版 Contracts 编译的兼容样本无需重新编译即可被新 Host 发现和激活。
