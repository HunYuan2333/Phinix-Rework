## 1. 范围、目标与采用方案

本方案规划迁移客户端的 HTTP、测试、状态机和依赖注入四项基础设施。允许较大重构，以后续可维护性、扩展性、可靠性和开发难度为主要标准，一次性修改代码量为次要标准。

| 项目 | 规划采用 | 主要迁移对象 | 完成后的行为 |
| --- | --- | --- | --- |
| HTTP | HttpClient + Polly.Core；先显式管理客户端与 handler 寿命 | 红包 Relay 的同步请求、取消、超时和重试组织；商店 HTTP 的共同执行机制 | 网络调用可取消、可测试、限制明确；重试责任只有一处，领域确认仍由插件解释 |
| 测试 | NUnit + NUnitLite，保留可执行入口；标准 adapter 后续按项目接入 | 现有控制台回归 harness | 每个场景独立报告，失败返回非零退出码，可筛选与参数化 |
| 状态机 | Stateless，先迁移单笔红包库存发送操作 | RedPacketInventorySending 中分散的状态转移 | 合法转移集中表达，状态提交与副作用分开，旧托管记录仍可读取 |
| DI | Autofac，作用域与插件生命周期统一组织 | 客户端宿主装配、插件内服务创建、订阅与资源释放 | 普通服务构造函数注入；插件内对象有明确所有者；旧插件入口继续可用 |

HTTP 中的 HttpClient 是 BCL API，Polly.Core 是请求执行策略库。第一版不要求引入 IHttpClientFactory 或 Generic Host；若后续客户端配置数量明显增长，可在同一传输抽象后增加 factory，而不改变领域调用方。

基础依据：[框架与库选型评估](/home/hunyuan2333/Phinix/Phinix-Rework/docs/branch-local/dev/客户端框架与库选型评估.md)、[设计哲学](/home/hunyuan2333/Phinix/Phinix-Rework/docs/Design-Philosophy.md)、[兼容与恢复边界](/home/hunyuan2333/Phinix/Phinix-Rework/docs/Compatibility-Boundaries.md)。

本轮默认继续使用现有持久化 provider、JSON 编码器和协议字段，以便单独判断这四项迁移的效果。SQLite、JSON 替换和真正的 DLL 热更新留作独立选型；如果迁移发现现有记录不足以恢复某项副作用，应形成有版本说明的修复任务，不能假装 Stateless 已解决持久恢复。

## 2. 必须保持的行为

1. 官方与第三方扩展走相同发现、注册、激活、关闭路径。被禁用扩展不实例化，依赖失败仍阻止其激活。
2. 宿主只提供通用服务，不引用 Chat/Trade/Inventory/RedPacket 的业务 Contracts 或实现。
3. Legacy 与 Framework 协议差异留在明确命名的 adapter。网络流水线继续使用现有拦截、默认处理、观察机制。
4. 排队、发送尝试和普通快照不产生成功确认；超时或取消后已发送的操作可能仍是结果未知。
5. 物品转换整批成功或整批失败。重复确认、重试和恢复不能再次提交、返还或交付同一份物品。
6. 持久提交成功后才发布权威内存状态和执行对应后续动作；保存失败不得表现为已经完成。
7. 游戏 API、翻译、UI 与涉及游戏对象的清理保持主线程边界。旧会话或旧存档回调不能修改新环境。
8. 改运行机制与修复业务语义分别记录。若为了可靠性必须调整行为，单独列出兼容影响及测试，不能藏在“换库”提交里。

## 3. 实施顺序与依赖

| 阶段 | 交付物 | 前置条件 | 可独立验收的结果 |
| --- | --- | --- | --- |
| M0：版本与运行环境试验 | 候选版本、完整依赖清单、真实 Mono smoke 结果、现有场景清单 | 无 | 确认四项技术可以在目标环境分发与运行 |
| M1：测试基础迁移 | NUnit/NUnitLite 入口、fixture 与场景映射、可执行结果报告 | M0 的测试库验证 | 原有覆盖不减少，新增场景可以独立运行 |
| M2：拆开宿主装配与启动 | 延迟激活入口、启动失败清理、兼容构造路径 | 现有启动/失败场景基线；runner 可渐进迁移 | 不接 Autofac 也能验证启动顺序与职责拆分 |
| M3：Autofac 基础与插件试点 | 客户端 composition root、作用域负责人、Chat 试点、旧插件桥梁 | M2、Autofac 环境试验通过 | 一个真实插件获得明确依赖和成对清理 |
| M4：HTTP 迁移 | 红包 async transport、单一重试负责人、取消和限额处理 | HTTP 特征测试基线；生命周期边界与 M3 对齐 | HTTP 行为可模拟验证，旧会话响应不会污染新会话 |
| M5：Stateless 单笔操作迁移 | 红包发送转移规则、候选提交协调器、旧状态恢复测试 | 状态/恢复测试基线；HTTP 结果分类稳定 | 状态变化不再散落，保存失败与重复事件可确定处理 |
| M6：扩展 DI 覆盖与收尾 | Inventory/Trade/RedPacket 装配迁移、残留机制清理、整体验收 | M3—M5 | 四项形成一致的生命周期与测试组织 |

默认集成顺序是适用依赖的 M0 环境验证 → 相关场景基线/渐进 M1 → M2 → M3 → M4 → M5 → M6。M2 可以在现有 harness 下先行，不要求所有测试先换 runner，也不要求四个候选库全部通过才开始一个试点。HTTP 的纯传输与 Stateless 的纯规则可独立验证；实际接入逐项进行，不同时改变多个机制。

各阶段按可回归验证的提交拆分；每阶段完成都应有实际收益，不需要等整个方案结束才可以使用。

## 4. M0：锁定版本与验证真实运行环境

### 4.1 依赖进入哪些工程

| 依赖 | 进入位置 | 边界要求 |
| --- | --- | --- |
| Autofac | 客户端装配实现层，必要时独立成客户端运行时工程 | 不让 Common/Utils 的通用 registry 直接依赖 Autofac；客户端适配通过中立工厂或可选接口接入 |
| Polly.Core | 客户端 HTTP 执行实现层 | 不暴露 ResiliencePipeline 到领域业务契约；不改变 LiteNetLib 流水线 |
| Stateless | 红包/交易操作的内部规则实现，尽量不引用 Verse/Unity | 公共业务 API 不返回 StateMachine 类型；状态库不成为跨插件通信协议 |
| NUnit / NUnitLite | 对应 Tests 工程 | 与生产代码完全分开，不进入 mod 产物 |

具体版本在 M0 通过试验后锁定。本方案不直接照抄官网示例版本，也不把 NuGet 的兼容推断当作 Mono 验证结果。

版本清单必须记录：包版本、实际使用的目标资产、传递依赖、许可证、谁负责打包、与当前 System.Memory/Unsafe 等依赖是否一致。存在同名程序集时，要测试实际加载行为，避免插件分别携带不同版本。

### 4.2 试验与通过条件

- net472 客户端与 net10 测试环境分别验证 restore、编译和基本运行。
- 在真实 RimWorld/Mono 环境测试容器 Resolve/Dispose、Polly 取消与超时、Stateless 转移；记录运行环境及依赖加载路径。
- 测试同时启用现有官方扩展与一个旧接口第三方样例。确认新增程序集不破坏既有解析。
- 包布局验证确保所有运行时依赖被正确分发，测试 DLL 和游戏引用 DLL 没有进入客户端产物。
- 新增或搬移代码时，核对 legacy csproj 的显式 Compile 项；不修改 vendored protobuf 来绕过 SDK 问题。

通过条件是编译、加载、运行与分发均有证据。如果最新版依赖组合不能通过，应换成有明确维护依据的兼容版本继续验证；不能只让 net10 测试通过后就宣称客户端兼容。

| 第二批：游戏依赖测试 | [InventoryRuntimeTests](/home/hunyuan2333/Phinix/Phinix-Rework/Tests/InventoryRuntimeTests/InventoryRuntimeTests.csproj)、[RedPacketInventoryRuntimeTests](/home/hunyuan2333/Phinix/Phinix-Rework/Tests/RedPacketInventoryRuntimeTests/RedPacketInventoryRuntimeTests.csproj)、[LegacyTradeRuntimeTests](/home/hunyuan2333/Phinix/Phinix-Rework/Tests/LegacyTradeRuntimeTests/LegacyTradeRuntimeTests.csproj) | 保留 net472 编译与既有 runtimeconfig 执行方式，先验证 runner 与依赖加载再迁移场景 |

### 5.2 具体步骤

1. 为每个原 harness 列出现有场景，建立“旧入口调用 → 新 fixture/test”映射。以场景语义核对覆盖，不仅比较测试数量。
2. 接入 NUnit 和 NUnitLite，入口采用经典 Main(args)，返回 AutoRun.Execute(args) 的退出码。保留原有 dotnet run / dotnet exec 调用方式。
3. 初期可以将现有场景方法作为独立 Test 调用，保留断言与生产代码执行路径。随后按 Discovery、Lifecycle、Pipeline、Http、OperationState、Recovery 拆 fixture；不重写全部断言后才允许迁移。
4. 静态共享状态、游戏对象或固定文件路径的测试显式非并行；独立测试使用临时目录，并在 teardown 清理。测试 A 执行后不能改变测试 B 的结果。
5. 新增 fake clock、可控 dispatcher、脚本化 HttpMessageHandler、失败注入存储和可取消任务；由测试控制事件发生顺序，避免靠长时间 sleep 验证逻辑。
6. 手动开发与发布检查继续检查非零退出码，增加机器可读结果。当前 GitHub Actions 只构建并发布服务端 Docker 镜像，本轮不追加测试或客户端工作流。若需要 dotnet test，再为相应工程加入匹配的 Test SDK/adapter；不要同时更换 runner、目标框架和游戏依赖加载路径。
7. 链接生产源码的测试工程同步更新 Compile 清单及包引用，避免测试旧副本或遗漏新增依赖。

NUnitLite 支持可执行测试入口及经典 Main，适合现有 harness 的演进。[官方运行器文档](https://docs.nunit.org/articles/nunit/running-tests/NUnitLite-Runner.html)。

### 5.3 验收

- 原有场景一一对应，失败包含具体场景、异常与上下文，不再仅有最外层 ex.Message。
- 支持仅执行一类场景，结果可以单独收集；测试失败不会返回零。
- 固定种子的事件序列和故障注入可以复现；重复运行不存在顺序依赖。
- net472 特殊执行路径单独有验证记录，不能用 net10 独立测试代替。
- 所有测试依赖只在测试产物中存在。

## 6. M2—M3：Autofac 与宿主生命周期迁移

### 6.1 先拆开装配与激活

[PhinixFrameworkClient 构造流程](/home/hunyuan2333/Phinix/Phinix-Rework/Client/Source/Framework/PhinixFrameworkClient.cs:62) 当前在构造期间注册自身服务、发现并激活插件。若直接交给容器，插件可能在宿主对象图未完整建立时开始运行。

目标顺序：创建宿主通用服务与传输对象 → 完成宿主服务登记 → 收集并校验扩展元数据 → 按策略创建/注册插件 → 按依赖顺序激活 → 发布可用能力并允许正常消息处理。

具体要求：

- 构造函数只建立本对象的必要依赖，不启动插件、订阅网络或发请求。
- 通过明确且防重复的初始化/启动入口执行运行动作；异常后清理已经创建的资源。
- 现有公开构造入口若有外部调用者，保留兼容桥梁；新装配入口使用延迟启动路径，两条路径都只能启动一次。
- 构造宿主、注册宿主服务和插件发现不得形成循环解析；不把尚未构造完成的对象交给插件。
- 消息入口在启动完成前保持受控状态，部分初始化不表现为客户端已可用。

M2 先用现有手工创建路径验证这些行为，避免把启动职责问题与容器问题混在一起。

### 6.2 composition root 与插件入口

Autofac 的实现放在客户端装配层。共享 registry 仅接受中立的创建/生命周期适配，不引用 Autofac，也不硬编码官方插件类型或 ID。

旧 IPhinixExtensionModule、Register(builder)、Activate(hostContext)、Shutdown(hostContext) 入口继续可用。第一版可以保留模块自身的无参构造，将主要 DI 收益落实到插件内部的普通业务服务；不要求一开始就让所有模块构造函数注入全部服务。

对采用新装配方式的插件，新增独立的可选组合接口，提供最少的服务登记和装配能力。其具体签名作为 M3 的第一项设计交付：

- 不给既有第三方接口新增必需成员，以免破坏二进制兼容。
- 只有装配回调可以解析服务；领域服务构造函数声明依赖，不携带容器或服务定位器。
- 服务注册仅覆盖类型/工厂与基本生命周期，不复制 Autofac 的全部 DSL。
- 新旧插件使用同一策略、顺序和错误隔离机制；没有“官方插件特殊初始化分支”。

GetRequiredService 作为旧插件桥梁保留。迁移后的普通业务类不得继续用它隐藏必需依赖。接口缺失在装配时产生明确错误；不要注册空实现来掩盖不完整环境。

### 6.3 对象归属与作用域

| 生命周期 | 典型对象 | 所有者与关闭方式 |
| --- | --- | --- |
| 宿主运行期 | 通用 dispatcher、设置入口、日志入口、传输门面 | 宿主 composition root；游戏提供的外部对象明确为外部所有 |
| 插件运行期 | 业务 API 门面、UI provider、插件内部工厂 | 每插件一个作用域；由插件生命周期负责人显式关闭 |
| 插件与连接绑定期 | 请求取消源、连接相关订阅、协议状态 | 由插件负责人按连接代次创建/取消；不让常驻对象捕获旧连接 |
| 插件与存档绑定期 | 当前存档操作协调器、游戏对象绑定、存档相关订阅 | 换档时取消和清理，传入明确存档身份；不将 Thing/GameComponent 提升为宿主单例 |
| 单笔业务操作 | 候选变更、操作上下文、提交结果 | 由业务协调器管理；持久记录寿命不依赖 scope 是否存在 |

连接和存档可以独立变化。作用域按明确的资源归属建立，交叉绑定由负责人协调，不使用过度复杂的标签树自动推断寿命。

插件作用域之间的 API 继续通过现有注册表的所有者规则连接。外部插件提供的 API 是借用对象，不由消费方容器 Dispose。依赖插件未完成注册/激活时，消费者不能解析并开始业务。

若插件重新创建，已经被其他插件捕获的旧 API 不会自动更新。本轮继续保持更新 DLL 后重启生效；作用域设计支持完整关闭与重建，但不宣称已经支持运行时替换 DLL。以后若开放动态停启，需要依赖插件一起重建或稳定代理，另行验收。

Autofac 支持局部注册和作用域对象释放，但手动创建的子作用域仍需创建方显式关闭。[作用域文档](https://docs.autofac.org/en/latest/lifetime/working-with-scopes.html)、[释放规则](https://docs.autofac.org/en/latest/lifetime/disposal.html)。

### 6.4 停止与失败处理

统一顺序：停止接收新工作 → 取消后台任务并使旧代次回调失效 → 撤销 API/handler/provider → 关闭 UI 绑定和订阅 → 等待需要收尾的工作 → 在正确线程释放资源及子作用域 → 释放插件作用域。

不得在主线程通过 Wait/Result 长时间阻塞等待后台任务。若停止超时，要保留可诊断的退出状态和必要资源归属，不能释放后台工作还在访问的对象后宣称已安全关闭。

每项清理均需幂等且隔离异常；一个插件的 Dispose 失败不阻止其他插件关闭。未确认业务记录由现有存储继续托管，关插件不会自动返还物品。

### 6.5 试点与验收

先迁移 [Chat 插件](/home/hunyuan2333/Phinix/Phinix-Rework/Extensions/Chat/Client/BuiltInChatClientExtension.cs)，验证业务服务、UI provider 与订阅的装配和释放。它不涉及库存提交，适合先证明通用机制。随后用 Inventory → Trade → RedPacket 验证依赖链和关键操作。

验收：禁用不构造；依赖排序保持；构造/注册/激活失败撤销能力与资源；重复启动被阻止；连续加载退出没有重复订阅；主线程清理可验证；旧接口第三方样例仍运行；普通业务测试无需启动完整客户端。

## 7. M4：HTTP 迁移

### 7.1 目标职责

| 组件职责 | 做什么 | 保留在哪一层 |
| --- | --- | --- |
| 请求执行 | HttpClient、handler 寿命、响应限额、总取消、执行策略 | 客户端 HTTP 实现层 |
| Relay transport | URL/headers、GET/POST、raw 协议响应解析 | 红包客户端 adapter |
| 目录/载荷 transport | 来源限制、重定向政策、ETag、MIME、载荷验证 | 商店客户端 adapter |
| Relay 消费协调 | 队列顺序、cursor、caught-up 判定、事件去重 | 红包业务协调层 |
| 库存操作确认 | 哪个结果可以提交预留、结果未知如何托管 | 红包库存发送应用服务 |

不强制 Relay 与商店使用同一个 HttpClient 或同一套 headers/policy。它们可以复用受限读取、取消和执行策略的实现，但 endpoint 政策分别配置。

### 7.2 迁移步骤

1. 抽取可注入的 Relay transport，保留现有调用桥梁。先用 fake handler 对当前请求与响应行为做特征测试。
2. 将同步 HttpWebRequest 改为 SendAsync；移除“专门占用线程等待同步网络”的执行方式，但保留必要的串行协调。
3. 同一生命周期复用客户端/handler；handler 所有者负责释放。显式保留当前代理、认证和重定向语义，不能因 HttpClient 默认设置改变行为。
4. 每次连接、轮询和发送捕获明确代次与取消 token。响应进入业务队列前检查代次；主线程消费时再次确认连接和存档身份。
5. 限制覆盖整个响应体，不仅检查 Content-Length。使用 net472 实际支持的异步流 API、限额和取消路径；避免直接 ReadToEnd 导致无界内存增长。
6. ResponseHeadersRead 后继续应用整个请求/响应读取的时间预算；读取慢或无限响应不能绕过超时。总取消覆盖发送、等待退避及响应体消费。
7. 移除旧 ThreadPool 包装和多余重试计时器前，先证明新执行器接管其职责。队列、稳定 EventId、分片顺序和 cursor 不因换 transport 被删除。
8. 商店已有 HttpClient 注入与受限读取，先保持其 endpoint 校验，再逐步复用共同机制，不要求把它改成 Relay 风格。

关键接受结果需要保留或能够重新核对，不能与可丢弃的 UI 刷新共用“队列满时丢最旧项”的处理方式。派发失败或业务应用失败必须保持未决状态，不能只写日志后当作已经消费。

当前入口：[RedPacketRelay](/home/hunyuan2333/Phinix/Phinix-Rework/Extensions/LegacyRedPacket/Client/RedPacketRelay.cs)、[RepositoryTransport](/home/hunyuan2333/Phinix/Phinix-Rework/Extensions/PluginStore/Client/RepositoryTransport.cs)。HttpClient 的 handler 生命周期需要明确管理；现代 .NET 的 SocketsHttpHandler 示例不能直接当作 Mono 方案。[官方指南](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines)。

### 7.3 重试责任表

| 操作 | 策略 | 谁负责 | 失败后的业务含义 |
| --- | --- | --- | --- |
| 商店目录/载荷 GET | 有界尝试；对明确的瞬时失败退避，响应限制与取消贯穿执行 | Polly 执行策略；外层刷新任务不再同时即时重复尝试 | 读取失败或保留合法缓存，不产生业务成功 |
| Relay GET 轮询 | 单次轮询内有界重试；耗尽后由轮询协调器安排下一轮 | Polly 管本轮，协调器管下轮；两层总预算和次数有明确区分 | 不推进未确认的消费 cursor，不凭失败认定历史为空 |
| Relay POST 事件 | 第一版 Polly 仅管理单次尝试的超时/取消；保留有稳定 EventId 的队列作为唯一发布重试负责人 | Relay 发送队列 | 保留未决项；不新建 EventId；超时不自动释放库存 |
| 协议/内容校验失败、主动取消 | 不作为瞬时网络失败重试 | adapter/协调器明确报告 | 不消费损坏结果；过期会话结果丢弃 |

当前 POST 已有稳定 EventId 和队列重试，迁移时不叠加 Polly 内层 retry。若以后将发布重试也交给 Polly，必须同时移除原队列的尝试策略，并验证中继去重语义。

Relay 的 HTTP 接受、历史中的匹配 Create 与库存领域接受结果之间的关系按现有协议测试保持。不能把“任意 HTTP 2xx”推广为所有交易的成功确认，也不能忽略现有已接受回调的用途。

响应失败分类包括瞬时网络错误、HTTP 拒绝、内容不合法、取消、超时及发布结果未知。不同类型的 POST 失败是否确定未执行必须有证据，不能只按异常类型猜测。[Polly 重试文档](https://www.pollydocs.org/strategies/retry.html)。

### 7.4 验收场景

- 连接前取消、发送中取消、读取中取消；换档后的旧响应无效果。
- 超大、无 Content-Length、慢速、截断与损坏响应；商店仍拒绝非法来源/重定向/MIME。
- Relay 分片先于 Create，事件 ID 在重试中保持一致，发送顺序不被并发任务打乱。
- POST 服务端已接受而响应丢失，不自动退款；重新发送不生成新的业务操作。
- cursor 只在业务消费完成后推进；队列满、解析失败或历史未追平不能触发过期返还。
- 取消请求不会取消已经生效的远端操作；重新连接后按现有规则核对未决状态。

## 8. M5：Stateless 迁移

### 8.1 首个迁移对象

先迁移 [RedPacketInventorySending](/home/hunyuan2333/Phinix/Phinix-Rework/Extensions/LegacyRedPacket/Client/RedPacketInventorySending.cs) 中单笔库存红包发送。沿用 [托管记录](/home/hunyuan2333/Phinix/Phinix-Rework/Extensions/LegacyRedPacket/Client/RedPacketInventorySendStore.cs:12) 的 Queued、Accepted、Settling、Settled、Uncertain 状态及原有序列化值。

不把整个 RedPacketStateMachine 逐行改写成一个更大的 Stateless 实例。它仍然承担消息解析、领取协调和 UI 等职责，应先从中抽出单笔操作规则。

### 8.2 状态与事件梳理

以下表格是现有行为的梳理起点，正式实现前由特征测试核对每个分支。业务余额、Claim 去重及特殊红包结果是状态之外的数据，不能只迁移 enum 而丢失它们。

| 当前状态 | 事件/条件 | 候选结果 | 必须满足的约束 |
| --- | --- | --- | --- |
| Queued | 接受等待超时 | Uncertain | 不退款；保留稳定 PacketId/ReservationId |
| Queued / Uncertain | 当前操作的真实接受证据 | Accepted | 身份与内容匹配；保存 Accepted 后尝试移交预留 |
| Accepted | 一次合法领取 | Accepted 或 Settling | 领取去重与余额一致；余额归零进入结算 |
| Accepted | 过期且历史确认追平 | Settling | 未追平不能推断剩余物品可以返还 |
| Settling | 所需结算动作完成 | Settled | 预留提交和返还使用稳定标识；不得提前宣告完成 |
| 非 Settled 状态 | 现有中断处理 | 按当前恢复规则进入 Uncertain | 保留原记录的余额与结算字段；恢复能力不能凭空增强 |
| 已处理状态 | 重复/过期事件 | 明确忽略或记录诊断 | 不使用重入副作用重复提交或返还 |

### 8.3 关键实现：在候选副本上 Fire

Stateless 可以通过外部 getter/setter 访问状态，但如果 setter 直接写权威记录，Fire 就会先改变状态，再尝试保存；保存失败时可能造成内存与磁盘分叉。

因此采用以下步骤：

1. 按操作 ID 串行接收事件，验证事件代次、存档和当前权威记录。
2. 克隆现有记录，在候选副本上构建或绑定 Stateless。guard 只读取事实；记录转移与待执行动作，不调用游戏、网络或存储。
3. Fire 在候选副本上执行，得到候选状态及余额/去重等变更。对非法事件显式分类，不用通用 Ignore 吞掉所有异常。
4. 通过现有 store 保存候选记录。保存失败时丢弃候选副本，不修改已发布记录，不执行对应副作用，不推进协议消费 cursor。
5. 保存成功后发布记录，再根据当前状态和稳定操作标识执行提交/返还/通知等动作。
6. 后续动作失败保留可恢复状态；只有所需动作成功后，才提出下一次状态转移。

不在 OnEntry/OnExit 中直接发送请求、落地 Thing 或调用存储。状态机的事件回调也不能直接成为权威提交发布通道。

Stateless 支持外部状态访问，但仍是单线程状态机，不能由多个 HTTP/UI 回调并发 Fire；本方案通过操作协调器串行处理。[Stateless 官方项目](https://github.com/dotnet-state-machine/stateless)。

### 8.4 现有双存储边界

红包托管记录和 Inventory 的预留/存入记录是两个独立提交边界。迁移继续依靠稳定标识和恢复协调，不能宣称一次 Fire 能把两者变成原子事务。

验证中断点：Accepted 保存后、预留提交后、返还完成后、Settled 保存前后。对已有标识覆盖不了的副作用（例如特殊游戏事件），单独记录恢复缺口与所需版本化改动，不在恢复时无条件重放。

重启时只读取已保存状态，不因恢复状态机实例而再次执行 entry 动作。当前尚未实现的历史自动核对，不会因换库自动获得。

### 8.5 验收场景

- 每个状态×合法/非法事件有明确结果；相同事件序列可复现。
- 保存失败不改变权威状态，不产生后续物品副作用。
- 重复接受、重复领取、过期确认和未知操作 ID 不重复提交。
- 接受后库存提交失败、返还失败与进程中断可以继续托管并按稳定标识重试。
- 旧记录包括 Uncertain/Settling 可以读取，序列化 enum 值与字段意义保持一致。
- 切换存档或停止插件不退款、不串账；状态机测试和真实库存/Relay 适配集成测试分别通过。

## 10. 回退、发布与风险控制

| 迁移项 | 安全回退点 | 不能这样回退 |
| --- | --- | --- |
| 测试 | 保留场景映射与可执行入口；回退 runner 不影响生产数据 | 删除失败场景、让异常返回零、仅依赖测试数量 |
| Autofac | 回退某个插件的装配适配，继续使用同一公共插件路径 | 新旧实例同时注册、重复订阅、跨容器共享对象被重复 Dispose |

| Stateless | 在候选提交边界使用同一已持久记录回到旧规则实现 | 启动两套同时消费事件的状态机，或依靠回退版本自动退款 |

每阶段保持单一权威记录与单一运行负责人。若需要开发期切换开关，只在明确停止并清理的生命周期边界切换，不提供运行中随意切换业务引擎的入口。

发布前核对新依赖与插件契约的版本组合；旧接口支持不等于任意混搭新版实现和旧基础程序集都安全。客户端包同时更新所需基础依赖，避免用户只替换一份 DLL。

主要风险包括：程序集共存、跨插件借用对象被误释放、启动顺序循环、旧回调串入新存档、双层重试、响应体超时遗漏、候选状态提前发布，以及红包与库存两处记录的恢复边界。这些都需要直接验收，不能用“编译通过”覆盖。

DI 试点补充以下故障注入：构造到一半失败、注册失败、激活后失败、依赖提供者停止、取消后仍有回调抵达、清理超时。登记创建/注册/启动的完成阶段，只回收本方拥有的资源；消费者先停止使用借用 API，再关闭提供者，不能因作用域释放重复 Dispose 外部对象。

停止流程应具有可观察的在途工作清单或等效完成信号。在“逻辑上拒绝新工作/旧代次结果”之后确认不再访问待释放资源；超时留下可诊断状态并保留必要所有权，不在主线程同步长等，也不允许将超时后的迟到回调写入新存档。

每项迁移单独记录基线行为、失败样本、适用环境、产物依赖和回退点。容器/传输/规则可以逐项回退，但已产生的业务记录不得被清空；格式发生变更时先证明旧读取器安全，否则回退到兼容读取实现而不是直接换旧 DLL。
