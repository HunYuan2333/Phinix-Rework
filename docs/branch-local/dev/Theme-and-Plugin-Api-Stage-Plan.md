# F8：主题系统与插件公开 API 扩展阶段评估

日期：2026-10-10。状态：阶段设计草案；主题/UI/新业务 API 主体未实施。同日后续已清理两个维护插件的旧作者入口，见 §8.3 与维护插件记录。

## 1. 阶段目标与交付判断

本阶段建立完整的客户端主题系统，并补齐第三方与内置插件共同使用的公开 API。主题加载、专门的设置窗口、主题选择器、商店上架和新 UI 的配色自定义按同一条用户流程交付；API 扩展以真实调用场景及内置插件迁移验证，避免只增加接口数量。

2026-10-10 用户明确：Steam 客户端统一更新，目前没有第三方插件，不要求维持旧客户端或新旧业务接口混用。旧 UI/API 可以弃用并协调删除；确需接续的旧调用通过各自 adapter 转换，新业务不接收任何兼容信息。adapter 包括旧 UI/主题/设置/codec/插件入口等接口适配，不限于 LegacyAdapter 协议插件。继续保护既有主题数据、用户设置、业务状态和受支持外部系统，详见 [旧接口边界审查与删除评估](Compatibility-Interface-Boundary-Audit.md)。

评估结论：现有 `ThemeLoader`、`IUiTheme`、DI、API 注册、响应式布局、托管包校验和安装事务足以作为基础。需要补齐主题身份、选择与覆盖规则、原子加载、统一刷新和数据包管理；API 需要补齐可直接使用的操作入口、资源访问、UI 控件及可观测结果。工作涉及 Client、Common、Index 和维护中的独立插件；主题本身不要求服务端改动。

建议以 F8 编号纳入后续计划，不改写 F7 的交付与游戏验收状态。基础功能尚待游戏验收的事实保留；F8 文档与只读盘点可以先完成，安装层与 DI 的后续代码变更须携带 F7 回归用例。

## 3. 兼容性不变量

1. 新业务只消费一套当前契约；旧接口、DTO、版本/schema 分支与协议模式限于 adapter/基础设施。维护中调用方协调迁移后删除旧入口，不为不存在的第三方长期保留旧二进制 API。稳定包 ID、模块 ID 与持久化键继续保护。
2. 旧 `PhinixTheme version="1"` 与活动 Mod 的主题目录继续可读。首次升级保留用户原有配色效果；不因安装新主题或增加注册键自动替换用户已提交选择。
3. 主题选择和用户覆盖是客户端配置；不写入交易、库存、聊天业务账本，不向服务器协商主题，不修改原版/Framework wire 协议。
4. 主题只能修改 Phinix 自己消费的样式键。不全局修改 Verse/Unity 皮肤，不对其他 Mod 的 UI 做 Harmony Patch；每次绘制在 `finally` 中恢复 GUI/Text 状态。
5. 解析、发现和展示失败按单个主题隔离；无效主题不能留下部分颜色，亦不能使商店其他包无法管理。目录结构、完整性或身份违规仍按现有严格边界拒绝。
6. 主题切换不能触发 DLL 重载或业务插件重新激活。DLL 安装、修订、启停仍遵循现有重启规则；纯主题数据在完整验证后可以当次会话应用。
7. 主题默认值只由键的所有者定义。用户覆盖、主题覆盖与默认值分别存放，缓存可以全部从权威状态重建；取消预览不改持久化配置。
8. 插件平权：内置和第三方消费相同宿主 API；业务契约由相应插件 Contracts 所有，宿主不得引用 Chat/Trade/Inventory/Store 的业务契约。
9. 新业务包装 API 保留真实确认、整批物品处理、请求幂等、结果未知恢复及主线程游戏操作。不把“进入发送队列”或“处理器已处理”包装成业务成功。
10. 禁用、退出和部分激活失败必须释放自有注册与订阅；调用方不得释放借用的宿主服务或其他插件 API。延迟回调核对会话/激活代次。

## 4. 主题运行时设计

### 4.1 职责与状态

在现有主题实现上按实际职责拆分：发现候选、纯数据解析/验证、目录与选择状态、样式键注册、解析最终快照、主线程应用、设置窗口。类名不作为公开契约，避免先搭建通用资产框架。

权威状态由主题服务持有：已验证候选目录、当前提交的选择、按主题保存的用户覆盖、注册键及其默认值。有效颜色快照、筛选列表、预览和富文本缓存均为派生状态，使用版本号重建。文件 I/O 不在每帧或每次 `GetColor` 中执行。

普通模式的覆盖顺序：键所有者默认值 → 内置基础主题 → 选中的一套主题 → 该主题的用户覆盖。首版不支持用户任意堆叠多套主题或跨包继承，避免循环依赖和不可解释的优先级。

首次升级由主题迁移 adapter 按原来源顺序解析已有配色，转换为普通用户主题与规范键数据，原文件保留。新选择器不提供兼容模式或旧叠加开关，之后按统一选择规则运行。后续旧 XML 导入/活动 Mod 来源读取也在输入 adapter 转换成当前模型，主题运行时不判断历史格式。全新安装使用内置默认主题。

主题身份由来源与稳定主题 ID 组成：内置、活动 Mod、用户本地、商店包四类。商店定位使用 `sourceId + packageId + themeId`；包内文件名不是唯一身份。旧无 ID XML 在来源 adapter 中用来源 ID 与标准化相对路径生成稳定身份，不使用绝对路径作为持久键。重复主题 ID 给出诊断，不以文件系统枚举顺序决胜。

### 4.2 解析、提交和回退

XML v1 由读取 adapter 接受颜色和旧浮点参数并归一化。新主题描述增加稳定 ID、显示名/作者、主题 schema 和宿主支持范围；文件中颜色保持可复用的 v1 结构。主题描述 schema、样式键集合版本和包清单版本分别管理，不把三者混为程序集版本。

解析到临时纯数据模型后整体验证，成功才生成下一快照；提交时一次替换有效快照并递增版本。颜色必须为有限数值，范围按键定义验证；禁止 NaN/Infinity、DTD/外部实体、危险路径和重复声明，限制文件字节、XML 深度和条目数。新包出现损坏值时整套拒绝；旧文件允许的历史缺省行为由 v1 适配器明确保留，并记录一次诊断，避免升级突然改变旧配色。

未知键由输入层保留在原始数据中，规范模型只接收当前声明的键；可选插件未安装不阻止主题应用，后来注册键时重新解析。旧浮点参数由读取 adapter 映射到受支持的当前参数；无法无损映射的项给出输入诊断，不让新 UI 选择旧布局行为。首版编辑只开放颜色和有边界的视觉参数。

基础平台色每次都从不可变默认集合重建，避免删除某个覆盖键后沿用上一次属性值。新调用方只读取已解析的规范样式快照；缺值由主题解析服务统一补默认。若维护插件短期仍需旧 `GetColor` 返回语义，仅在老接口 adapter 中处理，迁移完成后删除该入口。

选中主题消失、Mod 停用或包被卸载时，有效主题回退内置默认，保留原选择意图和用户覆盖供恢复；展示缺失原因。安装成功不自动应用，更新已选主题通过完整验证后替换有效数据；验证失败保留上一份已验证快照。应用配置写入失败时不显示成功，并回滚预览/提交，事务规则在 F8-1 固定。

### 4.3 统一刷新与资源所有权

确立统一主题读取/注册/变更契约，主线程通知有效样式版本变化。全部维护中 UI 迁移到当前契约，刷新富文本、用户名颜色与日志缓存。当前没有第三方消费者，直接删除 `IUiTheme` 与业务 `Reload()` 入口；文件读取 adapter 负责历史主题数据。

颜色注册使用所有者、命名空间和可释放句柄。内置键和插件默认值使用相同机制；插件退出撤销自身元数据和默认值，不删除用户存储的覆盖。跨插件同名键拒绝，同一所有者重复注册幂等；旧注册行为只在必要的 adapter 内转换。

首版主题不加载纹理、字体、声音、脚本或程序集，降低生命周期与其他 Mod 兼容成本。未来增加图像需另行定义大小、解码和 Unity 对象释放策略，不能因资源清单支持图片就默认开放。

## 5. 专门设置窗口与主题选择器

主题窗口由宿主提供通用入口，断线、主菜单以及禁用 Chat/Store 时仍可进入。入口加入 Phinix 设置；商店主题详情的“选择主题/自定义”按钮通过通用窗口服务打开相同窗口。现有 Chat 重载入口改为打开主题设置或调用通用重载，不保留独立业务刷新逻辑。

窗口提供以下并列功能：

- **选择**：列出内置、本地、活动 Mod 与商店主题，搜索/来源筛选、名称、作者、状态、适用范围；明确区分已安装与已选择。
- **预览**：在窗口内部展示通用卡片、状态/按钮、聊天和交易的示例视觉元素。业务插件可贡献预览 provider，宿主不直接依赖业务 Contracts。未提供的插件不生成预览。
- **自定义**：按宿主与插件分组，显示键的中文名称、说明、默认色、主题色、用户色；支持 RGBA 输入、色板、恢复单项/当前分组/本主题覆盖。
- **提交**：明确“应用”和“取消”；预览只影响窗口内样例，应用后全 Phinix 更新。恢复内置主题可在任何损坏来源状态下使用。
- **导出与本地安装**：按 2026-10-11 最新需求，选择器保留导出，目标为可经商店安装的主题 ZIP，显示输出路径并提供复制/打开目录；本地导入统一交给商店，在商店纯主题包安装闭环完成后移除选择器导入入口。既有用户 XML/配置继续可读。可选快捷提交先评估，不把上传、提交候选与审核上架混为一项；详见 Theme-Export-and-Quick-Publishing-Assessment.md。

宽窗口使用主题列表、预览和编辑区域；窄窗口切换为列表/详情/编辑分页。沿用 `UiScreenSafeArea` 和响应式布局辅助类，语言切换、UI 缩放、长主题名、颜色输入与弹窗焦点纳入验收。颜色对比提示帮助作者发现文字不可读，但不强制改写用户合法的颜色。

主题配置是客户端全局配置，不按存档复制。按主题保存用户覆盖，切换后可以恢复各主题调整。插件未启用的键可列为未使用，重新启用后继续有效。

## 6. 新 UI 的样式键开放

### 6.1 优先从现有响应式 UI 公共层接入

2026-10-10 用户补充：几个插件已使用宿主提供的响应式 UI 包装，希望从共同入口接入主题。本轮代码核对确认 Chat、Trade、Inventory、Store 的主 Tab 均实现 `IResponsiveMainTabProvider`，宿主 `ServerTab` 根据布局提示分配区域，再调用 `IMainTabProvider.Draw(Rect)`；Trade/Store 还消费 `ResponsiveToolbarLayout`，宿主设置消费 `ResponsiveFormLayout`。

因此主题化首选共同 UI 层作为主要入口。但当前 `ResponsiveFormLayout`、`ResponsiveToolbarLayout`、`ResponsiveSplitLayout` 主要输出几何位置，`IResponsiveMainTabProvider` 只提供尺寸提示；插件内部仍直接调用 `Widgets`、设置 `GUI.color` 并绘制自己的元素。改一次布局计算器不能自动改掉所有插件控件的颜色。

在现有公共层上补齐带主题的绘制入口：宿主外壳统一绘制导航、侧栏框架与通用背景；公开控件负责按钮、输入框、列表行、卡片、分隔和状态文本；响应式组合控件复用已有几何计算，再用相同样式角色绘制工具栏、表单和分栏。纯几何方法保持现有签名与无分配行为，不读取文件或操作 GUI 全局状态。

公开绘制入口接收通用 UI 上下文，包含本次绘制使用的样式快照/版本、必要的布局参数和作用域；由 DI 注入或显式传参，不从 `Client.Instance` 静态获取。首批 API 可从 `DrawButton`、`DrawSurface`、`DrawTextField`、`DrawStatus`、`DrawToolbar` 等小型入口开始，最终命名在 F8-0 固定。布局与控件同属公开 UI 能力，主题数据由同一主题服务提供。

控件默认使用语义角色（主按钮、危险操作、次级文字、选中行等），插件仅为报价双方、提及背景等业务视觉提供自有键/显式样式覆盖。角色到颜色键的映射由公共 UI 层维护，主题设置根据注册元数据自动生成编辑项。主题应用时，新一帧控件读取同一有效快照，无需每个普通按钮独立订阅事件；只对缓存颜色/富文本的消费者使用版本失效机制。

迁移顺序：宿主外壳和主题窗口 → 商店/扩展管理 → Chat/Trade/Inventory → 维护中的独立插件。完成态只有一套公共 UI 绘制契约；几何算法可复用，旧包装与重复绘制入口迁移后删除。不自动将任意 `Draw(Rect)` 转译成新控件，不通过全局 `GUI.color` 乘色包裹插件；特殊业务元素也从统一绘制上下文消费当前样式。

### 6.2 配色键覆盖与编辑范围

在 F8-0 建立可核对的样式键表：稳定键、显示名称、所有者、默认值、使用位置、RGBA 范围、是否可编辑、输入 adapter 的旧键映射及失效缓存。不能只增加 XML 键而没有真实消费点。

| 区域 | 首批开放项 | 兼容要求 |
| --- | --- | --- |
| 宿主外壳/设置/主题窗口 | 内容背景、表面、边框、分隔、主/次/禁用文本、强调、悬停/选中/焦点 | 输入 adapter 归一化原平台键；当前角色默认在解析层确定 |
| 常用控件 | 主/次/危险按钮、输入框、占位符、校验错误、切换/滑块、链接、提示 | 绘制状态与 GUI 恢复分开，白色乘色复位不能机械替换 |
| 扩展管理 | 各模块状态、依赖警告、选中行、日志级别与诊断 | 保留 `ext.*`；日志缓存随版本更新 |
| 商店 | 各来源/包类型徽章、卡片、进度、更新提示、错误/忙碌状态、主题色板 | 保留 `plugin-store.*`；不得只凭色彩区分包来源与状态 |
| Chat | 提及、自己/他人、回复、通知、图片加载/失败、输入区域、未读/状态 | 保留 `chat.*` 与用户名 HSV 键，刷新已缓存文字 |
| Trade | 双方报价、确认/等待、取消、列表/面板、搜索与错误 | 保留 `trade.*`；视觉变化不改物品或操作状态 |
| Inventory | 条目/来源、预留/恢复/只读、计划、选中、数量与操作反馈 | 新增插件命名空间；库存账本行为不受主题影响 |
| LegacyAdapter 与独立插件 | 使用通用控件并注册自己的显示键 | 无 UI 的模块无需虚构配色；红包、人才贸易按真实消费点逐步迁移 |

语义键用颜色角色表达，插件特殊颜色仍有自有命名空间。可提供少量有实际覆盖的内置配色作为示范，具体色值在 UI 阶段确定；不在此文档声称第三方 UI 已全部主题化。

### 6.3 单一 UI 契约与旧接口 adapter 边界

按用户最新要求，完成态不混用新旧 UI 包装。维护中的宿主、内置插件、Example、红包和人才贸易迁移到同一当前绘制/布局契约；几何算法可复用，旧 wrapper 和重复入口在调用归零后删除。无须维持不存在的第三方旧 UI；无法语义适配的任意旧绘制代码直接重构，不用 global tint 模拟迁移。

旧高层 UI 调用若暂需接续，由独立 facade adapter 翻译为当前控件请求。新 UI 不引用旧接口，也不查询“是否旧 provider”或选择兼容绘制分支；具体迁移完成时间与删除条件列入清单。通用当前控件仍可在实现内部调用 Verse/Unity 原语，这不构成旧 API 混用。

主题旧键、v1 XML、无 ID 来源和首次旧配置叠加在输入/迁移 adapter 归一化。主题服务和控件只消费当前模型/规范键；缺当前值由解析服务补默认，不在每个按钮或业务样式中执行旧键回退。原主题文件保留，迁移结果是普通用户主题，设置窗口不需要兼容开关或历史 schema 信息。

绘制作用域仍须逐次保存/恢复实际 GUI/Text 状态，支持嵌套与异常退出；group、clip 和滚动区域由创建者成对关闭。`GUIUtils.SaveTextFormat/RestoreTextFormat` 的单组静态字段不适合作新嵌套作用域，消费者迁移后评估删除这组旧帮助方法。

新控件保持禁用、命中、焦点、输入编辑、键盘提交/取消、Tooltip、滚动及工具栏溢出的业务行为。切主题不重复消费事件、不补发请求、不丢编辑内容；同一绘制过程使用一致快照，样式提交在安全边界生效。主题不全局修改 `GUI.skin` 或其他 Mod 样式。

当前 UI/API、数据读取 adapter 与旧接口 adapter 的引用关系和删除门槛统一按 [边界审查](Compatibility-Interface-Boundary-Audit.md) 执行。新业务读取不到 CompatibilityMode、旧 DTO、旧键映射或历史版本分支，完成态只保留当前入口。

## 7. 商店主题包与端侧发布

### 7.1 包类型与目录升级

新增独立的 `phinix-theme` 管理类型、`theme-zip` 载荷和纯数据清单；名称暂定，在 F8-0 冻结。保持现有 `phinix-dll` 包定义，不用空 DLL/假模块满足主题条件，也不将主题登记成可执行扩展模块。

主题清单包含包 ID、名称、版本、宿主范围、主题 schema、主题描述列表、文件路径/长度/SHA-256 及显示本地化。首版一包可带多个主题变体，但包级更新/卸载一起执行；不允许可执行依赖或加载业务 DLL。对特定插件键的支持作为显示信息，缺失可选插件不会阻断通用主题。

建议升级商店目录至下一 schema（暂记 v4），明确新客户端解析既有 DLL/工坊条目及主题条目。所有客户端统一更新，因此不维护旧客户端 v3 目录；目录发布与客户端上线协调即可。已经安装的 DLL 包、收据和恢复日志仍需可读，这是数据兼容，与支持旧客户端不同。

纯主题包不需要 `targetFramework`、`abstractionsRange`、程序集和模块字段。与旧 `PhinixTheme v1` 文件兼容通过主题解析器完成，包格式不承担 CLR 兼容判断。首版 ZIP 限制为清单、描述和声明的 XML/JSON/文本本地化文件，拒绝 DLL、脚本、链接、额外文件及路径别名。

### 7.2 安装、管理与来源

共用现有来源绑定、冻结载荷、哈希/长度校验、暂存、收据、journal 与提交决定；在中立包存储边界增加数据包处理，代码扩展运行时继续只发现 DLL 模块。主题包放在受管的独立主题根目录，不复制到用户 `Themes` 覆盖目录或 RimWorld Mod 安装目录。

主题包具备已安装、可更新、验证失败、当前选中/使用中状态；不复用“模块激活成功”表达纯数据应用。首版不增加主题包启停开关，已安装候选通过选择器控制是否使用。卸载已选包回退默认并显示影响，保留本地用户覆盖；无关 DLL 包的期望启停状态不改变。

商店本地安装可识别纯主题 ZIP，沿用来源标识、冲突与正式包不可被本地包静默覆盖规则，普通用户不需要 DevMode；代码插件侧载仍按已有 DevMode 规则。选择器不再承担本地导入；既有 XML 读取/归一化留在输入 adapter，不将 XML 自动标为受管包或 Index 批准。

主题与 DLL 混合目录里的包身份、已安装文件占用、依赖与冲突校验都须明确包类型。主题不占用程序集/模块名称；它仍受来源/包 ID、文件边界和不可变正式版本锁约束。

### 7.3 Index、工具及上线顺序

Index 的候选校验、可信 Validator 固定源码快照、准入策略、自动更新策略、受控发布与客户端共同支持新类型。策略分支须按类型验证主题身份与文件声明，不能假设所有 GitHub 包都有 `assemblies/modules`。作者主题文件只做数据解析，校验器不执行作者脚本。

1. Common/客户端完成新类型、主题验证器和本地安装闭环，固定契约与包格式。
2. 可信校验器及 Index 更新到固定提交，现有 DLL/工坊候选与历史审核证据仍可验证；新增主题准入规则。
3. 客户端发行与 Index v4 发布协调，发布前做完整目录演练；目录不能提前指向尚未上线客户端无法读取的格式。Cloudflare/直连端点、缓存/ETag 和不可变 published 快照一起更新，旧缓存应重新获取。
4. 发布演示主题并检查正式 Release → 准入 → 发布 → 商店可见 → 安装 → 应用 → 更新 → 卸载。

不新增强制签名门禁。包完整性、来源和人工批准规则继续有效；同版本不同正式载荷拒绝。本地可修订规则仍受本地来源限制。回滚客户端与 Index 时需要协调目录读取版本，新增主题收据应保留并隔离而非删除用户数据。

## 8. 插件公开 API 扩展评估

### 8.1 包装 API 的判断标准

现有宿主已提供会话、用户、设置、主线程调度、窗口、声音、链接、翻译、环境和扩展控制；Common 有 API 注册、日志与插件存储入口；客户端有响应式几何工具。现有能力优先文档化和复用，只有缺少一致行为、所有权或可观测结果时新增契约。

新包装 API 让作者表达用户意图、读取稳定快照、订阅变化，由主体处理状态与确认，具体 adapter 处理历史契约及外部协议。新接口不暴露旧 service/DTO、容器、wire packet、模式或 schema。旧 public 入口按实际维护消费者迁移并删除；必要的 adapter 契约限定边界，不进入普通业务 API 面。

每个新增 API 必须交付：能力发现与可用状态、输入/输出、线程、寿命、结果/错误码、版本/依赖声明、失败回退、Example/独立作者实验及可接入的默认行为，不要求逐接口实际内置消费者。接口名以下均为草案，不作为已交付能力。

### 8.2 宿主通用能力

| 优先级 | 拟补能力 | 具体用途与边界 |
| --- | --- | --- |
| P0 | 主题读取/变更、键描述/作用域注册、主题窗口服务 | 单一当前主题契约；直接迁移维护中调用方并删除老 `IUiTheme`。规范样式快照不暴露旧键/schema/兼容模式 |
| P0 | 包资源访问 | 模块绑定的 `IClientResourceService`，有界读取自身声明资源；共用 managed 文件验证，适配传统 Mod；不公开任意可写路径，不扫描其他 Mod 内容 |
| P0 | 公共 UI 控件和绘制作用域 | 作为主题接入的主要入口，在已有响应式几何层上增加主题化控件及表单/工具栏组合；显式 UI 上下文提供样式快照，统一恢复 GUI/Text、焦点与长文本；详见 §6.1 |
| P0 | API 可用状态查询 | 在现有注册与依赖管理上提供已声明/已激活/失败/不支持状态和版本信息；避免“resolve 成功即业务可用”的假设 |
| P1 | 主线程工作提交的可观测结果 | 统一契约报告排队拒绝、取消和失效会话；旧 void 入口必要时由 adapter 转发，当前业务不靠旧返回语义推断成功 |
| P1 | 插件设置描述与作用域帮助器 | 在已有 `Get/Set` 上补命名空间、schema、类型验证、默认值、迁移与可发现设置项；不立即重写全部设置存储 |
| P1 | 用户通知与诊断摘要 | 在显示消息与日志上提供受限 toast/状态反馈和操作关联 ID；不泄露凭据、玩家私密信息或内部异常对象 |
| P1 | 文件选择/确认等通用交互 | 复用本地侧载界面和窗口服务，使第三方获得取消/错误等结果；不允许任意文件系统权限代理 |
| P2 | 游戏上下文辅助能力 | 仅包装重复使用的主线程检查、当前存档/地图身份与代次；不返回长期持有的世界对象或泛化所有 RimWorld API |

资源读 API 与 Common 已有 `IExtensionStorageProvider` 的写存储职责区分；不重复开发第二套日志、DI 或包注册中心。P1/P2 在真实样例确认后进入后续切片，不将全部能力设为首发阻塞项。

### 8.3 内置插件 API 纳入同一阶段

| 插件 | 当前可用基础 | 拟公开/包装能力 | 状态所有者与风险 |
| --- | --- | --- | --- |
| Chat | `IFrameworkChatClientApi` 提供造包、渲染、历史与 UI 模型；现有聊天服务及消息 feed | `IChatReadApi` 的不可变消息/未读快照与变化事件；`IChatSendApi` 的正文、提及、回复操作；可选 Chat 窗口入口 | Chat 处理历史、发送和回复规则；业务可用性与发送结果由统一端口提供，协议差异限定 adapter，不能把排队当送达 |
| Trade | `IFrameworkTradeClientApi` 混合仓库、造包和响应处理；另有更新结果及 Legacy 注入接口 | `ITradeReadApi`、`ITradeOperationsApi`、`ITradeWindowApi`：创建/打开/更新/接受/取消，返回可关联操作 ID 与状态 | Trade 保留唯一 token、真实回执和待确认托管；旧 Legacy 注入契约迁移到统一事件端口后删除，外部 driver 不影响主体 |
| Inventory | 已有 read/deposit/extraction/registration/reservation 分离 API，并有旧聚合接口 | 统一 codec/交付契约，注册处适配旧接口；完善能力状态、错误码、不可变快照和预留生命周期 | 库存主体控制 ledger、codec 与预留；不得新增忽略 custody 或绕过结果未知核对的便捷发物品入口 |
| Plugin Store | 已有控制器、安装/管理服务，商店 UI 注册 Tab/设置/横幅 | `IPluginStoreReadApi` 只读目录/已安装/更新；`IPluginStoreWindowApi` 打开详情；交互安装请求返回用户取消/进行中等状态 | Store Contracts 拥有业务入口；所有写操作回到既有校验、用户意图和事务，不给第三方直接提交裸 journal |
| LegacyAdapter | 当前协议模式、原始传输与 Trade adapter 入口 | 基础设施保留外部协议 driver；业务只得到中立能力/操作结果，不获知模式或协议名 | 协商、包转换与关联留在 adapter；当前业务无旧接口调用与协议分流 |

Chat/Trade 的现有 `IChatUiHostContext` / `ITradeUiHostContext` 是高耦合 UI 接缝。维护中消费者迁移到当前操作/读取接口；确需过渡的旧调用通过独立 adapter，迁移后删除旧契约与实现。新 API 不要求制造 `ClientFrameworkContext` 或处理响应包；Legacy 入站专用接口亦改为统一领域事件端口，主体不保留 Legacy 方法。

维护中的红包、人才贸易与 Example 作为独立作者路径验证对象，按自身真实需求消费新增契约；其现有缺陷修复、DI 迁移和卸载存档限制分别记录，不以 F8 接口包装宣布已解决。宿主不增加红包/人才贸易专用服务。

2026-10-10 同日清理：红包/人才贸易已直接迁移 Compose 并删除自身旧 Register，打包抽象下限收紧为 1.9；逐项接口使用与待删除边界见 [维护插件评估](Maintained-Plugins-Old-Api-Assessment.md)。两个插件可控，不为它们默认增建长期 adapter，当前端口就绪后直接迁移并删除旧调用。

服务端内置 Chat/Trade 的 API 可在 F8-0 做盘点，但端侧阶段首批契约不依赖服务端升级。若发现新的远端能力才能满足业务 API，另开契约与协商切片，本阶段先给出 Unsupported/能力缺失结果。

### 8.4 版本、依赖与生命周期

当前契约冻结后协调客户端、Common、维护插件、工具/CI 的发行输入。可以删除已迁移旧接口并改变 API，破坏性版本号据实际变化确定；不以旧“1.0/2.0 才删除”计划拖延无消费者代码清理。持久化/wire 标识变更仍需独立迁移或保留读取 adapter。

必需业务依赖在包/module 声明中明确，消费者在 provider 已激活后获取；可选依赖缺失必须能继续运行自身功能。跨插件 API 留在该插件 Contracts，纯客户端契约不迁入游戏中立 Common。Common 只承担中立包格式/安装契约及确有需要的运行时基础设施。

新包装操作区分 Rejected、AcceptedForProcessing/Pending、Confirmed、Uncertain/Unsupported 等语义，按对应业务精确定义，不强制所有 API 使用一套万能状态枚举。提交 ID、token、会话身份由主体统一关联；重复调用的幂等规则公开。订阅返回可释放句柄或有明确取消配对，回调异常逐消费者隔离。

新增组件由内置插件首先消费，第三方样例使用同一路径。新增接口已注册、样例编译通过、游戏场景通过和正式包已发行是四项不同证据。

## 11. 范围边界与风险处理

本阶段首发以配色数据为主，纹理/字体皮肤、主题脚本、DLL 热加载、项目生成器、额外 NuGet SDK、强制签名及通用远程业务协议扩展不纳入首批。已有整 Mod ZIP 安装取消决定继续有效。

主要风险是样式注册与插件生命周期耦合、切换后缓存不一致、安装类型贯穿不完整，以及高层业务 API 把底层处理成功误写成业务完成。分别通过作用域注册、版本驱动刷新、客户端/Index 共用可信验证规则，以及有确认/未知状态的业务操作契约控制。

窗口草图、准确 API 名称、各包格式上限和发行版本在 F8-0 固定；不影响本轮文档形成，也不需要以这些常规实现选择暂停评估。若第三方实际用法要求破坏现有公开签名或迁移持久状态，应先记录具体调用与迁移方案，再单独处理。

## English summary

F8 delivers client-side theme management, a dedicated selector/editor, themed public responsive controls, data-only Store theme packages, and practical plugin-owned business APIs. Steam clients update together and no third-party plugins currently require indefinite old binary API support. Maintained modules migrate together to one current contract; obsolete interfaces and duplicate UI paths are removed after real consumers are migrated.

Adapters cover all old interfaces, not only the LegacyAdapter plugin. Old caller facades, theme/configuration readers, codec adapters and external protocol drivers convert at explicit boundaries. New business/UI never sees old interfaces, schema versions, legacy keys or protocol modes. Existing theme/configuration/ledger/receipt data and supported server behavior remain protected. See the companion compatibility boundary audit for confirmed leaks, adapter responsibilities and deletion gates.

Theme migration produces ordinary canonical profiles without a compatibility selector. Controls consume one validated style snapshot; geometry and interaction behavior are preserved. Runtime remediation and game acceptance remain pending; this document and the audit do not claim implementation completion.
