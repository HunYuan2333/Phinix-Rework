# 插件商店可行性评估与功能设计

日期：2026-09-30。分支：`dev`。

状态：可行性论证与设计建议，尚未实现。文中的包清单、接口名称、目录及参数均为提案，不代表当前框架已有能力。2026-10-01 补齐双渠道分发与官方索引自动化调研；详见 [双渠道索引与 GitHub 自动审核发布评估](插件商店双渠道索引与GitHub自动审核发布评估.md)。仅修改设计文档。

2026-10-02 补充 [安全性与维护成本独立评估](插件商店安全性与维护成本评估.md)：用户确认开放申请、首次人工批准及后续自动检查，默认源 GitHub 插件须有可审查源码；分析同进程 DLL 的权限边界与小规模项目的基本措施，其他新增政策仍为建议。

## 1. 结论与范围

**可行，建议采用“普通客户端商店插件 + GitHub 审核索引 + 工坊/GitHub 双渠道 + 显式包依赖清单”的方案。** 工坊条目索引工坊链接，GitHub 条目索引作者仓库与固定 Release 资产。GitHub 包可自动下载、校验和安装；工坊首版引导订阅，不承诺由商店直接下载。依赖计划区分可自动下载和需要外部安装的节点，插件仍通过原有模组加载及适用的 Phinix 扩展生命周期生效。

已由用户明确的要求：

- 首版面向游戏内客户端；服务端暂时手动安装。
- 从 GitHub 获取列表；源可配置，并有默认源。
- 默认源由 Phinix 维护，是经过审核的插件索引仓库。
- 评估自动解析和下载依赖，包括传递依赖链。
- 特殊网络环境下允许配置**仅插件商店使用**的 HTTP、SOCKS5 等代理。
- 本阶段只做评估与功能设计，保存文档，不实际实现。
- 工坊模组索引工坊链接；轻量 GitHub DLL 包索引 GitHub 链接，评估类似 AstrBot 的自动化。
- 官方仓库发布审核后的索引，DLL 由作者仓库发布；首次入库人工批准，后续版本自动检查后更新索引。
- 默认源允许任何作者申请，审核后收录；GitHub 插件必须有可审查源码，无源码 DLL 不收录。源码存在不等于已证明源码/产物一致或代码安全。

当前推荐、尚未由用户明确确认的产品决策：

- 首版支持两种来源；GitHub 首选轻量标准 ZIP，纯 DLL + 明确清单可评估生成最小本地模组壳。安装结果优先保持标准模组身份，不直接写 Phinix/Workshop 目录。
- 安装与启用分开：新包默认不启用，玩家在原生模组列表中启用、排序并重启；不承诺当前游戏热加载。
- 首版优先提供浏览、搜索、依赖计划、新包安装、缓存及代理；升级覆盖、卸载和自动修改模组列表进入后续阶段。

| 能力 | 可行性 | 主要条件或限制 |
| --- | --- | --- |
| 默认/自定义 GitHub 索引 | 高 | 约定索引格式，缓存与限流，显示来源 |
| 下载客户端插件包 | 高 | 下载编译好的 Release asset，校验后安装 |
| 工坊条目展示与跳转订阅 | 高 | 索引包含工坊 ID/链接；Steam 负责实际下载 |
| 自动补齐直接及传递依赖 | GitHub 链可行；混合链有外部步骤 | 显式清单；工坊节点需实际安装后核对，不能假装已满足 |
| 首次人工入库、后续自动更新索引 | 高 | 绑定发布者身份和发行规范，通过检查后自动收录 |
| 任意现有 DLL 自动推导完整依赖 | 低，无法可靠保证 | 程序集引用不能描述资源、模组依赖和下载位置 |
| HTTP 代理访问 HTTPS GitHub | 高，需游戏运行时验证 | 商店专用 handler、CONNECT、认证、重定向 |
| SOCKS5 代理 | 有条件可行，主要技术风险 | net472/Unity 兼容传输实现，远端 DNS 与认证验证 |
| 当前进程内即时加载、升级、卸载 | 不适合首版承诺 | 程序集、Defs、资源、静态状态及生命周期限制 |
| 客户端安装后自动具备服务端功能 | 不成立 | 服务端插件与协议能力需管理员另行部署 |

## 2. 依据：设计哲学、开发者指南与当前代码

本评估已阅读 [Design-Philosophy.md](../../Design-Philosophy.md)、[Phinix 附属 Mod 开发者指南](../../Phinix附属Mod开发者指南.md)、[兼容与恢复边界](../../Compatibility-Boundaries.md) 及 [branch-local 文档约定](../README.md)，并核对以下代码。指南中的示例与行号不能替代当前代码事实。

| 当前事实 | 代码证据 | 对商店的影响 |
| --- | --- | --- |
| 客户端先加载程序集，再发现扩展、构建依赖图和激活 | [Client.cs](../../../Client/Source/Client.cs) 的构造过程 | 下载完成不等于发现/注册/激活完成 |
| 客户端探测基础目录及活跃第三方模组的顶层 `Assemblies` | [Client.cs](../../../Client/Source/Client.cs) 的 `GetExtensionProbeDirectories` | 独立模组包能利用现有入口；任意新建包目录不会自动成为探测目录 |

| 相同程序集 simple name 已加载时跳过新候选 | 同上 `tryLoadAssembly` | 同名多版本共存与热替换不能靠重复调用 Loader 解决 |

| 当前启用策略从设置读取一次性快照 | [StaticActivationPolicy.cs](../../../Client/Source/Framework/StaticActivationPolicy.cs) | 管理面板开关也不表示即时卸载或热启用 |
| 扩展管理 UI 直接访问宿主实现 | [ExtensionManagerTab.cs](../../../Client/Source/GUI/Windows%20and%20panels/ExtensionManagerTab.cs) | 商店插件不能照搬 `Client.Instance` / `PhinixFrameworkClient` 访问方式 |
| 普通插件已有 Tab、设置面板、快捷设置面板、开窗、主线程调度及存储接口 | [IClientExtensionAbstractions.cs](../../../Client/ClientExtensionAbstractions/Framework/IClientExtensionAbstractions.cs)、[FrameworkTypes.cs](../../../Common/Utils/Framework/FrameworkTypes.cs) | 商店 UI、源配置与下载状态可通过通用扩展点接入 |
| 存储 Provider 只分配插件路径 | [FrameworkTypes.cs](../../../Common/Utils/Framework/FrameworkTypes.cs) 的 `FileSystemExtensionStorageProvider` | 不提供安装目录选择、文件事务、版本锁或恢复 |
| 服务端已有 `Extensions` 与 `UserExtensions` 探测目录 | [Server.cs](../../../Server/Server.cs) | 可给管理员下载说明；首版不从客户端写服务端目录 |

## 3. 分发来源与本地加载形态分别设计

用户后续要求工坊与 GitHub DLL 两类条目，本节相应调整。**不再要求所有作者都只发布标准 ZIP**；前一版推荐保留为本地安装形态建议。来源有工坊/GitHub，载荷有标准包/纯 DLL，加载方式有 Phinix 扩展/普通 RimWorld patch 模组，三者不是同一维度。具体清单与安装路径见补充评估。

### 3.1 两种方案的取舍

| 维度 | 标准 RimWorld 独立模组包（推荐） | 裸 DLL / 专用插件目录 |
| --- | --- | --- |
| 内容 | 可完整携带 About、语言、Defs、贴图和多个 DLL | 还需自行定义资源位置与加载方式 |
| 身份 | RimWorld packageId、插件模块 ID、商店包版本各自明确 | 需要另建身份与包边界 |
| 发现与启用 | 使用已有模组与扩展加载入口 | 任意专用目录目前未被自动探测；需要增量宿主能力 |
| 安装位置 | 玩家本地 `Mods` 的独立目录 | 不宜写入 Phinix 或 Workshop；用户目录还需探测契约 |
| 多 DLL 与 Contracts | 一个完整包，清单规定归属 | 平铺目录容易出现同名程序集和版本覆盖 |
| 使用成本 | 玩家需启用并重启 | UI 可能更省步骤，但要承担新加载模型的成本 |
| 更新与恢复 | 每包有清晰文件边界 | 需追踪每个 DLL 的归属、共享库和资源 |

**推荐理由**：Phinix 插件是 RimWorld 模组中的扩展模块，不保证是单一 DLL。独立包与开发者指南推荐的分发方式一致，能够保留资源和标准模组身份，并避免 Steam 更新覆盖商店写入的内容。它也更方便手动安装、排查问题和第三方发布。

安装包格式与是否“一键启用”是两个独立决策。采用标准包不会阻止未来增加启用辅助；首版不自动改模组列表，主要是控制依赖、排序与存档影响。

### 3.2 GitHub 标准 ZIP 的建议包约定

- ZIP 根目录直接包含 `About/About.xml` 和 `phinix-package.json`，不允许随机多层外包装目录。普通顶层 `Assemblies` 作为首版支持基线；复杂 `LoadFolders.xml` / 版本资源布局需专门适配和验收。
- 使用稳定且唯一的 RimWorld `packageId`；声明 Phinix 模组依赖及加载顺序。额外模组依赖也必须写入 About，不能只存在于商店索引。
- 清单列出包提供的所有 ExtensionId、包依赖、必需外部模组、运行环境与程序集身份。
- 不重复分发 Phinix 核心 DLL、RimWorld/Unity 参考 DLL；依赖其他插件 Contracts 时由明确的所属包提供，不能每包各带一份不同版本。
- 普通第三方运行库可随包分发，但需声明归属、许可证与程序集身份；不能从 DLL 名称猜测 NuGet 包并在线下载。
- 模组之间的加载顺序由模组声明与玩家排序决定；单个模组内 DLL 顺序仍需按现有工具链要求打包。模块依赖图无法修复发生在反射之前的程序集加载失败。
- 首版不支持安装脚本、编译源码、执行仓库命令或任意安装钩子。

GitHub 包安装目标为已确认可写的本地 RimWorld `Mods` 根目录下的商店管理目录，例如 `Mods/PhinixStore_example.notes/`。前缀只用于目录归属，不改变 About 的 packageId。不能根据 Phinix 所在目录推导可写位置，因为它可能位于 Workshop。纯 DLL 需要审核清单和已验证加载入口，再生成最小 About/Assemblies 壳；工坊内容由 Steam 管理，不复制到此目录或改写工坊文件。

## 4. 架构边界与接入方式

商店自身作为标准独立模组，通过 `IPhinixExtensionModule`、`IActivatablePhinixExtensionModule` 走普通发现、注册、激活和关闭流程。官方默认源是商店配置默认值，不是宿主给商店的特殊权限。

建议逻辑分层：

```text
商店 Tab / 独立窗口 / 设置面板
              ↓ 用户意图与只读状态
CatalogService → DependencyResolver → InstallCoordinator
       ↓                ↓                    ↓
GitHubSource       本地包快照          DownloadTransport
       ↓                                     ↓
索引缓存                              校验 → 暂存 → 安装日志
```

- GitHub 适配器、HTTP/代理、安装目录操作属于客户端商店实现，不放进 Common，也不经 Phinix 联机传输层发送 HTTP。
- GitHub HTTP 请求是外部内容获取；设计哲学关于 Message/Command/Item 管线的要求适用于与 Phinix 服务端通信，不意味着所有互联网 HTTP 必须塞进游戏协议。
- 包模型与解析器先作为商店内部、无游戏依赖的逻辑；未来确有复用需求再抽独立契约/库，不提前增加框架负担。
- 商店不引用 Client/Server 宿主工程、不读取 `Client.Instance`、不直接调用宿主私有 Loader 入口。
- 通过 `IMainTabProvider` 提供商店 Tab；通过 `IClientSettingsPanelProvider` 和可选快捷设置面板提供入口与网络设置，使用 `IClientWindowService` 打开商店窗口。设置入口不要求先登录服务器，主菜单 Mod Settings 路径也应可访问。
- `Register` 只注册对象；`Activate` 注入服务、创建客户端及取消上下文；`Shutdown` 取消任务、解绑事件、释放连接和文件句柄，阻止迟到回调更新已关闭 UI。
- Verse 模组信息在主线程读取为快照；网络、哈希、解压及包解析在后台进行。翻译、开窗、共享 UI 状态通过现有 dispatcher；进度合并后更新，不能每个数据块都占用主线程队列。
- 商店首次安装仍需随官方发行版提供或由玩家手动安装自身，不存在“未安装商店却从商店安装商店”的启动路径。

### 4.1 可能需要的通用框架增量

现有激活策略只提供禁用查询，不是完整的模块状态和安装包目录 API。首版可使用商店本地记录和 Verse 的已安装模组快照做安装计划，精确运行状态则不能假装已有公开查询能力。

若需要可靠显示“运行中 / 注册失败 / 宿主与契约版本”，评估增加通用只读 `IClientExtensionCatalog`、`IClientRuntimeInfo` 一类接口（名称待设计），放入 ClientExtensionAbstractions，并提供宿主适配。它们对所有插件开放，不含 GitHub、下载或商店业务。旧接口保留，遵守增量兼容原则。

因此，“基础浏览和新包安装可以主要在普通插件内完成”可成立；“完整运行状态、全部路径和版本信息零宿主改动保证可得”尚不能成立。复杂包探测、热加载和启动前更新另行论证。

## 5. GitHub 索引与版本来源

### 5.1 推荐获取方式

默认维护一个**独立审核索引仓库**。GitHub 包文件放在各作者仓库的 Releases；工坊模组保存工坊定位。官方只发布索引，不统一构建/重托管第三方 DLL，不代替 Steam 发布工坊内容。

配置字段建议：源 ID、`owner/repository`、索引入口路径、跟踪分支或固定提交、显示名称、信任状态。默认仓库的实际地址尚未提供，本文不虚构已经存在的默认源。

首版支持单个当前源，允许切换默认/自定义源、恢复默认。多源聚合后续再做；切换源不自动替换已安装包的归属。依赖只从当前计划允许的源解析，禁止索引悄悄引入新源。

建议采用小入口文件 + 按提交固定的完整目录快照：

1. 默认拉取已发布 stable 入口，得到索引 Release/tag、目录快照 commit 和内容摘要；不直接把开发中的 main 分支当正式目录。自定义源可显式指定 ref。
2. 本次安装计划只使用该 commit 下的包版本记录；如拆成多个文件，它们全部来自同一提交。
3. 保存快照标识、原始内容摘要与获取时间，避免解析过程中分支变化产生混合版本。
4. 浏览阶段不逐个访问每个作者的 Releases；选定包后才获取必要资产信息或使用已审核的固定下载定位。

GitHub Contents API 支持 `ref` 指定提交、分支或 tag，也支持 raw 内容。其返回的下载 URL 可能过期，因此缓存仓库定位与 commit，不持久依赖临时下载 URL。[GitHub Contents API](https://docs.github.com/en/rest/repos/contents)

### 5.2 缓存、限流与离线

- 仅在首次打开、用户刷新或缓存过期时请求；Draw 不发起网络操作。建议缓存有效期 30 分钟，最终参数可调整。
- 缓存按源身份、索引路径和 ref 隔离；保存 ETag/Last-Modified，支持条件请求，离线仍可浏览上次有效目录并明确标记时间。
- GitHub 公共 REST API 的未认证主限额为每来源 IP 每小时 60 次；多人共享代理出口可能共同消耗额度。[GitHub REST 限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- 识别限流响应与 `Retry-After` / reset 信息，不无限重试；普通认证失败、源不存在与限流必须区别显示。[GitHub API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- 默认支持公共源，不要求 GitHub 账号。私有源/token 可后续增加；绝不能内置共享 PAT。
- 原始索引无效时保留上一份有效缓存；未来不支持的 schemaVersion 拒绝安装，不尝试忽略关键字段。
- 首版离线安装只接受已有锁定计划且哈希匹配的完整缓存；离线时不能声称已获得最新撤回信息。

### 5.3 索引管理与审核

作者通过官方索引仓库 Issue 表单提交；bot 做格式、来源、依赖与载荷初审，生成可审阅的元数据 PR，首次由维护者批准入库。后续监测已批准来源的新版本，检查通过后自动更新索引。索引 tag 触发正式目录发布，作者 tag/Release 是独立的二进制发布过程。详见 [自动审核发布评估](插件商店双渠道索引与GitHub自动审核发布评估.md)。

审核侧校验 schema、标识唯一性、依赖闭包可满足性、环境声明和包结构；检查是否包含框架/游戏 DLL及不允许的文件。AI 报告只是初审参考。工坊条目需显示审核的对象与时间，不把条目首次批准等同于之后每次 Steam 自动更新内容都已审核。

索引应提供正常、撤回、停止维护等状态。撤回版本禁止新安装；已经安装的版本显示提示，不能自动删代码或清持久化数据。普通发布标签并不等于不可变内容；若作者启用 GitHub immutable releases，可增加资产稳定性，仍保留商店自己的固定哈希。[GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)

## 6. 清单模型与依赖解析

### 6.1 必须区分的身份

| 身份 | 示例 | 用途 |
| --- | --- | --- |
| SourceId | `phinix.default` | 来源、缓存和信任边界 |
| 商店包 ID | `example.notes` | 依赖解析、安装记录与发布归属 |
| RimWorld packageId | `example.phinixnotes` | 模组启用、加载顺序、Workshop 重复检查 |
| ExtensionId | `example.notes.main` | Phinix 模块运行时依赖 |
| 包版本 | `1.2.0` | 商店选择、升级及版本范围 |
| 程序集身份/版本 | `Example.Notes.Client` / `1.2.0.0` | CLR 类型及程序集冲突检查 |

一个包可以提供多个 ExtensionId 和 DLL；DLL/模块名称不能唯一推导 GitHub 包地址。安装记录须固定源与包身份，同时对 RimWorld packageId、ExtensionId 和程序集 simple name 检查全局冲突。

### 6.2 清单提案

每个包版本描述至少包含：

- 包 ID、包版本、名称、作者、简介、项目地址、许可证、维护/撤回状态。
- RimWorld packageId、提供的模块 ID、各模块必需的模块 ID。
- 客户端目标运行时、RimWorld 支持版本、Phinix/Contracts 兼容范围；需要原生库时列 OS/架构。
- 必需包依赖及版本范围、可选依赖、外部模组依赖、已知冲突。
- `distribution.kind`、`payloadKind` 与 `integrationKind`：分发来源、载荷形态、是否参与 Phinix 生命周期分别声明。
- GitHub：固定 artifact 仓库/tag/commit/asset 定位、SHA-256、下载大小和布局；工坊：publishedFileId、链接、作者、审核时间与版本可验证性，不捏造固定 Release/hash。
- 是否需要服务端配套插件、服务端版本/能力要求。元数据只用于说明，不能当成已完成服务器协商的证据。

如下为概念示例；仓库、版本兼容范围与哈希均是占位，不可作为可安装清单。字段尚未冻结：

```json
{
  "schemaVersion": 1,
  "packageId": "example.notes",
  "version": "1.2.0",
  "distribution": { "kind": "github-release", "payloadKind": "rimworld-mod-zip" },
  "integrationKind": "phinix-extension",
  "rimWorldPackageId": "example.phinixnotes",
  "modules": [
    { "id": "example.notes.main", "dependsOn": ["example.storage.main"] }
  ],
  "compatibility": {
    "side": "client",
    "targetFramework": "net472",
    "rimWorldVersions": ["1.6"],
    "phinixRange": ">=0.9.7 <0.10.0"
  },
  "dependencies": [
    { "packageId": "example.storage", "versionRange": ">=2.0.0 <3.0.0", "optional": false }
  ],
  "externalMods": [],
  "serverRequirement": { "required": false },
  "artifact": {
    "repository": "EXAMPLE_OWNER/EXAMPLE_REPO",
    "tag": "v1.2.0",
    "assetName": "example.notes-client-1.2.0.zip",
    "sha256": "REPLACE_WITH_64_HEX_CHARACTERS",
    "sizeBytes": 1048576
  }
}
```

完整发行规范还需加入包内 `phinix-package.json` 与目录的交叉校验；索引控制选择与期望哈希，包内自述不能反过来覆盖索引身份、路径、依赖或版本。

### 6.3 可以解析什么，不能推导什么

1. **商店包依赖**：可自动递归下载，例如 A → B → C；清单明确指定包 ID 与版本范围。
2. **模块依赖**：现有 DependsOn 仍负责 Register/Activate 顺序和缺失阻断。索引提供模块 → 包映射，确保包依赖闭包实际提供全部必需模块。
3. **程序集依赖**：只反映 CLR 引用，不能说明哪个仓库/资产提供它，也不能覆盖 Defs、翻译和动态反射加载依赖。解析 PE 元数据可作审核补充，不能代替作者清单。
4. **RimWorld 模组依赖**：About 声明和商店清单需一致；在选定源中明确提供 GitHub 包时可以下载。工坊依赖列入完整计划，首版引导订阅并等待实际安装后核对；未知版本不能通过严格版本约束。DLC/付费内容只检查和指引，不自动从未知地址补齐。
5. **宿主与随发基础包**：Phinix/游戏视为环境前置，不由依赖链自动升级。当前官方模块往往随 Phinix 包一起发布，不能为了补一个 `builtin.*` 模块就下载某个 DLL覆盖宿主随发版本。
6. **可选依赖**：默认不自动加入；缺失时作者必须能降级。编译时无条件引用一个并未提供的 Contracts DLL，不能仅在商店标为 optional 就保证降级。

首版只承诺清单明确且在允许源中存在的 GitHub 依赖可自动下载。混合链可以完整解析并展示，但工坊步骤未完成时状态为等待外部安装，不宣布整条链成功。历史包无清单时可由维护者补元数据，标记仅手动安装；不在运行进程中 `Assembly.Load` 待检查包去猜依赖，以免验证阶段就加载了插件代码。

### 6.4 解析与安装计划

```text
固定目录快照和目标版本
  → 获取本地已安装/已启用/来源/已加载身份快照
  → 过滤运行环境不兼容、撤回、预发布候选
  → 展开必需依赖并合并各路径版本约束
  → 选择版本，必要时有限回溯
  → 检查环路、外部模组、模块提供者及程序集冲突
  → 生成锁定计划和依赖优先顺序
  → 玩家确认一次完整计划
  → 下载、校验、暂存、提交安装
```

选择规则建议：

- 定义固定 SemVer 2.0 子集：首版只支持 `>=x.y.z <x.y.z` 和精确版本，预发布默认不选。不能使用字符串大小比较版本；程序集四段版本只作程序集信息。
- 一个 packageId 只选一个版本；共享依赖合并约束。先保留已经满足条件、可验证的安装版本，再选择最高可兼容稳定版；选择顺序固定以保证可复现。
- 单纯拓扑排序不能处理版本冲突。例如 A 要求 B `<2.0.0`，C 要求 B `>=2.0.0` 时不存在合法交集；应报出两条依赖路径，不能选一个“最新版”继续安装。
- 先前版本候选可能有不同依赖，所以需要有限回溯；达到节点、候选或耗时上限时报出无法完成解析，不伪称“没有版本”。
- 首版不给已安装包自动升级、降级或覆盖；依赖只能通过变更已有包满足时阻断计划并给出明确原因。后续增加升级时，必须重算所有受影响已安装包的约束，不能只算当前目标的子树。
- 本地手动/Workshop 包只有可信版本元数据时才参与版本约束；无法确认版本则显示未知并阻断严格依赖，不能用 AssemblyVersion 猜包版本。
- 已安装但未启用或被 Phinix 禁用的依赖，不需要重复下载，却仍需明确启用提示。安装计划满足不等于运行图已经满足。
- 重复 RimWorld packageId（特别是本地与 Workshop 两份）、模块 ID 或程序集名称必须先处理；不默默采用后发现的文件。

建议保护限额：计划最多 64 包、依赖深度 32、每包最多 32 个候选版本，解析耗时上限 5 秒。它们是待实验调整的初值，不是性能测试结论。

安装计划展示新增包、已满足依赖、需启用的模组、来源、版本、总下载/解压大小、服务器要求和阻断原因。确认后锁定目录快照、全部版本及哈希；源或代理配置变更后需重新生成计划，不能后台换版本。

## 7. 特殊网络环境：商店专用代理

### 7.1 产品范围与配置

代理覆盖商店自行发起的索引、元数据、GitHub 插件与依赖包请求，包括 Release 重定向。商店预览图若首版支持，也使用同一策略；外部浏览器由浏览器决定代理。Steam 实际工坊下载不由商店 HTTP/SOCKS5 客户端控制，不能向用户承诺这些设置能解决 Steam 下载问题。

配置模式建议：明确直连、显式跟随系统代理、HTTP 代理、SOCKS5 代理。默认明确直连；不静默继承环境变量或其他模组的全局网络配置。“HTTP 代理下载 HTTPS 文件”和“通过 TLS 连接到 HTTPS 代理服务器”需要在 UI 中区别。

| 字段 | 建议语义 |
| --- | --- |
| 类型 | Direct / System / HTTP / SOCKS5；HTTPS proxy 单列能力状态 |
| 主机、端口 | 默认示例为本地地址；校验合法主机和 1–65535 端口，支持 IPv6 |
| 认证 | 无认证或用户名/密码；不将密码拼进日志中的代理 URL |
| DNS | SOCKS5 默认由代理解析目标域名；本地 DNS 为显式选项 |
| 超时/重试 | 连接、请求和停滞超时；可取消，有限次重试 |
| 连接测试 | 分别测索引、资产及重定向，不仅测端口可达 |
| 失败策略 | 显式代理失败时保留错误，默认不退回直连 |

使用专用网络客户端/传输实例。禁止修改 `WebRequest.DefaultWebProxy`、进程级默认代理、全局证书验证回调、系统代理或 Phinix 联机网络配置。凭据仅绑定所选代理；原站认证、代理认证与下载重定向分别处理。

### 7.2 客户端运行时可行性

客户端目标是 net472，实际运行于 RimWorld 的 Unity/Mono 环境；服务端 net10 的能力不能当作客户端能力。Microsoft 文档支持在 `HttpClientHandler.Proxy` 上为单个 handler 配置代理。[HttpClientHandler.Proxy](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclienthandler.proxy?view=netframework-4.8.1)

Microsoft 将 HttpClient SOCKS 支持列为 .NET 6 新增能力，示例使用 `SocketsHttpHandler`。由此不能推定 net472/Unity 的现有 handler 接受 `socks5://` 并正确工作。[.NET 6 SOCKS 支持](https://devblogs.microsoft.com/dotnet/dotnet-6-networking-improvements/)

推荐策略：

1. **HTTP 代理**：优先用兼容的 HttpClientHandler/WebProxy 实例，经 CONNECT 获取 HTTPS 内容；验证无认证及用户名/密码认证。企业 NTLM/Kerberos 与 PAC 不作为首版跨平台保证。
2. **SOCKS5**：定义商店内部 DownloadTransport 边界，选用经维护与许可证审查、兼容 net472/Unity 的实现，再验证远端 DNS、认证、TLS/SNI、流式大文件和取消。尚未选定具体库，本评估没有已验证可用的库结论。
3. **传输库不可用时**：专门实现/维护 SOCKS5 隧道是技术上可行的备选，但不仅是 SOCKS 握手，还需正确集成 HTTP、TLS、重定向、连接池和流式读取，成本明显增加。优先复用成熟传输实现，避免自写完整 HTTP 栈。
4. **HTTP 本地入口作为兼容路径**：用户已有代理软件若提供 HTTP 或 mixed 端口，可通过该入口使用；这不等于已满足纯 SOCKS5 支持，不能把它作为取消 SOCKS5 要求的理由。
5. **HTTPS proxy**：目标站是 HTTPS 并不要求代理地址是 `https://`。若确需 TLS-to-proxy，作为单独的兼容性验证项，不能把 HTTP CONNECT 的成功外推为 HTTPS proxy 成功。

SOCKS5 是用户要求的一部分。首版发布门槛应包含其验证结果；若唯一 SOCKS5 入口不可用，应明确标为阻断项并重新评估，不用“设置框已提供”冒充功能支持。实际支持能力取决于传输适配器，不仅取决于 URI 格式。

### 7.3 DNS、重定向与诊断

- SOCKS5 远端 DNS 必须实际把目标域名交给代理；不能先在本地解析成 IP，再仅在 UI 显示“代理 DNS”。代理服务器自身域名的解析是另一个问题，可允许填 IP 避免本地 DNS 依赖。
- HTTP CONNECT 使用目标域名建立隧道，TLS 验证仍针对最终 HTTPS 主机；不能因为代理环境复杂就关闭证书校验。
- GitHub 资产下载 API 可能直接返回内容或返回 302；两种都要处理。重定向后的资产域名同样必须走所选代理。[GitHub Release assets API](https://docs.github.com/en/rest/releases/assets)
- 限制重定向次数（建议最多 5 次），禁止 HTTPS 降级到 HTTP；源策略明确允许下载主机，拒绝任意不可信跳转。允许的 CDN 主机需按实际请求验证，不凭空写死一个域名就声称覆盖全部 GitHub 下载。
- 跨主机不转发原站 Authorization；Proxy-Authorization 只能发送给代理。临时签名资产 URL 不长期缓存，查询参数不写完整日志。
- 显式代理不采用目标本地地址自动绕过、不静默回退直连。下载目标与重定向目标拒绝本地/私网等非预期端点；本地代理地址允许使用 loopback，两种地址不能混为一谈。
- 连接测试读取少量实际索引与测试资产内容，检查格式/哈希及重定向。测试只请求固定受信目标，不把任意 URL 输入变成通用网络探测器。
- 错误分类：代理连接失败、407/认证失败、SOCKS 协商失败、DNS 失败、TLS 失败、GitHub 限流、下载中断、校验失败。仅“连上代理端口”不能显示下载可用。
- 配置变化只影响新任务；运行中的任务固定网络策略，先取消或完成再切换。索引与包下载默认共用一份商店策略，避免依赖下载遗漏代理。

代理密码默认仅在当前进程保存，普通设置只存类型、主机、端口与用户名。如果以后提供“记住密码”，用平台凭据存储并明确支持范围；不假定 Windows DPAPI 在 Linux/macOS 可用。不保存到仓库、普通 JSON、安装锁文件或游戏存档。远程 HTTP/SOCKS5 的基础用户名/密码认证不保证客户端到代理链路加密，应在配置说明中准确表达其能力。

## 8. 下载、安装、持久化与恢复

### 8.1 GitHub 下载校验

- 只下载索引指定的编译产物，不拉源码 ZIP 后现场构建。
- 流式落盘和 SHA-256 校验；不能把整包读进内存。检查实际字节数，拒绝 HTML 错误页、大小异常与哈希不匹配。
- SHA-256 校验防止包内容偏离审核索引，但不证明插件代码安全；索引与资产同时被篡改时，仅靠同源哈希不能提供独立真实性保证。默认源仍需仓库权限、审核与发布保护；签名索引/离线信任密钥可在加强阶段引入。
- 默认源审核不等于沙箱：插件 DLL 最终以游戏进程权限执行。自定义源界面明确显示信任来源，不允许用同包名覆盖默认源既有归属。
- 解压前后阻断绝对路径、`..`、符号链接、跨平台路径碰撞、重复文件和压缩炸弹；XML 解析禁用外部实体/DTD。
- 建议初值：索引 2 MiB、单包下载 128 MiB、解压 512 MiB、最多 10,000 文件、最多 2 个并发下载；超限拒绝并显示原因。更大内容需要明确扩展策略。
- 校验 ZIP 内 About、package manifest、依赖与程序集归属；程序集元数据检查不执行插件入口。无法证明清单一致时拒绝安装，不静默丢文件。
- 中断首版允许整包重试；断点续传后续增加，必须验证资产身份、Range 行为与完整哈希，不能拼接不同资产版本。

### 8.2 推荐状态机

```text
Idle → Resolving → AwaitingPlanConfirmation
                 → Blocked
AwaitingPlanConfirmation → Downloading → Verifying → Staging → Committing
                                                               → InstalledPendingEnable
中间阶段 → Cancelled / Failed
提交开始后异常 → RecoveryRequired → RolledBack / InstalledPendingEnable
```

解析、网络、解压和提交均有取消/超时边界；进入文件提交后不能靠直接中止线程取消，需完成当前原子步骤再回滚。UI 观察状态，不能在 Draw 中推进安装或直接改磁盘状态。

建议连接超时 15 秒、索引请求 30 秒、下载停滞 30 秒、单包总下载上限 15 分钟、最多重试 2 次并退避。代理认证错误、清单错误、哈希失败和不兼容不作无脑自动重试。参数需在慢速网络实验后调整。

### 8.3 GitHub 本地包的暂存与提交边界

1. 获取安装目标锁并检查可写空间、包身份及目录不存在；首版只安装新包。
2. 在插件数据目录缓存下载；在目标文件系统、RimWorld 不扫描的位置准备 staging。staging 的非扫描性需实测，不能只靠目录名以点开头就假定隐藏。
3. 完整依赖闭包下载并校验成功后才提交；中途失败时不把剩余半包当作成功。
4. 写持久化事务日志，记录新目录、已提交步骤、包锁与内容摘要。逐包以同文件系统目录 rename 提交，在每一步之后记录进度。
5. 全部成功后持久化安装记录，显示“已安装，待在模组列表中启用”。不得自动改 `ModsConfig`、调用 Loader 或宣布已经 Active。
6. 可恢复失败时仅移除/退回本事务创建且归属、摘要仍匹配的目录。外部已经修改的文件不自动删除，进入 RecoveryRequired。

上述事务只覆盖商店管理的 GitHub 本地包。工坊订阅和 Steam 下载是外部操作，不属于该文件事务；混合依赖链不能承诺整体原子回滚，也不能因 GitHub 包失败就自动退订玩家的工坊模组。

**单个目录 rename 与整个依赖链事务不同**：跨多个模组目录不天然具备 ACID 原子性。崩溃可能留下部分已提交新目录，需根据持久化日志恢复。首版所有新包未启用，降低下一次启动的影响；不能保证玩家手动启用不完整包后仍安全。RimWorld 模组扫描早于商店插件恢复，商店不具备通用启动前恢复特权。

若未来需要替换已加载 DLL、自动升级完整依赖链或启动前恢复，则需另设退出后的安装器/启动前组件，或通用宿主阶段设计。不能假定商店在 Activate 时就能安全替换已经加载的包。Microsoft 说明 .NET Framework 无法只卸载单个程序集；RimWorld/Unity 的实际行为仍需在游戏验证。[程序集加载与卸载](https://learn.microsoft.com/en-us/dotnet/standard/assembly/load-unload)

### 8.4 持久化记录与生命周期

- 插件专属存储保存 sources、目录缓存、安装记录、版本锁及事务日志，schema 可迁移，损坏时提示并保留原文件。
- 版本锁记录源身份、快照 commit、精确包版本、依赖边、artifact 定位与哈希；安装记录附加 RimWorld packageId、模块 ID、目录及文件归属。
- 写入临时文件、刷盘、替换和备份策略由商店负责，StorageProvider 不自动提供这些语义。
- 商店禁用后已安装模组仍由 RimWorld/Phinix 正常加载；商店不是其他插件运行的必需依赖。
- 卸载商店不自动卸载其下载的模组。后续卸载功能也只管理代码与安装文件，不删除其他插件数据、存档、待交付记录或库存。
- 文件回滚不等于业务数据/存档回滚。升级、降级、禁用业务插件可能造成 codec 缺失或恢复能力变化，尤其涉及库存和交易时不能把“文件操作成功”当作物品安全证明。
- 首版不改变 Legacy/V2 协议、交易确认、持久化迁移或物品所有权。服务器需要配套插件时只显示部署条件，客户端商店不冒充服务器能力确认。

## 9. 功能与交互设计

建议有三个页面：

1. **浏览**：搜索、兼容筛选、名称/作者/版本/渠道、审核范围；详情包含依赖、运行环境、许可证、项目与服务端要求。工坊按钮是“打开工坊”，GitHub 按钮是“下载并安装”，不能给工坊跳转显示下载已完成。
2. **本地与任务**：已安装/未启用/版本未知、下载与校验进度、失败原因、重试/取消、待重启提示；运行状态通过通用查询契约或明确标记未知。
3. **源与网络**：默认/自定义源、恢复默认、直连/系统/HTTP/SOCKS5、认证、DNS、分阶段连接测试、缓存清理。密码输入不回显。

GitHub 链交互：点击安装 → 查看完整计划 → 一次确认必需包 → 下载/校验/安装 → 列出应启用模组及顺序 → 玩家启用并重启。混合链额外列出工坊步骤，实际下载安装并核对之前保持等待状态。不静默升级已有包；官方索引自动收录新版本与玩家本地升级是两个功能。

依赖图示例：

```text
Example Notes 1.2.0          新安装
└─ Example Storage 2.1.0     新安装
   └─ Phinix Rework          环境前置，已满足

需启用：Example Storage → Example Notes
服务器要求：无
```

窄屏详情降级为单栏/子页；列表虚拟滚动，长名称与译文可截断配 Tooltip。使用现有响应式几何、主题和屏幕安全区工具，缓存布局及翻译，异常路径恢复 GUI 全局状态。任务进度不能占用每帧大量分配或阻塞主线程。

## 11. 成本和风险评估

以下是单名熟悉代码的开发者的粗略工程估算，不是排期承诺；范围为标准包首版，包含验证和文档，不包含新服务器功能：

| 工作 | 估算工作日 | 不确定性 |
| --- | --- | --- |
| 运行时/目录/代理验证 | 3–5 | 缺少游戏运行环境无法关闭风险 |
| 索引规范、审核校验与源缓存 | 3–5 | 实际默认仓库与维护流程尚未确定 |
| 包版本与依赖解析 | 4–7 | 多版本约束、外部包未知身份 |
| 下载、校验、安装记录与恢复 | 5–8 | 跨平台路径与崩溃一致性 |
| UI、设置与错误反馈 | 3–5 | 离线入口、多语言与小屏 |
| 回归及游戏内验收 | 3–5 | 代理认证、CDN、不同操作系统 |

上述 **21–35 个工作日** 是前一版标准 GitHub 包客户端的基线估算，前提是找到可用 SOCKS5 实现；不包含本轮新增的索引 bot/自动更新流水线。双渠道跳转和 DLL 壳也会增加工作，补充估算见后续文档；不能把旧合计作为全部新范围报价。HTTP 与 SOCKS5 的设置 UI 工作量很小，运行时兼容性才是代理成本主体。

主要风险排序：

1. **SOCKS5/HTTPS proxy 在 Unity/Mono 下兼容性**：必须在真实游戏验证，服务端 .NET 10 测试不能替代。
2. **索引完整性与作者发行规范**：依赖自动化质量取决于准确清单，错误元数据不能靠下载器弥补。
3. **共享 Contracts 与同名程序集冲突**：没有通用并行多版本隔离，禁止“各带一份依赖 DLL”式发布。
4. **文件提交与启动顺序**：首版新增且未启用包可控，覆盖已加载包显著扩大恢复难度。
5. **特殊网络中的不同 GitHub 域名、DNS和共享出口限流**：必须逐段诊断，不只提供代理地址输入框。
6. **升级/卸载的存档和物品恢复影响**：商店不能自行认定插件持久化数据可删除；列为后续管理功能的硬边界。
