## 1. 评估范围与结论

重点是 RimWorld 客户端。服务端目前使用量较小，不作为本轮重构的主要驱动力。允许较大重构，把一次性迁移代码量放到次要位置，优先考虑长期可维护性、扩展性、可靠性和后续开发难度。

这里把两种成本分开：一次性改代码的成本可以接受；未来持续承担的运行机制复杂度、依赖升级、程序集冲突、原生组件分发和调试成本，仍然需要认真比较。功能更多并不自动意味着工程上更好。

**总体建议：值得重构客户端的依赖装配、生命周期和可靠业务操作基础设施，并选择性采用成熟库；保留现有宿主与插件的分层方向。** 不建议用一个大型应用框架覆盖整个客户端。

| 决策领域 | 当前倾向 | 主要价值 | 优先级 |
| --- | --- | --- | --- |
| 依赖装配与对象生命周期 | 引入标准 DI 容器；深入重构插件作用域时倾向 Autofac，否则 Microsoft.Extensions.DependencyInjection 足够 | 显式依赖、统一对象归属、降低初始化与释放难度 | 高 |
| 回归测试组织 | NUnit；保留可执行入口时使用 NUnitLite | 独立报告、筛选、参数化、便于新增故障场景 | 高 |
| 交易与红包操作状态 | 选择性使用 Stateless | 集中表达合法状态转移，便于验证确认与恢复行为 | 高，随业务可靠性重构推进 |
| 库存账本与操作记录 | 长期倾向 SQLite，先验证客户端 provider 与分发 | 事务、约束、增量更新，减少自建存储引擎维护 | 后置；先恢复设计与环境/收益验证 |
| HTTP 与瞬时故障策略 | HttpClient；适合重试的调用采用 Polly | 统一取消、超时、退避与故障模拟 | 中高 |
| JSON | 新格式倾向 Json.NET；System.Text.Json 为备选 | 统一格式处理与扩展方式 | 中 |
| 日志 | 内部采用 Microsoft.Extensions.Logging，适配现有接口和 Verse | 统一分类、上下文、异常信息 | 中 |
| 程序集元数据读取 | 按需求采用 System.Reflection.Metadata / PEReader | 减少格式解析代码，避免为检查而加载程序集 | 局部采用 |
| 队列、插件发现、网络流水线、主线程调度 | 保留领域规则；仅替换确有收益的底层机制 | 避免引入第二套执行模型 | 按问题决定 |

这是基于当前代码职责和官方资料的工程判断。没有候选库集成实验、性能基准或 RimWorld 内运行验证；“推荐”表示值得推进选型，不表示可以直接安装最新版并发布。

相关背景：[设计哲学](/home/hunyuan2333/Phinix/Phinix-Rework/docs/Design-Philosophy.md)、[兼容与恢复边界](/home/hunyuan2333/Phinix/Phinix-Rework/docs/Compatibility-Boundaries.md)、[此前客户端持久化评估](/home/hunyuan2333/Phinix/Phinix-Rework/docs/branch-local/dev/客户端持久化与SQLite评估.md)。此前持久化评估偏重迁移成本；本文在允许较大重构的前提下，更重视长期存储维护责任，因此对 SQLite 更积极。2026-10-05 统一执行优先级：SQLite 保留为长期候选，恢复链、实际容量/提交成本与原生部署验证先行；态度变化不是新的性能证据。

## 3. 无论选什么库，都必须保留的边界

1. 官方插件与第三方插件使用同一条发现、注册、激活、关闭路径；宿主保持业务中立。
2. Legacy/V2 差异保留在协议 adapter 中，不能由 UI 或通用 DI 容器决定业务成功标准。
3. 网络发送尝试、普通快照和权威操作确认分别处理。结果未知不能直接自动返还物品。
4. 物品转换与交付保持整批语义，不能通过跳过失败项来完成操作。
5. 业务先准备变更，再持久提交，再发布结果；网络和游戏物品副作用需要可恢复记录协调。
6. 游戏 API、翻译与 UI 工作仍按现有主线程边界执行。Task、状态机或容器都不能自动提供这个保证。
7. 生命周期结束必须阻止过期回调访问旧存档对象；释放容器并不等于远端业务操作已经取消。

库应该替代通用机制，实现这些边界的业务服务与协调器仍需自己维护。

## 4. DI 容器：Microsoft.Extensions.DependencyInjection 与 Autofac

### 4.1 候选比较

| 方案 | 优点 | 缺点与长期成本 | 适用条件 |
| --- | --- | --- | --- |
| 保留手工构造，改成明确的集中装配入口 | 无额外依赖；创建顺序容易直接跟踪；小规模对象图足够清楚 | 扩展后要自己维护工厂、对象归属和清理；容易再次出现服务定位与重复初始化约定 | 若刻意把服务数量和生命周期种类控制得很小 |
| Microsoft.Extensions.DependencyInjection | 常见的注册与构造函数注入模式；生命周期种类少，开发者容易掌握；可统一容器创建对象的释放 | 普通作用域不构成有继承关系的子容器；插件局部注册与特殊归属需要额外设计；程序集依赖仍需管理 | 启动时完成注册，运行时主要按固定服务图创建作用域 |
| Autofac | 支持子作用域局部注册、标记作用域及较灵活的对象归属；适合插件内部服务装配 | 需要理解作用域可见性、实例共享与释放规则；使用太多命名服务、自动扫描或生命周期技巧会增加调试难度 | 确实需要插件局部对象图，并愿意明确规定生命周期模型 |

Microsoft 官方把内置容器定位为多数应用的默认选择，同时将子容器和自定义生命周期列为考虑替代容器的理由。Autofac 允许创建作用域时补充局部注册。这些能力是比较依据，Phinix 是否采用则属于本项目的工程判断。[微软 DI 指南](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines)、[Autofac 作用域文档](https://docs.autofac.org/en/latest/lifetime/working-with-scopes.html)。

### 4.2 本项目的倾向与约束

**若这次会重构插件内部生命周期，优先验证 Autofac；若选择固定注册图和普通作用域，优先 Microsoft DI。只选一个主容器。** Autofac 的理由是插件局部注册与对象归属需求，不是它支持更多功能。

实施时应达到以下结果，否则安装 DI 包本身没有多少收益：

- 普通业务服务通过构造函数声明依赖，服务定位集中在装配入口与兼容桥梁。
- 拆开插件装配、连接协调、业务操作和 UI 生命周期，不能把所有字段简单改成构造参数就宣布完成。
- 为宿主常驻、插件实例、连接会话、存档上下文分别定义寿命。连接与存档可能独立变化，不应粗暴套成一棵嵌套树。
- 容器管理自己创建的对象；游戏提供的对象、外部共享实例和跨插件 API 的归属必须另行明确。
- 跨插件 API 保留可见性与所有者规则。Autofac 的兄弟作用域不会自然互相看到局部注册，不应为方便访问而把所有业务实例提升为宿主单例。
- 订阅和后台任务由可释放组件封装；Lifecycle 协调器负责取消、阻止旧回调并按正确线程关闭作用域。
- 被禁用插件仍不能提前实例化；构造、注册、激活失败必须隔离，并撤销其公开能力。
- 容器实现尽量留在装配层；第三方插件契约仅提供必要的注册能力，避免重造一个完整容器 API，也避免让所有插件被迫采用容器特有高级类型。

Autofac 不会自动释放手动创建的子作用域，创建方仍需显式释放。容器释放也不会自动取消普通 C# 事件订阅或卸载程序集。[Autofac 释放规则](https://docs.autofac.org/en/latest/lifetime/disposal.html)。

性能判断：依赖主要在启动或生命周期切换时解析，并保存在业务对象中。禁止为每帧渲染、每条物品预览频繁 Resolve。引入容器的主要理由是工程质量，本轮没有证据证明其会改善运行性能。

## 5. 状态管理：手写转移表、Stateless 与工作流框架

| 方案 | 优点 | 缺点与长期成本 | 本项目选择 |
| --- | --- | --- | --- |
| 显式 enum + 纯转移函数/转移表 | 依赖最少；状态规则与持久化边界可直接表达；简单流程易读 | 状态与事件组合扩大后，需要自己维护合法性检查、规则展示和测试组织 | 简单操作继续使用，是合理基线 |
| Stateless | 集中配置转移、guard、层级状态；支持外部状态访问和规则检查，方便理解复杂操作 | 有额外概念；不是持久工作流引擎；把大量副作用塞入 entry/exit 回调后仍会难以维护 | 优先在单笔红包发送、待确认交易、交付恢复等复杂操作中试用 |
| 大型持久工作流框架 | 对长流程的调度、恢复和管理提供更多现成功能 | 需要额外持久化、执行宿主和框架生命周期；与游戏主线程及存档回档仍需整合 | 当前不推荐；现有需求不足以抵消持续复杂度 |

Stateless 提供外部状态存储访问方式，但库本身不负责事务和持久恢复。[Stateless 官方项目](https://github.com/dotnet-state-machine/stateless)。

建议的组织方式是“当前状态 + 事件 → 候选新状态与待执行动作”，由应用服务完成持久提交，随后执行副作用。重启后的状态由存储恢复，重复确认按稳定操作 ID 去重。同一笔操作的事件处理需要串行协调，库不会自动解决多个回调同时修改状态的问题。不建立覆盖全部客户端的巨大状态机。

采用条件：业务状态正在跨多个回调修改，合法转移难以审查，且明确存在重试、结果未知、重启恢复分支。若某个流程只有几个直线步骤，手写纯函数可能更容易维护。

性能判断：状态转移通常低频。主要收益是减少错误与提高审查能力，不应把 Stateless 作为帧率优化方案。

## 6. HTTP 与故障策略：BCL、HttpClientFactory、Polly

| 方案 | 优点 | 缺点与长期成本 | 本项目选择 |
| --- | --- | --- | --- |
| HttpClient + 少量显式策略 | BCL 接口清晰；可注入 HttpMessageHandler；少量端点容易管理 | 请求取消、handler 寿命、退避和异常分类仍需自行规范 | 推荐作为基础，统一替代剩余 HttpWebRequest 路径 |
| IHttpClientFactory / Microsoft.Extensions.Http | 集中管理 handler 寿命与不同客户端配置；便于与 DI 配合 | 增加依赖及配置概念；必须验证 Mono 上的真实行为 | 客户端种类和配置增长时采用；不要求同时引入 Generic Host |
| Polly / Polly.Core | 通用超时、重试、退避等策略可组合并集中测试 | 配错重试对象会放大请求或产生重复副作用；仍需定义故障语义与业务恢复 | 推荐用于目录读取、查询、轮询等适合重试的调用 |
| 全套应用宿主与后台服务模型 | 生命周期与后台任务组织更统一 | 游戏已经提供宿主生命周期；额外执行模型仍要桥接，不能自动解决存档切换 | 当前不推荐作为客户端底座 |

微软指南区分不同 .NET 环境下的 HttpClient 生命周期管理；现代 .NET 的 SocketsHttpHandler 配置不能原样视为 net472/Mono 方案。Polly 的策略只解决调用执行问题。[HttpClient 指南](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines)、[Polly 一般规则](https://www.pollydocs.org/general.html)、[Polly 重试策略](https://www.pollydocs.org/strategies/retry.html)。

业务边界：

- 查询、下载和可恢复轮询可使用自动退避；本地取消、协议校验失败等不能一律当作瞬时故障重试。
- 发布、扣除或交付需要稳定操作 ID 与明确的远端去重保证；不能因超时认定未执行。
- 重试策略与总超时的套用顺序必须固定，区分单次尝试超时和整个操作预算。
- 断线、退出和换档要结束后台工作；已经执行的远端操作仍需状态核对。
- UI 结果在主线程交付，旧会话结果不能应用到新存档。
- 不对已有 LiteNetLib 消息流水线再套 HTTP 中间件模型。

## 7. 持久化：文件、SQLite 与 LiteDB

### 7.1 存储引擎比较

| 方案 | 优点 | 缺点与长期成本 | 本项目选择 |
| --- | --- | --- | --- |
| 保留并完善当前文件快照/日志 | 部署简单；没有新增原生库；现有存档关联与恢复语义延续 | 自己维护日志增长、截断、压缩、恢复和结构演进；多个状态一同提交需要额外机制 | 合理的过渡方案；小型配置与简单缓存仍适合文件 |
| SQLite | 事务、唯一约束、索引和增量更新适合账本与操作记录；可用通用工具检查数据 | schema 迁移、连接/写入归属、锁和备份仍需设计；常见 provider 涉及原生组件分发 | 若重构库存及可靠操作，长期首选候选 |
| LiteDB | 托管 .NET 文档数据库；可减少原生组件分发压力；文档模型便于存放对象记录 | 引入文档数据库自身的映射、查询和恢复规则；关系型约束与查询组织需要按另一套模型设计 | 原生 SQLite 部署验证不顺利时的备选，不因“纯 C#”自动认定更可靠 |

SQLite 提供数据库内部的事务保证；LiteDB 官方将其定位为托管 .NET 嵌入式文档数据库。表中的项目适配判断并非官方排名。[SQLite 事务说明](https://sqlite.org/transactional.html)、[LiteDB 官方概览](https://www.litedb.org/docs/)。

对本项目，优先采用 SQLite 的理由是减少长期自建存储引擎责任，并让库存状态、预留、操作记录的内部提交更明确。不是因为已经证实当前 SQLite 读写比文件更快。

### 7.2 SQLite 数据访问层比较

| 方案 | 优点 | 缺点 | 倾向 |
| --- | --- | --- | --- |
| Microsoft.Data.Sqlite + 显式 SQL/repository | 轻量 provider，可独立使用；事务与读写语句直接可见 | 参数绑定、记录映射、schema 迁移要自己维护 | 表与查询数量有限时优先 |
| Microsoft.Data.Sqlite + Dapper | 减少重复的行到 DTO 映射；仍保留显式 SQL | 不提供数据库迁移或完整业务事务模型；仍要维护 SQL 与字段对应 | 映射代码明显重复后再加入 |
| 大型 ORM | 对大量实体、查询组合与映射提供更多自动化 | 引入跟踪、映射及版本依赖；关键提交边界仍需自己控制；需额外核对客户端目标框架 | 当前不作为客户端默认方案 |

Microsoft.Data.Sqlite 可以脱离 EF Core 独立使用，Dapper 提供对象映射；二者不要求构建完整应用框架。[provider 官方说明](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/)、[Dapper 官方项目](https://github.com/DapperLib/Dapper)。

provider 版本、SQLitePCLRaw bundle、原生库加载方式尚未选定。常规 NuGet restore 成功不代表游戏 mod 打包后可以加载；需要验证实际支持的平台和架构。[SQLite 原生库与 bundle 配置](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/custom-versions)。

### 7.3 仍需自己的可靠性设计

- SQLite 事务不能同时覆盖远端服务、地图物品与 RimWorld 存档。需要稳定操作 ID、可恢复待办记录、确认关联和结果未知处理。
- 外部账本比游戏存档新时，必须保留存档身份与回档判断；不能根据“数据库记录完整”直接重放所有操作。
- 不把当前全量 JSON 日志原封不动搬成一个大字段并认为存储重构完成。适合独立更新的条目、预留与操作记录应有明确结构；opaque 物品载荷可以继续作为受限 blob 保存。
- 游戏存档仍可保留必要的身份与版本锚点，数据库提供账本与操作记录，两者的权威关系要先定义。
- 旧数据导入采用可核对、可重复执行且保留原文件的流程；迁移成功后不能继续双写两套独立权威账本。
- 确定持久化配置、备份、检查点和磁盘失败行为。若使用 WAL，备份过程必须正确处理附属文件。
- Microsoft.Data.Sqlite 的异步 ADO.NET 方法实际同步执行；不能仅将方法换成 Async 就认为主线程不再受阻。[异步限制](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async)。

## 8. JSON：Json.NET、System.Text.Json 与现有 BCL

| 方案 | 优点 | 缺点与兼容风险 | 本项目选择 |
| --- | --- | --- | --- |
| DataContractJsonSerializer 等现有 BCL | 无新运行库；旧格式已围绕其行为建立；简单 DTO 足够使用 | 动态结构与特殊格式扩展不够统一；商店 JSON 经 XML 模型读取增加理解步骤 | 保留旧格式编码器；不要求为了统一立即移除 |
| Json.NET | DTO、DOM、converter 工具成熟；可处理 DataContract/DataMember；客户端新格式容易统一 | 默认行为可能接受协议不允许的输入；日期、byte[] 等表示不等于旧 BCL 格式；需管理程序集共存 | net472 客户端新 JSON 处理的优先候选 |
| System.Text.Json | UTF-8 API、较少分配的设计；现代 .NET 生态一致；严格模式适合新协议 | 不直接支持 DataContract 属性；在旧工具链上需核对依赖；source generator 另有构建约束 | 新 DTO 与 UTF-8 处理需求较强时的备选 |

Json.NET 支持 DataContract 的 opt-in 行为，byte[] 默认是 Base64；System.Text.Json 官方明确区分其性能取向、可用框架和不支持的序列化属性。二者不是旧格式的无损替换。[Json.NET 序列化指南](https://www.newtonsoft.com/json/help/html/SerializationGuide.htm)、[System.Text.Json 概览](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/overview)。

选择时先固定协议与存储的实际数据表示，再选择 serializer。对旧日期、空值、枚举、字典和 byte[] 建立真实样本；格式变更通过版本化处理。JSON 库不接管大小、深度、重复字段处理或包身份规则。尤其不能因换 Json.NET 而放宽商店当前要求的严格 JSON 输入。

不启用来自不可信输入的任意类型实例化，也不直接序列化活跃的 Thing 对象图来替代已有物品 codec。跨端表示由契约决定，而非客户端和服务端各自的默认设置决定。

没有实际样本基准前，不宣称 System.Text.Json 一定能改善当前游戏卡顿。全量克隆、重复物化和同步刷盘可能比 serializer 选择更重要。

## 9. 测试：NUnitLite、标准 test runner、xUnit 与当前 harness

| 方案 | 优点 | 缺点与长期成本 | 本项目选择 |
| --- | --- | --- | --- |
| 现有控制台 harness | 极少依赖；可精确控制入口与运行环境；已有场景可直接执行 | 筛选、独立失败报告、参数化和测试发现要自己维护 | 特殊游戏依赖启动路径可以暂时保留 |
| NUnit + NUnitLite | 标准测试模型，同时保留可执行程序入口；适合现有 console harness 演进 | 仍要处理测试隔离、静态状态和特殊依赖加载 | 当前最顺手的优先候选 |
| NUnit + Test SDK/adapter | 标准 IDE/CI 集成、独立发现和结果输出 | 要适配现有可执行程序及游戏依赖运行路径 | game-independent net10 测试项目适合采用 |
| xUnit | 常见测试模型、fixture 与数据驱动测试；适合拆分独立场景 | 既有 harness 的组织需重新适配；没有明确收益要求全仓统一换用它 | 合理备选，但优先级不高于 NUnit |

NUnitLite 官方提供可执行入口运行方式；xUnit 当前也提供自己的项目与运行器组合，因此不能简单把二者概括为“只有 NUnit 能做控制台测试”。这里倾向 NUnitLite 是基于当前项目形态和演进方式。[NUnitLite 文档](https://docs.nunit.org/articles/nunit/running-tests/NUnitLite-Runner.html)、[xUnit 入门](https://xunit.net/docs/getting-started/v3/getting-started)。

游戏独立测试目标与 mod 的 net472 目标分开决定。现有 net472 游戏依赖测试在 .NET 10 中运行的特殊方式，要单独验证，不能承诺直接换 adapter 即可。

最有价值的测试内容是：重复/过期确认、未发送与结果未知、关闭窗口后确认、存档切换后的旧回调、持久提交失败、进程在副作用前后中断、重复恢复不复制物品、插件激活失败与资源清理。标准 runner 不替代这些场景。

测试库只进入测试工程，不随客户端 mod 分发。默认测试并发不能导致共享静态状态或游戏环境测试互相干扰；应显式规定隔离方式。

## 10. 日志：现有接口、Microsoft.Extensions.Logging 与 Serilog

| 方案 | 优点 | 缺点与长期成本 | 本项目选择 |
| --- | --- | --- | --- |
| 现有 IExtensionLogger / 回调 | 插件边界稳定；便于接入 Verse 与现有管理界面；已经有结构化记录入口 | 自己维护日志约定和各类适配；业务若过早拼接字符串会丢失上下文 | 可保留为公开兼容接口 |
| Microsoft.Extensions.Logging | 常见 ILogger 模型；类别、级别、模板和 provider 组织一致 | 需要 Verse/现有日志缓存适配；公开暴露其类型会增加第三方依赖约束 | 推荐内部标准化，逐步适配现有接口 |
| Serilog | 结构化事件与丰富输出目标；适合独立文件或集中诊断 | 额外配置、输出组件和文件生命周期；必须处理日志量与游戏关闭 | 有明确文件诊断或多输出需求时加入，当前无需默认采用 |

Microsoft.Extensions.Logging 提供日志抽象和 provider 机制，Serilog 偏重结构化事件与输出生态。[微软日志说明](https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/overview)、[Serilog 官方介绍](https://serilog.net/)。

关键改善是统一 extensionId、operationId、saveId、sessionId 与异常信息，让恢复过程可追踪。日志不能替代持久操作记录，不应记录凭据或完整物品载荷。后台日志到 UI 缓存的转交仍要保持线程边界。

## 11. 其他通用机制是否替换

| 当前职责 | 候选替代 | 可能收益 | 为什么不是无条件采用 |
| --- | --- | --- | --- |
| 主线程派发、后台结果队列 | System.Threading.Channels + 现有主线程消费边界 | 明确有界容量、等待和关闭，减少后台队列协调代码 | Channel 不会自动在 Unity 主线程执行，也不会持久保存关键业务结果；业务结果和可丢弃 UI 刷新必须分开 |
| 程序集 PE/元数据读取 | System.Reflection.Metadata / PEReader | 使用标准解析工具，在不执行程序集的情况下读取元数据 | 当前手写 PE 检查范围有限；仍需保留内容限额和包政策，依赖净收益要看新增检查需求 |
| 简单版本与范围判断 | NuGet.Versioning | 支持成熟的版本/范围解析语义 | 当前商店有意采用受限规则；更完整语义可能扩大协议，额外验证后未必减少代码 |
| 边界与业务校验 | FluentValidation 一类规则库 | 大量重复 DTO 校验时可集中表达错误 | 当前安全边界常涉及大小、路径、codec 和所有权，不能全部交给通用表单校验；先看重复量与目标版本支持 |
| 简单 C# 事件与订阅 | 明确订阅对象或资源集合；有需求再评估 Rx | 统一释放订阅；复杂事件组合可能更方便 | 全面 Rx 化引入调度与错误传播模型，不能自动解决旧会话回调与持久恢复 |

Channels 提供不同有界队列满载策略；选择 Wait/拒绝写入或丢弃哪一项本身是业务决定，不能对关键确认默认 DropOldest。[Channels 文档](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels)。PEReader 的职责是读取 PE 格式，不是授权插件或证明程序集安全。[PEReader API](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.portableexecutable.pereader?view=net-10.0)。

以上均是局部选型候选，没有确定包版本。特别是 NuGet.Versioning 与 FluentValidation，本轮不建议立即引入，也没有进行适配实验。

## 12. 当前不建议作为总体架构底座的方案

| 方案 | 可以提供什么 | 本项目不采用的主要理由 |
| --- | --- | --- |
| MEF | 部件发现、导入导出与组合 | Phinix 仍需要禁用前不实例化、依赖顺序、能力注册、失败隔离与撤销；再维护一套 composition 不一定减轻总责任 |
| MediatR / 全面 CQRS 中介 | 进程内请求分发与处理行为 | 当前已有明确网络流水线和插件 API；强制所有业务绕行中介会增加追踪路径，缺少足够的公共职责可交出去 |
| Generic Host / 全套后台服务 | 应用宿主与后台生命周期组织 | RimWorld 已控制应用和主线程；需要保留自己的存档与连接生命周期，默认采用不解决核心边界 |

| 全面 Rx 化或换 UI 框架 | 响应式事件与另一套 UI 开发方式 | 现有 UI 与 Verse/IMGUI 结合；没有证据表明换模型能减少总复杂度 |

MEF 确实提供 composition 能力；不推荐它是项目职责匹配判断，不是认为它无法构建插件系统。[MEF 官方说明](https://learn.microsoft.com/en-us/dotnet/standard/mef/)。

若未来某个独立子系统出现上述框架明确擅长的问题，可以重新评估；本轮不为潜在功能提前引入。

## 14. 建议推进方式与验收标准

### 阶段一：标准测试体系与依赖/生命周期试点

先选择一个依赖相对简单的插件，验证容器的对象创建、关闭和异常隔离，再用 Trade 验证复杂对象图。保留现有公开能力与插件政策。标准测试组织与重构相配合，不要求先搬完全部测试才能开始。

验收：禁用不实例化；缺失依赖和激活失败不会污染 registry；重复进入/退出不会重复订阅；切换存档后旧回调失效；第三方样例插件不需要引用宿主实现。普通业务测试无需构造整个游戏客户端即可运行。

### 阶段二：一条可靠业务操作链

选择库存报价或红包库存发送，先定义状态与确认语义，在现有存储上验证 Stateless；SQLite 后续单独评估，不把状态机试点绑定到数据库替换。目标是从 UI 迁出待确认操作，并获得可恢复的操作记录，不是只搬 enum 或改文件扩展名。

验收：明确失败可恢复；结果未知继续托管；重复确认不重复提交；持久提交失败不发布成功；副作用前后中断可恢复；回档和换档不串账；整批转换失败不部分交付。

SQLite 环境试验可以提前并行开展，以免完成业务迁移后才发现原生加载问题，但不在通过试验前把它定为唯一发布方案。

### 阶段三：统一 HTTP、诊断和格式工具

将旧请求路径迁入统一 HttpClient，按操作类型配置 Polly；接入日志适配；新格式采用统一 JSON 工具，旧格式保留兼容读取。需要增加程序集检查时，再决定是否引入 Metadata 库。

验收：取消与超时不留下旧会话回调；不同失败类型可诊断；非幂等操作没有无条件重试；历史数据样本仍可读取；依赖未重复或漏打包。

### 性能验收

本轮没有性能瓶颈实测。未来比较真实场景的耗时与分配：库存条目增长后的预览刷新、账本提交与启动恢复、慢磁盘、断网后恢复及多次加载存档。容器不进入逐帧解析路径；不把数据库方法名带 Async 视为已经避免主线程阻塞的证据。

如果主要耗时来自全量克隆、重复物化或同步刷盘，优先修改数据访问与提交方式；不把换 serializer、DI 或 native DLL 当作默认性能答案。

## 17. 采用门槛与决策收口（2026-10-05）

候选库分别决策，不因为试点通过就一次安装整套组合：

| 候选 | 通过后允许推进 | 不通过时保留什么 |
| --- | --- | --- |
| DI | Chat 生命周期与旧插件桥梁通过真实 Mono、失败回滚、分发验证后，再推广到依赖链 | 先保留独立的构造/启动整理与手工装配；不让容器失败阻塞三仓 |
| NUnit/NUnitLite | 原有场景能逐项映射、失败退出码正确，才逐批切换入口 | 现有 harness 与断言继续使用，不删除难迁移场景 |
| HttpClient/Polly | 单一重试负责人、总取消/限额和结果未知规则通过特征测试后接入 Relay | 原 transport 经明确生命周期停止后可回退；不双发同一操作 |
| Stateless | 候选状态先持久提交，旧记录与副作用中断测试通过后替换单笔规则 | 现有规则与同一权威记录；不改变状态序列化值或自动退款 |
| SQLite | provider/原生部署、增量模型、旧数据迁移与回档演练有证据后单独批准采用 | 当前文件存储与已完成的恢复改进，不默认为全局账户账本 |
| JSON、日志、局部工具 | 有明确问题和格式/依赖共存样本，再做小范围适配 | 现有编码器与公开接口，避免随 DI 一起改变所有格式 |

首版 SQLite 试点沿用游戏存档中的完整快照与现有权威关系；以后若只保留身份/版本锚点，需要另行设计跨机器迁移、旧档恢复与缺失外部数据库时的行为，不能在选型时顺带缩减恢复资料。

每个正式采用记录至少列出：确切版本、目标资产、传递依赖/许可证、分发与释放负责人、真实运行验证、收益和回退条件。服务端无需为了客户端试点采用同一容器或版本；共享接口保持中立。

先完成生命周期与消费者试点，再冻结共享接口并物理拆仓；全面 DI、HTTP、状态机按具体业务收益推进。NUnit 全量迁移不成为其他工作的硬门槛，现有覆盖可以作为启动基线。GitHub Actions 范围继续仅为服务端 Docker Hub 发布，客户端与新增基础设施验收作为手动开发/发布检查。
