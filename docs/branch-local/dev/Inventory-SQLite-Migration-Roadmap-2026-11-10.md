# 库存 SQLite 与跨存档共享迁移 Roadmap

日期：2026-11-10。状态：方案已制定，下面实施项均未完成。

## 1. 用户决定与实施基线

- 直接在 dev 准备数据结构升级，不维持新旧客户端同时运行或双写两套库存。
- 库存脱离 RimWorld 存档，以本地 SQLite 为唯一权威，同一本地库存配置内所有存档共用。
- 进入旧存档时检查历史库存，通过迁移接口导入 SQLite；数据库提交成功后清理旧存档库存。
- 保留历史格式读取和迁移入口；新业务仅使用当前库存模型。
- 客户端业务基线 075c929，含 99bcef8 的 P6 配套改造及后续 Legacy/库存修复；Server main/dev 为 207f17d。Relay 独立保留，不作为本方案依赖。
- 本方案是本地库存升级，不把库存余额迁到服务端，不改变交易成功回执的权威性。

默认共享范围为同一本地客户端库存数据配置，不因 Game、存档路径、另存为、服务器连接或登录账号变化重新创建余额。服务器、主体、交易和来源信息继续保存在记录中；凭据及网络请求权限不会因此跨账号共用。复制安装目录或同步数据库不属于跨机器同步方案。

## 2. 权威与边界

SQLite 保存条目、不透明 payload、存入幂等回执、预留、待核对操作、迁移回执和全局 revision。存档不再输出余额镜像；内存 ledger 只是已提交数据的投影，提交失败不能发布成功或推进投影。

GameComponent 保留历史读取和升级标记职责，停止作为库存权威。读旧档不能回滚数据库、再次导入同一资产或覆盖新余额。没有旧库存的新游戏直接使用共享数据库。

跨存档共享的是库存数据，不是地图对象或正在执行的交付动作。提取、物化、存入、批次和定时动作仍绑定发起 Game/地图/模块代数；切游戏取消未执行工作，已执行但未证明结果的动作留待核对，不能转投新地图。UI 与 Host 继续通过普通插件合同消费状态，不加入库存专用 Host 分支。

## 3. 分层和预留迁移接口

| 所有者 | 计划职责 |
| --- | --- |
| InventoryStorage（Inventory 自有内部模块） | SQLite 连接、事务、schema 升级、唯一约束、备份与数据库健康状态 |
| Inventory 领域服务 | 数量、预留、幂等、交易结果应用；维护唯一权威及状态转换 |
| LegacyInventoryMigration | 历史存档/journal 解析、来源识别、映射、导入和清理凭据 |
| GameAdapter / GameComponent | 主线程读取旧数据、发布升级标记、绑定当前游戏及正常保存清理 |
| Trade / RedPacket 等消费者 | 使用当前库存 API；保留各业务的结果核对与来源凭据 |

预留内部端口（名称为设计草案，实施时随现有工程收敛）：

- `ILegacyInventoryReader.Read`：返回不可变的版本、SaveId、原序号、原始快照、指纹和关联旧文件证据，禁止隐式改写。
- `IInventoryMigrationService.Inspect/Import/GetReceipt`：规划导入、原子执行和查询既有回执；能表达 AlreadyImported、Imported、NeedsReview、Failed。
- `IInventoryMigrationSource`：历史格式适配入口；先支持现有 Scribe JSON 与 legacy journal，后续新增来源复用同一导入契约。
- `IInventoryStore.Execute`：单次库存命令及其幂等记录在同一事务提交，返回持久结果。
- `ILegacyInventoryCleanup`：只接收当前来源对应的已提交迁移凭据，不能自行决定清空库存。

SQLite provider 和连接类型不进入公共插件合同。公共 API 若需演进，统一迁移维护消费者，不保留旧余额写入通道。Trade 的历史 SaveIdentity/JournalIdentity 绑定需要显式映射到新 StoreId/来源证据，不能直接把旧字段改名或随便授权旧回调。

## 4. 数据结构与事务

| 表/记录 | 内容与约束 |
| --- | --- |
| store_meta / schema_migrations | StoreId、schemaVersion、全局 revision、升级记录 |
| entries / payloads | 稳定条目 ID、codec/version、数量、完整 payload 和 hash、来源；不解码重建资产 |
| deposit_receipts | 原业务幂等标识、主体/endpoint 命名空间、请求 hash 和原 hash 版本；同标识冲突拒绝 |
| reservations / reservation_lines | 稳定 owner/operation/reservation ID、数量、状态、证据及终态；活跃预留持续锁定 |
| pending_transfers | 物理转移操作 ID、原 Game/世界来源证据、阶段和核对结果 |
| schedules | 原计划数据及来源游戏；迁入后暂停，明确选择目标游戏后才能继续 |
| migration_sources / migration_receipts | 稳定来源谱系、快照指纹、原序号、映射、导入结果与 revision；唯一来源认领 |
| migration_evidence | 原始历史数据/可验证备份索引、未核对的 journal 证据与冲突说明 |

导入条目、回执、预留、映射和迁移完成凭据必须同一事务提交。只增加余额而没有导入回执的状态不允许出现。数据库 schema 升级与游戏存档数据导入分开版本化。

数据库放在框架提供的稳定用户数据路径，不使用存档路径或 Steam mod 安装目录作为键。实施阶段验证 provider、SQLite native 库、事务持久化配置及实际支持的游戏运行时/OS；锁冲突必须有界返回，数据库不可用时保留既有数据并明确受限，禁止悄悄新建空库或退回存档写余额。

## 5. 旧存档自动迁移协议

1. **读取**：在正确的 Scribe 阶段读取历史字段，保留原始数据。主线程完成来源捕获后暂停该来源库存写入，将纯数据交给迁移服务。
2. **识别**：核对原 SaveId/谱系、快照指纹、序号、payload、回执和预留。序号 0 也可合法携带历史状态；不能只看 Entries.Count，有回执、预留或 pending 操作的空余额仍须迁移。
3. **去重**：先查 SQLite 的来源认领和迁移回执，不依赖存档是否已写升级标记，也不把文件路径或快照 hash 单独用作导入唯一键。
4. **取证**：完整归档源快照和相关旧文件。可独立验证且属于同一来源的 journal 后续状态纳入迁移计划；不能证明归属或冲突的文件保留为待核对证据，不能直接重放、删除或假装已恢复。
5. **导入**：首次且无冲突的来源自动整批导入。活跃/Unknown 预留保持锁定；PendingExtraction 转为待核对记录，不自动退款或重新物化。未知 codec 保存原 payload，缺 Mod 不能过滤资产。
6. **提交**：在同一事务写入全部数据及 migration receipt，成功后再更新缓存并提示“旧库存已迁移”。任何失败回滚整次导入，源存档保持原样。
7. **清理**：凭已提交回执，在当前 GameComponent 清除旧余额 JSON，并记录升级版本/迁移引用。下一次正常成功保存时不再写旧库存，只写最小升级标记；不在加载过程中直接覆盖 .rws，也不强制立即保存整个游戏。
8. **重入**：若尚未保存就退出或崩溃，再加载同一旧档时命中 DB 回执，只重做清理，不再加库存。保存失败继续保留待清理状态；SQLite 导入成功不依赖存档清理成功。

无旧库存的新存档也需明确记录已使用新结构，避免后续保存把共享库存导出回旧字段。数据库内 migration receipt 是防重复的权威，存档升级标记只用于提示和清理。

### 存档副本和分叉的处理

- 同一 SaveId 的原档、自动保存轮换、重命名、另存副本及备份属于同一历史谱系，只允许首次认领导入一次。
- 首次迁入后，再看到相同谱系但不同序号/内容，不能当成新库存相加，也不能用旧状态覆盖 DB。精确已知副本可直接清理；未核对分叉保留原始快照并标记待核对，不能谎称该分叉资产已导入并清空它。
- 不同 SaveId 也可能包含同一交易或复制来源。先按业务回执和来源 ID 检查重复；证据不够时隔离冲突，禁止仅因 SaveId 不同就盲目累加。
- 无 SaveId 的老格式保留原始状态，使用独立迁移证据建立来源映射；不能每次加载临时生成新 GUID 进而重复导入。无法证明唯一性时进入人工核对入口。
- 迁移服务提供版本化的后续核对/补迁端口，但补迁只能以独立资产来源证据追加，不能重新套用整份旧快照或仅计算余额差。

## 6. SQLite 与地图物品的边界

SQLite 事务覆盖数据库内部状态，不能与 RimWorld 世界保存共同原子提交。旧存档导入也不能证明该旧档里的地图物品与外部余额不存在历史重复。本方案不承诺通过迁移消除读档复制或本地篡改。

新提取/存入必须先持久记录稳定操作 ID 和阶段，再经正确 Game 主线程执行实体变更；结果不确定时持久保留待核对，既不自动再发也不凭关闭窗口/切档恢复余额。保存回执只能证明相应世界快照，不能恢复全局库存旧版本。跨这个边界的崩溃与读档恢复规则是上线门槛，不能因为改用了 SQLite 就删掉。

旧“放弃恢复”动作不能继续通过恢复存档余额覆盖共享库存。替换为针对具体迁移来源/转移操作的核对动作；不提供一键把全局数据库回滚到当前存档的入口。

## 7. 实施切片与退出条件

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| S0 基线与合同 | 固定 P6 提交，列清全部库存调用方、历史格式和状态；确认共享范围 | 所有余额/预留/回执/计划/物理交付路径有 owner，无隐藏存档写入入口 |
| S1 存储基础 | 引入 Inventory 自有 SQLite store、schema 和运行时依赖打包 | 真实支持运行时可打开/关闭/升级 DB；并发、事务失败、崩溃恢复通过 |
| S2 领域切换 | 库存命令全部通过 DB 提交，缓存只读投影，Game 切换解除余额恢复 | 新存档、跨档切换、菜单往返使用同一余额；失败不发布成功 |
| S3 迁移端口 | 旧字段读取、来源认领、映射和导入事务；冻结正常写入直到导入决策完成 | 完整历史状态迁入；重复加载/复制/序号 0/冲突分叉不重复加库存 |
| S4 清理闭环 | 正常保存清理旧字段、升级标记、原始证据备份与待核对入口 | DB 提交后崩溃、保存失败、旧备份重入均不丢失或重复导入 |
| S5 业务接入 | Trade、红包及维护消费者使用新库存作用域，迁移旧绑定/预留 | 原 owner/幂等和服务端回执标准保留；跨 Game 回调不生成物品 |
| S6 交付与调度 | 持久转移状态、批次中断、计划暂停/重新绑定 | 切档、强杀、读旧档、未知交付均有明确状态，不自动再发 |
| S7 收尾 | 备份恢复、诊断、历史 adapter、文档和实际包验收 | 常规路径不再写存档余额或 legacy journal；历史读取入口仍可用 |

S3/S4、S5/S6 必须闭环后才能作为可用升级交付。可以按切片开发，不把中间状态当成已完成数据升级。无新旧库存双写过渡期。

## 8. 验证矩阵与交付证据

- 数据守恒：完整 payload、可用量、锁定量、回执、预留及 pending 状态逐项核对；来源条目映射可追踪。
- 幂等：相同旧档多次进入、复制/改名/自动保存、不同旧序号、多个来源重复业务回执；数据库唯一约束与应用规则同时覆盖。
- 断点：导入前、事务中、提交后但缓存未刷新、提交后未清理、清理后保存失败/未保存退出、保存成功后再读老副本；每个点只能得到完整旧态或完整已导入态。
- 故障：磁盘满、权限/锁冲突、损坏/更新版本 schema、数据库缺失但存档标记已迁移；明确阻断或核对，不创建空余额掩盖丢失。
- 旧证据：健康/孤立/冲突/缺 authority/截断 journal，不能把已迁移后续变更无条件遗弃或静默恢复。
- 业务：交易终态与报价回包乱序、重放、未知预留、账号/endpoint 切换、原 Game 失效；SQLite 不替代服务端结果证据。
- 游戏：不同地图/世界、不同 tick 历史、缺 codec/Mod；计划不随新档 tick 意外重跑，切档不投放旧动作。
- 包：实际支持的 RimWorld 1.6/1.7、Windows/Waylith 及支持的其他平台，native SQLite 依赖、独立路径、强杀后重启；离线组件结果与实机结果分别记录。

备份应覆盖数据库一致快照、迁移回执和源证据，不能运行中随意只复制一个 DB 文件。恢复旧 DB 属于全局库存回滚，不能同时保证其后所有交易/资产仍不重复；必须有明确恢复记录和核对流程。降级旧客户端不在支持范围，不能把 SQLite 库存重新导出到旧存档造成双权威。

本次仅落地 roadmap，未实现 SQLite、未迁移玩家数据、未新增运行验证结果。
