# SQLite 白盒结果与黑盒进入条件

日期：2026-11-10；客户端 dev 未提交工作区。在实现首轮 36 项业务检查后增加故障路径检查。本轮使用生产源码、真实 SQLite、合成资产；没有运行游戏或迁移玩家数据。

## 已接受的边界

用户明确接受：地图/世界存档回档造成的物品重复、消失不再治理，不为此增加防读档或补偿机制。测试仍要求共享数据库自身的余额、来源认领、回执和预留按约定更新；正常交易不能谎报成功或因无关历史问题停摆。

## 本轮发现并修复

压缩完成记录后，相反的交易终态原先可以作为新交付被接受：成功事件处理并清掉大载荷，再收到同一 endpoint/recipient/trade 的取消事件，会绕过只扫描活跃记录的冲突检查。

先添加测试，`/tmp/phinix-whitebox-business4-20261110/test.log` 实际失败于 `Compacted success cannot later be accepted as a fresh cancellation`。修复 `TradeCompletionInbox.Record`：同时查相反终态的活跃记录或精简凭据，存在则拒绝。新增成功→取消、取消→成功两个方向的回归检查；不会重新交付或宣称新结果。

为直接编译真实核对代码，将原有无行为变动的 `TradeLifetimeCleanup` 辅助类拆到独立文件，并加入原工程编译清单；没有替换为测试 stub。

新增白盒重点：

- 写入中途失败：余额和 revision 不推进，明确重试只提交一次。
- 提交成功但确认丢失：不报成功、不盲重试，重读看到一次已提交结果。此为在真实事务外注入 OutcomeUnknown，未模拟操作系统断电。
- 数据库锁竞争：独立租约线程持锁，另一写入在有界等待后返回 Busy，不执行业务回调；锁解除后可明确重试。
- 导入来源回执写失败：通过 SQLite trigger 在实际事务中抛错，确认条目/revision 也回滚；重入不重复加余额。
- 真实 GameComponent/模块：迁移提交失败不清旧字段、不写升级版本；成功后才清理；旧档再次加载不重复导入；坏旧 JSON 保留且共享库存仍可使用。这是反射构造组件的白盒检查，未运行真实 Scribe 保存。
- 旧 pending 提取仅扣相关数量并给出放弃提示。
- 坏辅助交易证据仅隔离一笔，不反复刷警告，后续新报价可用。
- 错误 correlation、重复回包、已知成功后的传输异常不错误结算；本地结算阻塞后只重试本地动作。
- 原始持久结果不依赖整库可写；身份不匹配不改预留；明确拒绝只恢复一次；缺结果不当成拒绝。
- 现代交付未确认/Unknown 时保留大载荷，Confirmed 后清理并保留去重；清理后相反终态仍被拒绝。

复现脚本：`tools/quality/run-client-storage-tests.py`、`tools/quality/run-sqlite-business-tests.py`。后者直接编译库存/交易主要领域与持久化源码，引用指定构建图中的真实 Inventory 模块执行组件检查。本轮不是对全仓所有旧测试套件的全绿声明；旧 file-journal fixture 不代表新 SQLite 路径。

## 黑盒现在可以开始第一轮

无需等待红包/人才独立持久化改造。以本轮修复后的构建生成固定测试包、独立用户数据目录和备份存档，开始实际游戏验收；不在真实玩家唯一数据副本上升级。当前 staging 是隔离分析布局，未安装/发布，不把它当成已通过启动验证的发布包。

| 顺序 | 游戏场景 | 通过条件 |
| --- | --- | --- |
| 1 | 干净启动、未保存新游戏打开库存 | SQLite/native 依赖可加载，库存可用，无旧日志只读门槛 |
| 2 | 备份旧档升级，正常保存、退出、重进 | 余额/payload 保留；正常保存清旧字段；再次进入不重复导入 |
| 3 | 导入后不保存退出，再加载原备份 | 命中来源认领，不重复加余额，再次清理组件 |
| 4 | 切不同存档、另存为、返回菜单再进 | 共用本机余额；另存为可用；原 Game 的旧物理回调不转投新世界 |
| 5 | 正常存入、提取、预留、取消预留 | 界面与实际物品数量符合当前操作；局部 pending 不长期锁全库 |
| 6 | 两客户端与测试服务端正常报价、成交、取消 | 双方物品/提示正确，重复结果不再交付，交易后可继续下一笔 |
| 7 | 报价前本地失败、发送后断线、交付期间退游戏 | 前者明确未发送；后者不假退款；中断/可能丢失有提示，不静默冒充成功 |
| 8 | 游戏进程强杀后重开独立测试配置 | 数据库可打开；已提交数据可读；中断动作按有限恢复策略结束 |

库存单端 1–5 可以先跑；6–7 的完整端到端结果需要两个客户端与测试服务端。离线源码检查不能替代这些结果。至少分别在实际支持的 1.6/1.7 运行时完成核心路径；只打包了其他 OS/架构的 native 库不等于这些平台实测。
