# 主题与插件：当前分发流程、设想流程及延期范围

日期：2026-10-11。最新用户决定：先完成 T5 本地闭环，继续扩展 API；快捷上传与现有线上投稿/上架流程的后续实施一并延期。本文件描述流程，不授权任何远端写入。

| 事项 | 当前安排 |

| 商店本地主题包安装/更新/卸载、目录刷新/恢复 | 本地实现，普通用户无需 DevMode |

## 2. 当前线上插件流程

已使用 gh 只读核对远端 Index main `198227bb45f034077465d5f21120324afd08bf02`，以下描述对应这个固定快照；本地 checkout 不同，未同步或覆盖。

1. 作者在自己的公开 GitHub 仓库提供源码与正式 Release ZIP，包声明程序集、模块、语言资源及兼容范围。
2. 作者填写 Index Issue 投稿表单，提供固定资产/来源及候选信息。作者不用向维护者提供 PAT，但正常 GitHub 投稿需要账号。
3. intake 从可信 Index 代码检出 Validator，检查候选格式、仓库/Release/摘要及包内容；产生报告/证据，而不是直接上架。
4. 维护者审核并给予批准标记，准入/受控发布校验审核证据与不可变版本锁。
5. publisher 发布 catalog.json 快照并更新稳定目录指针；插件 ZIP 仍有其来源资产身份。自动来源更新检测也受现有审批与发布规则约束。
6. 客户端读取可信目录，规划、确认、下载、验证、安装；DLL 模块变更继续按当前规则要求重启。目录上架不代表用户已经安装或模块已经激活。

现有目录为 schema 3，生成器明确限定 github-release/phinix-dll；不能直接用该路线录入 theme-zip。当前客户端提供固定官方源，没有完成任意来源目录的用户配置能力。

依据：[远端说明](https://github.com/HunYuan2333/Phinix-Plugin-Index/blob/198227bb45f034077465d5f21120324afd08bf02/README.zh-CN.md)、[intake](https://github.com/HunYuan2333/Phinix-Plugin-Index/blob/198227bb45f034077465d5f21120324afd08bf02/.github/workflows/plugin-intake.yml)、[catalog](https://github.com/HunYuan2333/Phinix-Plugin-Index/blob/198227bb45f034077465d5f21120324afd08bf02/scripts/catalog.py)、[publisher](https://github.com/HunYuan2333/Phinix-Plugin-Index/blob/198227bb45f034077465d5f21120324afd08bf02/scripts/publisher.py)。

## 3. 本批主题本地流程

编辑配色 → 导出 → 确认名称/作者/包 ID/版本/ZIP 路径 → 数据校验与写 ZIP → 显示完整路径/复制/打开目录。

- 导出的是部分主题的显式值和用户草稿覆盖，包含未知键与 inherit，不默认铺平全部回退色。另存自己的包生成新 ID；导出信息按编辑的来源身份保存在本地作者设置中，不将来源主题的官方身份当作自己的包身份。
- 现有目标文件不会被覆盖；选择另一个路径。导出后的文件存在就是本地结果，打开文件管理器失败不撤销文件。没有上传提示、后台上传或登录依赖。
- 宿主范围使用实际客户端产品版本，当前为 0.9.7；SDK/API 2.0 和 CLR 1.9 不作为纯主题包的宿主范围。首批旧演示范围曾使用 2.0，本批重新提供适配当前产品版本的样例。

商店 → 本地主题包 → 选择主题 ZIP → 查看已校验候选/本地来源/版本 → 安装或更新 → 主题选择器选择 → 热应用。

- 本地主题包不需要 DevMode，不等同官方审核。代码插件侧载继续保留 DevMode 条件；主题入口不会放宽 DLL 安装。
- 本地相同 ID 的修订允许同版本不同摘要，禁止降级和重复摘要；预览时冻结预期已安装摘要，提交时重新核对。正式来源不可由本地包冒充或静默替换。
- 商店卸载按整包/全部变体执行；明确确认后，当前所选主题属于该包时回退默认，保留用户 profile。更新移除变体、意外丢失或损坏仅回退显示并保留选择意图。
- 选择器本地导入入口已移除；既有用户 XML、配置与公开输入边界保留，不自动删除、接管或标成受管包。

存储位于 SaveData/Phinix/ManagedThemes，使用独立 lease/目录和明确数据收据；共用 DLL 安装的 staging、preparing/committing 持久决定及 owned-tree 校验/删除引擎。主题设置后处理不是跨目录原子操作，卸载 journal 保留预期选择及设置摘要，后处理失败可重放，用户后续选择优先。普通主题业务不读恢复格式。

## 4. 将来设想的主题投稿流程（延期）

编辑 → 导出成功 → 用户主动选择“提交商店” → 准备发布资料 → 选择身份/托管方式 → 提交固定候选 → 校验 → 审核 → 受控上架。

| 作者情形 | 可能的路径 | 尚需实施 |
| --- | --- | --- |
| 有 GitHub、维护自己的资产 | 浏览器认证，确认作者仓库/Release，再自动准备候选 | 受限授权、资产上传、来源绑定、预填提交及结果查询 |
| 有 GitHub、不想每主题建仓库 | 共享主题库投稿，可信工作流接收/发布资产 | 库管理、更新所有权、审核/资产版本、creator/publisher 区分 |
| 没有 GitHub | ZIP 分享给发布者，或使用独立网页接收服务 | 委托关系，或作者身份恢复/限额/存储/队列与运营 |

自动录入索引应表达为自动生成/提交候选，不能自动绕过批准。至少区分已导出、已提交、校验失败、待审核、已上架、被拒绝及结果未知；取消/失败不删除本地 ZIP，超时先查提交状态再重试。

无账号的一键公开提交需要代发布者或服务，不可能从 gh 自动获得 GitHub 写权限。客户端不能嵌入维护者 token，玩家不需要安装 gh。接收服务可以与运行时解耦，主题文件仍可独立下载/分享，但不能把集中接收服务描述为完全去中心化。

名称、显示作者和本地包 ID 不证明远端更新所有权。首次匿名投稿不能靠昵称覆盖既有包；后续更新要验证真正发布身份。许可证/再分发授权和预览资料需单独定义，当前严格清单不允许随意增加资源文件。

## 5. 恢复线上阶段时的先决项

重新确认用户要恢复线上交付；核对当时远端版本而不是直接使用本次快照；协调客户端与主题目录类型上线，固定可信校验源码及批准规则；然后选定投稿身份/托管路线，完成相应契约、交互和验收。没有这些条件时继续本地 API/Example 工作。

详细选项分析保留在 Theme-Export-and-Quick-Publishing-Assessment.md。此文件与当前交付计划优先于此前“本地完成后立即做预填提交”的建议。
