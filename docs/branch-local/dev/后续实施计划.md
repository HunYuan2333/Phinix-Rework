## 2. 三仓架构与回滚依据

### 2.1 仓库关系与固定 Gitlink 规则
项目统一称为 **Phinix Rework**，拆分为三个独立源码仓库：
- **`Phinix-Rework`**：RimWorld 1.6 客户端宿主、游戏 UI 及内置客户端扩展。
- **`Phinix-Rework-Common`**：共享契约、网络加密传输、用户模型及中立扩展运行时。
- **`Phinix-Rework-Server`**：独立专用服务器程序及官方服务端扩展。

**依赖固定规则**：
- 客户端和服务端均将共享仓作为 Git 子模块固定在 `Dependencies/Phinix.Common`，通过项目引用直接参与编译。
- 获取与构建必须使用固定提交的 gitlink（`git submodule update --init --recursive`），**严禁使用** `git submodule update --remote`。
- 仓库更名不改动既有程序集名称、代码命名空间、协议标识、模组 packageId、持久化键或子模块目录名。

## 3. 当前阶段：F7 作者体验与插件自动化构建

2026-10-09 用户调整顺序：下一开发批次（明天）首先实现开发者模式下的本地插件侧载，再补齐第三方作者的最小开发闭环。**skill 编写、模板生成器和其他新的作者工具全部阻塞，直到这些基础功能验收完成**。当前仅更新计划，不提前实施代码。

已上线的插件与 Index Actions 继续运行；它们不属于暂停对象。交付门槛见 [开发者基础能力交付计划](Developer-Foundation-Delivery-Plan.md)。

### 3.1 已交付的独立插件自动构建规则
用户要求将 `Phinix-Example-Plugin`、`Phinix-Legacy-RedPacket`、`Phinix-Legacy-TalentTrade` 三个独立插件仓库的分支管理与自动构建纳入 F7 统一规划：

1. **统一建立 main / dev 分支**：
   - 实施时重新核对远端最新分支和并行修改。已有分支直接保留，缺失分支从已确认的最新主线创建。
   - `main` 分支用于已确认交付的稳定代码；`dev` 分支用于日常开发。
2. **仅在 main 提交后自动编译打包**：
   - Actions 工作流以 `push.branches: [main]` 为触发条件。
   - `dev` 分支的提交不编译、不打包。PR 阶段不自动编译；若提供手动触发入口，也必须限制在 main 分支。
3. **统一构建与打包入口**：
   - 采用 .NET 10 SDK、各仓现有的 `pack.py` 以及可信的 `ManagedPackageTool`。
   - 明确固定对应的客户端提交及其 Common/protobuf gitlink，不使用浮动宿主分支作为构建输入。
   - 构建清单准确记录插件提交、宿主/共享层版本、包版本与 ZIP SHA-256 摘要。
4. **合法获取游戏编译引用**：
   - 当前维护仓使用私有编译引用包并固定摘要；第三方作者应提供自己的合法编译引用，不要求取得维护者私有仓访问权。
   - 游戏引用 DLL 和任何凭据严禁进入 Git 仓库、插件 ZIP、公开 Actions 产物或日志。
5. **main 构建通过后自动正式发行**：
   - main 推送后，构建与校验成功才发布新版本的 GitHub Release，附插件 ZIP、摘要与构建来源；失败保留未公开草稿，同一提交重试复用版本，不覆盖旧产物。
   - Index 每小时动态扫描已批准来源，合格更新批量准入并统一发布索引；新来源、批准范围变化仍走审核流程。
6. **各仓行为严格验收**：
   - 分别验证：main 提交触发并成功完成云端构建打包；dev 提交不启动编译；ZIP 不含游戏/宿主 DLL 并通过静态校验。
