# 已知问题记录模板（原因未确认 / 日志不足）

> 用于记录现象已由用户报告、但目前缺少足够证据定位原因的问题。把已证实事实、用户描述和待验证假设分开写；没有证据的字段写“未知”或“尚未收集”，不要补猜测。

## 基本信息

- **状态：** 待定位 / 调查中 / 已有临时规避 / 已修复待验证 / 已关闭
- **影响范围：** 客户端 / 服务端 / 插件 / 其他
- **严重程度：** 低 / 中 / 高 / 阻断
- **首次报告：** YYYY-MM-DD（未知则写“未知”）
- **最后更新：** YYYY-MM-DD
- **关联版本或环境：** 未知则写“尚未收集”

## 用户可观察到的现象

用简短、可验证的方式描述用户看到什么、影响什么。说明是否偶发、是否能稳定复现，以及目前已知的触发前提。不要在本节写根因推断。

## 复现步骤与频率

1. 前置状态：
2. 操作：
3. 预期结果：
4. 实际结果：
5. 复现频率/尝试次数：

未知项标记为“尚未确认”，不要把推测步骤写成已复现步骤。

## 当前证据

### 已确认

- 列出日志、转储、代码或可重复观察直接支持的事实；尽可能注明文件名、时间戳、事件或代码位置。

### 尚未确认 / 缺失

- 列出定位所需但尚未取得的材料，例如完整日志、原生崩溃报告、转储、版本和触发上下文。

## 代码审查与可能方向

- **已审查路径：** 列出相关入口、线程/生命周期/状态交互。
- **疑点：** 仅写值得验证的代码或环境交互，并说明为什么可疑。
- **反证或降低可能性的证据：** 记录与假设不吻合的事实。
- **当前判断：** 给出有边界的优先级；明确根因是否尚未确定。

## 用户报告时请提供

只收集定位需要的信息，并避免要求用户提供密码、令牌、聊天正文或其他无关个人信息。

- 相关应用、游戏、模组/插件版本和运行环境；
- 崩溃前后的主日志及相关错误日志；
- 若可取得，原生崩溃报告、故障线程信息或转储；
- 触发前的操作、时间、复现频率和最近一次成功/失败情况；
- 与本问题直接相关的环境条件（例如输入法、网络状态或已启用的插件）。

## 规避方式与诊断计划

- **临时规避：** 没有经过验证的规避方式时写“暂未确认”。
- **下一步：** 列出可以证伪/证实当前疑点的具体检查或诊断数据。
- **隐私与性能边界：** 说明新增诊断不得记录的内容，以及避免高频/阻塞写日志的要求。

## 关闭条件

说明何时可以把问题标记为已修复或关闭，例如：确认根因、修复已合并、目标环境复现通过，并且新日志能区分修复前后的路径。没有达到条件前保持“待定位”或“调查中”。
