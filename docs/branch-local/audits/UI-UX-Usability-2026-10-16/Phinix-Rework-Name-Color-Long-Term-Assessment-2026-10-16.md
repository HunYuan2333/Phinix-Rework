# Phinix Rework 昵称逐字调色远期评估

日期：2026-10-16。状态：**远期功能，仅评估，暂不实现。**

本文独立于当前UI/UX实施方案。当前只纳入“改名入口更直接、输入与保存反馈更清楚”；不因本文存在就开始实现逐字调色、颜色选择器、富文本生成器或服务端改造。

## 1. 用户目标与命名

多数玩家没有计算机背景。现有名字可使用颜色标签，但要求用户自行拼接，难以编写、修改和排查错误。

远期目标：玩家输入自己的昵称，点选其中某个字或一段文字，选择颜色并预览，由界面生成现有格式支持的标签。用户不需要知道标签语法。

用户所说“输入ID”在本文按**显示昵称/显示名**理解；不修改账号UUID、认证标识、协议字段名或人物身份关联。玩家界面统一称“昵称”或“名字”，避免让用户寻找一串账号标识。

## 2. 当前可证事实与未核实项

- `Client/Source/GUI/Windows and panels/SettingsWindow.cs:276`已有昵称输入、预览和设置名称动作；它位于连接窗口，而且该表单只在在线时绘制。当前发现性不足，快捷改名另由当前方案处理。
- `Client/Source/Client.cs:816`的UpdateDisplayName调用现有user manager；当前表层返回void，不提供“服务器已接受”的独立成功证明。
- `Client/Common/UserManagement.Client/ClientUserManager.cs:168`的UpdateSelf要求已登录，构造并发送更新包。返回true说明本地调用已走发送路径，不是权威更新回执。
- `Extensions/Chat/Client/ChatTheme.cs:63`根据名称格式显示设置处理原始名字；`Utils.TextHelper.StripRichText`支持剥离包含color等标签的文本，代码也存在`<color=#...>`用法。
- 搜索和提及已有去标签路径，例如ChatMainTabProvider/ChatSidebarProvider使用去标签名称，ChatMentionUtility保留标签而处理提及高亮。不能由此断言所有页面、服务端和第三方插件都已正确处理逐字标签。
- 这里通常所称“HTML调色”应按游戏实际支持的**富文本颜色标签**理解，不是嵌入浏览器或支持任意HTML。
- 本轮未核验当前服务端实际允许的名字长度、字节限制、颜色语法、规范化/拒绝规则，也未跑两端互通。实施前必须查真实边界，不能假定客户端能显示就一定能同步。

## 3. 建议的普通玩家流程

入口放在未来快捷改名窗口中的“名字样式”，不放到全局主题颜色编辑器。个人名字格式与全局主题是不同任务，但仍共用Host控件、主题和动作系统。

流程：

1. 输入昵称，显示正常文字，不把标签混进逐字选择区。
2. 下方按用户可见字符显示可点选的字块，选中字符有明确边框和文字提示。
3. 点色块应用到当前字符；可切到“整个名字”一次选择统一颜色。
4. 同时看到完整名字预览；当前名字与未应用草稿分开。
5. 点击“应用名字”，由owner校验、生成字符串，再走现有名字更新路径。
6. 明确显示“已保存供下次登录使用”“已提交名字修改”“当前名字已更新”等有相应证据的状态，不把按钮回调当服务器确认。

第一版远期候选只考虑：单字/选段颜色、统一颜色、清除所选颜色、恢复本次编辑前状态、实时预览。颜色以可识别的调色板为主，精确颜色值放次级入口。

渐变、动画、闪烁、字体大小、字体样式、模板市场、多个名字预设和自动换名都不作为首个候选的默认范围。逐字颜色本身先做可靠，再评估是否真的需要更复杂功能。

## 4. 简单界面背后的必要规则

### 4.1 字符与编辑

- “每个字”按用户可见字符/字素处理，不能直接逐个UTF-16 char生成标签，避免把代理对、组合音标或emoji拆开。
- 中文输入法正在选词时不重新切分并覆盖输入。完整提交本次文本变化后再更新字块。
- 增删文字后如何保留颜色须有明确规则。只能在能可靠对应的字符上保留，歧义处提示或回到未着色状态，不能把颜色默默错移到另一个字。
- 1.6/net472与1.7/net10可用的Unicode分段行为可能不同。实施前验证普通中文、拉丁组合字符、代理对和多码点emoji；不能只在新版运行时测试。

### 4.2 生成标签

示意：名字“星河”可生成`<color=#FFAA00>星</color><color=#66CCFF>河</color>`。这只是表示形式示意，最终支持的色值格式需按真实游戏与服务端核验。

- 用户编辑的是纯文本与颜色草稿；wire/display字段继续使用现有的最终昵称字符串，不另建一套网络颜色协议。
- 同色连续字符可以合并为一个标签区段，减少字符串膨胀；颜色变化时再分段，所有标签必须成对闭合。
- 对输入中的尖括号、实体、已有标签采用已验证的游戏文本规则。不能直接套浏览器HTML转义后假定游戏一致，也不能无条件拼接任意用户标签。
- 同时校验可见长度、生成后字符串长度/字节量及服务端约束。达到上限时在应用前解释，不等服务器拒绝后才让用户猜。
- 前端禁止无意生成透明到不可见的昵称；具体颜色/透明度边界需另行决定，不自动限制现有手写名字或改变服务器规则。

### 4.3 已有手写名字

- 打开样式编辑器不应立即重写或规范化当前名字。
- 能无损理解的颜色标签可转为可视草稿。不能无损理解的嵌套/其他标签要保留原始名字，说明当前编辑器不能完整编辑，不静默删标签。
- 是否允许玩家明确选择“按纯文字重新编辑”作为转换动作，应在远期交互评审决定；转换前提供原样备份/恢复本次原文的办法。
- 关闭或取消保留已保存原名；“恢复本次编辑前状态”与“清除颜色”含义分开。
- 应用成功后不维护两份互相竞争的名字权威。颜色映射是编辑草稿，实际昵称字符串仍沿现有settings/user management归属保存和同步。

## 5. UI/UX重点

| 场景 | 玩家应理解的内容 | 不应要求玩家完成的工作 |
|---|---|---|
| 选一个字改色 | 正在改哪个字，选了什么颜色 | 找到标签中的字符位置 |
| 改整个名字 | 一次统一调色，仍能再改个别字 | 复制粘贴多个color标签 |
| 修改文字 | 哪些颜色保留，哪些对应关系需重新确认 | 修复嵌套/闭合标签 |
| 当前显示未变 | 对方/本地可能关闭格式显示，或服务器尚未更新 | 自行猜测发送是否成功 |
| 名字过长 | 彩色格式超过限制，减少颜色区段或文字即可继续 | 阅读底层字段或包体错误 |
| 旧名字无法可视编辑 | 当前名字原样保留，可取消 | 承担一次打开窗口就被去格式的风险 |

预览至少包含当前主题上的名字，并能看纯文字形式。色块选择与选中字块不只靠颜色区别；深色/浅色主题切换仍能辨认。

若本地“显示名字格式”关闭，明确说明预览样式可能不在当前聊天显示。预览不得偷偷强制打开用户设置，也不能保证所有接收方一定显示相同颜色。

## 6. 归属与兼容边界

- 名称编辑由Host现有用户/名称管理能力拥有；Chat等插件只消费显示名与变更事件。不为Chat、红包、人才分别实现名字编辑器。
- 复用同一公共presentation/theme/action/confirmation；需要通用色块/字符选择能力时补公共展示能力，不让某个内置模块绕开Host私绘。
- 不把昵称调色写入全局theme profile，不增加第二主题系统。
- 继续按UUID关联用户、交易、屏蔽、通知和其他业务，不以带标签昵称充当身份主键。
- 搜索/提及匹配应使用恰当的去格式展示名，但去标签不是改变或重新分配身份。重名、空格和特殊字符按现有业务规则处理。
- 旧服务端、Framework/Legacy路径、输入校验、设置保存、登录名称选择、历史消息和第三方显示都要独立验证。发现需要协议/服务端规则变更时另列项目，不以“只是生成标签”跳过讨论。

## 7. 实施前验证清单

1. 查明当前服务端、两版游戏的真实标签支持、名字长度和字符串处理，记录原样往返/规范化结果。
2. 打开、编辑、取消、应用已有纯文字及手写富文本名字，证明不丢原文、不产生半截标签。
3. 分别验证中文/英文/组合字符/emoji/空格/尖括号、增删与粘贴、中文输入法。
4. 用两客户端验证名称更新、成员列表、聊天历史、回复、提及、搜索、屏蔽、交易和通知；名字仍按原UUID关联。
5. 测试格式显示开/关、主题切换、深浅颜色、窄窗、长名字和高缩放。
6. 模拟离线、明确拒绝、更新已发送但暂未观察到结果、重连和再次登录；反馈不夸大同步成功。
7. 检查1.6与1.7公共合同/消费者组合；编译、白盒和游戏验收分别记录。

## 8. 排期结论

**保留为远期独立功能，不进入当前UI/UX实现批次。** 当前先做快捷改名入口及既定库存、商店、主题、首次引导、交易和红包易用性。未来启动本项时，以普通玩家可操作性和现有富文本无损兼容作为入口门槛，不先建设完整名字装饰系统。
