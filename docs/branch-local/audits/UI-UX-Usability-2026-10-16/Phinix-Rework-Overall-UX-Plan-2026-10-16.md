# Phinix Rework 总体易用性优化方案

日期：2026-10-16。方案基线：Host `27878e7fb78c11fec4f390db317dc0db5b0b10c9`，结合本轮90项操作路径审查、用户填写的频率表，以及“多数玩家没有计算机背景”“首次引导提供红包和人才贸易安装选择”“库存显示物品图标”的补充反馈。

这是待实施方案。本轮只新增本文，没有修改实现、主题、协议或存档，没有提交、推送、发布。下文的路径和点击数是设计目标，尚未通过游戏验收。

后续确认：右侧固定本人昵称区、独立快捷改名窗口及右侧紧凑化已定稿，排为首个实现切片。实施顺序、编号与门槛以[实施roadmap](../../dev/UI-UX-Usability-Implementation-Roadmap-2026-10-16.md)为准，本文保留总体目标。

## 1. 总体方向

让玩家围绕“我要做什么”操作：聊天、找物品并取出、给对方报价、领红包、安装功能、换主题。普通流程不要求理解插件包、模块、编解码器、请求token、运行时或内部存储单位。

本轮的核心是：**入口容易找到，操作尽量原地完成，连续操作不用反复填写，结果和下一步一眼看懂。**

不把所有页面改成引导向导。首次选择可以有短引导；日常高频操作应直接完成，不能每次都教一遍。按钮数量减少不等于体验改善：必要的交易确认保留，搜索、阅读、返工和状态判断同样纳入验收。

| 范围 | 本轮方向 | 依据 |
|---|---|---|
| 默认主题、公共控件 | 第一批修正状态辨识，所有页面受益 | 已发现普通按下态、危险文字、区域边界和选中/悬停问题 |
| 库存 | 第一批增加图标、搜索、行内提取和连续操作 | I-01～04均高频；图标为用户明确补充 |
| 交易 | 重点减少选物返工，保留双方报价核对 | T-02高频，其他操作中频 |
| 商店和主题 | 统一普通玩家管理体验，直接使用成品主题 | 浏览、安装、更新、启停、卸载、换主题均高频 |
| 聊天 | 保障输入与阅读，简化回复/提及的发现 | 发送最高频，回复/提及预计后续高频 |
| 红包 | 清楚发送、直接领取、减少填写丢失 | 发送和领取高频 |
| 首次引导 | 接收方式＋自愿安装红包/人才贸易 | 用户明确要求 |
| 人才贸易、Example | 不做专项页面改版 | 用户明确排除；公共能力调整仍做兼容验证 |

频率表中的“典型规模”和“最不顺手一步”大多留空。本文据已知频率与源码负担确定实施方向，不虚构日均次数、耗时收益或精确投资回报。

## 2. 首次引导：一次选好接收方式和可选功能

### 2.1 保留自然触发时机

当前弹窗归Inventory所有，真实触发是：主窗口打开，且尚无有效的物品接收偏好。它不是游戏进程启动就弹出。

建议沿用“第一次打开可用的主窗口”作为首次引导时机，避免游戏加载/读档途中连续弹窗。已有有效接收偏好的玩家不因本次升级被迫重新选择；可从设置主动打开“初次设置”。

### 2.2 玩家看到的流程

使用一个简短窗口，分两块内容，不再接连弹出几张无关对话框：

**物品收到哪里？**

- **收到库存**：先保存在当前存档的物品库存，需要时再取到地图。
- **直接空投**：收到后按现有规则投放到地图。地点仍由现有交付规则决定。

两项都用普通语言说明，并保留明确选择，不暗中替玩家改变既有偏好。

**还想使用哪些功能？**

- **红包**：发送和领取物品红包。
- **人才贸易**：与其他玩家交易或租借角色。

两项自愿勾选，默认不预选，避免未表达意愿就下载。已安装、待重启、不可安装的项目显示真实状态，不重复安装。“暂不安装”不影响聊天、交易或接收方式保存。

底部按当前选择显示“开始使用”或“开始使用并安装所选功能”。只有已展示名称、说明、重启要求并由玩家主动勾选后，这个按钮才代表本次安装意图。

### 2.3 安装及失败体验

1. 先确认并保存接收偏好。安装失败不能把已完成的接收方式选择抹掉。
2. 使用商店现有可信目录、依赖规划、摘要/来源/环境校验与安装流程。不能因为来自首次引导就绕过预检。
3. 有需要核对的依赖或替换计划时，只展示一次完整核对；与普通商店遵守相同确认规则。
4. 每个所选插件独立显示“下载中、检查中、已安装，需要重启、安装失败”。不承诺两个包共同原子安装，不在一个失败时自动卸载另一个成功包。
5. 成功后说明“已安装，重新启动游戏后可用”，不把安装文件完成写成已经激活。允许稍后重启，不自动关闭游戏。
6. 无网络时提示“现在无法下载，可稍后在商店安装”，允许继续使用已完成的基本设置。
7. 玩家关闭窗口或离开视图不等于撤销已开始的安装。安装由原owner持续管理；取消按原installer的能力执行。
8. 首次选择被跳过后不在每次开窗反复推销。保存“完成/跳过”的独立引导状态；下载失败可以从商店继续处理。

这会增加少量一次性操作，但能省去新用户事后寻找商店、搜索插件、确认是否已安装的路径。不能拿首次引导与之后每次操作混算收益。

### 2.4 架构安排

不能把红包/人才的ID、下载地址和安装分支写进Host或Inventory。

- Host提供普通、可选的首次设置步骤承载能力，同一presentation/theme/action/confirmation渲染。
- Inventory贡献“物品接收方式”步骤，继续拥有偏好校验和保存。
- Store贡献“可选功能”步骤，并通过自己的目录配置呈现这两个推荐项。未安装的红包/人才自身无法贡献安装前入口，所以这部分必须由Store目录/推荐配置提供。
- Store继续拥有包规划、下载、校验、安装和结果。Host只组合通用步骤与显示投影，不引用Store、红包、人才Contracts。
- Store缺失/停用时仍可完成接收方式；Inventory缺失时也不生成失效步骤。可选步骤失败不阻断无关步骤。
- 当前尚无上述完整通用引导契约，也未发现公开的通用安装API。它们是明确需要设计的新接缝，不能声称只往原对话框加两个checkbox即可完成。优先让Store自行承接安装步骤，避免为此公开一个不必要的全局安装服务。
- 引导记录属于普通设置，不写进物品账本，不修改存档交付协议。新设置键、完成时机与重开入口在实现时一并确定。

## 3. 高频路径的目标行为

### 3.1 库存：看图找物品，原地取出

建议默认页面为一张紧凑、可搜索的物品列表。每条显示：**图标、名称、可用数量、必要状态、数量输入、提取按钮**。来源详细信息、每日计划、批量和恢复操作继续可达，但不占据普通提取的主要位置。

**库存图标列入第一批：**

- 组标题和展开后的具体条目都显示适当的物品图标。无法可靠确定时使用统一问号占位，不隐藏整条记录。
- 保留名称和数量，不能只靠图标识别物品。品质、材质、状态有差异时仍须通过文字/详情区分，不能因外观相同合并条目。
- 优先借用Def等只读展示资源，不为取图标物化真实Thing，不触发codec解码交付或改变所有权。
- 公共列表已有`WithImage`和图像寿命能力，无须新增renderer。Inventory当前展示元数据只有Label/GroupKey/ItemsPerUnit，没有可靠图标身份；需要在Inventory自己的可选展示元数据或可选展示能力中补齐，由生产者提供可信图像标识/描述，在游戏适配层解析。
- 不从本地化名称或GroupKey字符串猜Def，不把Unity Texture硬塞进中立库存业务合同。旧codec没有图像信息仍可正常显示文字/占位。
- 图标获取、失败占位、缓存失效与借用寿命配套处理，不逐帧物化或重复解码。

**查找：** 顶部直接搜索名称；匹配结果直接露出可操作条目，避免还要逐组展开。来源/状态筛选使用已有事实，默认展示可用库存，并明确存在预留/待核对记录。搜索不能让风险记录悄悄消失。

**提取：** 直接在对应行填数量、点“提取”，去掉“选条目→再打开提取编辑器”两层视图准备。仍是玩家一次明确的提取提交，不删除业务校验，不把点击行变成取物。

**连续操作：** 成功后留在当前搜索结果和滚动位置，按新余额更新当前行。原数量仍合法可保留；超余额时显示新余额并要求改正，不静默改成另一个提取量，也不自动再次提取。条目耗尽后让用户看见本次结果，再移除或标记已取完。

**单位：** 普通物品显示“件”；整份保存对象明确显示“1份＝X件”等真实单位。玩家不需要手算，但数量输入不能越过codec的整对象边界。

**部分成功：** 结果明确展示已取出多少、尚未取出多少与原因。若当前owner结果只提供bool/错误字符串，应补充只读、结构化展示事实，不靠解析日志或猜字符串重建权威。不能添加一个会整笔重复提取的通用重试按钮。

本轮不把“多记录同名物品任意合量提取”混入行内操作。那需要明确按哪些记录扣减、部分成功如何展示，应另列业务设计。

### 3.2 交易：保持现有行内数量，解决刷新返工

当前行内输入、双方报价比较、下部提交已存在，本轮不再全面重排一次。

- 搜索、翻页和不相关数据刷新不应无条件清空全部数量。草稿以业务owner可证明的稳定身份关联：库存用EntryId；地图物品/分组要核对对象、来源及组成变化，不能按名称或行号重新套用。
- 同一Game/owner寿命内，仍有效的条目保留输入；数量减少显示需修正；物品消失标出对应草稿失效。不能把旧数量自动转移到新物品。
- 顶部或提交附近显示“已选几种物品”“还有几项数量需修改”，并能定位错误条目。被搜索隐藏的错误也应能找到。
- 提交后的待确认报价与尚未提交的草稿明确分开。提交成功后只处理相关草稿，不把未知请求当失败重建并重发。
- 保留“提交报价”与“确认交易”两个不同意图，以及双方最终确认。按钮文案说明当前提交什么、还在等谁。
- 重置、取消在已有规则允许时继续可用；不能因一个非法数字封死退出或纠错。

这里主要收益是减少返工和找错误，不承诺基础提交点击数会明显下降。跨存档持久保存草稿、跨Game重建托管不在本轮范围。

### 3.3 商店：常用管理直接在列表完成，失败原地看懂

- 默认让玩家看到功能名称、用途、是否已安装/可更新，以及一个与当前状态对应的主要动作。
- 安装、更新、启用/停用可通过列表行上的公共动作直接发起；不必为了每次操作先选中条目进入详情。详情仍用于版本、依赖、来源及较长说明。
- “全部、已安装、可更新”放在可见位置。连接方式因用户标为高频，保持顶部可发现，记住用户选择；不擅自自动切线路或重复提交安装。
- 依赖/替换需要核对时，规划完成后提供一处完整核对，不再把同一计划先展示一遍、点按钮后又重复展示一遍。仍使用相同公共确认和owner freshness校验。
- 普通界面使用“已启用”“已停用”“重新启动后生效”“等待移除”等玩家语言。包与模块的详细状态放到管理详情，不能伪造一个统一成功状态掩盖真实差异。
- 卸载保留确认。撤销待移除后要说明实际回到的状态，不能把Disabled写成已启用。
- 本地插件ZIP继续遵守开发者模式范围；普通玩家的安装主路不要求选择文件、填写路径或解读SHA。

**失败信息采用两层：**

1. 原地说明“哪一步没完成、是否已有安装结果、下一步能做什么”。例如“下载未完成，尚未安装，可重试下载”或“已安装，请重新启动游戏”。
2. “查看详细信息/复制诊断”再提供错误阶段、原因、受影响包与请求信息。不能让“复制摘要到外部编辑器”成为理解失败的必经步骤。

只在owner能证明重试安全时提供“重试”。结果未知应显示“正在核对/查看状态”，不统一写“重试安装”。进度条不得以不明的本地进度冒充远端业务完成。

### 3.4 主题：先服务换主题，编辑单独进入

- “主题”默认打开简洁选择列表，每行提供“使用”。无需先打开颜色编辑器，再开第二张选择窗口。
- 点某行“使用”是明确应用该主题的意图，沿用现有Apply的保存与热应用顺序。列出当前使用项，失败时保留旧主题并解释原因。
- “编辑颜色”“导出”作为次级入口，继续使用当前draft/profile、继承、未知key和导出规则，不建立第二套主题服务。
- 商店把在线主题和已安装主题放在同一管理流程；已安装主题直接提供“使用”。安装成功后给出“使用此主题”，不在后台自动替用户换主题。
- 本地主题ZIP入口从“更多工具里的本地主题窗口”提升为商店主题区域可发现的“导入主题”；继续使用原受限文件选择、Inspect和安装服务。可直接导入不代表允许绕过包校验。
- 选择、安装、使用、编辑、导出五种状态用清楚的文案区分。编辑器不因追求简单而改变未应用草稿、Apply持久化或导出冻结draft的含义。

### 3.5 红包：发送表单易理解，领取直接操作

- 发送区先选物品，再清楚填写“总共多少件”“分成几份”，类型用“每份相同/随机分配”等易理解说明辅以原名称。
- 保留物品图标、来源和可用数量；数量预设直接作用于已选物品。份数与总量边界现场提示，不要求玩家通过点发送来试错。
- 发送保留一次完整确认，明确物品、数量、份数和分配方式；特殊物品风险仍保留。不要把同一内容再做第二次重复确认。
- 明确拒绝/确定未发送时保留输入，方便纠正。已经提交而结果未知时保留只读提交摘要并阻止重复发送，不能把表单恢复成可随便再发。
- 收到列表每行可直接“领取”或“详情”，无需先选一行再去上部找按钮。使用原claim准入和防重复规则，不能仅靠UI禁用保证幂等。
- 领取状态用“等待领取结果”“已存入库存”“已空投到地图”等owner能够证实的事实。尚未证实到账时不能显示后两种成功文案。
- 详情明确快照时间，可重新查看最新详情；库存去向可提供普通导航直达库存相关记录。没有安全关联入口时不做伪精确定位。

人才贸易只加入首次安装选择，不改其交易/市场/租借页面。共享控件调整仍确保它能正常使用。

### 3.6 聊天、导航和设置：不打断聊天，减少找入口

- 发送仍保持“输入→Enter/发送”。重点验收中文输入法、选词回车、焦点、粘贴、回复后的继续输入，以及提交拒绝时草稿不丢。
- 回复、复制、链接和媒体动作使用熟悉的消息上下文入口，常用项优先显示，少用项后置。若加入悬停回复按钮，必须扩展通用feed动作能力；不能拿普通list的WithControls冒充feed已支持，也不能在Chat单独自绘一套。
- 提及补全要易发现、可关闭，不能抢走正在输入的中文。它是未来高频能力，先验收输入可靠性再增加交互。
- 成员搜索和sidebar切换在窄窗可发现，抽屉不覆盖仍能点击的主内容。导航保留稳定名称/顺序及溢出入口，扩展增多不把标签挤成不可读。
- 设置按“连接、聊天、物品接收、扩展管理、外观”等用户目的组织，提供直接分组定位；底层仍收集通用provider，不能按内置插件写Host白名单。
- **改名提供直接入口**：右侧sidebar导航之上固定一个紧凑的本人昵称区，平时显示渲染后的昵称及“改名”；切换用户/通知不消失，也不随成员列表滚动。窄窗空间不足或无sidebar时，从明确命名的“修改名字”菜单项进入，不藏在“全部设置”或连接参数中。
- 点击“改名”打开独立小窗口：标签原文输入、实时渲染预览、“保存”和“取消”。不让同一个行内文本框随焦点在彩色名字和长标签源码间跳变，也不失焦自动保存。以后可在同一窗口增加可视化调色，当前不放未实现按钮。
- **右侧紧凑化**：移除重复“用户”标题及常驻选择成员说明卡；搜索、在线人数、屏蔽折叠组合为紧凑工具区。没有选中成员时不预留一整张动作卡；选中后显示短姓名上下文和实际动作，更多贡献动作使用公共菜单。成员列表用现有紧凑行并占剩余区域。
- 新增本人区后，以相同窗口/缩放/数据的正常未选中状态为对照，成员列表可用高度不小于原基线。靠减少重复内容和多层卡片留白腾空间，不缩小文字、命中区域或隐藏禁用/异常原因。成员选择、本人改名和通知状态三者不得混用。
- 当前源码的连接设置其实已有在线改名表单，但入口仍埋在连接页；新入口复用同一名称管理服务，原有设置入口可保留，不能新建另一份名字权威。主窗直达目标是“改名→输入→保存”，约2+f次点击；窄窗菜单路径约3+f，不要求滚动查找。
- 新改名窗口的输入是临时草稿，取消不改变已保存昵称；保存后的本地设置与服务器更新分别按现有能力反馈。在线提交不冒充已被服务器接受；离线只可明确保存为下次登录使用，不能显示服务器已同步。现有入口逐字写设置的行为与新窗口草稿需要统一核对，不能让“取消”只在文案上存在。
- 玩家已手写标签的名字不得因使用快捷入口被静默去标签、重排或覆盖。首批保留原始字符串并提供预览，名称样式可视化编辑另列远期评估，暂不实现。
- 连接页继续负责连接；复杂日志/模块细节进入管理页。无Store时Host的扩展管理恢复入口必须保留。
- 横幅展示简短状态与一个相关动作，允许关闭/收起。通知列表已读与业务完成分开，不以标已读改变交易状态。

## 4. 主要路径前后对照

统一从“主窗口已打开、尚未进入目标功能”起算。N为主Tab入口：可见标签1次，溢出菜单2次。f为聚焦输入框的实际点击，g为是否先展开库存组0/1。输入字符、滚动、分页、窗口缩放、下载等待另计；目标不承诺固定耗时。

| 任务 | 当前路径/基础点击 | 目标路径/基础点击 | 收益与保留事项 |
|---|---|---|---|
| 修改昵称 | 全部设置中查找；源码另有“设置→连接→改名表单→提交”，约3+f及条件滚动 | 本人昵称旁“改名→输入→保存”，约2+f；窄窗菜单约3+f | 改善入口发现和表单专注度；服务器更新与本地保存分别核对，保留手写标签 |
| 找库存物品 | 进入→滚动→必要时展开组；无搜索 | 进入→搜索，直接看到匹配图标/名称/条目 | 补齐缺失入口；不伪造搜索节省的秒数 |
| 单条提取 | 进入→展开→选条目→开提取→输入→确认；N+g+3+f | 进入→行内输入→提取；N+1+f | 基础减少2次视图准备；有搜索时输入另计；业务执行仍一次明确提交 |
| 连续提取k条 | 每条约3+f，另有组展开/回滚 | 每条约1+f，结果原地更新 | 每条少2次视图准备；仍逐笔执行，不新增整批回滚承诺 |
| 交易选多物品并提交 | 行内输入已有，刷新可能清全部草稿 | 保留有效草稿→定位错误→提交 | 基础点击不强减，重点消除重填；保留最终双方确认 |
| 领取红包 | 进入→选红包→领取；N+2 | 进入→该行领取；N+1 | 少1次选择；不减少中继等待或交付校验 |
| 发送红包 | 进入→选物→输入→发送→确认 | 同样保留发送与一次确认，原地校验/保存输入 | 不强行删确认；明确拒绝后不用重填，unknown不允许盲重发 |
| 首次安装单个无额外依赖的新包 | 进入→选包→安装；N+2 | 进入→行内安装；N+1 | 省去详情选择；原有无额外计划确认规则不变 |
| 依赖/替换计划或更新 | 选包→发起→计划按钮→再次确认，约N+4 | 行内发起→一处完整计划核对并安装，约N+2 | 去掉选择和重复计划入口；规划完成、确认时重新检查状态 |
| 商店切连接方式 | 进入→菜单→选方式；N+2 | 顶部明确显示当前方式→选择；N+2 | 不虚报减少点击，主要改善发现与反馈 |
| 卸载插件 | 进入→选包→卸载→确认；N+3 | 进入→行内卸载→确认；N+2 | 保留危险动作确认及重启生效事实 |
| 从设置换主题 | 设置→主题编辑→选择器→主题→应用；5 | 设置→主题列表→对应行使用；3 | 减少2次，沿用现有保存权威 |
| 本地主题导入 | 商店→更多工具→本地主题→选择ZIP→选文件→安装 | 商店主题区→导入主题→选文件→安装 | 减少工具窗口层级；选择文件的输入/目录点击与校验仍存在 |
| 安装红包/人才 | 自行找商店→搜索→分别理解安装状态 | 首次引导勾选→明确安装意图→按需核对计划 | 减少发现成本；增加的是一次性引导，不改变重启和独立包结果 |

行内按钮在窄窗需要折行或菜单时，应把新增点击计回目标，不能按宽屏路径宣称所有窗口都已达标。

## 5. 默认主题与公共交互统一改善

路径优化与可辨识性同步实施，避免按钮变近却更难看清。

- 页面、面板、输入、按钮建立明确边界。默认主题按实际fallback后的最终值验收，不只修改注册默认值。
- 普通、主要、危险、选中、悬停、禁用、处理中分别定义。选中与悬停至少有稳定可见的形状/标记差异；保留文字含义，不只靠颜色。
- 修正Normal按下态亮底仍用亮字、Danger红字对底不足等已证问题。焦点、输入错误和当前选择不能都靠“按钮变灰”表达。
- 常用文字保持可读；时间戳、引用等次级信息不能为了弱化层级变成难辨认。图标不能挤掉数量、长物品名和错误提示。
- 主动作靠近输入或对应行；只有必要的长文本进入详情，错误和完成反馈尽量不让用户滚到页顶找。
- 处理中只锁相关动作，在owner允许时继续搜索/阅读其他内容。不能取消业务级锁，只为让界面看起来活跃。
- 窄窗口采用可预测的折行/切栏，动作始终可达。固定头/脚按实际内容测量，不能让空说明占据主要空间。

## 6. 实现边界和公共能力清单

| 能力 | 已有情况 | 本轮使用/需要补齐 |
|---|---|---|
| 紧凑列表、行内数量/按钮、图标 | 公共list已有CompactRows、WithControls、WithImage | Inventory/Store/红包优先复用；不新增插件renderer |
| 搜索字段、校验、选中状态 | 公共text field、validation、selection已存在 | 插件投影提供过滤结果、原文draft和业务原因 |
| 主题选择/应用 | catalog/Apply和公共theme session已有 | 新简单选择界面复用同一服务；编辑器为次级入口 |
| 分栏、固定区、工具栏、菜单 | split、fixed/aligned header/footer、inline toolbar等已有 | 先调投影布局与现有属性；实际不足再扩公共能力 |
| 设置分组 | 当前provider主要有SectionId/Order，不足以自动表达玩家目的分组 | 如现有元数据不足，补可选通用分组元数据；旧provider进其他设置，不按插件ID写死分类 |
| 首次多步骤/多贡献者引导 | 当前只有Inventory专属接收选择窗 | 需要最小通用承载/生命周期契约，Inventory和Store分别贡献 |
| 安装与失败详情 | Store内部controller和原有安装链已有 | 改Store投影与只读失败分类；不把包权威移入Host |
| 库存图标来源 | renderer支持图像，库存展示元数据尚缺图像身份 | 库存/codec的可选展示契约与游戏适配解析；不动物品payload |
| 跨页定位/跳转 | shell有稳定导航ID，但未发现完整通用导航请求服务 | 库存到账/商店入口若需跨页直达，补通用导航请求，不写红包/Trade专用Host方法 |
| feed悬停快捷动作 | 不能由普通list行控件直接推定可用 | 确需时补通用feed action展示；首批不以此阻塞核心改进 |
| 连续操作结果/草稿保留 | 由各owner掌握业务身份和结果 | owner保留同Game原文/事实，Host仅提供投影/定位；不产生新自动重发机制 |

公开合同发生新增时，Host、内置消费者和三插件按同一API3组合验证两版绑定；不假定小改动不影响ABI或反射形状。仍使用当前1.6与1.7引擎adapter，不复制两套业务UI源码。

以下必须保留：真实关联回执、未知结果托管、物品完整性/整批转换、主线程游戏操作、codec单位、包哈希/来源/环境/依赖检查、重启生效、主题Apply先持久化再发布。

不纳入本轮：一键自动确认交易、未知结果自动退款/重发、自动协议切换、跨存档托管恢复、同名物品强行合并、多插件安装自动原子回滚、全新多物品红包协议、人才页面专项重构。

## 7. 建议实施顺序与每批交付

顺序结合用户频率、明确新增要求和公共依赖，不用猜测工期。

**首个切片：右侧固定本人区＋快捷改名＋成员区紧凑化。**

按已确认的截图区域完成Host共享本人区、统一名称编辑owner、成员工具与列表投影。验证用户/通知切换、抽屉、无Chat/无sidebar、富文本、取消与显式保存、在线/离线及输入法；用同条件截图和列表可用高度证明紧凑化有效。对应UX2-01～03。

**随后：公共状态＋库存小改。**

修正默认主题/按钮状态；库存图标、搜索、匹配条目直达、行内提取与原地反馈。图标属于低学习成本、容易感知的收益，不应排在大型引导工程之后。交付相同场景前后截图、普通和整份codec单位用例、逐条提取路径比较。

**第二批：商店与主题的普通玩家流程。**

行内主要动作、一次计划核对、原地失败详情、明确重启状态；主题简单选择、商店使用/导入主题。先把安装结果和失败处理做清楚，为首次引导复用同一链打基础。

**第三批：首次引导。**

落最小通用承载；Inventory接收方式、Store可选红包/人才、跳过/离线/已安装/失败/待重启路径。只复用已验证的安装能力，不复制installer。

**第四批：交易连续编辑＋红包。**

先稳定物品身份和草稿核对，再保留有效数量/定位错误；红包明确拒绝保留表单、unknown锁提交摘要、收到列表直接领取、到账反馈。不能为了上线视觉改版先绕过业务状态。

**贯穿各批：聊天输入与公共回归。**

中文输入、焦点、消息阅读、成员sidebar、确认、窗口缩放和第三方消费者每批验证。快捷改名入口纳入当前UI/UX，随主窗口入口/聊天体验切片处理；回复/提及发现、设置分组可按公共能力成熟度进入后续切片，不另起一次全面UI重写。

逐字名字调色是独立远期功能，参见[远期评估文档](./Phinix-Rework-Name-Color-Long-Term-Assessment-2026-10-16.md)。当前仅优化改名入口和反馈，不实现颜色编辑器、渐变或标签生成器。

人才贸易只参加可选安装与公共兼容回归；Example继续充当公共API/控件验证消费者，不投入专项外观重排。

## 8. 验收方式

### 8.1 普通玩家任务验收

选取无计算机背景、未被提前教路径的参与者，用任务描述而非按钮名称测试：

1. 第一次打开：选接收方式，只安装红包，理解何时可用。
2. 断网第一次打开：完成基本设置，明确插件尚未安装。
3. 在库存找到指定物品，认图核对名称，连续提取多条，不进入计划或恢复页面。
4. 给两种物品改数量，搜索另一种，再遇到余额变化，知道哪一项需改，其他数量没有丢。
5. 安装/更新功能，遇失败能说出发生在哪一步、下一步做什么；不要求复制技术诊断才能理解。
6. 换一个已安装主题；从文件导入主题后使用；能区分安装和使用。
7. 发一个红包并领取另一个，能分清等待结果与已到账。
8. 中文输入法聊天、回复、提及，不因选词回车误发。

记录完成/放弃、求助、误入次数、搜索/滚动/往返、重填字段、是否理解最终结果。点击数作辅助，等待网络时间单列；不以快读说明的开发者代替目标玩家。

### 8.2 技术和游戏矩阵

| 范围 | 必测项 |
|---|---|
| 环境 | 真实1.6/net472与1.7/net10对应联合组合、准确引用/候选指纹；单版通过不代表另一版通过 |
| 版面 | 主窗640×480～1280×800可用区域，1024×768/1080p/4K屏幕与1×/1.5×/2×缩放；中英文长名称、多行错误 |
| 图标 | 普通物品、材质/品质差异、缺Def、缺codec、第三方无图像元数据、主题/语言切换、100/1000/接近库存上限记录；不物化、不改变账本、不逐帧解码 |
| 提取 | 正常、数量超额、整份单位、逐栈部分成功、条目耗尽、地图不可用、预留变化、重复点击；不额外增加一次提取 |
| 草稿 | 搜索/翻页/刷新、对象消失/数量变化、同名不同对象、关窗/断线/切Game；不得串行、串物品或跨Game绑定 |
| 商店/引导 | 无Store、离线、已装、停用、待移除、仅一个插件成功、两个均失败、依赖变化、关闭窗口、重启激活；校验与取消标准不变 |
| 主题 | 默认与自定义profile、选择/应用/编辑/导出、无效draft、导入失败、当前主题被卸载；保持原保存和fallback规则 |
| 公共消费者 | Chat/Trade/Inventory/Store/Theme/红包/人才/Example，同一renderer及action freshness/confirmation；无官方白名单 |

性能验证针对本次新增搜索和图标缓存、列表刷新、草稿匹配进行。小静态改色不写镜像实现测试；owner状态、身份映射、结果未知和安装生命周期必须做有效性质测试。白盒/编译不代替游戏验收。

## 9. 方案状态及后续决策边界

已确定纳入：普通玩家导向、固定本人昵称区与快捷改名、右侧成员区紧凑化、库存图标、库存查找与连续提取、交易减少返工、商店/主题路径、首次可选安装红包和人才、明确失败细节、共用状态辨识。逐字名字调色只做独立远期评估，不并入当前实施批次。

未确定为发布承诺：具体字号/像素/颜色、最终图标元数据形状、通用引导/导航契约名称、具体包目录项身份与可下载范围、第三方目标玩家实测规模。它们在实现切片中依据真实源码和候选核对，不用假ID或临时下载地址补全。

本方案不要求在开始实现前重新填完90项表。可先按上述批次形成可审查的实现切片；任何会改变交易确认、物品权威、保存格式或协议的需求独立列项，不随UI方案自动实施。
