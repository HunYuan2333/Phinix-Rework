# 聊天图片功能可行性评估

> 评估日期：2026-05-31，修订：2026-06-01

---

## 当前消息管线（经验证）

```
客户端UI → TryHandleOutgoingMessage → BuiltInChatClientExtension
→ BuiltInChatMessagePayload (protobuf bytes) → FrameworkPacket.PayloadBytes
→ DataContractJsonSerializer (byte[] → base64, ~33%膨胀) → NetDataWriter
→ LiteNetLib ReliableOrdered → Server广播 → 客户端解析渲染
```

关键参数：外封套 JSON，内载荷 protobuf，无显式包大小限制，LiteNetLib 自动分片。服务端历史默认 40 条，客户端最大 1000 条。

---

## 逐环节评估

| 环节 | 可行性 | 说明 |
|------|--------|------|
| UI 选择图片 | ✅ | `System.Windows.Forms.OpenFileDialog` 或 Unity FileBrowser |
| 图片压缩 | ⚠️ | .NET Framework 4.7.2 无原生 WebP，推荐 `System.Drawing.Bitmap`→JPEG |
| Proto 扩展 | ✅ | `bytes image_data` 字段直放二进制 |
| Message Handler | ✅ | 复用 `IClientMessageHandler` + `IMessageRenderer` |
| 网络传输 | ⚠️ | 单张 200KB（文本的 100-400x），广播放大，大包阻塞同通道小包 |
| UI 渲染 | ⚠️ | `Texture2D.LoadImage` 阻塞主线程、纹理内存、高度计算需扩展 |

---

## 关键架构决策

**正确路径：** `JPEG → protobuf bytes image_data → PayloadBytes(byte[]) → JSON外封套(自动base64) → LiteNetLib`

**不要**额外套一层 base64（会双重编码）。

---

## 缓解策略

- 客户端强制缩放 ≤1280×720，JPEG quality 60-70
- 服务端 256-512KB PayloadBytes 上限 + 每用户每分钟 3-5 张频率限制
- 纹理异步加载（`IClientMainThreadDispatcher`）+ 滚动卸载
- 服务端历史文本+图片引用分离存储

---

## 综合结论：🟡 可行但工程改动中等

第一优先级：Proto 扩展 + 客户端图片处理 + ChatMessageList 异步渲染
第二优先级：服务端大小/频率限制 + 纹理 LRU
第三优先级：历史存储分离 + 缩略图预生成 + 慢速连接兼容
