# 客户端库存与恢复边界

> **English**: [Inventory.md](./Inventory.md)

## 当前设计：共享 SQLite 库存（2026-11-10）

库存契约 v7 使用框架用户数据目录下的本机共享数据库：`Phinix/ExtensionData/builtin.inventory/databases/inventory.sqlite3`。Trade 使用同一套中立基础设施管理各自的 `builtin.trade/databases/trade.sqlite3`。宿主不拥有两者的业务表结构。物品载荷以 BLOB 存储，每次余额变动不会重写未变化的条目。

读取、重命名或复制世界存档不会回滚该库存余额。成功执行一次性导入后，游戏存档仅保留升级标记；旧分支余额不会重复导入。存在重叠的独立来源时保留原字段并给出警告，未核实的旧日志变更不会自动恢复。本机数据库标识变化或缺失时会明确提示，存档无法重建原全局余额；复制世界的标记不会切换或冻结其他本机数据库。

物理交付回调仍绑定原 `Game` 实例。中断的提取可显式放弃，放弃会消耗其预留数量并提示可能丢失物品；不确定的预留可通过确认显式放弃并进入 `Abandoned` 状态（而非 `Committed` 或 `Restored`）。其他可用库存不受影响。损坏的旧数据不会静默清空旧快照，不可用的数据库也不会被报告为写入成功。

Trade 在发送前准备阶段失败时会恢复本地托管，而不是变为 `Unknown`。已确认的终态操作会压缩大载荷并保留小体量去重记录。这是面向游戏 Mod 的有限恢复，不承诺跨越 SQLite、远端服务器与游戏世界存档的原子提交。详见 [SQLite 实现与检查](branch-local/dev/SQLite-Implementation-2026-11-10.md) 与 [通用存储设计](branch-local/dev/Client-SQLite-Storage-Design-2026-11-10.md)。

> 以下关于“按存档路径记录的日志”段落用于说明历史格式与旧行为，不再是当前写入路径。

## 核心组件、幂等存入与呈现边界

- **组件创建与恢复**：RimWorld 1.6 的 `GenTypes.AllActiveAssemblies` 仅枚举游戏程序集与各激活 Mod 的 `ModAssemblyHandler.loadedAssemblies`，不包含从 `Common/Extensions` 动态加载的程序集。因此库存激活时通过精确名称的 Harmony Prefix 拦截 `GenTypes.GetTypeInAnyAssembly(string, string)` 提供 `InventoryGameComponent`，停用时一并卸载，不修改存档类名、谱系 ID 或快照字段。
- **插件架构与接口**：`builtin.inventory` 为客户端插件。`InventoryExtension` 持有共享客户端契约，`InventoryExtension.Client` 负责存储、提取、每日计划与界面；服务端项目不引用库存。生产方声明依赖 `builtin.inventory`，通过 `IInventoryRegistrationApi` 注册带版本的 codec，并在游戏主线程调用 `IInventoryDepositApi` 存入，停用时释放注册作用域。`IInventoryReadApi` 提供状态、限额、快照与变更事件，`IInventoryExtractionApi` 负责提取与计划，`IInventoryApi` 保留为兼容门面。
- **原子存入与溯源**：每笔存入以稳定 `DepositId` 为幂等键，对来源、物品标识、版本、数量与原始载荷计算哈希（本地化显示名不影响幂等）。重复提交相同 ID 与内容返回 `AlreadyCommitted`，同 ID 不同归属数据返回 `Conflict`；生产方仅在 `Committed` 或 `AlreadyCommitted` 后释放托管。支持附带 `OriginKind`、`OriginId`、`OriginUserId`、`OriginDisplayName` 与注册 `IInventorySourcePresenter`。
- **契约 v5 呈现与分组**：`IInventoryItemPresentationCodec.PresentItem` 在不物化游戏对象的前提下提供本地化名称、组键 `GroupKey` 与单位 `ItemsPerUnit`。界面按 codec/版本、物品标识、来源与溯源分组展示，可用总数扣除待决预留；展开后逐条提取或设每日计划。

## 提取、预留与跨业务边界

- **手动提取与地图校验**：手动提取按 codec 堆叠上限拆分，每堆独立执行“预留 → 交付 → 完成”序列。交付前校验地图未销毁、存在安全落点且 `Current.Game.Gravship` 为空。`IInventoryVerifiedDeliveryCodec` 返回已交付、拒绝或不确定；拒绝时恢复余额，不确定时保持锁定以待人工核对。每日计划复用同一链路。
- **外部预留边界（`IInventoryReservationApi`）**：其他客户端插件通过稳定操作 ID 原子预留一批条目，获取不可变快照并经由业务 adapter 转换。活跃与不确定预留会扣减 `GetAvailableSnapshot()`；权威成功提交并扣减，明确拒绝则恢复，发送后结果未知保持锁定。库存本身不引用 Trade、红包或旧协议类型。
- **全局交付模式（`inventory.deliveryMode`）**：跨存档设置决定普通 Trade 与 LegacyRedPacket 领取时使用直接空投或存入库存，修改后立即生效；人才交易保持独立，不受此设置影响。
- **与 Trade / LegacyRedPacket 协作**：Trade 将权威 `FrameworkItemPayload` 作为不可分割条目保留；库存模式下仅在 `Committed`/`AlreadyCommitted` 后回执，直接空投模式下整批落地验证后回执。从库存报价时先原子预留并生成临时不落地对象，转换后立即销毁。LegacyRedPacket 同样从库存预留所选数量或整条带状态物品，在 HTTP 接受 `create` 或中继历史回显后移交所有权；断线/重启后未决发送记录保持不确定状态供界面核对。

## 同类记录批量提取

`IInventoryBatchExtractionApi` 由同一个库存模块注册，与现有 `IInventoryExtractionApi` 并存。`StartBatchExtraction(IReadOnlyList<InventoryBatchItem>, expectedVersion, out reason)` 在游戏主线程校验版本、非空唯一条目 ID、可用数量、codec/版本/堆叠上限、最多 10,000 条记录与单位总数溢出后，冻结当前 Game/存档/投放地图并启动运行期队列；`BatchProgress` 提供不可变进度快照。

`Root.Update` 每帧按 `TryExtractSingleStack`（日志预留 → `DeliverVerified` → 完成）处理一个合法堆，逐堆原子、整批允许部分完成且不自动重试或退款。任一失败、账本变更或存档/投放地图变化即停止后续队列；已交付部分保留，未执行部分留在库存，不确定交付沿用标准核对。关闭页面不停止队列，`StopBatchExtraction` 仅停止剩余部分；队列不跨重启持久化。

在库存页点击分组标题可展开/折叠并选中该组进行批量提取（“提取一批”或“提取本类全部”）。提取遵循原有 codec/来源/溯源边界并排除锁定量；≥100 条记录或 ≥1,000 单位时确认弹窗会提示可能的卡顿风险。`InventoryPresentationActionContext` 可选携带 `GroupKey` 与 `GroupRecords`。
