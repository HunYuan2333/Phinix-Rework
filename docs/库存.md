# 客户端库存与恢复边界

创建和恢复组件是两条边界。RimWorld 1.6 的 `GenTypes.AllActiveAssemblies` 只枚举游戏程序集及各启用 Mod 的 `ModAssemblyHandler.loadedAssemblies`，不是 AppDomain 内所有动态程序集，因此单独补 `FillComponents` 不能解析存档中的库存 `Class` 节点。库存启用时，对 `GenTypes.GetTypeInAnyAssembly(string, string)` 加仅匹配库存组件确切全名的 Harmony Prefix，在原生查找前提供 `InventoryGameComponent`，也绕过以前缓存的 null。其他类型查询不变，关闭扩展时与原有补丁一起卸载。存档类名、血统 ID 和快照字段不变；不通过清空库存或重放奖励代替恢复。更新后重读未损坏的原存档；如果恢复失败后已保存覆盖，可能须使用备份。

重放本地 claim/assign 时，库存入账记录暂不可查会保留中继游标，并使用原有的限频恢复提示，不能每个 tick 又输出“未经请求的领取”警告。准确入账记录恢复后，只更新历史领取显示，不再入账第二份奖励；真正未请求的结果仍不能授权新奖励。

`builtin.inventory` 是独立客户端插件。`InventoryExtension` 提供共享客户端契约；`InventoryExtension.Client` 负责按存档隔离的账本、日志、提取、每日计划与界面。服务端工程不引用库存。生产者声明依赖 `builtin.inventory`，通过 `IInventoryRegistrationApi` 注册带版本的 codec，并在游戏主线程通过 `IInventoryDepositApi` 入账。带作用域的 codec 与来源展示器注册必须在扩展关闭时释放。`IInventoryReadApi` 提供状态、容量限制、快照和变更事件；`IInventoryExtractionApi` 负责提取与计划。原 `IInventoryApi` 作为兼容门面保留。

每笔入账是带稳定 `DepositId` 的原子批次。账本对来源、物品标识、版本、数量与原始载荷取哈希；本地化显示名称只是界面元数据，不影响幂等判定。同一 ID 与相同内容重试返回 `AlreadyCommitted`；同一 ID 对应不同所有权数据时返回 `Conflict`。生产者仅在 `Committed` 或 `AlreadyCommitted` 后释放自己持有的物品。Codec 决定能否无损合并；不可拆分的物品保留完整不透明载荷，数量为一。

生产者可以在入账时填写 `OriginKind`、`OriginId`、`OriginUserId` 和 `OriginDisplayName`。这些字段会复制到生成的库存条目，其中稳定的类型、事件 ID 与用户 ID 会参与新版入账回执。只有载荷、生产者来源和稳定追溯身份都相同的可合并物品才会合并，因此不同红包或不同交易获得的物品会保持为可单独追溯的条目。显示名称是为阅读保存的当时快照，不影响幂等判定；稳定事件 ID 与用户 ID 承担审计身份。生产者可以为自己的来源 ID 注册 `IInventorySourcePresenter`，让业务标签和追溯格式留在生产者插件里。没有追溯字段、或生产者插件暂时缺失的旧条目仍然有效，并使用通用来源展示。

契约版本 5 增加可选 `IInventoryItemPresentationCodec`。`PresentItem` 只读取元数据，不物化游戏对象，提供本地化名称、codec 内稳定 `GroupKey` 和正数 `ItemsPerUnit`。库存页按 codec/版本、物品身份、来源、来源类型和来源用户分组；没有用户 ID 时仍按事件隔离。即使汇总显示，各事件 ID、EntryId、载荷和预留仍保持独立。可用总数不包括发送预留。展开后逐份提取或设置计划；不可分条目仍按整份输入，界面明确注明每份的实际物品数。本次没有组提取、载荷重写、状态等价假定、存档迁移或协议变更。缺失或无效的展示能力回退为独立旧式条目。缓存在账本、注册、游戏和语言变化时刷新，不在 Draw 中还原所有 Thing。

RimWorld `GameComponent` 保存库存快照和存档血统 ID。由于内置扩展程序集会从 `Common/Extensions` 动态加载，库存扩展会在 `Game.FillComponents` 后显式且幂等地挂载自己的组件，不依赖 RimWorld 更早的类型缓存发现该组件。客户端扩展存储中的 journal 记录每个较新的账本状态，`TryDeposit` 成功前会刷盘。命名空间由存档内 ID 与规范化存档路径共同确定，所以复制到另一条路径后的新事务不会串入原存档。新游戏须先保存才能入库。加载到比 journal 更旧的快照时暂停写入，玩家可以选择恢复较新事务，或保留当前存档并隔离旧分支日志；系统不自动重放。崩溃造成的未完整尾记录会被隔离，之前校验通过的完整记录仍可使用；中间记录损坏或快照无效时停止写入，保留源文件供排查。`ExposeData` 期间不截断日志，因为此回调不能证明整个游戏存档已成功写完。

手动提取允许玩家输入本次数量，并按 codec 的单堆上限自动拆分。数量大于条目余额时会明确显示可用余额，不再误报为整数格式错误。任何预留之前都会拒绝已销毁地图、没有合法落点的地图，以及 `Current.Game.Gravship` 尚未清空的整段逆重飞船飞行/落地过程；RimWorld 只在 `WorldComponent_GravshipController.LandingEnded` 中清空该值。`IInventoryVerifiedDeliveryCodec` 返回“已交付、已拒绝、结果不确定”：已拒绝会恢复余额，结果不确定才进入人工核对。旧 codec 保持源码兼容，并在调用后接受相同的持有关系检查。每日计划走同一流程。

`IInventoryReservationApi` 是其他客户端插件发出库存物品时的所有权边界。消费者以稳定操作 ID 原子预留一批条目，取得不可变条目快照后，再由业务插件自己的适配器完成转换。有效预留和结果未知预留会从 `GetAvailableSnapshot()` 中扣除，但不会提前删除底层条目；匹配的权威成功才提交扣除，明确拒绝才恢复，结果未知继续锁定。预留记录随存档进入 journal，同一操作 ID 会校验内容。库存不引用 Trade、红包对象、网络包或旧协议字段。

跨存档设置 `inventory.deliveryMode` 决定普通 Trade 完成物品和 LegacyRedPacket 奖励是直接空投，还是进入当前存档库存。尚未选择时，首次打开 Phinix 窗口会弹出选择框；设置页也可以随时切换。消费者在每次交付时现读设置，因此立即生效。人才交易明确保持独立：不再依赖库存，继续使用原有 Pawn 序列化、返还和空投路径，也不受这项设置影响。

普通 Trade 将权威完成事件中的每个 `FrameworkItemPayload` 完整保存。库存模式仅在原子入账返回 `Committed` 或 `AlreadyCommitted` 后确认服务端结算；直接空投模式会先完整还原整批物品、检查相同的地图/逆重飞船边界并验证空投仓取得持有权，之后才确认。被拒绝或结果不确定的交付保持待处理。Legacy Adapter 先把旧 `ProtoThing` 转换成同一种规范载荷；老服务器不支持新版持久确认，因此其失败交付只能在当前客户端进程内恢复。

Trade 的候选列表也通过预留 API 消费库存。库存先让条目已注册的 codec 生成不落地预览；预留成功后，再整批生成仅供转换的临时对象。Trade 立即把临时对象转成自己的快照并销毁副本，它们不会生成到地图或进入空投。缺失 codec 或无法无损物化的条目不会静默降级后加入报价，待相应 codec 恢复后仍可使用。现有请求 token 是所有权提交键：匹配成功回执提交预留，拒绝回执恢复，派发后的发送异常标记为结果未知；所有旧协议翻译仍限制在 Legacy Adapter 内。

LegacyRedPacket 的候选列表也会合并地图物品与可用库存，库存候选带“库存”标记。显示和选择的数量是条目内的实际物品数，而不只是完整状态记录的份数。先预留所选单位（不可分状态条目须预留整份），将不落地的临时对象转成红包自身模板，立即销毁临时副本。状态分片和 create 整批入队；重试保持相同事件 ID 和队首位置。只有所有状态分片成功后 create 获得 HTTP 接受回执，或中继历史中出现完全匹配的 create，才能把所有权从库存移交给持久化的红包发送者记录。这是中继发布确认，不是普通交易服务器的业务确认。不可分状态条目的未选部分通过幂等入账返还；带状态奖励与返还按合法堆叠上限拆分，每份保留原始状态字节。每次领取余额先持久化，再消费入站事件。普通红包剩余物品须等到过期，并确认一次覆盖过期时刻的成功轮询已完整消费，才返还库存；轮询失败、满页或积压都不能当作无人领取的证据。特殊红包保留既有概率返还/袭击规则。

发送者记录使用宿主的通用扩展存储，按当前存档实际存在的预留 ID 关联，加载其他存档不能自动释放托管。发布等待超过 20 秒转为结果未知，同一会话中后续真实回执仍可解决。断线、切换游戏或进程重启会把未完成的发送者记录保留为待核对。尚未实现跨中断的中继领取历史自动核对：这些记录不会自动重发或返还，红包页会显示待处理数量，不能宣称已完成崩溃自动恢复。这条路径不持久化真实 Thing 引用。

Rework 红包保留旧 `create` 预览供老客户端读取，同时在其前发送有界的附加 `state` 分片。载荷与 Trade 使用同一份压缩 Scribe 状态，并以 SHA-256 校验；Rework 接收端收齐全部分片前不能领取。带状态的堆叠物可以分给多人：每份从原始状态还原，只缩小 `stackCount`，各份确定性数量之和仍等于原始数量。老 Phi 会忽略附加分片，所以仍保持旧版的预览字段还原效果。绑定到外部 Pawn 的引用，以及第三方组件没有通过 Scribe 暴露的状态，仍无法跨存档重建。
