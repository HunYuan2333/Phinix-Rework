# Approved source updates

First admission requires a maintainer's `plugin-approved` label. For a stable three-part version with a standard `<prefix><version>.zip` asset, that approval also records an explicit `same-major` source policy. Nonstandard names and prereleases remain manual. Previously admitted packages need a separately reviewed policy; this deployment enrolls only Example Plugin.

Policies live in `update-policies/<SHA256(package-id)>.json`. They bind the original human-approved candidate, package ID and fixed asset prefix. Monitoring runs every six hours, or through **Plugin source updates** with `check_only=true` (read-only discovery and validation) or `false` (admit a valid update). Use a fresh dispatch after failure: approval evidence requires run attempt 1.

Eligible versions keep the approved repository/owner identities, author/license/tags, target framework, game versions, assembly/module/dependency IDs and external-mod IDs. New bytes, localized display text, changelog and compatible ranges may change. Tags must resolve to a descendant of the approved source commit. New major versions, changed identity/scope, missing/mutated assets, failed static checks or unresolved prior admissions pause publication. Review the change through the ordinary application process and explicitly revise the policy when appropriate; removing a policy stops monitoring without withdrawing accepted versions.

The trusted workflow reads fixed release identity and size, hashes the ZIP, statically checks its manifest/resources/PE metadata and independently verifies its fixed bytes. It never executes author code or build scripts. An exact metadata-only evidence PR is automatically merged; controlled publication rechecks the approval and new origin before atomically updating the immutable catalog release, version locks and stable pointer. Each accepted candidate also has a permanent content-bound approval digest, so expired Actions logs do not invalidate an unchanged accepted decision. Current code still validates the full catalog and dependency closure.

No new version means no PR, catalog release or stable change. Errors preserve the previous catalog and create or update one `Update blocked: <package-id>` Issue with `plugin-error` and a run link. Successful publication records a per-run receipt, closes that tracking Issue and removes its error label. Initial submission Issues retain their normal approval/publication feedback. Read-only dispatches do not create or edit Issues.

Limits are explicit: 32 monitored source policies, 256 version records, at most one admitted version per scan, 50 recent releases per repository, 128 MiB per package, 512 MiB new payload per publication and a 2 MiB catalog. Sources rotate using their last accepted update time; one busy source cannot continually jump ahead of others. API calls and execution time are bounded. Hitting a limit requires a reviewed operational change; never silently discard history or overwrite accepted bytes.

GitHub and CF expose the same catalog/package protocol and version locks. Publication does not update an installed client automatically. The client checks metadata at startup, shows a localized notice/changelog, and downloads/replaces only after the player explicitly confirms an upgrade. A restart activates the new assembly. Profile data is retained; plugin-specific data migrations remain the author's responsibility.
