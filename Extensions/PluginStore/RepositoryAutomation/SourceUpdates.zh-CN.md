# 已批准来源的自动版本发布

首次准入仍由维护者添加 `plugin-approved`。稳定的三段版本号使用标准 `<前缀><版本>.zip` 资产名时，这次批准同时记录明确的 `same-major` 来源更新策略；非标准名称、预发布版本继续人工处理。已准入的历史插件需要单独审阅后添加策略，本次仅登记示例插件。

策略位于 `update-policies/<包 ID 的 SHA256>.json`，绑定首次人工批准候选、包 ID 和固定资产名前缀。每六小时检查一次；也可执行 **Plugin source updates**：`check_only=true` 只读发现和验证，`false` 才准入新版本。失败后发起新的运行，勿直接重跑旧运行：审核证据要求首次尝试。

新版本必须保留已批准的仓库/作者身份、author/license/tags、目标框架、游戏版本、程序集/模块/依赖 ID 和外部 Mod ID；允许更新包字节、多语言介绍、更新日志和兼容范围。Tag 必须指向原批准源码提交的后继。新主版本、身份或范围变更、资产缺失/被改写、静态校验失败或上一版本尚未发布时暂停。通过普通申请审阅变化，必要时明确修改策略。删除策略会停止监测，已发布版本仍保留。

可信工作流固定 Release 身份和大小，计算 ZIP 哈希，静态检查 manifest、资源和 PE，并独立复核固定字节；不执行作者代码或构建脚本。仅含固定元数据的证据 PR 自动合并；受控发布再次验证审核与新资产来源，然后原子更新不可变目录发布、版本锁和 stable 指针。已接受候选保留与内容绑定的永久审核摘要，避免 Actions 日志过期使已批准版本失效。发布仍验证完整目录及依赖闭包。

无新版本时不生成 PR、目录 Release 或 stable 变更。失败保留原目录，创建或更新一个 `Update blocked: <包 ID>` 跟踪 Issue，标记 `plugin-error` 并附运行链接。成功发布必须有逐次永久回执，再关闭该异常 Issue 并移除异常标签。首次申请保持原有审核及发布反馈。只读检查不会创建或编辑 Issue。

当前边界：32 个自动监测来源、256 条版本记录、每次最多准入一个版本、每仓库检查最近 50 个 Release、单包 128 MiB、每次发布新载荷合计 512 MiB、目录 2 MiB。按最近接受更新时间轮转，避免单个频繁更新来源长期抢占。API 调用及运行时间均有限制。触及上限必须审阅调整，不静默丢历史或覆盖旧资产。

GitHub 与 CF 使用相同目录/下载协议和版本锁。目录发布不会自动更新玩家已安装插件。客户端启动时只检查元数据，显示本地化提示与更新日志；玩家明确确认后才下载替换，重启后加载新程序集。保留用户配置目录；业务数据格式迁移仍由插件作者负责。
