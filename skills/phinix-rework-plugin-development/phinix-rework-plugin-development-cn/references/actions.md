# 可选的自动发布

手动上传经过本地验证的 Release 与自动构建都是有效路线。只有需要自动化或排查已有 CI 时才读工作流；不为简单插件强制搭建云端流水线。

## 固定输入

维护插件当前的 `ci/config.json` 固定 Host 提交，Host 的 Common gitlink 再固定共享源码；1.6/1.7 私有编译引用按固定资产和摘要取得。核对当前文件，不把 skill 的历史 SHA 当作最新 pin，也不在 CI 随意追踪 main。包版本可由 CI 覆盖，最终以 Release/ZIP 为准。

需要两版产物和 API3 引用。在源码之外暂存输出，验证包和依赖闭包，确认不含游戏/Host DLL。维护脚本的 `release.py`、`build.py`、`publish.py` 是该仓实现，不假定它们自动适用于所有第三方项目。

## 发行与重试

当前维护流程使用版本预留、双版构建/预检、上传后核对，再公开 Release。失败时保留准确草稿/运行标识；先判断是否已经公开，不能因通知失败重新递增版本、覆盖资产或无限重试。同一 Tag 与包字节绑定。

版本分配、源文件摘要检查、并发队列和私有引用权限均以实际脚本/工作流为准。不把推送权限当部署所有组件的授权，不关闭源检查来消除 CI-only 修改带来的失败。

## Index 通知

`ci/notify_index.py` 只唤醒 DLL 来源扫描，不授予准入，也不是主题发布器。维护者可选配置具有 Index Actions 调度权限的 `INDEX_UPDATE_TOKEN`；第三方作者不需要持有它。缺失或通知失败时保留 Release，查看明确警告，已批准策略的定时扫描仍可发现后续版本。

当前通知实现最多发起三次新 main 扫描，在共享二十分钟期限内等待；这是已实现边界，不承诺零丢失或立即上架。遇到 TrustedHeadChanged 时使用新快照，不重跑旧 GITHUB_SHA 绕过检查。分别核对通知、scan 报告、changed/errors、受控发布和商店结果，见 [publication.md](publication.md)。

需要为主题添加自动化时，先按独立主题准入流程评估；不能把 DLL 的小时扫描宣传为已经支持主题自动更新。
