# 简单托管 DLL 的工程组织

选择托管路线后，第一次组织代码、增加第二个功能或整理职责混杂的实现时读。只做小改动时按所需小节使用。本参考随 Phinix skill 分发；简单 DLL 不需要下载、安装或启用 RimWorld 工程 skill。

## 用几句话确定本次切片

动手前明确玩家可见结果、这次涉及的状态/依赖，以及如何确认完成。小白可以用“点击后做什么，数据保存在哪里，失败时显示什么”表达；技术人员直接列接口、状态所有者与不变量。计数 Tab 三句话足够，不要求额外设计报告。

一个切片覆盖从用户操作到结果的完整路径：先跑通最小 Tab/设置/翻译，再补涉及的失败处理和验证，最后打包侧载。消息或物品切片同时包含缺依赖、拒绝与未知结果，不把恢复留到最后。功能完成之前先不抽公共框架。

## 单项目起步，随实际职责拆分

默认一个插件项目、一个程序集。当前 Example 在一个源码文件里已有 Extension、State、Tab、SettingsPanel 四个职责；保留这样的组织也可以。需要分文件时，可沿用 Example 的 `example/` 目录（下列是组织建议，不是必须创建的文件）：

```text
example/
  MyPlugin.csproj
  PluginExtension.cs              # Compose、激活、关闭与注册
  PluginState.cs                  # 当前功能状态与操作规则
  PluginTab.cs                    # 展示状态、接收用户操作
  PluginSettingsPanel.cs          # 仅在需要设置面板时
  package-config.json
  Resources/Localization/
pack.py
```

保留已有项目文件名也可以；如果改名，要一起核对 pack.py 的项目定位。当前 Example 使用 `EnableDefaultCompileItems=false` 和显式 Compile Include；新建/移动源码后同步编译清单，否则文件存在但不会进入 DLL。项目和目录名只是组织方式，独立身份仍按 [local-loop.md](local-loop.md) 一起修改。

| 实际变化 | 适当组织 |
| --- | --- |
| 一个 Tab 和少量设置 | 一个项目，小量类或单文件；不建立分层解决方案 |
| 多个相对独立功能 | 按功能分组，如 Notifications/、History/；各自放状态、操作和 UI，保持一份共同组合入口 |
| 网络/文件/库存等外部边界 | 在拥有该功能的目录加窄适配器；只翻译外部结果，不替领域决定成功 |
| 其他插件确实需要消费 API | 再提取稳定公开 Contracts；是否独立程序集取决于消费者与版本需求，不能为了看起来规范而拆 |
| 大量原生游戏生命周期、Defs/资源或深层 Harmony | 回到 [routes.md](routes.md) 评估 Mod，确定后联合外部工程 skill |

按“因哪个功能变化”组织，不把所有实现堆成 Utils/Helpers/Managers。不要仅为缩短文件或每个类一个接口而拆分。必需依赖明确引用公开契约；仅在有多个实现、易变边界或有价值测试缝时才加自己的接口。中立 DI 可以直接注册具体 State，不要求为它另建 IState。

## 职责与依赖方向

- **Extension 是组合入口**：接宿主、建 scope、注册 provider、安排 Start/Stop；不在 Compose 中写 UI、消息业务或物品算法。
- **State/操作类拥有功能规则**：明确有效状态和转换条件，不依靠多个散落布尔量或调用顺序猜测。几种多阶段状态确有必要时用 enum/状态机；简单计数不需要。
- **Tab/设置面板是视图**：读状态、调用操作，展示拒绝/等待；不直接改另一个功能的集合，不在 Draw 制造权威确认或反复持久化。
- **适配器连接公开服务**：宿主、库存、传输/存储的外部形状在此转换；不削弱整批交付、确认与恢复规则。

简单功能不要求再套独立 Domain 层。出现纯算法或状态转换时，可从 Verse/GUI 适配中提取普通 C#，让有价值的规则能独立验证；不要为抽象而复制现有宿主机制。跨插件协作通过提供者的公开 Contracts，不增加宿主业务中介。

UI 与设置面板注入同一个 State，沿用 Example 的做法；不是各自维护一份计数并“通常一起更新”。是否持久化、谁修改与何时有效，先定清楚再选类名。

## 每份状态有来源、作用域和失效规则

| 状态 | 简单 DLL 的决定 |
| --- | --- |
| 持久设置 | 使用宿主 settings 的唯一键前缀；例如计数值从 settings 读取，State 不再维护第二份权威计数 |
| 模块运行状态 | 插件 scope 拥有；Shutdown 对未完成初始化和重复关闭可用 |
| 连接/存档状态 | 按当前上下文取得，不等同模块生命期；切档与断线不留旧游戏对象 |
| UI 临时状态 | 选中项、滚动、筛选值；明确是否跨打开/切档保留，不承担物品所有权 |
| 昂贵派生视图/缓存 | 能从权威来源重建；按数据、筛选、语言和世界变化失效；少量数据直接读，不先加缓存 |
| 外部操作结果 | 匹配稳定操作 ID；已经派发但未知结果保留待核对，不由 UI 或超时预测成功 |

事件、缓存和后台工作的清理规则见 [composition.md](composition.md)。后台 I/O/纯数据计算不阻塞游戏线程；需要后台任务时才定义取消、超时与有界队列，在 dispatcher 动作内重查上下文。IMGUI 可一帧多次进入 Draw，昂贵 I/O、全局扫描和注册不能放在绘制路径；简单本地操作无需为“异步化”新建线程。性能优化针对测得热点，不机械禁止 LINQ 或所有分配。

## 最小检查与交付

检查风险对应的性质，不为了简单包装器模拟整个 Verse：

- 简单 Tab：编译/清单/引用预检，再从准确 ZIP 侧载重启，检查文字、设置保留、重复启停与旧回调失效。
- 有确定性规则：测试边界值、非法转换与重复操作，不仅复刻实现步骤。只涉及显示文案/布局时用实际 UI 检查。
- 有外部操作：覆盖缺依赖、明确拒绝、取消、过期上下文与结果未知；物品功能仍须遵守 [verification.md](verification.md) 的确认和恢复标准。

沿用 pack.py/工具的明确载荷选择，构建输出先留在 bin/或独立输出目录，不直接覆盖已安装 DLL。校验最终 ZIP 的 manifest、身份、资源与摘要，排除测试/陈旧 DLL 和编译引用；测试的就是将交付的那个 ZIP。移动文件后尤其检查 Compile Include 和 pack 定位，不用清理整个工作区来消除产物混淆。

日志记录激活、重要状态转换和可操作失败信息，包含稳定模块/操作标识，不在每帧刷屏或输出凭据/完整载荷。重复错误限流应有连接/存档/模块等明确作用域，避免某次故障把以后诊断永久压掉；优先利用现有日志与“复制摘要”，不要求新增诊断平台。

给用户的交付说明可以很短：完成的行为、准确包与目标宿主版本、实际验证、未验证项及下一步。只在真实增加兼容/数据风险时补充决策记录，不强制给每个简单 DLL 增加架构文档、脚手架或额外工具。
